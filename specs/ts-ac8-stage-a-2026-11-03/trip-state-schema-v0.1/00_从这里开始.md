# 从这里开始｜Trip State Schema V0.1 交付包导览

这个包交付的是旅行产品的**业务状态规则**：系统要记住什么、谁能改变、改变后哪些内容要复核，以及为什么形成当前判断。它不是界面设计，也不是已经接通真实旅行数据的线上系统。

## 如果你是 AI 产品经理

建议按这个顺序读，不必先看代码：

1. [正式规格总览](01_产品总览/FINAL_CANDIDATE.md)：约 9 类信息域、10 个业务对象、2 类系统记录和三类状态维护机制，以及已定的产品边界。
2. [七个旅行场景](03_场景与验收/SCENARIO_VALIDATION.md)：用探索目的地、跨候选偏好、预算变化、外部住宿确认和行程变化等情形检验规则。
3. [V1 评审清单](01_产品总览/V1_READINESS.md)：哪些已足够进入下一轮评审，哪些仍未验证。
4. [真实验证结果](03_场景与验收/VALIDATION_REPORT.md)：测试实际跑过什么；通过不等于真实供应商、真实模型或生产部署已验证。
5. [八项机制融合与工程同步交接](90_可运行工程包/TS八项机制融合与工程同步交接包.md)：A/C 域规则进入 TS 的位置，以及留在 DC/NAP/UX 的部分。

## 如果你要交给后端或 Agent 团队

请从 [工程接入说明](90_可运行工程包/README.md) 进入可运行工程包，再看 [完整工程规格](02_业务状态规则/SPECIFICATION.md)、`schemas/`（机器可校验的数据格式）、`rules/`（字段与状态规则）、`examples/`（合法／非法及多轮样例）、`tripstate/`（参考运行逻辑）和 `tests/`（自动化测试）。程序接入必须同时执行数据格式和跨对象业务校验；不能只凭 JSON Schema 就判断决策安全。

压缩包根目录的 `package-index.json` 是机器定位入口，列出每个文件的用途、规范位置、阅读镜像位置和 SHA-256。`01_产品总览`、`02_业务状态规则`、`03_场景与验收` 是便于阅读的自动生成镜像；`90_可运行工程包` 保留原始可复现目录结构。镜像与原文件逐字节一致（仅跨目录的 Markdown 相对链接会被改写）；后续修改只在工程源文件中进行，重新打包生成阅读镜像，不要分别维护两份规则。

所有埃及、交通、金额、时间与回执示例均是**合成测试数据**。当前判断是 **Ready for V1 Review**，不是 Ready for Production。

本次 A/C 八项机制融合的包修订标识为 `2026-11-03-ac8-stage-a-candidate`；机器 Schema 仍为 0.1.0。此修订待技术负责人验收，不能据此认定 GitHub TypeScript 同步或八项完整产品行为已经完成。
