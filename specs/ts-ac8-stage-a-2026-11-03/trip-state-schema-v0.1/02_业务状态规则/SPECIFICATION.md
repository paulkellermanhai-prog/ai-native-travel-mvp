# Trip State Schema V0.1 正式工程规格

版本：机器合同 0.1.0；A/C 八项机制包修订 2026-11-03-ac8-stage-a-candidate。状态：本地规格与参考实现候选，待技术负责人核验；实际测试见验证报告。本文是后续开发与验收依据，不代表 GitHub 代码同步或真实旅行数据、模型、产品体验已获验证。

## 1. 来源与冻结决策

本规格继承《Handoff trip state schema》§3–9 的语义与架构；PRD V0.1 的 PRD-001–009、§5–7 定义首版要求；《项目思考总纲 V2》定义产品原则；《Handoff 产品机制设计》提供历史依据。

A 域 P03/P04/P05 的已裁决规则和 C 域《行动价值决策与反馈闭环｜产品机制规范 V0.1》共同约束本规格中适用的状态、证据、授权与读取行为。C 域五个专题及收口记录用于追溯，完整行动价值规则以域级规范为准。TS 只维护权威旅行业务状态及必要证据；理解假设、行动价值与时机、交付结果各由语义理解、DC、NAP 和运行记录承担。来源指纹与逐项工程吸收见 `source-manifest.json` 和 [八项机制交接](../90_可运行工程包/TS八项机制融合与工程同步交接包.md)。

较早 Handoff 将局部重算深度列为待定，后续 PRD-006 将影响判断与有限重算纳入 P0。本规格按后者定义接口和有限参考实现。交接文件中的枚举是候选设计，本轮针对内在冲突做明确修订，见第 11 节。

冻结：9 类信息域、10 个业务对象、2 类系统记录；跨候选偏好机制 B；模块化对象 + 统一规则；完整定义语义、增量工程实现。完整事件溯源、完整决策依赖图、酒店深选、国际机票搜索与联合优化、订单交易、逐日景点排程不在本版。

| 信息域 | 承载对象 |
|---|---|
| 旅行目标与意图 | TripGoal；OperationIntent 提供操作依据 |
| 用户偏好与顾虑 | Preference |
| 现实约束与预算 | Constraint |
| 目的地实体与体验知识 | DestinationEntity |
| 候选与取舍关系 | Candidate、Preference、Decision |
| 外部事实与核验 | ExternalFact |
| 旅行骨架与方案 | Skeleton |
| 用户决定与确认 | Decision |
| 未解决问题与变化影响 | OpenIssue；DecisionContext 提供当前任务投影 |

业务对象共十类，DecisionContext 保持业务分类但仅作为只读派生对象。ChangeRecord、OperationIntent 是两类系统记录。旅行根容器、命令封装、提案标识和数据库基础设施不增加业务对象类别。

## 2. 机器规范和字段规则

机器契约为 `schemas/*.schema.json`，声明源为 `tripstate/contracts.py`。字段字典包括所有顶层属性说明及机器可读的嵌套路径；交接用最终字段字典见 `FIELD_DICTIONARY_FINAL.md`，对象关系、传播、权限、枚举与状态矩阵见同目录 Final 文档。转换表由同一转换声明生成。语义守卫由独立代码与反例测试验证，不能仅从 Schema 合法推断业务正确。

- 固定 `$schema` 为 Draft 2020-12，`$id` 使用保留的 `trip-state.example` 命名空间；这些是身份标识，校验器通过本地注册表解析，不访问网站。
- 根版本 `schema_version=0.1.0`。所有对象禁止未知额外字段。持久对象字段均明确必填，允许未知处使用 `null`；不将缺失、空列表、零值和 null 混为一谈。
- 标识在单趟旅行内唯一，业务 ID 不能原位改类型。系统记录和投影使用独立标识空间；引用必须在同一旅行内解析，并匹配规定类型。
- 日期为源业务时区下 `YYYY-MM-DD`；时刻必须带时区，内部比较转换 UTC，系统记录输出 UTC。日期区间两端包含。金额为币种最小单位整数；不自动换汇。人数为人、停留为夜、耗时为分钟。
- 范围支持 trip、entity、skeleton、date、traveler。全程不带对象 ID，局部范围明确对象；参与人必须在 TripGoal 登记。实体／日期／个人细粒度约束可以完整保存、进入上下文；本参考计算器尚不进行局部日内排程或个人分摊，必须返回对应未知，不宣称该部分已满足。
- `version` 是对象版本，`revision` 是旅行聚合版本；两者不互相替代。引用旧版本可以用于审计，但不能越过新鲜度检查作为当前结论。
- 证据定位符可指向输入、实际展示/行为事件、文档或供应商回执，不因是字符串便声称已核验。TS 校验定位符的结构和业务引用，不从字符串推断用户看过什么；展示机会及行为对象须由可信交互记录和上游解释核对。来源原文不被重新解释后的结论覆写；已提交的旧解释与旧来源保留在历史差异中，未提交原话按 DC/宿主的授权留存规则处理。

## 3. 唯一权威来源与对象关系

| 内容 | 唯一权威来源 | 其他位置的表达 |
|---|---|---|
| 目标与任务 | TripGoal | 上下文仅引用 |
| 偏好原意、明确程度、范围 | Preference | 候选关联偏好 ID，不复制全局偏好 |
| 预算、日期等要求 | Constraint.value | 骨架与计算结果引用约束 |
| 地理身份和知识资料 | DestinationEntity | 候选引用实体；实体不保存用户是否选择 |
| 探索与排除判断 | Candidate | 用户确认行为另由 Decision 表达 |
| 外部观察与证据层级 | ExternalFact | 用户确认不能写事实核验层级 |
| 版本内容 | Skeleton.stops/connections | 城市顺序仅由 stops 顺序表达，不另存 order 副本 |
| 当前采用的骨架 | 根 effective_skeleton_id | “有效骨架”标签由根引用派生 |
| 谁确认何种选择及范围 | Decision | 与当前采用关系必须原子一致 |
| 问题与其解决依据 | OpenIssue | dismiss 不改变事实与约束 |
| 任务读取结果 | DecisionContext | 不接受独立业务写入 |

骨架存储用途 `scenario/plan` 与生命周期 `active/superseded/archived`。活动 plan 未被根引用时为暂定骨架；被根引用时为当前有效骨架；scenario 始终隔离。有效在这里表示“当前被采用并维护”，不表示“现实可行性已全部证实”。

`assessment.status` 为 unchecked、pending、verified、blocked、stale；`verified` 仅指参考计算覆盖内的检查，仍不等于全程可购买、全程预算完整或真实产品验收。展示必须同时显示检查范围、cost_coverage 和 unknowns。

已知硬约束冲突阻止新骨架采用。用户可在明确看到未知项并承认其限制后采用 pending 骨架。后来事实失效时保留原采用引用和 confirmed 决定，检查状态改为 stale／blocked，并产生问题；不自动删除用户选择，也不继续宣称可行。

所有已确认骨架修改必须新建版本；新版本 `parent_id` 指向旧骨架。采用新版本时旧骨架 superseded，同范围旧 Decision revised，并原子更新根引用。撤销采用决定清空根引用，不自动回退某个可能已经过期的历史版本。

关系基数：一个旅行有 0..N 个持久业务对象，最多一个 active/revised 目标；一个实体可对应 0..N 个局部候选，一个候选引用 1..N 个实体；偏好与候选是多对多引用；一个骨架有 1..N 个有序停留及恰好 N−1 个相邻连接；一个 Decision 指向一个候选或骨架版本。同一候选最多一个 confirmed 选择；全旅行最多一个 confirmed 骨架采用决定，与根当前引用一一对应。OpenIssue 可关联多个受影响对象；上下文可按任务生成多份，只引用同一旅行版本。历史版本不参与新的失效改写，需复用时创建新版本。

城市／体验候选的实体种类必须匹配；城市级骨架只引用城市停留。父实体、父骨架和决定替代谱系均禁止循环。假设约束覆盖必须唯一且保持约束种类。停留 nights=null 表示尚未分配，不能补零；合计相应保持未知。完整嵌套字段、类型与缺失语义见 [共享结构规范](SHARED_TYPES.md)。

Candidate 的状态或确认决定变化，若其实体存在于某骨架停留中，相关骨架检查须待复核。Candidate 被排除后不级联删除偏好和证据；若旅行日期与已确认住宿期间重叠，单独排除或拒绝住宿城市被阻止。完整关系基数、归档与传播见 `OBJECT_RELATIONSHIPS_FINAL.md`、`PROPAGATION_FINAL.md`。

## 4. 偏好跨候选机制 B

Preference 独立于 Candidate 生命周期。排除卢克索不删除文化兴趣、转场顾虑、基础实体或原始证据；同一偏好可关联其他候选，但只有其 scope 和 condition 适用时才参与该候选判断。

“喜欢卢克索”只支持局部兴趣。选择探索内容时要区分实际展示、轻量喜欢、明确表达和拒绝；仅对确实互动过的具体对象建立有来源的弱证据，未展示、接触不足或没有反馈均不提供排斥证据。三次具体喜欢不能自动概括为“只喜欢古迹”、否定未见的自然体验或确认城市。弱兴趣只支持低风险、可逆的个性化；明确且与当前任务相关的兴趣可供 DC/NAP 考虑深化，但不得由 TS 自动收窄探索空间。“喜欢文化体验”可以保留明确的全程表达。确需扩大范围时创建新的、有明确证据的 Preference；新表达以 `dependencies(relation=association, object_id=旧偏好 ID, paths 包含 /status)` 指向旧表达，再将旧表达标为 `superseded`。后继引用必须同旅行、可解析且替代谱系无环；单纯撤回使用 `withdrawn`。替代关系和证据均保留在来源与历史中，不能静默修改原局部表达的范围。

“喜欢 X，但如果 Y 太高就可能不去”保存正向兴趣、负向顾虑和条件取舍，而非立即产生排除决定。certainty 描述 explicit/inferred/ambiguous/unknown，support 描述 weak/supported，status 描述 active/superseded/withdrawn。优先级不是硬约束。

条件语言仅支持 always、all、any、not、eq、ne、lt、lte、gt、gte；叶子引用对象字段路径与比较值。不执行任意表达式或代码。缺值、null 阈值、不可用事实、类型不匹配产生 unknown；all 中 false 优先、any 中 true 优先，否则传播 unknown。数值大小比较不对字符串做隐式转换。

重新考虑必须给出条件中实际引用的触发对象，且条件结果为 true；仅进入 reintroduced，不自动成为用户已选。参考实现提供三值计算和明确命令，不实现自动提炼偏好、自动判断局部表达能否全局化或完整候选排序。

## 5. 三类状态维护机制

### 5.1 候选变更 → 校验 → 有效状态合并

输入转为 OperationIntent，包含入口、原话／操作说明、目标与发生时旅行版本。LLM 只能提出业务命令；程序校验形状、引用、状态转换、来源、权限、约束和依赖。通过后合并；需要确认时只留下提案及历史，业务状态不变。

执行主体由宿主注入 `Actor(role,id)`；请求 JSON 禁止 actor、权限标志、任意 patch、直接 status/assessment/verification 写入。宿主必须先完成身份认证与该旅行访问授权；参考实现不提供登录系统。

明确用户修改请求可以作为对应范围授权，不必再弹一次泛化确认。只澄清指代或表达顾虑时，允许在已有安全范围内继续提供帮助，重要变更须另有明确授权。TS 接收结构化命令，不能凭 input.text 自动识别“那个”所指或判断该句是否授权删除；语义理解/写桥在对象或授权范围仍不明时不得提交重要命令，只能保留未知并转入澄清。TS 对实际提交仍执行既有权限、版本、确认及原子守卫。对已确认的候选或骨架决定，withdraw_decision 的实际 User 必须匹配 Decision.confirmed_by。直接提交和接受模型提案使用同一检查。模型或系统拟修改明确目标、约束、明确偏好、采用骨架或用户决定时进入 pending_confirmation。固定现实条件不可普通放宽；系统只有在其 evidence 依赖的事实已 contradicted/superseded 时，才可将旧固定约束标 invalidated，再加入替代约束。单纯事实过期不足以取消硬约束；旧记录保持可追溯。

确认绑定提案内容摘要、旅行版本和用户看到的变更范围；默认最多有效 5 分钟，且不晚于已有事实的下一次到期时刻。确认时重新验证当前条件；任何旅行 revision 变化都要求重新预览，V0.1 不做自动重基。用户拒绝提案留下 rejected 历史，原状态保持。

确认候选与确认骨架分离。不能通过“排除候选”静默移除当前骨架城市；与已有明确候选接受／拒绝冲突的新骨架，要求在同笔提交中明确撤销对应决定。普通骨架确认不授予交易权限。

业务提交采用复制后校验再替换；更改对象、影响标记、问题、根引用、历史和幂等结果需构成同一个提交单位。参考实现用进程内锁和内存复制验证该语义；生产数据库须用事务与唯一约束实现，不能据此宣称崩溃恢复已测试。

### 5.2 当前状态 + 变更历史

当前状态供业务读取；OperationIntent 留存输入；ChangeRecord 留存前后快照差异、来源输入引用、原因、提案摘要、涉及对象、确认用户及聚合版本。新增用 before=null；修改同时保留前后；替代、撤销和失效通过业务命令和 status 差异表达。

`pending_confirmation` 记录的 diff 是“若获确认的拟议结果”，不是已应用值；GET state 不含这些拟议值。`applied` 才对应业务写入。对无业务变化的合法重复检查可留记录但不增加 revision。结构非法或守卫失败请求返回错误且不落业务历史；生产传输／安全日志另行承担失败请求记录，不伪装为已提交 ChangeRecord。

历史只追加，用户纠错产生新版本。上游依据原话和旧证据区分支持、纠错、真实变化、条件细化及暂不可区分；同一输入可形成多个合法业务变更，或不形成业务变更。TS 只接收有来源且有适用范围的命令，不以模型标签代替用户事实。TS 保留原证据及无关状态，并只复核受影响的依赖。字段 source 表示最新明确写入依据，历史快照保留旧来源。撤销、再次考虑、事实重新查询均不删除证据。连续地图编辑修改同一暂定骨架；与之无关的有效骨架保持不变。

本包不承诺完整事件重放，也不提供“一键恢复旧快照”。恢复旧方案应从旧内容创建新暂定版本，按当前约束和事实重新检查后再确认。

### 5.3 依赖关系、失效与有限重算

依赖由对象 ID、版本、字段路径、relation 组成。input 计算边必须无环；evidence 依据可以形成引用回路，但传播按集合去重终止；association 不触发重算。

字段级差异只影响实际读取该路径的显式依赖；保守传播链为条件／偏好／事实 → 候选 → 骨架 → 依赖该版本的决定。骨架显式引用的交通和费用事实、候选的偏好关联、决定的目标及依据构成隐式依赖，不允许因漏填 dependencies 而失效不传播。新增或变更的适用约束也会触发骨架复核。

变化先使受影响候选／决定 review_state=stale，骨架 assessment=stale，并建立或重开依赖问题；保留原值和无关对象。用户的 confirmed 选择不被事实失效改为 revoked。程序执行 recalculate 后写入新检查结果；失败则整笔重算不提交，之前的 stale 标记保留。

条件表达内引用的事实也参与传播；经过 Preference／Constraint 的间接影响只传递适用性变化，不篡改用户原偏好或取消原约束。计算结果因时钟前进而改变时，同样向下游决定传播，但不把刚完成的有效重算再次标为 stale。被排除候选不能通过 retain 绕过 reconsider；骨架与决定的 supersede 只能由专用采用／选择命令原子触发。

首次计算会登记使用的约束、事实和版本。时效由显式 check_freshness 命令维护，消费事实和构建上下文时额外检查当前时钟；生产调度按最早 expires_at 唤醒，建议一次提交完成失效标记，再分别触发重算。无生产定时器实现。

参考计算支持停留夜数合计、硬日期／天数范围、登记人数核对、连接对应关系、已知班次耗时与时间衔接、城市级入离境端点／时刻约束、条件表达和费用分组汇总。交通节点到城市的映射、机场接驳、完整路线搜索、疲劳模型、换乘最短安全时间、逐日体验或酒店计算未实现，必要时保留未知。

“预算大概两万”可作为可调整的任务证据跨轮使用。币种、人数或费用范围未知时，由授权的 DC/宿主任务语境保留原话、来源和适用范围；TS 的 OperationIntent 只记录已提交或待确认的业务操作，不能作为所有未提交话语的跨会话存储保证。恢复后须能从授权任务证据找回相关原话，不能伪造为新输入或硬上限。口径齐备且符合用户表达时，可写入正式软预算。费用按币种和人数分组，按 item_key 防重。预算只累计相同币种、人数和预算费用范围的已知分项；已知分项超出硬上限即冲突，未超不证明全程可负担。cost_coverage 仅为 none/partial，本实现不生成全程总价。

## 6. 外部事实与工具接入

ExternalFact 不把用户认可作为核验依据。查询结果区分 result、partial、empty、timeout、error、no_service；其中 empty/timeout/error 不表示没有服务，值保持 null。明确 no_service 必须有 transport.service_exists=false 的可追溯来源证据。condition.value=null 仍是未知，不能升级为核验成功。

核验、时效、适用性是独立字段。可信适配器 ingest_fact 从查询条件、原始结果、必需字段和时效推导核验层级；即使提供方没有报告缺项，程序也检查交通是否具有明确服务存在及起止时刻。供应商接口成功不自动等于核验成功。

本实现最高输出 date_specific；purchasable 是为后续已核实库存证据保留的契约层级，不由当前适配器生成。estimated 不能用于确立指定日期班次存在。所有实际核验都仍依赖可信来源接入，本包使用合成提供方，未验证现实真实性。

同一日期、方向、查询参数和对象范围内仍可用的交通观察，对服务存在性给出相反结论时，两条观察均不可作为已核验的采用依据。可信接入层对其他证据完成可比性核验后，可用未解决的 conflict OpenIssue 指向争议事实。骨架引用其中任一争议交通或费用事实，或硬要求无法在缺少争议证据时判定，采用流程按 HARD_CONFLICT 拒绝。已采用方案保留用户决定并标记受影响结果待复核。没有服务、证据缺失与证据冲突分别呈现。更换查询日期或重新查询创建新事实 ID；旧事实可由系统标记 superseded/contradicted，历史保留。旅行日期改变时旧查询可变 not_applicable，但不篡改原观察。查询失败不覆盖旧有效观察；旧观察是否仍可消费独立按 expires_at 与适用条件判断。

为验证“已有外部预订限制未来方案”而不引入订单对象，V0.1 在既有 ExternalFact.query.parameters + value.condition 内定义严格 `reservation-v0.1` 只读住宿回执 profile：须包含住宿类型、回执号、城市、入住／退房日期和 confirmed/cancelled 状态，且由可信 Tool 提供完整指定日期证据。同回执至多一条 active 版本；已确认回执的替代／反证必须在同笔提交中导入仍有效的同回执后继。当旅行窗口与住宿期间相交而骨架不含该城市时为已知冲突；旅行日期移出住宿期间时保留回执并标记后续处理未知，不机械强制经过旧城市。回执过期只要求复查，不自动取消。城市在骨架中仍不能证明具体入住夜数匹配，计算返回未知。本 profile 不提供查询真实库存、下单、支付、改退或订单生命周期；宿主必须验证提供方身份和真实回执。

## 7. Decision Context

POST decision-context 接受 task_id 与种子对象 ID，返回对象引用、版本清单、组装时刻、旅行 revision、到期时刻及不可用事实 ID，不复制业务值作为独立真相。

组装包括用户指定对象、所有活动约束、所有 confirmed 决定、当前骨架与未解决问题，再沿依赖及相关引用闭包扩展。V0.1 有意保守包含全旅行硬约束，不通过模型相关性裁剪；dismissed 问题仍会作为未证明已解决的限制进入上下文。

`context_is_current` 检查旅行身份、生命周期、revision、时间、约束集合、决定、问题、版本清单和事实状态。时间超过边界或任何提交导致 revision 改变时重建。stale_fact_ids 包括已识别但尚未消歧的不可消费事实。独立 DC 0.1.0 运行合同负责当前任务解释、检查点及跨会话恢复；本节 POST decision-context 是 TS 参考投影契约。两者只读取 TS 权威状态，不得复制成第二业务真值。消费层根据目标、当前证据和关键缺口比较备选行动，优先回应明确需求，并综合用户负担与时机决定立即、延后、后台准备或不介入；TS 不记录 V/C/E、候选行动、累计打扰、介入时机或用户效果，业务历史也不等于完整提示、曝光和交付流水。结果回执只证明操作结果，后续仍要检验用户是否获益。新增加的约束因此不会被旧引用清单漏掉。

GET state 返回最后一次提交的权威快照，不因读取隐式写历史；freshness 是上次维护值，不是永久保证。任何据此作可行性判断的消费者必须同时检查 expires_at 或构建 Decision Context。确认和重算均在程序内重新检查事实，不能依赖客户端展示。

## 8. 更新 API 与错误语义

本地 `dispatch` 实现以下 HTTP 行为契约，未部署 HTTP 服务。

| 方法与路径 | 输入 Schema | 输出 Schema |
|---|---|---|
| GET /trips/{id}/state | 路径中的旅行 ID | state |
| POST /trips/{id}/decision-context | context-request | DecisionContext |
| POST /trips/{id}/changes/preview | change-request | response，outcome=preview |
| POST /trips/{id}/changes | change-request | response |
| POST /trips/{id}/changes/{proposalId}/confirm | confirm-request | response |
| GET /trips/{id}/changes | 路径中的旅行 ID | history |

路径段名称在上层计划称 changeId，正式绑定的是提案 proposal_id；每次 pending／applied／rejected 历史条目有独立 ChangeRecord.id，并引用同一 proposal_id。避免把历史记录 ID 与待确认提案 ID 混用。

change-request 包含 expected_revision、idempotency_key、reason、input 与 commands。支持 create、revise、transition、adopt_skeleton、decide_candidate、reconsider、recalculate、ingest_fact、check_freshness、resolve_issue、dismiss_issue、withdraw_decision。create/revise 的字段白名单按对象类型给出；事实、用户决定和上下文走专用通道。

只在命令契约允许的字段做 revise；不得任意删除对象。进入终态后的历史对象不可原位改写。输入版本过旧返回 409，不做最后写入者胜出。幂等键按主体和操作域隔离；同键同内容返回原结果，同键异内容返回 409；确认完成后原提交键返回最终处理结果。

preview 返回拟议前后差异、受影响 ID、确认要求和提案摘要，不写状态、历史或幂等缓存。普通提交返回 200 applied、202 pending_confirmation、409 conflict、422 rejected；权限错误 403，未找到 404，方法错误 405，提交内部错误 500。所有业务错误带稳定 code 与可读 message。GET 成功体使用各自 Schema；失败体统一 response。

多个命令作为一个原子批次校验；V0.1 最多采用一个骨架。需批量创建互相引用对象时，提交末尾统一检查引用。结构不合法、权限越界、无效转换、未知确认范围、已知硬冲突、固定条件违规和引用错误均拒绝整笔提交。

## 9. OpenIssue 关闭规则

resolve 必须携带非空理由及有效、与问题对象相关的证据。过期事实、未生效约束、待复核决定或仍存在未知／冲突的受影响骨架不能用作“问题已经解决”的证明。证据不能只是任意不相关对象 ID。

dismiss 只表达用户暂不处理；保留理由、原缺口及其可行性影响。依赖再次变化会重开相应问题。参考实现采用保守整对象检查，可能要求先解决该骨架其他未知项才能关闭骨架级问题；精细到单项检查的关闭策略留给后续增量，不能宽松误关。

## 10. 生产接入、持久化与增量出口

生产存储建议按旅行聚合保存当前对象与 revision，按追加方式保存两个系统记录；数据库不是本次选型结论。需要在一个数据库事务内完成版本比较、对象写入、采用引用、审计记录、幂等结果和待确认提案消费；幂等键设置唯一约束。参考实现只证明进程内互斥和失败前不提交，不证明跨进程或断电后的持久性。

候选提案缓存必须在生产持久化并设置有效期；用户的确认身份需真实认证与旅行访问控制。外部工具先通过可信适配器，写入事实时同时保存可追溯回执。隐私保留和供应商原文授权期限需在生产接入时确认。

阶段一：接入输入提取器，复用结构与语义校验、状态维护及操作意图，验证探索→保存→纠错。阶段二：接入任务策略与多入口，消费 Decision Context，保持单一权威。阶段三：替换合成事实与有限计算，逐项验证真实数据覆盖和更细计算。阶段四：完成真实用户端到端测试。每一阶段都复用本包回归测试，新增能力必须增加独立验证证据。

## 11. 内部冲突修复与兼容映射

交接没有已发布的持久 JSON，因此没有可直接运行的旧数据迁移脚本。本表是语义迁移规则；有真实历史数据时须逐条校验，不能猜测补值。

| 原设计候选 | V0.1 定稿 | 修复原因／转换要求 |
|---|---|---|
| Preference.status 中 explicit/inferred/supported | status + certainty + support | 明确程度不是业务生命周期；缺证据的旧值保留 unknown，不强推明确 |
| DestinationEntity.available/unavailable | known/retired + coverage；可用性放 ExternalFact | 避免实体目录和特定日期服务混淆 |
| Skeleton scenario/tentative/valid/blocked 同一状态 | purpose + status（生命周期）+ effective_skeleton_id + assessment | 当前采用与现实核验独立；旧 valid 必须核对用户确认，不直接迁移为已证实 |
| Candidate.status 与 candidate_status | 唯一 status | 消除两份权威 |
| ExternalFact verified/stale/unavailable | query_status + verification + freshness + applicability | 超时／空集不能迁移成无服务；缺核验来源降为 unverified |
| cities + order + stay_allocation | 有序 stops + connections | 避免城市顺序和停留重复字段互相冲突 |
| related_ids 泛化关系 | 字段专属引用 + typed dependencies | 明确普通关联、证据和计算影响 |
| 预算单独副本 | Constraint.value 带预算模式 | 防止预算意向与硬上限互相覆盖 |
| DecisionContext 保存复制的状态值 | 只读版本引用投影 | 防止另一份旅行真相 |
| 系统记录延迟独立落库 | 状态与审计原子提交契约 | 防止状态已变但原因丢失 |

版本 0.1.0 严格拒绝额外字段；任何字段或枚举扩展须发布新 schema_version、新 `$id` 和迁移说明，不能在旧契约下静默新增。回归测试、字段字典、转换表与样例在同一次变更中更新。

## 12. 验收解释

Schema 合法只证明结构；语义测试证明给定输入下的规则；参考运行证明本地维护链路；真实模型、数据、用户效果分别需要证据。详细实际结果见 VALIDATION_REPORT.md，逐项追踪见 TRACEABILITY.md。

未测试的生产能力不得用“已定稿”一词替代。后续工程应使用此定稿契约接入、验证并记录偏差，而不是重新开启宏观产品定义。最终候选的七场景运行证据和 V1 评审边界分别见 `SCENARIO_VALIDATION.md`、`V1_READINESS.md`。
