# 4.1 F4 的产品定位与核心用户问题

## 4.1.1 为什么需要 F4？

用户通过 F1–F3 已经可以：

- 了解目的地。
- 表达兴趣和顾虑。
- 比较旅行骨架。
- 采用某一套旅行方案。

但旅行规划不会在采用方案后结束。

用户可能继续调整：

> 我想在卢克索多待一天。

> 开罗两天够不够？

> 阿斯旺先放在最后。

> 这两座城市能不能换一下顺序？

也可能直接在地图或时间轴上操作，而不通过聊天输入每一项修改。

如果 ANTU 只能重新生成一份完整行程，用户很难持续维护自己的旅行决定。

因此，F4 的主要目标是：

让用户能够通过直观操作和自然语言，连续修改同一份旅行计划，并始终理解自己正在改变什么、什么仍然有效，以及什么时候才真正提交。

【设计已收敛｜B、C】

## 4.1.2 F4 不只是可视化编辑器

它有三个层面的职责。

第一：直接操作旅行。

用户通过地图、时间轴、信息卡及自然语言对旅行安排进行修改。

第二：即时理解修改。

用户在编辑过程中，应立即看见确定性的结构变化，而不必每次等待完整 AI 分析。

第三：安全完成修改。

多次修改在一个编辑会话中形成整体草稿，最终进行必要校验与提交。

因此，F4 同时是：

- 一个可交互的旅行工作空间；
- 一套编辑会话机制；
- 一套与旅行状态、校验和确认规则衔接的业务操作流程。

## 4.1.3 F4 的设计原则

【历史摘要记载为 F4 后期收敛方向｜B】

原则一：浏览与编辑分离。

查看内容不自动修改旅行。

原则二：连续编辑优先。

不要求用户每改一天、每移动一座城市就确认一次。

原则三：多入口操作同一份草稿。

地图、时间轴及编辑会话内明确的自然语言指令，应该作用于正确的共同编辑对象。

原则四：即时反馈与深度分析分层。

能够确定计算的简单变化即时显示；复杂 AI 影响分析在适当节点集中执行。

原则五：有效方案受到保护。

未提交草稿、假设和浏览行为不能直接覆盖当前有效旅行。

原则六：重要新取舍仍由用户决定。

完成编辑不意味着用户自动接受系统后来发现的额外牺牲。

# 4.2 F4 的用户场景与进入方式

## 4.2.1 场景 A｜已有骨架，用户希望直接修改

### 已有状态

用户已经采用一套埃及八天旅行骨架。

例如：

开罗三天 → 卢克索三天 → 阿斯旺两天。

这里的天数只用于说明机制。

### 用户目标

调整城市停留，使旅行更符合当前偏好。

例如：

> 卢克索我想多待一天，开罗可以少一天。

### 可能的入口

- 打开地图编辑。
- 在时间轴上调整城市停留。
- 在 AI 对话中直接表达修改。
- 从某座城市的信息区执行明确编辑操作。

### F4 必须保证

不同入口不会产生相互独立、无法协调的修改结果。

## 4.2.2 场景 B｜用户在地图上探索后决定调整

用户先点击阿斯旺，浏览某项体验。

随后明确表示希望调整停留。

### 重要区分

点击城市： 浏览。

浏览体验： 了解内容。

右滑表示兴趣： 对体验产生正面反馈。

点击明确的加入或调整操作： 产生行程修改意图。

前三者不能自动等同于第四者。

【设计已收敛｜B；UX-02.5-B 补充 A】

## 4.2.3 场景 C｜用户在编辑途中提出 AI 问题

用户已经进入编辑会话，修改了开罗和卢克索的停留。

然后说：

> 开罗只有两天是不是太赶了？

这是一项信息或分析请求。

系统应结合当前编辑草稿回答。

但不能因为用户提出问题，就自动将开罗恢复为三天。

### 与明确修改的区别

用户随后说：

> 那就把开罗改回三天。

这才是明确编辑指令。

如果当前编辑会话仍在进行，应作用于同一份草稿。

【设计已收敛｜B】

## 4.2.4 场景 D｜用户在编辑中提出假设

用户已将卢克索从三天增加到四天。

然后问：

> 如果这次不去阿斯旺呢？

这不是直接删除阿斯旺。

系统应形成独立的假设预览，并与当前草稿比较。

除非用户进一步明确要求将假设应用到当前编辑，否则不能覆盖草稿。

这一机制在 F5 后期进一步明确。

## 4.2.5 场景 E｜用户编辑到一半退出

用户已经修改了两个城市，但没有点击「完成编辑」。

关闭 ANTU。

几天后重新打开。

### 后期 Owner 裁决

用户应当能够恢复上次的工作进度，尽可能返回最后成功保存的操作位置。

同时重新判断此前现实可行性核验结果是否仍然适用。

【Owner 已确认｜A：UX-02.5-A】

### 对 F4 的意义

编辑会话不能只存在于当前屏幕的临时视觉状态中。

它必须具有可恢复的业务依据与编辑成果保护能力。

具体持久化方式仍待工程核查。

# 4.3 F4 的核心工作空间布局

这一部分是 F4 设计中 Owner 直接提出过具体要求的重要内容。

## 4.3.1 整体布局的最终讨论方向

【历史摘要记载 Owner 明确提出｜B，原始裁决待补证】

整体工作空间包含：

顶部：横向旅行时间轴。

左侧及中央：占主要面积的地理地图。

右侧：较窄的上下文信息区。

地图内部可以出现城市浮层卡。

对话入口与整个工作空间联动，并可用于自然语言操作。

### 结构示意

以下为依据已讨论布局重新排布的文字原型，不是原始截图。

```
┌──────────────────────────────────────────────────────────────┐
│ 顶部旅行时间轴                                               │
│ 开罗 3 天 ─── 卢克索 3 天 ─── 阿斯旺 2 天                     │
├────────────────────────────────────┬─────────────────────────┤
│                                    │                         │
│              地图                  │   右侧上下文信息区      │
│                                    │                         │
│      ○ 开罗                        │   整趟旅行摘要 /        │
│           ╲                        │   当前城市摘要          │
│            ○ 卢克索                │                         │
│                 ╲                  │   体验价值              │
│                  ○ 阿斯旺          │   时间与转场代价        │
│                                    │   当前未知与问题        │
│    ┌──────────────────────┐        │                         │
│    │ 地图内部城市浮层     │        │                         │
│    │ 体验 / 安排 / 操作   │        │                         │
│    └──────────────────────┘        │                         │
├────────────────────────────────────┴─────────────────────────┤
│ AI 对话 / 自然语言操作入口                                    │

```

注意：

这不是已确认的完整像素级页面规格。

顶部时间轴、地图主工作区、右侧较窄信息区及地图内部浮层属于已讨论的具体布局方向。

对话输入区在何处固定、如何展开，以及响应式屏幕如何排列，当前没有足够原始证据证明已被最终裁决。

## 4.3.2 为什么地图要占据主要空间？

F4 后期讨论特别强调：

地图不应与右侧信息区机械地五五分屏。

【历史摘要记载 Owner 明确提出｜B】

原因在于：

- ANTU 需要让用户理解城市真实地理关系。
- 城市间连接是旅行规划的重要对象。
- 用户需要通过地图直接查看和修改。
- 地图内部还需要承载城市浮层卡。
- 如果地图过窄，容易失去可操作性和空间判断价值。

因此，右侧信息区应相对紧凑，地图成为主要可操作空间。

## 4.3.3 地图与时间轴的职责分工

### 地图主要回答

- 城市在哪里？
- 城市之间如何连接？
- 某座城市有什么体验？
- 当前路线的空间关系如何？
- 哪些地理对象受到调整影响？

### 时间轴主要回答

- 城市按照什么顺序安排？
- 每座城市停留几天？
- 哪些停留发生变化？
- 城市间时间安排如何连接？
- 新的顺序或停留如何影响整趟旅行？

### 重要规则

两者可以都有编辑入口。

但不应拥有两份不同的旅行数据真相。

例如用户在时间轴将卢克索由三天增加到四天：

地图、时间轴和右侧摘要应反映同一份草稿的最新状态。

不需要用户在地图中再修改一次。

【设计已收敛｜B、C】

# 4.4 右侧上下文信息区

这是 F4 中需要重点保留的设计成果。

## 4.4.1 右侧信息区的定位

它不是一个传统的景点百科侧栏。

它应帮助用户理解当前旅行安排的实际价值、代价和缺口。

【历史摘要记载 Owner 明确提出｜B】

### 信息区至少存在两种内容焦点

1. 整趟旅行摘要。
2. 某座城市的聚焦摘要。

两者根据当前用户操作切换。

## 4.4.2 整趟旅行摘要

用户没有聚焦某座城市，或者明确返回整体旅行视角时，右侧信息区展示：

- 当前整趟旅行的主要城市。
- 已经保留的重要体验。
- 当前旅行方案能够获得什么。
- 可能失去或尚未安排什么。
- 主要交通与时间代价。
- 重要用户条件。
- 尚待解决的决定。
- 未核验的现实条件。
- 已识别的重大冲突。

### 为什么不是只展示城市列表？

如果右侧只是重复：

> 开罗 3 天、卢克索 3 天、阿斯旺 2 天

那么它和顶部时间轴没有形成有效分工。

右侧应当解释：

这些安排对用户而言意味着什么。

## 4.4.3 城市聚焦摘要

用户点击卢克索后，右侧信息区切换到卢克索相关内容。

可以展示：

- 卢克索当前停留安排。
- 已选择的核心体验。
- 用户对该城市的兴趣和顾虑。
- 在整趟旅行中保留卢克索能够获得什么。
- 当前安排的主要时间和交通代价。
- 尚未解决的城市局部问题。
- 与相邻城市的关联影响。

### 重要边界

不能因为用户聚焦卢克索，就把 AI 的全部任务上下文永久改成卢克索。

地图焦点、右侧展示焦点和 AI 当前处理的对话任务可以关联，但必须根据实际任务正确区分。

## 4.4.4 整体摘要与城市摘要如何切换？

后期讨论形成的具体行为包括：

用户点击城市：

地图展示该城市浮层。

右侧信息区切换到对应城市摘要。

用户切换到另一座城市：

地图浮层及右侧城市摘要更新为新焦点。

用户关闭城市浮层：

右侧信息区返回整趟旅行摘要。

用户通过返回控制进入整体旅行视角：

右侧信息区可以先返回整趟旅行摘要，不必强制同时关闭地图中仍有价值的城市浮层。

【历史摘要记载为已确认交互方向｜B】

### UX-04 需要验证

- 返回控制的位置。
- 城市浮层关闭与右侧摘要返回的视觉反馈。
- 地图浮层保留时，右侧展示整趟旅行是否会造成理解歧义。
- 用户通过对话聚焦城市时，右侧是否自动切换。
- 小屏幕上是否需要以分层视图替代同时展示。

## 4.4.5 编辑中切换信息焦点不能中断编辑

这是 F4 的重要连续性规则。

用户可能：

1. 正在编辑卢克索停留。
2. 点击阿斯旺查看体验。
3. 返回整体旅行摘要。
4. 再次点击卢克索。
5. 继续此前尚未完成的编辑。

整个过程中：

- 编辑会话保持。
- 已产生的修改保持。
- 草稿不会自动提交。
- 页面焦点变化不等于修改目标变化。
- 用户不需要重新开始编辑。

查看焦点的切换与编辑会话生命周期是两回事。

【设计已收敛｜B】

# 4.5 浏览模式与编辑模式

这是 F4 过程中最重要的机制区分之一。

## 4.5.1 为什么要区分两种模式？

地图上存在大量可点击对象：

- 城市。
- 体验地点。
- 城市间连接。
- 交通选项。
- 当前旅行安排。
- 可能的候选内容。

用户点击这些对象，可能只是想了解。

如果系统把地图上的每次操作都解释为修改，用户会失去浏览自由，也很难理解当前旅行究竟有没有发生改变。

因此，后期设计收敛为：

地图默认处于浏览模式，直接编辑需要明确进入编辑态或执行具有清晰修改语义的操作。

【设计已收敛｜B】

## 4.5.2 浏览模式

### 默认行为

用户可以：

- 点击城市。
- 查看城市浮层。
- 浏览具体体验。
- 点击交通连接。
- 查看交通信息。
- 切换地图焦点。
- 查看旅行时间轴。
- 打开右侧整体或城市摘要。
- 与 AI 讨论当前旅行。
- 查看其他方案或历史版本。

### 这些行为通常不应修改什么？

- 当前有效骨架。
- 已确认的城市组合。
- 已确认停留。
- 未提交的编辑草稿。
- 交通方式采用决定。
- 历史版本。

### 浏览模式仍然可以产生反馈

例如用户明确右滑表示对某项体验感兴趣。

这可以按 F1 规则记录兴趣反馈。

但不能自动等同于行程采用。

因此：

浏览模式不是完全没有状态变化，而是不会因为普通查看操作自动发生旅行方案修改。

## 4.5.3 编辑模式

用户通过明确入口进入旅行编辑。

例如点击：

编辑行程。

进入后，用户可以修改旅行骨架中的相应对象。

### 编辑态需要具备的行为

- 支持连续修改。
- 对修改对象和操作意图进行明确关联。
- 即时更新草稿的可视化呈现。
- 保留原有效方案。
- 支持撤销和放弃。
- 支持完成编辑。
- 允许用户在编辑过程中查看其他城市或体验。
- 可以接受清晰的自然语言编辑指令。

### 重要规则

进入编辑模式不是用户确认所有后续修改的意思。

用户仍然需要完成编辑会话，系统仍然需要按照权限和约束规则处理正式应用。

## 4.5.4 进入编辑模式是否必须弹窗确认？

历史讨论没有确立必须增加一个单独的“是否进入编辑模式”确认步骤。

F4 后期反而强调减少多余确认。

因此，不能在归档时自行增加：

`点击编辑 → 确认进入编辑 → 开始修改`

这类强制流程。

可以通过明确编辑入口和可理解的界面状态完成模式切换。

入口视觉形式属于 UX-04 的工作，不应重新增加业务授权关卡。

## 4.5.5 离开编辑页面是否自动结束编辑？

不是。

【设计已收敛｜B；UX-02.5-B 后期确认 A】

用户可能在编辑过程中：

- 查看地图中的其他城市；
- 打开体验详情；
- 切换到 AI 对话；
- 比较一个假设；
- 查看历史方案；
- 返回整体旅行摘要。

这些操作本身不应自动提交或放弃当前草稿。

### 应区分

页面切换： 用户改变当前查看内容。

工作上下文切换： 用户暂时处理另一项任务。

完成编辑： 用户明确提交本轮编辑意图。

放弃编辑： 用户明确不再保留本轮未提交修改。

四者不能混为同一种事件。

# 4.6 同一次编辑会话中的连续修改

## 4.6.1 为什么需要编辑会话？

最初容易出现的设计方式是：

用户改变一个城市天数，系统立即执行完整分析、要求确认，然后才能继续修改下一项。

这种方式在复杂旅行规划中存在明显问题。

例如用户的最终目标是：

> 卢克索多一天，开罗少一天，整趟旅行还是八天。

如果第一步把卢克索从三天改成四天，系统马上按九天方案进行全面重算、提出警告并要求确认，会中断用户原本准备连续完成的操作。

因此，F4 后期形成：

多次修改先在同一份编辑草稿中累积，用户完成这一轮编辑时，再对聚合结果进行必要分析和校验。

【历史摘要记载 Owner 明确认可｜B】

## 4.6.2 连续编辑代表性案例

初始有效方案：

| 城市  | 当前有效停留 |
| --- | ------ |
| 开罗  | 3 天    |
| 卢克索 | 3 天    |
| 阿斯旺 | 2 天    |
| 总计  | 8 天    |

用户进入编辑模式。

### 第一步

将卢克索从 3 天调整为 4 天。

草稿变成：

开罗 3 天、卢克索 4 天、阿斯旺 2 天。

当前草稿合计 9 天。

### 第二步

将开罗从 3 天调整为 2 天。

草稿变成：

开罗 2 天、卢克索 4 天、阿斯旺 2 天。

合计恢复为 8 天。

### 正确系统行为

第一步就可以立即显示：

- 卢克索 +1 天。
- 草稿当前合计 9 天。
- 相对于八天边界存在暂时不一致。

但不应仅因为用户还没有完成第二步，就强制启动完整 AI 方案分析与独立确认。

第二步完成后：

- 开罗 -1 天。
- 卢克索 +1 天。
- 总天数仍为 8 天。

当用户点击「完成编辑」，系统再对本轮整体调整分析其实际影响。

### 重要边界

允许暂时存在尚未完成的编辑草稿，不等于可以隐藏已知硬约束问题。

如果系统可以立即确定当前草稿超出了明确天数，可以就地提示。

但该提示不必强制打断用户后续编辑。

这与“不要每次操作都进行完整 AI 评估”并不矛盾。

## 4.6.3 编辑草稿需要保留什么？

从用户体验角度，需要能够恢复：

- 本轮开始编辑时的有效方案。
- 用户本轮已经提出的修改。
- 当前修改累积后的草稿。
- 相关城市、顺序和停留变化。
- 当前浏览和编辑位置。
- 哪些影响已直接确定。
- 哪些复杂影响尚未完成核验。
- 已发现的重大冲突。
- 尚未完成的编辑任务。

【设计已收敛｜B；后期 UX-02.5-A 补充 A】

### 工程注意

这里描述的是业务和用户体验需求。

不意味着必须新建名为 `EditSession` 或 `DraftState` 的正式 Trip State 对象。

需要由工程对照正式 Schema 和运行机制确定承接方式。

## 4.6.4 多次编辑之间如何保持连续？

用户可以在一次编辑会话中：

1. 调整卢克索天数。
2. 调整开罗天数。
3. 修改城市顺序。
4. 点击阿斯旺查看信息。
5. 通过 AI 询问整体影响。
6. 继续修改某座城市。
7. 完成编辑。

系统始终需要知道：

这些修改属于同一次尚未提交的编辑工作。

不能因为用户点击阿斯旺，便误以为本轮编辑结束。

也不能因为 AI 回答了一次问题，就自动把草稿应用成有效方案。

# 4.7 编辑过程中的即时反馈

这是 F4 对交互响应性提出的关键要求。

## 4.7.1 两种反馈不能混淆

F4 后期明确区分：

即时、确定性的反馈。

与：

需要 AI 分析或事实核验的综合反馈。

它们发生的时机和需要的计算能力不同。

## 4.7.2 应当即时更新的内容

例如用户将卢克索从三天调整到四天。

系统可以立即更新：

- 卢克索的显示停留天数。
- 顶部时间轴中的长度或天数。
- 整趟旅行当前草稿的天数合计。
- 与原方案相比增加的一天。
- 右侧信息区的相关数字。
- 本轮编辑记录。

如果用户调整城市顺序：

可以立即更新：

- 时间轴顺序。
- 地图中当前规划连接。
- 编辑记录中的顺序变化。
- 相关连接已改变、需要进一步检查的提示。

### 注意

这些是能够直接从编辑操作与当前草稿计算的结果。

不要求每次都调用 AI 做完整旅行分析。

## 4.7.3 不应立即编造的内容

用户增加卢克索一天后，系统不能在未经相应分析的情况下直接声称：

> 整趟旅行会轻松很多。

也不能立即断言：

> 你可以多完成三项历史遗迹体验。

因为实际能否做到，还依赖：

- 用户的具体体验安排。
- 城市内交通。
- 现实开放条件。
- 原有旅行顺序。
- 其他城市是否受到压缩。

这些属于需要进一步分析的内容。

## 4.7.4 即时编辑记录

【历史摘要记载 Owner 要求｜B】

编辑过程中应当存在简洁的修改说明。

### 城市层面

例如：

- 开罗：3 → 2 天。
- 卢克索：3 → 4 天。

### 整趟旅行层面

例如：

- 总天数保持 8 天。
- 城市组合未改变。
- 城市停留重新分配。
- 交通及体验连锁影响待完成编辑后检查。

### 设计目的

用户应能随时理解：

我刚刚改了什么？

而不需要在 AI 长篇说明中寻找答案。

## 4.7.5 不应每次重新生成完整解释

历史讨论中特别强调：

用户连续编辑时，不需要每改一项就触发全套 AI 规划和解释。

原因包括：

- 打断操作流。
- 增加等待时间。
- 增加运行成本。
- 对尚未完成的中间状态反复计算。
- 让用户阅读大量最终可能失效的分析。
- 产生不必要的重复确认。

### 允许的例外

如果某一操作直接触及明显的重大决定或可确定的硬约束冲突，系统应及时就地提示。

这不等于必须对每一步执行完整行程重算。

# 4.8 地图、时间轴与 AI 对话编辑同一份草稿

这是 F4 中最重要的跨入口机制。

## 4.8.1 设计问题

用户可能通过不同方式表达同一个编辑意图。

例如：

地图操作：

在地图或相应编辑控件中增加卢克索停留。

时间轴操作：

将卢克索的停留从三天调整为四天。

自然语言：

> 卢克索加一天。

如果三个入口各自维护不同结果，会出现：

- 时间轴已经显示四天，地图仍显示三天。
- AI 对话继续基于旧天数分析。
- 一个入口的修改覆盖另一个入口。
- 用户不知道哪份方案有效。

### 形成的规则

同一个编辑会话中，不同入口的明确编辑操作，应作用于同一份编辑草稿。

【设计已收敛｜B】

## 4.8.2 地图编辑

### 用户可以执行的操作类型

已有设计讨论涉及：

- 改变城市顺序。
- 调整城市停留。
- 增加或移除城市。
- 修改某些旅行连接。
- 在相关对象上触发明确编辑。

具体由拖动、点击、加减控件或其他操作完成，仍需 UX-04 验证。

### 系统必须知道

- 用户操作的是哪个旅行对象。
- 操作前是什么。
- 操作后是什么。
- 本轮编辑的基础方案是什么。
- 修改是否作用于当前草稿。
- 是否涉及已确认的重要决定。

### 不得自动推断

用户移动地图视角或点击城市，不等于用户改变城市顺序。

用户查看交通连线，不等于已采用交通方式。

## 4.8.3 时间轴编辑

### 用户操作

例如：

将开罗停留由三天缩短为两天。

### 系统反应

- 当前编辑草稿更新。
- 时间轴立即显示新分配。
- 地图中的旅行安排与相关摘要同步。
- 编辑记录新增对应变化。
- 不因为一次调整就直接覆盖有效方案。

### 与地图一致

如果用户再通过地图调整卢克索停留，应继续修改同一草稿。

不能产生两个互不一致的编辑版本。

## 4.8.4 编辑中的自然语言指令

### 场景一：明确修改

用户：

> 把卢克索增加一天。

如果当前编辑会话已经存在，系统应将这项明确指令作用于当前草稿。

### 场景二：继续修改

用户：

> 开罗减少一天。

系统应识别该操作仍属于同一编辑会话。

### 场景三：问题

用户：

> 卢克索四天会不会太长？

系统应该回答或分析。

但不能把这个问题自动理解为缩短卢克索停留。

### 场景四：假设

用户：

> 如果不去阿斯旺呢？

应形成假设分析，不自动删除阿斯旺。

### 场景五：明确把假设应用到草稿

用户：

> 那把不去阿斯旺这个改动加到当前编辑里。

才将相应改变纳入当前草稿，并继续遵守编辑会话和校验机制。

【设计已收敛｜B；F5 进一步细化】

## 4.8.5 编辑会话外的自然语言修改

这里有一项后期重要边界：

用户不必先打开地图编辑模式，才能通过自然语言明确要求修改旅行。

例如用户正在普通对话中说：

> 把卢克索改成四天。

系统应能够按当前旅行状态、权限和校验规则处理该修改意图。

不能回答：

> 请先打开地图进入编辑模式，然后再告诉我。

### 如何与编辑会话规则衔接？

已经存在编辑会话：

明确修改进入当前草稿。

没有显式地图编辑会话：

仍可通过合法的自然语言业务修改流程处理，必要时形成暂定修改、计算影响并完成相应确认与应用。

### 重要限制

这不授权自然语言修改绕过业务校验。

也不意味着每个自然语言请求必须生成一个与地图编辑完全相同的可见模式。

具体运行实现待工程核查。

【设计已收敛｜B】

## 4.8.6 多入口中的操作语义不能混淆

| 用户行为          | 系统应当理解      | 是否修改草稿    |
| ------------- | ----------- | --------- |
| 点击卢克索         | 查看卢克索       | 否         |
| 打开城市浮层        | 浏览城市信息      | 否         |
| 点击某项体验详情      | 获取信息        | 否         |
| 右滑体验          | 对体验感兴趣      | 不自动修改旅行草稿 |
| 时间轴明确调整停留     | 编辑停留分配      | 是         |
| 在编辑态明确移动城市顺序  | 编辑城市顺序      | 是         |
| “卢克索加一天”      | 明确修改指令      | 是，若正在编辑   |
| “卢克索四天会不会太多”  | 问题          | 否         |
| “如果不去阿斯旺呢”    | 假设          | 否         |
| “把这个假设加入当前编辑” | 明确应用假设到草稿   | 是         |
| 查看历史版本        | 历史浏览        | 否         |
| 恢复历史版本        | 明确恢复意图，须经校验 | 不应直接无校验覆盖 |

核心原则：操作入口可以不同，业务含义必须明确。

# 4.9 F4 编辑中的 AI 分析与行动边界

## 4.9.1 AI 不应在每一步都重新规划

用户正在完成一组修改时，系统不应该不断生成新的全程规划。

应优先保持轻量、稳定的直接操作体验。

### 即时阶段

处理：

- 明确操作；
- 基础数据更新；
- 确定性结构计算；
- 编辑记录；
- 已知重大冲突的必要提示。

### 完成编辑阶段

处理：

- 整组修改的综合分析；
- 对其他城市的连锁影响；
- 重要体验得失；
- 当前可执行的现实核验；
- 事实依赖；
- 需要用户处理的新取舍；
- 最终是否具备提交条件。

## 4.9.2 用户主动发问时仍可分析

“延迟全面核验”不是禁止编辑中 AI 回答问题。

例如：

> 如果开罗减少一天，金字塔之外的体验会受到什么影响？

系统可以针对当前问题给出有依据的分析。

### 但需要保护两个边界

第一：回答不自动修改草稿。

第二：局部问答结果不应冒充整份编辑草稿已经完成最终校验。

## 4.9.3 AI 可以主动准备修复，但不能擅自牺牲价值

如果在编辑过程中或完成编辑时发现：

新的安排可能挤占某项已确认的核心体验。

系统可以主动分析：

- 哪些体验受到影响。
- 是否存在其他调整方法。
- 哪些改变较小。
- 哪些方法更符合用户已表达偏好。

但不能直接认定：

> 为了恢复八天总长度，删除用户喜欢的某项体验最方便，所以自动删掉。

### 产品边界

系统承担规划劳动，用户保留重要取舍权。

【设计已收敛｜B】

# 4.10 完成编辑：批量校验与一次性确认

这是 F4 从普通地图编辑器转变为 AI-native 旅行规划工作空间的关键机制。

## 4.10.1 「完成编辑」代表什么？

用户已经在一个编辑会话中进行了多项修改。

例如：

- 卢克索增加一天。
- 开罗减少一天。
- 调整一项城市连接。
- 保留其他安排。

用户点击：

完成编辑。

这项操作表达：

用户希望将本轮编辑作为一组修改，进入必要的校验和正式应用流程。

### 不能误解为

- 每项尚未分析的影响都已经得到用户授权。
- 已经核验全部现实条件。
- 可以跳过硬约束。
- 可以自动删除其他已确认体验。
- 可以直接执行预订、购买或交易。

## 4.10.2 为什么不要求逐项确认？

【历史摘要记载 Owner 明确认可｜B】

用户在编辑会话中已经连续表达了修改意图。

如果每调整一个城市天数就要求确认一次：

- 打断操作。
- 增加冗余步骤。
- 让用户难以完成组合调整。
- 可能针对尚未完成的中间草稿过早请求确认。

因此，采用：

编辑期间连续修改，完成编辑时一次处理整组改动。

## 4.10.3 为什么完成编辑后不应该再弹一次通用确认？

F3 已经形成“选择即确认”。

F4 对应的后期原则是：

「完成编辑」本身已经表达对这组明确修改的提交意图，不应在普通情况下再增加一个重复确认弹窗。

例如：

用户已经明确把卢克索调整为四天、开罗调整为两天。

系统完成必要检查后，如果不存在超出用户已知范围的新重大取舍，可以按照既有授权直接应用该组修改。

不需要再问：

> 你确定要将卢克索改成四天、开罗改成两天吗？

### 但必须保留新的必要裁决

例如，完成编辑后发现：

新的转场安排会导致原本已经确认的某项关键体验无法保留。

而用户之前并不知道这个后果。

系统应当说明并要求用户判断相关新取舍。

这不是重复确认同一组修改。

重复确认与新发现的重要价值裁决，属于不同情况。

## 4.10.4 完成编辑后的系统处理顺序

### 步骤 F4-S01｜固定本轮提交范围

确定：

- 当前旅行。
- 本轮编辑所依据的有效版本。
- 已累积的全部修改。
- 用户明确要求保留的内容。
- 相关硬约束。
- 已确认的重要安排。
- 当前事实与未知事项。

### 步骤 F4-S02｜检查基础版本

判断用户编辑时所依据的版本，是否仍然适合作为提交基础。

如果期间另一个设备或其他流程已经更新有效版本，不能直接覆盖。

### 步骤 F4-S03｜执行结构及已知约束检查

例如：

- 总天数是否一致。
- 城市顺序是否有效。
- 有无明确硬约束冲突。
- 有无直接影响已确认决定的变化。

### 步骤 F4-S04｜分析整体变化

检查：

- 相对于原有效方案改变了什么。
- 哪些城市受影响。
- 哪些体验能够保留。
- 哪些体验可能失去。
- 哪些交通连接改变。
- 哪些现实条件需要重新核验。

### 步骤 F4-S05｜执行当前能够完成的现实核验

按已有日期、旅行细节和数据能力检查相关现实约束。

没有具体日期时，不应强制进行不可能完成的班次核验。

### 步骤 F4-S06｜判断是否存在阻断问题

如果没有阻断当前确认范围的问题，可按合法权限完成应用。

如果存在已知重大冲突或尚未授权的重要取舍，应保留草稿，向用户解释。

### 步骤 F4-S07｜完成提交或保留草稿

成功：

生成新的有效旅行安排，并保留版本与依据。

需要进一步处理：

保持原有效方案，保存当前草稿及待解决问题。

失败或状态未知：

不得虚报成功，必须按权威状态判断实际结果。

上述顺序为根据已收敛产品行为整理的逻辑顺序，不是正式工程调用链或接口设计。

# 4.11 无旅行日期时的编辑与校验

这一部分是 F6 后期对 F4 的重要补充。

## 4.11.1 用户可以不选具体旅行日期而完成编辑

【Owner 已确认｜A：F6 后期】

用户可以在没有出发日期的情况下：

- 选择城市。
- 调整城市顺序。
- 分配停留。
- 选择重要体验。
- 形成较充分的旅行骨架。
- 完成一轮编辑。
- 在当前可核验范围内确认规划内容。

不能因为日期为空就一概禁止提交旅行骨架。

## 4.11.2 完成编辑时检查什么？

需要依据当前规划精度及已知条件确定检查范围。

### A. 与日期无关的结构检查

例如：

- 城市停留天数是否与总天数一致。
- 明确硬约束是否被突破。
- 方案内部是否存在已知结构矛盾。

### B. 一般安排和连接检查

例如：

- 在已有可靠信息下，当前连接是否存在明显问题。
- 某些体验与停留分配是否存在可以确定的冲突。
- 已知时间关系是否合理。

### C. 需要具体日期的现实检查

例如：

- 指定日期的班次。
- 活动实际开放时间。
- 具体时间衔接。
- 实时可预订性。

如果没有日期或相关数据，这些事项不能被标成已经通过。

## 4.11.3 完成编辑后的状态表达

例如用户完成八天骨架的调整。

如果已检查的结构条件没有发现冲突，系统可以告知：

> 当前旅行骨架已按本轮修改更新。总天数与已知结构条件符合要求；具体交通班次及活动时间还需要在确定日期后核验。

这属于说明性文案，不代表某个真实埃及方案已经通过检查。

### 重要区分

已确认规划内容：

用户明确采用的安排。

待核验现实条件：

尚缺少足够证据的具体执行事项。

已发现现实冲突：

通过有效检查确认存在不兼容的条件。

不能把后两者混同。

## 4.11.4 后续添加日期怎么办？

用户后来确定旅行日期时：

1. 识别哪些安排依赖日期。
2. 检查此前结果的适用性。
3. 对受影响部分重新核验。
4. 保留仍然成立的规划决定。
5. 对新发现的冲突进行标注。
6. AI 主动准备修复建议。
7. 需要新价值取舍时由用户决定。

### 不能默认

加入日期后重新生成整份行程并自动覆盖之前的全部规划。

### 工程影响

需要识别条件依赖和受影响范围，而不是只存一个“整份旅行已经校验通过”的布尔值。

具体对象、字段及计算机制需工程核查。

# 4.12 编辑中发现冲突时如何处理？

## 4.12.1 首先区分三种情况

### 情况 A｜明确可计算的中间草稿不一致

例如，八天旅行当前草稿暂时分配了九天。

系统可以立即提示。

但应允许用户继续修改，完成本轮整体调整。

### 情况 B｜完成编辑后发现阻断性冲突

例如，经过必要分析后发现某项明确安排与当前硬约束不兼容。

此时不应将冲突安排作为已确认的可执行结果提交。

应保留草稿，展示具体冲突和调整方向。

### 情况 C｜缺少现实核验条件

例如尚未确定具体日期，无法检查交通班次。

这不等于存在已知冲突。

可以保留相应规划层次，标记待核验事项。

## 4.12.2 冲突应该在哪里显示？

后期 F6 明确要求：

已发现的重要现实冲突，需要在相关工作空间中持续可见。

可能对应：

- 顶部时间轴的受影响行程段。
- 地图上的相关城市或连接。
- 右侧整体旅行摘要。
- 对应城市摘要。
- 当前编辑草稿的变化与问题说明。

### 为什么需要持续标注？

如果系统只弹出一次警告，用户关闭后可能无法再看到哪些安排存在问题。

用户随后切换城市或继续编辑时，可能误以为冲突已经消失。

## 4.12.3 编辑草稿的冲突与有效方案的冲突必须分开

### 场景

有效方案 A 没有相关冲突。

用户编辑草稿 B 时，引入了一项新的时间矛盾。

### 正确显示

当前编辑草稿存在冲突。

不能直接显示：

> 你已经确认的整趟旅行出现严重冲突。

除非有效方案本身确实受到影响。

### 原因

草稿与有效方案是不同的业务对象或业务上下文。

警告必须指向正确范围。

这对地图、时间轴和右侧信息区尤其重要。

## 4.12.4 AI 修复建议

系统应当解释：

- 冲突具体发生在哪里。
- 为什么发生。
- 是否已经有可靠事实支持。
- 影响哪些体验或交通。
- 哪些内容可以保留。
- 哪些调整可以解决问题。
- 哪些调整涉及用户新的价值取舍。

### 权限边界

如果修复只是直接执行用户已授权范围内的合法调整，可以按正式权限处理。

如果修复需要牺牲此前已确认的体验或改变重要决定，必须向用户说明并获得相应授权。

不能为了提交草稿成功而自动牺牲用户价值。

# 4.13 「撤销操作」「放弃编辑」「完成编辑」的区别

F4 后期明确需要同时支持这些不同操作。

## 4.13.1 撤销单次操作

用户在编辑会话内做错了一次修改。

例如刚把卢克索从三天改成四天，想撤销。

### 正确行为

撤销相应操作对当前草稿的影响。

不需要放弃整个编辑会话。

其他未撤销的编辑仍然保留。

### 工程要求

需要能够识别本轮操作及其前后关系。

但不能据此推断已有正式 Schema 必须采用某种具体撤销栈结构。

## 4.13.2 放弃整个编辑会话

用户决定：

> 这次修改先不要了。

### 正确行为

- 不应用本轮草稿。
- 保留原有效旅行方案。
- 明确处理本轮未提交修改。
- 不影响已经正式确认的其他旅行信息。
- 不删除历史有效版本。

### 与页面切换的区别

关闭城市浮层、打开其他页面或暂停工作，不应自动等同于放弃整次编辑。

用户必须能够理解自己是否正在执行真正的放弃操作。

## 4.13.3 完成编辑

用户表达：

这组修改就是我想提交的调整。

系统按已确认的流程完成必要校验和应用。

成功后形成新的有效版本。

若存在阻断性问题，则保留草稿和原有效方案。

## 4.13.4 暂停编辑

用户暂时离开、切换任务或关闭应用。

### 后期补充

【Owner 已确认｜A：UX-02.5-A】

应尽可能保存并恢复最后成功保存的编辑进度。

暂停不是放弃，也不是完成。

### 当前未定

自动暂存的具体触发频率、保存策略及前端离线机制，属于工程待核查内容。

不能在源资料中擅自设定固定秒数或自动保存接口。

# 4.14 F4 与 F5：编辑中的假设预览

## 4.14.1 为什么要单独讨论？

用户在编辑时，经常会产生不确定想法。

例如：

> 如果这次不去阿斯旺，整趟旅行会不会更轻松？

他可能只是想知道答案，并没有决定删除阿斯旺。

如果系统把这个问题直接应用到草稿，会破坏此前已经完成的编辑。

## 4.14.2 后期确立的 A/B/C 关系

【设计已收敛｜B】

假设：

A：当前有效旅行方案。

B：基于 A 正在编辑的草稿。

C：基于 B 提出的假设预览。

对应关系：

```
当前有效方案 A
      │
      └── 编辑草稿 B
               │
               └── 假设预览 C
```

### 重要规则

C 不是新的有效方案。

C 也不能自动覆盖 B。

用户只是在观察一种可能性。

## 4.14.3 用户继续问假设

用户：

> 如果不去阿斯旺，开罗可以增加一天吗？

系统可以继续围绕假设 C 分析。

如果用户之后说：

> 那还是先保留阿斯旺。

系统应回到原编辑草稿 B。

不能因为已经讨论过假设 C，就认为 B 中阿斯旺被删除。

## 4.14.4 用户明确将假设纳入编辑

用户：

> 就把不去阿斯旺这个调整加到现在的编辑里。

此时才把相应明确修改应用于 B。

之后继续在同一编辑会话中操作。

不要求立刻将 B 提交为有效方案。

## 4.14.5 用户在编辑会话外采用假设

如果没有正在进行的编辑会话，用户对某个明确假设说：

> 就按这个方案来。

系统需要根据该指代、方案范围和权限，进入既有确认与校验流程。

不因为 F5 的存在额外创造“先选中再确认”的通用中间状态。

### 与 F3 的关系

F3 的“选择即确认”仍然成立。

但必须确保选择对象明确、必要校验完成，并且不存在未经告知的重大新取舍。

# 4.15 UX-02.5 对 F4 的后期补充

这部分是 F4 正式知识底稿必须保留的新增设计，不应因为原来 UX-02.4 未包含这些要求而省略。

## 4.15.1 UX-02.5-A｜跨会话恢复与编辑续接

【Owner 已确认｜A】

### 原讨论场景

用户正在编辑埃及八天旅行。

已经完成：

- 卢克索：3 → 4 天。
- 开罗：3 → 2 天。

期间还查看过阿斯旺，并与 AI 讨论过调整对旅行节奏的影响。

但没有点击「完成编辑」，就退出 ANTU。

三天后重新打开。

### 后期 Owner 的明确要求

用户回来，应当能够恢复上次操作到的最后一个步骤。

不仅恢复聊天文本，还包括实际旅行规划工作的进度。

### 恢复的核心内容

业务状态：

- 当前有效旅行方案。
- 未提交的编辑草稿。
- 已有旅行约束。
- 已确认的重要决定。
- 相关历史版本。

编辑进度：

- 本轮修改了什么。
- 修改累积后的草稿。
- 当前编辑是否完成。
- 上次查看的城市或对象。
- 继续编辑所需要的操作上下文。

决策上下文：

- 为什么进行了这些修改。
- 之前讨论过哪些取舍。
- 哪些问题还没有解决。
- AI 已经提供过哪些分析。

现实核验：

- 上次涉及哪些现实可行性检查。
- 相关事实是否仍适用。
- 哪些部分需要重新检查。

## 4.15.2 恢复时是否重新核验？

【Owner 已确认｜A】

用户明确提出：

如果上次会话已经做过现实可行性检验，重新进入后需要系统重新检查相关条件；发现冲突时，用对应标注显示出来。

### 准确的产品要求

恢复内容与重核验是两个相关但不同的任务。

第一步应确保用户此前的有效成果和草稿可以正确恢复。

第二步，对之前涉及的现实核验结果检查适用性。

对于已失效、条件变化或需要更新的结果，重新进行必要检查。

### 重要区别

不应将所有历史核验结果直接永久视为有效。

但也不意味着恢复时必须无条件重新请求所有外部服务或重算整趟旅行的所有对象。

后者是工程实现策略问题，需要根据事实有效期、依赖关系、当前条件和数据可用性确定。

### 如果重新检查发现冲突

系统应：

- 正确关联冲突对象。
- 判断冲突属于有效方案还是草稿。
- 在地图、时间轴或信息区中显示。
- 提供必要解释。
- 在可行范围内准备修复建议。
- 不自动修改用户此前确认的安排。

### 如果重新核验失败

应显示：

待重新核验。

不能直接宣称有冲突。

也不能将旧的可行性结论当作当前已核验结果。

## 4.15.3 恢复后的用户入口

此前 UX-02.5-A 曾提出：

用户正常进入旅行项目时，可以看到存在未完成编辑的提示，并决定继续编辑或查看有效方案。

### 初步 UI 行为

继续上次编辑：

恢复编辑会话、草稿及必要操作焦点。

查看当前方案：

展示已确认有效旅行，不自动放弃草稿。

稍后继续：

保留未完成工作。

### 与 Owner 后期要求的关系

Owner 进一步强调，应尽可能恢复最后操作位置。

因此，归档应保留两个层面：

已确认的恢复目标： 能够续接最后成功保存的工作进度。

尚待 UX-04 验证的入口方式： 正常进入项目时，是自动回到编辑位置，还是先呈现轻量恢复提示，以及如何允许用户切回有效方案。

当前可见原始消息没有对所有进入路径作出最终 UI 裁决，不能自行升格为固定启动弹窗。

## 4.15.4 UX-02.5-B｜跨流程切换与状态一致性

【Owner 已确认｜A：用户明确回复“我同意”】

### 原讨论场景

用户正在编辑埃及旅行。

突然返回 F1 探索，在卢克索右滑某项体验。

### 正确规则

- 右滑作为兴趣反馈正常记录。
- 不自动将体验加入旅行。
- 不修改尚未提交的编辑草稿。
- 当用户明确要求加入行程时，才执行编辑。
- 如果当前编辑会话仍然存在，应使用正确的草稿上下文。
- 返回编辑时，此前修改保持。

### 后期统一规则

工作上下文与业务修改分离。

这不是要求为每个 Flow 创造独立工作空间。

而是保证不同交互入口在共享旅行状态时，仍具有明确的操作语义。

## 4.15.5 UX-02.5-C｜异常失败与用户成果保护

【后期设计已收敛｜A；未见 Owner 对 C 中每条工程细则的独立批准原话】

这一阶段提出了五类异常场景。

### 异常一：编辑中断网或退出

需要保护：

已经成功保存的草稿及编辑进度。

建议补充的能力：

自动暂存、保存结果反馈、恢复最后成功保存的位置。

尚待核查：

自动暂存是否已被正式技术规格覆盖。

### 异常二：AI 规划或校验失败

正确行为：

- 保留编辑草稿。
- 保留原有效方案。
- 对尚未完成的校验明确标注。
- 允许重新检查受影响部分。
- 不把工具失败当作规划通过。

### 异常三：已知现实冲突

正确行为：

- 相关警示持续可见。
- 不因切换页面自动消失。
- 可提供 AI 修复建议。
- 区分草稿冲突与有效方案冲突。

### 异常四：提交时网络中断

这是后期重点补充的工程安全要求。

用户点击「完成编辑」后，网络断开。

系统不能直接认为：

- 一定提交失败。
- 一定提交成功。

因为请求可能已经到达服务端，只是结果没有返回前端。

必须核实权威业务状态。

重复点击或重试时，还应避免同一次业务修改被执行多次。

### 异常五：有效版本在编辑期间变化

用户基于 V3 开始编辑。

之后其他设备或合法流程产生了新的有效版本 V4。

用户再提交旧草稿时，不能直接覆盖 V4。

应检查基础版本，保留草稿并处理差异与冲突。

# 4.16 F4 的全部可恢复初步 UI 设计

本节集中整理 F4 讨论中出现的视觉与组件方案。

以下所有 UI 方案都属于 UX-02 设计源资料，应完整交给 UX-04，但不能因为行为规则已收敛就宣布视觉最终定稿。

## UI-F4-01｜顶部横向旅行时间轴

来源： UX-02.4 F4 后期布局讨论，B。

### 功能

- 显示城市顺序。
- 显示停留分配。
- 展示城市之间的旅行段落。
- 支持相关直接编辑。
- 即时显示草稿变化。
- 标明受影响连接和必要状态。

### 初步形态

```
当前编辑草稿

开罗             卢克索               阿斯旺
2 天 ─────────── 4 天 ──────────────── 2 天

原有效方案：
3 天             3 天                  2 天
```

### 待 UX-04 验证

- 时间轴是按日期比例还是城市节点组织。
- 没有具体出发日期时如何显示相对天数。
- 拖动与加减停留控件如何协作。
- 草稿与有效方案是否同时显示。
- 冲突标记如何定位。
- 小屏幕下的横向滚动。

## UI-F4-02｜左侧／中央大面积地图

来源： F4 后期 Owner 布局要求，B。

### 功能

- 空间化呈现城市。
- 展示路线连接。
- 支持城市和交通对象浏览。
- 支持进入编辑。
- 与时间轴及右侧信息区同步。

### 设计重点

地图是主要工作空间，而不是占屏幕一半的陪衬元素。

### UX-04 待验证

- 地图主体尺寸。
- 缩放范围。
- 城市和连接标识。
- 编辑模式中的控制点。
- 城市浮层遮挡与移动。
- 候选、草稿和有效路线的视觉区分。

## UI-F4-03｜地图内城市浮层卡

来源： F4 后期布局讨论，B。

### 功能

用户点击某座城市时，在地图工作空间中展示对应内容。

包括：

- 城市信息。
- 核心体验。
- 当前规划安排。
- 相关操作入口。
- 与当前任务有关的补充信息。

### 交互要求

- 城市切换可以更新浮层。
- 关闭浮层可以回到整体旅行摘要。
- 查看其他城市不结束编辑。
- 浏览卡片不自动修改草稿。

### UX-04 待验证

- 浮层位置与大小。
- 卡片展开方式。
- 浮层与右侧面板如何避免重复。
- 多个地图对象之间的切换体验。
- 是否保留上一次详情滚动位置。

## UI-F4-04｜右侧整体旅行摘要

来源： F4 后期 Owner 布局要求，B。

### 必须承接的内容

- 当前整趟旅行骨架。
- 获得与保留的主要体验。
- 重要成本与取舍。
- 计划中的内容与尚未确定的内容。
- 受编辑影响的部分。
- 需要进一步决定的问题。
- 已知冲突或待核验事项。

### 设计原则

右侧信息区不能只是重复顶部时间轴或地图的地名信息。

它应该解释当前旅行安排的实际意义。

## UI-F4-05｜右侧城市聚焦摘要

来源： F4 后期 Owner 布局要求，B。

### 触发

用户聚焦某座城市。

### 显示

- 当前城市停留。
- 主要体验。
- 已做决定。
- 该城市的价值。
- 与其他城市安排的关系。
- 局部缺口或待核验信息。

### 退出

可返回整体旅行摘要。

关闭地图城市浮层后，右侧通常返回整体摘要。

但从右侧主动返回整体摘要时，不一定要同步关闭地图浮层。

这是需要保留的细节。

## UI-F4-06｜浏览与编辑入口

来源： F4 浏览／编辑分离讨论，B。

### 行为要求

默认支持自由浏览。

用户可以通过明确入口进入编辑。

### 设计约束

不能让普通点击产生隐式修改。

### UX-04 待验证

- 编辑入口位置。
- 当前模式怎样被识别。
- 何时显示编辑控件。
- 用户如何返回浏览。
- 编辑中查看信息时如何保持模式连续。

## UI-F4-07｜草稿编辑中的即时变化显示

来源： F4 多轮编辑讨论，B。

### 必须呈现

例如：

- 卢克索：3 → 4 天。
- 开罗：3 → 2 天。
- 总天数保持八天。
- 部分交通与体验影响尚待核验。

### 目的

用户不必等 AI 完成全局分析，才能理解最直接的修改结果。

### UX-04 待验证

- 行内变化标注。
- 原值与新值如何比较。
- 是否用加减符号。
- 编辑记录与主体布局的关系。
- 哪些待核验提示应当轻量呈现。

## UI-F4-08｜本轮修改记录

来源： F4 后期 Owner 对即时修改总结的要求，B。

### 信息范围

城市层面：

每座城市本轮有哪些变化。

整趟旅行层面：

本轮修改累计产生的结构变化。

### 重要限制

编辑记录应侧重：

- 实际执行了什么操作。
- 能够直接计算什么。
- 哪些复杂影响尚未分析。

不应把尚未核验的 AI 推测提前写成确定结果。

## UI-F4-09｜完成编辑操作区

来源： F4 后期编辑会话机制，B。

### 至少需要表达的操作

- 完成编辑。
- 撤销相关修改。
- 放弃本轮编辑。

### 已确定的行为

- 完成编辑发起整组修改的合法提交。
- 不重复要求普通二次确认。
- 撤销与放弃不同。
- 校验失败时保留草稿。

### 未定视觉

- 控件具体位置。
- 是否始终固定在屏幕内。
- 不同状态下的按钮文本。
- 是否显示保存进度。
- 提交中的等待和错误状态。

## UI-F4-10｜完成编辑后的整体影响摘要

来源： F4、F6，B、A。

### 内容

- 本轮改变了什么。
- 对整趟旅行的影响。
- 已完成哪些检查。
- 哪些安排仍然有效。
- 哪些项目待核验。
- 哪些冲突需要处理。

### 重要边界

如果所有必要条件已经满足，不应再增加无意义的二次确认。

如果发现用户未授权的新重要取舍，则需明确说明，允许用户继续编辑或选择修复。

## UI-F4-11｜持续冲突标注

来源： F6 后期，A。

### 适用位置

- 地图。
- 时间轴。
- 右侧整体摘要。
- 右侧城市摘要。
- 相关草稿或方案预览。

### 必须区分

- 当前草稿中的冲突。
- 有效方案中的冲突。
- 现实事实待核验。
- 旧核验结果失效。
- 工具查询失败。

### UX-04 待验证

- 警示符号和颜色。
- 严重程度。
- 解释展开方式。
- 多个冲突如何集中管理。
- 冲突修复后如何正确更新提示。

## UI-F4-12｜恢复未完成编辑的提示

来源： UX-02.5-A，A。

### 初步方案

用户重新进入旅行项目时，可以得知：

- 存在上次未完成的编辑。
- 哪些修改已成功保存。
- 是否存在尚未完成的校验。
- 可以继续编辑。
- 可以查看当前有效方案。

### 示例信息

```
发现上次未完成的编辑

开罗：3 → 2 天
卢克索：3 → 4 天

2 项修改已保存
整体校验尚未完成

继续上次编辑
查看当前有效方案
```

这是曾讨论的 UI 行为方向，不是最终文案或控件定稿。

### 后期 Owner 补充

恢复应尽可能接近最后成功保存的实际操作位置，而非只提供一份静态总结。

## UI-F4-13｜编辑暂存与失败反馈

来源： UX-02.5-C，A。

### 需要让用户理解

- 修改是否已成功保存。
- 当前是否存在未保存操作。
- 哪些结果可以恢复。
- 完成编辑是否已经成功提交。
- 哪些校验失败。
- 当前是否需要重新尝试。

### 重要边界

不能因为界面显示了新草稿，就隐含承诺该草稿已经成功持久化。

也不能因为提交请求超时，就直接显示提交失败。

## UI-F4-14｜编辑中的假设预览

来源： F5，B。

### 情况

用户正在编辑 B，同时提出假设 C。

### 表达要求

- 让用户看出 C 是假设。
- 显示 C 与 B 的差异。
- 不将 C 直接写成当前草稿。
- 允许返回 B。
- 明确采用到草稿时再更新 B。

### UX-04 待验证

- 是否需要独立预览层。
- 是否复用方案比较区。
- 地图和时间轴如何区分 B 与 C。
- 如何返回原编辑草稿。
- 多个假设之间怎样切换。

不能因为 F5 有假设能力，就另外设计一套与 F4 完全隔离的旅行编辑页面。

# 4.17 F4 的设计演化与被修正方案

这一节保留 F4 从初步交互到后期收敛的变化过程。

其中部分初期方案只能根据历史摘要恢复，不能声称已经读到完整原始讨论。

## 4.17.1 E-F4-01｜从地图可编辑到明确区分浏览与编辑

### 初期设计问题

地图和时间轴支持直接操作。

但用户点击城市、查看体验和修改行程，可能使用同一个界面。

### 发现的风险

- 普通浏览被误当作编辑。
- 点击城市自动改变候选。
- 查看体验被当作正式采用。
- 用户无法判断是否已修改旅行。

### 后期方向

默认浏览，明确进入编辑态或使用明确修改操作。

### 保留的边界

浏览模式中仍然可以记录明确兴趣反馈。

但兴趣不等于正式修改行程。

当前状态：【设计已收敛｜B】

## 4.17.2 E-F4-02｜从逐次修改、逐次分析到编辑会话

### 初期可能采用的方式

用户每修改一个城市，就立即启动完整规划重算并请求确认。

### 发现的问题

一次完整修改可能需要连续调整多个城市。

中间状态可能暂时违反天数分配，但用户下一步就会修正。

逐次全面重算会增加：

- 等待成本。
- 运行成本。
- 交互打断。
- 冗余确认。
- 不必要的结果解释。

### 后期方向

同一编辑会话中连续修改，完成编辑后综合检查。

### 保留的例外

已知重大冲突仍可即时提示。

### 最终规则

即时确定性反馈 + 完成编辑后的聚合校验。

【历史摘要记载 Owner 明确认可｜B】

## 4.17.3 E-F4-03｜从每次编辑后确认，到完成编辑表达确认意图

### 初期问题

用户已经明确修改多项内容，但每一步都需要额外确认。

### 后期发现

同一组编辑被拆成多次确认，会增加操作成本并破坏连续性。

### 收敛方向

点击「完成编辑」表达对整组明确修改的提交意图。

普通情况下不再增加第二次通用确认。

### 仍需保留的要求

- 必要约束校验。
- 当前版本一致性检查。
- 对重要新取舍的用户裁决。
- 对阻断性现实冲突的保护。

### 被替换的方式

`每次修改 → AI 分析 → 用户确认 → 下一次修改`

不再作为默认编辑过程。

【设计已收敛｜B】

## 4.17.4 E-F4-04｜从地图与对话分别修改，到统一草稿

### 初期风险

如果地图和聊天分别执行旅行修改，可能形成不一致的结果。

### 后期规则

编辑会话中的地图、时间轴及明确自然语言指令，共同维护同一份草稿。

### 必须保留的区别

普通问题和假设不进入草稿。

### 最终方向

不同入口共享正确业务对象，而不是各自维护一个版本。

【设计已收敛｜B】

## 4.17.5 E-F4-05｜从地图与信息区平均分配，到地图主工作区

### 早期页面候选

讨论过地图、内容卡片、对话与信息区的不同协作布局。

### Owner 后期要求

地图不应仅占屏幕一半。

地图应成为主要地理工作区。

右侧信息区较窄，负责解释相关旅行价值、取舍和缺口。

顶部设置横向旅行时间轴。

### 最终方向

- 顶部时间轴。
- 左侧／中央大地图。
- 右侧上下文信息区。
- 地图内城市浮层。
- 对话入口可持续使用。

【历史摘要记载 Owner 明确提出｜B】

### 尚未确认

像素级尺寸、断点、具体视觉样式与最终页面组件。

## 4.17.6 E-F4-06｜从静态信息侧栏，到整趟旅行与城市双层摘要

### 初期问题

地图点击城市后需要提供局部信息。

但如果右侧面板只展示城市介绍，就无法解释该城市对整趟旅行的影响。

### 后期变化

右侧信息区具有两种焦点：

整趟旅行： 主要收益、安排、代价、未知和问题。

当前城市： 该城市的体验、停留、影响和缺口。

### 补充行为

- 点击城市进入城市摘要。
- 关闭城市浮层返回整趟旅行摘要。
- 允许单独从城市摘要返回整体信息。

【设计已收敛｜B】

## 4.17.7 E-F4-07｜从假设直接改变草稿，到假设独立预览

### 问题

用户在编辑时提出“如果不去阿斯旺”，并不一定已经决定删除它。

### 后期变化

建立：

- 有效方案 A。
- 编辑草稿 B。
- 基于 B 的假设 C。

### 最终规则

C 不自动覆盖 B。

用户明确要求纳入编辑，才修改 B。

【设计已收敛｜B】

## 4.17.8 E-F4-08｜从一次性页面编辑，到跨会话可恢复工作

### 早期隐含风险

如果编辑会话只保存在当前界面内，退出后可能丢失所有未提交成果。

### 后期新场景

用户连续修改多个城市，三天后重新回来。

### Owner 进一步要求

恢复最后成功保存的编辑进度。

对先前现实核验进行适用性检查，发现冲突应标注。

### 最终方向

编辑草稿持久化 + 工作位置恢复 + 现实条件重新校验。

【Owner 已确认｜A：UX-02.5-A】

## 4.17.9 E-F4-09｜从失败重试到权威状态核实

### 后期发现的问题

提交时断网，用户和前端可能不知道实际结果。

如果直接重复提交，可能产生两次有效修改。

### 补充方向

查询权威状态，确认实际结果。

重复请求不能导致同一业务修改被错误执行两次。

### 当前状态

【后期设计已收敛｜A：UX-02.5-C】

具体幂等机制尚待工程设计和测试。

## 4.18.2 Trip State 需要承接什么？

【工程待核查】

F4 要求正式旅行状态机制至少能够正确表达：

- 当前有效旅行骨架。
- 城市组合、顺序和停留。
- 明确的用户编辑意图。
- 本轮尚未提交的修改内容。
- 当前草稿与有效方案的区别。
- 重要已确认决定。
- 编辑导致的相关变化。
- 操作来源和上下文。
- 有效版本与变更依据。
- 现实条件和校验结果的适用范围。
- 当前需要保护的无关决定。

### 重要限制

不应因为 F4 需要编辑草稿，就直接认定现有 Trip State Schema 缺少草稿对象。

需要工程核对：

1. 哪些语义已由现有对象覆盖。
2. 哪些需要通过操作事件或运行会话承接。
3. 哪些确实需要新增持久化能力。
4. 如何保证不会出现第二份不一致的有效旅行状态。

## 4.18.3 Decision Context 需要承接什么？

【工程待核查】

需要支持：

- 当前工作任务。
- 当前查看对象。
- 当前编辑目标。
- 当前相关旅行版本。
- 当前草稿对应的决策问题。
- 已知用户偏好和约束。
- 已完成的分析。
- 尚未核验的条件。
- 当前假设基于哪份方案。
- 已发现的冲突和未解决问题。
- 跨会话继续工作所需的上下文。

### 一个重要场景

用户正在编辑卢克索，但地图上临时查看阿斯旺。

此时：

- 浏览焦点可能是阿斯旺。
- 编辑目标仍是当前埃及旅行草稿。
- AI 正在回答的问题可能是卢克索停留的影响。

系统不能只用单一“当前城市”覆盖所有任务指向。

## 4.18.4 NAP 需要承接什么？

【工程待核查】

F4 对 NAP 的要求包括：

- 识别浏览、问题、假设和明确修改。
- 判断操作是否有足够授权。
- 判断何时只需更新草稿。
- 判断何时需要即时提示重要冲突。
- 判断何时不应反复调用 AI。
- 判断何时进入整体规划分析。
- 用户完成编辑时识别提交意图。
- 发现新重要取舍时交还用户裁决。
- 不把 AI 回答交付当作用户确认完成。
- 不自动放弃或提交未完成编辑。
- 工具失败后采取合适的降级行动。

### 产品边界

F4 不要求为每一次页面点击都执行完整 NAP 推理。

对于语义已经确定的普通前端交互，工程可以采用合法且可靠的轻量执行路径。

具体哪些操作可以确定性处理，仍须结合正式 Policy、状态校验和评测设计。

## 4.18.5 前端需要承接什么？

【工程待核查】

前端需要具备多层状态表达能力：

浏览状态

- 地图焦点。
- 城市浮层。
- 当前体验或连接。
- 右侧信息区焦点。

编辑状态

- 当前是否在编辑。
- 正在编辑的草稿。
- 已修改的城市或连接。
- 本轮变化记录。
- 操作撤销。
- 完成编辑或放弃入口。

结果状态

- 已保存的草稿。
- 未保存修改。
- 校验进行中。
- 已完成的检查。
- 待核验事项。
- 已知冲突。
- 失败或提交结果未知。

这些信息可以采用不同的视觉层级，但不能在业务语义上混淆。

## 4.18.6 后端与接口需要承接什么？

【工程待核查】

重点检查：

- 是否可以持久化未提交编辑。
- 是否可以读取正确草稿。
- 编辑草稿是否关联正确的有效版本。
- 修改如何进行合法校验。
- 完成编辑如何避免重复执行。
- 提交超时后如何判断权威结果。
- 基础版本变化时如何防止覆盖。
- 编辑成功后如何保存历史。
- 相关事实核验结果如何关联当前版本和条件。

### 特别强调

“有跨会话恢复接口”不等于已经证明它能恢复全部编辑会话。

后期 Owner 已要求：

工程应逐项检查实际能力覆盖情况。

每项标注：

已覆盖／部分覆盖／缺失／待验证。

并提供测试证据。

这属于后续工程检查要求，不是本轮直接宣布的技术结论。

## 4.18.7 规划与校验执行能力需要承接什么？

【工程待核查】

F4 要求能够：

1. 正确计算基础天数与顺序变化。
2. 识别局部修改对其他城市的影响。
3. 分析体验保留或损失。
4. 检查硬约束。
5. 对有条件的现实事实重新核验。
6. 识别冲突所属对象。
7. 判断事实是否过期。
8. 为受影响部分准备修复方案。
9. 在缺少具体日期时支持条件化检查。
10. 不在每次操作后重复执行完整全局分析。
11. 在完成编辑后对整组修改进行必要检查。
12. 在失败后保留已有有效成果。

### 关键技术风险

如何准确确定受影响范围。

例如卢克索增加一天：

系统要知道哪些城市停留、连接、体验和日期条件可能受到影响。

不能完全依赖模型自由生成一段“应该没问题”的判断。

需要可检查的结构、依赖和测试依据。

# 4.21 F4 完整设计结论

F4 的设计成果，不是简单地让用户能在地图上拖动城市。

它形成了一套以统一旅行状态为基础、以地图和时间轴为主要可视化工作空间、以编辑会话为操作单位、以 AI 辅助分析与校验为支撑的持续规划交互机制。

其最重要的成果是：

第一：统一工作空间布局方向。

顶部横向时间轴，左侧／中央以地图为主，右侧为旅行上下文信息区，地图内部承载城市浮层。

第二：浏览与编辑分离。

查看城市、体验和交通信息不自动修改旅行。

第三：同一编辑会话允许连续修改。

用户不需要每调整一项就经历完整 AI 分析和确认。

第四：多入口编辑统一。

地图、时间轴和明确自然语言指令作用于同一正确草稿。

第五：即时反馈与深度分析分层。

直接可计算的变化即时展示，复杂影响在适当节点综合分析。

第六：完成编辑是一组修改的提交意图。

普通情况下不增加重复确认，但必要校验和新重要取舍仍需正确处理。

第七：草稿、假设和有效方案隔离。

任何浏览、假设或未完成操作都不能未经授权覆盖有效旅行。

第八：无日期也可以编辑并确认当前层次的规划。

但不能把具体班次和其他未知事实伪装为已核验。

第九：冲突持续可见，AI 主动准备修复。

不擅自牺牲用户已经确认的重要体验。

第十：用户成果必须能够被保护与恢复。

跨会话继续、事实重核验、提交幂等和版本一致性构成后期明确的工程要求。
