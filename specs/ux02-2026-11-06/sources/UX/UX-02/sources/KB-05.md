## 5.0 来源、证据与完整性声明

### 5.0.1 F5 的完整设计范围

F5 处理的是旅行规划中一种非常普遍的行为：

用户并不总是立即决定改变行程，而是会反复提出假设、比较可能结果、纠正原有判断，再决定是否真正修改。

例如：

> 如果不去阿斯旺呢？

> 如果卢克索多待一天，其他地方会怎样？

> 我刚才说错了，不是减少两天，是减少一天。

> 如果我把预算提高一些，是不是可以保留更多体验？

> 之前那个安排有没有办法恢复？

这些行为看起来都是“改变旅行”，但实际上可能分别代表：

- 假设探索。
- 新的比较要求。
- 对用户输入的纠错。
- 对既有规划条件的修改。
- 正式业务修改意图。
- 历史版本恢复。

F5 的关键设计成果，就是在支持这些灵活行为的同时，避免系统混淆操作语义、错误修改有效方案或重复计算整趟旅行。

# 5.1 F5 的产品定位与核心目标

## 5.1.1 F5 为什么重要？

在真实旅行规划中，用户经常无法一次性确定最喜欢的行程。

他可能已经采用一套方案：

开罗三天 → 卢克索三天 → 阿斯旺两天。

但随后开始思考：

> 如果不去阿斯旺，把时间分给卢克索，是不是更好？

这里包含一个重要区别：

用户提出了一种可能性，而不是已经决定采用这种可能性。

如果系统立即删除阿斯旺，就会破坏旅行状态。

如果系统完全不进行分析，只回答“可以”，又没有帮助用户理解取舍。

因此 F5 必须同时提供：

- 自由提出假设。
- 基于正确方案进行推演。
- 对比假设前后的实际收益和代价。
- 支持连续修改假设条件。
- 允许返回原方案。
- 在用户明确选择时转入正式修改或采用流程。
- 保留原有确认、事实和版本边界。

【设计已收敛｜B、C】

## 5.1.2 F5 与传统“重新生成行程”的区别

传统行程生成可能采用：

```
用户提出新要求
       ↓
重新生成整份行程
       ↓
用新行程替换旧行程
```

但这会产生一系列问题：

- 用户原有决定可能丢失。
- AI 不一定记得哪些体验已经确认。
- 用户无法明确知道新旧差异。
- 复杂修改可能影响无关城市。
- 没有办法轻松回到之前的版本。
- 每提出一个假设都可能制造新的正式状态。

F5 的方向不是无条件重新生成，而是：

以现有旅行状态为基准，对用户提出的可能变化进行受控推演与影响分析。

只有得到明确修改或采用意图后，才进入相应业务更新流程。

## 5.1.3 F5 不应该成为独立的规划系统

这是 F5 后期的重要收敛结论。

【设计已收敛｜B】

不需要为 What-if 单独建设一整套页面或业务模式。

原因在于：

ANTU 已经具备或正在设计：

- F3 方案比较。
- F4 地图及时间轴编辑。
- 旅行状态与版本管理。
- 规划与校验执行能力。
- F6 确认与保存。
- 跨 Flow 工作空间。

F5 应尽量复用这些能力，而不是另外建立一套互相竞争的旅行状态体系。

### 这里要准确区分

不建立独立 What-if 页面或模式：已收敛的产品方向。

假设仍然需要正确的临时业务上下文：必要的行为要求。

两者并不矛盾。

没有独立页面，不等于假设可以直接覆写当前方案。

# 5.2 F5 的用户进入场景

## 5.2.1 场景 A｜已有有效旅行，用户提出假设

### 当前状态

用户已经采用一套埃及旅行骨架。

### 用户输入

> 如果不去阿斯旺呢？

### 用户目标

了解删除阿斯旺可能产生的旅行价值变化。

### 正确行为

系统基于当前有效方案进行推演。

分析：

- 会失去什么体验。
- 可能释放多少时间。
- 其他城市可以获得什么调整空间。
- 相关交通如何改变。
- 整体旅行节奏可能受到什么影响。
- 哪些事实尚未核验。

不直接删除阿斯旺。

## 5.2.2 场景 B｜正在编辑草稿，用户提出假设

### 当前状态

用户已经进入 F4 编辑会话。

例如：

原有效方案 A：

开罗三天、卢克索三天、阿斯旺两天。

编辑草稿 B：

开罗两天、卢克索四天、阿斯旺两天。

### 用户输入

> 如果这次不去阿斯旺会怎样？

### 正确行为

系统应基于当前编辑草稿 B 推演。

而不是未经用户意图判断就回到有效方案 A 重新推演。

生成的假设预览 C 必须与 B 分离。

这是 F5 后期专门明确的机制。

【设计已收敛｜B】

## 5.2.3 场景 C｜用户连续比较多个可能性

用户可能依次询问：

> 如果不去阿斯旺呢？

> 那如果保留阿斯旺，但是卢克索减少一天呢？

> 哪一种可以保留更多历史文化体验？

系统需要持续理解不同假设之间的关系。

### 重要要求

- 不自动将前一个假设应用成有效方案。
- 不默认后一个假设一定以最新有效版本为基准。
- 不混淆不同假设的体验与时间分配。
- 比较结果必须与实际对应的假设一致。
- 如果用户明确指定基准，应遵循该基准。

## 5.2.4 场景 D｜用户纠正之前的修改指令

### 用户输入

> 不是把开罗减少两天，我说的是减少一天。

这不是普通的新假设。

它可能是对上一项编辑意图的明确纠正。

系统需要判断：

- 此前修改是否已经提交。
- 是否仍处于同一编辑草稿。
- 用户纠正的是哪个对象、数值或操作。
- 纠正是否影响其他计算。
- 是否需要重新校验受影响部分。

### 重要边界

不能因为纠正一句话，就清空用户其他已经合法完成的修改。

【设计已收敛｜B、C】

## 5.2.5 场景 E｜用户改变旅行条件

例如：

> 我原来准备八天，现在可能有十天了。

或者：

> 预算不一定非要两万，如果值得可以提高一点。

此类行为可能改变旅行规划的可行空间。

但需要区分：

- 明确改变的旅行条件。
- 仍然不确定的可能性。
- 仅用于假设比较的条件。
- 正式修改后的有效约束。

### 示例

> 如果我有十天呢？

属于假设。

> 旅行时间确定改成十天。

属于明确条件修改。

不能将两者当成相同状态变化。

## 5.2.6 场景 F｜用户发现原有事实不准确

例如某段交通之前只是估计，现在获得了更可靠的实际信息。

系统需要判断：

- 原有核验结果是否仍适用。
- 新事实影响哪段行程。
- 是否需要更新当前比较。
- 哪些决定不受影响。
- 是否存在真实冲突。
- 是否需要用户重新选择。

这属于事实变化导致的相关重算，不是用户主动接受新方案。

## 5.2.7 场景 G｜用户想比较历史版本与当前方案

例如：

> 之前那个两城版本，会不会比现在的三城更舒服？

需要读取正确的历史方案与当前方案。

进行实际差异比较。

查看和比较历史版本，不等于恢复历史版本。

如果用户随后明确希望恢复，则进入 F3 已设计的版本恢复机制。

# 5.3 F5 的核心状态关系：A、B、C

这是本章必须完整保留的机制。

## 5.3.1 三种不同的旅行内容

【设计已收敛｜B】

A｜当前有效方案

用户此前已经正式采用的旅行安排。

B｜当前编辑草稿

用户在 F4 编辑会话中累积的、尚未正式提交的修改。

C｜基于某一明确基准产生的假设预览

用于回答“如果怎样”的可能结果。

### 编辑中的典型关系

```
A｜当前有效方案
│
└── B｜未提交的编辑草稿
    │
    └── C｜基于 B 的假设预览
```

### 重要说明

A/B/C 是此次讨论中为解释三类工作内容使用的代号。

它们不是要求工程新增三个名为 A、B、C 的正式业务状态。

具体 Schema 和生命周期由正式 Trip State、Decision Context、NAP 规格承接。

## 5.3.2 A 与 B 的关系

用户通过 F4 进入编辑会话后：

- A 保持为当前有效方案。
- B 累积用户明确的编辑。
- B 可以显示尚未完成的结构调整。
- B 尚未完成编辑时不直接替换 A。
- 完成编辑后，按权限和校验结果决定是否形成新的有效版本。

## 5.3.3 B 与 C 的关系

用户在编辑过程中提出假设：

> 如果不去阿斯旺呢？

C 根据用户实际指代，以 B 为基准生成。

但 C 不自动成为 B。

例如：

B 仍包含阿斯旺。

C 只是预览删除阿斯旺会怎样。

用户查看 C、向 AI 询问 C，均不应删除 B 中的阿斯旺。

## 5.3.4 A 与 C 的关系

如果用户没有进入编辑会话，则可以直接基于有效方案 A 产生假设 C。

例如：

```
A｜当前有效方案
│
└── C｜假设预览
```

此时不需要为了生成假设，强制用户先进入 F4 的地图编辑模式。

## 5.3.5 C 是否可以直接成为有效方案？

不应因为假设被生成就直接应用。

但用户可以进一步明确表示采用。

例如：

> 那就按刚才这个不去阿斯旺的方案来。

此时需要结合当前工作上下文和明确对象，进入既有的采用或修改流程。

不能再人为设置一套独立的 What-if 采用状态机。

同时不能绕过必要权限、重要取舍和现实约束检查。

# 5.4 F5 的端到端主流程：有效方案上的假设比较

以下案例按照已知设计规则重构，用来说明行为，不代表原始聊天逐字记录或真实埃及交通核验结果。

## 5.4.1 场景背景

当前有效旅行 A：

- 开罗三天。
- 卢克索三天。
- 阿斯旺两天。
- 总计八天。

用户此前对多个历史文化体验和尼罗河体验有兴趣。

也表达过不希望旅途太赶。

用户提出：

> 如果不去阿斯旺，把时间分给卢克索，会怎么样？

## 5.4.2 F5-S01｜识别假设意图

### 用户操作

提出“如果不去阿斯旺”的问题。

### AI 理解

识别：

- 当前行为是条件推演。
- 假设对象是阿斯旺。
- 提议变化是移除阿斯旺。
- 可能涉及重新分配停留。
- 用户尚未表达正式删除意图。

### 系统不应做什么？

- 不立即删除有效方案中的阿斯旺。
- 不将用户兴趣改为“不喜欢阿斯旺”。
- 不将阿斯旺自动排除出所有后续候选。
- 不要求用户先确认删除才能查看影响。

### 状态要求

保持有效方案 A 不变。

建立正确的假设分析上下文。

## 5.4.3 F5-S02｜确定假设基准

系统需要判断：

- 当前是否存在正在编辑的草稿。
- 用户是否明确引用某个历史版本。
- 最近讨论的对象是否是另一个假设。
- 当前假设应当基于哪一份方案。

本案例中没有正在进行的编辑会话，且未指定历史版本，因此可根据当前上下文使用有效方案 A。

### 为什么必须明确基准？

如果系统将假设错误地应用在另一份方案上，即使计算正确，也可能生成与用户问题完全不符的结果。

### 工程要求

假设必须关联正确的源旅行内容或版本。

但具体怎样记录该关系，不在 UX-02 中规定 Schema 字段。

## 5.4.4 F5-S03｜形成新的假设预览

系统根据用户提出的变化，构造假设 C。

例如：

- 不再安排阿斯旺。
- 开罗和卢克索仍然是核心城市。
- 原阿斯旺停留时间需要重新考虑如何分配。
- 原有涉及阿斯旺的连接可能不再适用。
- 其他城市的体验安排可能因此变化。

### 关键限制

用户说“把时间分给卢克索”，可以作为明确的假设方向。

但如果用户只说“如果不去阿斯旺呢”，系统不能直接假定所有释放的时间都必须分给卢克索。

可以生成有条件的比较方向，或在重要差异需要裁决时明确说明。

## 5.4.5 F5-S04｜执行必要的影响分析

系统需要识别：

直接变化

阿斯旺是否从假设骨架中移除。

时间变化

原本分配给阿斯旺的停留如何处理。

体验变化

哪些阿斯旺体验会失去，哪些其他体验可能获得安排空间。

连接变化

原来连接阿斯旺的旅行段落如何受到影响。

旅行节奏

新方案是否减少转场，或是否改变城市间时间分配。

现实条件

哪些事实和费用可以继续使用，哪些需要重新检查。

### 重要边界

系统不得直接根据“城市少一座”断言整趟旅行一定更轻松。

应当分析实际的移动和停留变化。

## 5.4.6 F5-S05｜向用户展示假设差异

系统应当让用户看见：

当前有效方案 A 与假设 C 有什么实际区别。

### 说明性比较

| 维度     | 当前方案 A       | 假设 C             |
| ------ | ------------ | ---------------- |
| 城市组合   | 开罗、卢克索、阿斯旺   | 开罗、卢克索           |
| 阿斯旺体验  | 保留           | 不再安排             |
| 其他城市停留 | 原有分配         | 有重新分配空间          |
| 跨城连接   | 包含阿斯旺相关连接    | 相关连接可能减少或改变      |
| 核心取舍   | 保留更多城市体验类型   | 放弃阿斯旺，可能换取其他停留价值 |
| 现实条件   | 按 A 的依据与核验范围 | 受变化影响的条件需检查      |

不能凭该示例断言 C 在真实条件下必然更轻松或更便宜。

### 用户需要理解

不是简单“少了一座城市”，而是：

为了放弃阿斯旺，旅行失去了什么，又换来了什么。

## 5.4.7 F5-S06｜AI 可以提出有依据的建议

如果系统根据用户已有偏好判断某个假设值得考虑，可以解释：

- 为什么这个假设与当前顾虑有关。
- 它如何减少某些负担。
- 会失去什么体验。
- 哪些问题仍由用户判断。

但不能擅自宣布：

> 这个方案更好，所以已经帮你改了。

AI 提出倾向性建议，不等于用户已经接受。

## 5.4.8 F5-S07｜用户继续提问

用户：

> 如果不去阿斯旺，卢克索是不是可以安排得更深入？

系统应围绕 C 继续分析。

不需要重新从目的地探索开始。

### 可以继续比较

- 增加的停留时间能够支持哪些体验。
- 原本受压缩的内容能否恢复。
- 旅行顺序如何变化。
- 是否还有其他重要限制。

### 不能发生

一次解释之后就把 C 自动提交为有效方案。

## 5.4.9 F5-S08｜用户决定保留原方案

用户：

> 算了，我还是想保留阿斯旺。

### 正确行为

- 有效方案 A 不变。
- 不应用假设 C。
- 不将本次讨论错误写成用户永久排斥两城方案。
- 保留必要的决策上下文。
- 允许以后再次比较相关选择。

无需执行“把阿斯旺加回有效方案”的实际恢复操作。

因为它在假设讨论期间根本没有从 A 中删除。

## 5.4.10 F5-S09｜用户明确采用假设

另一种情况：

> 就按不去阿斯旺的方案来。

### 系统应做什么？

1. 确认指代的是哪份假设。
2. 读取对应的具体安排。
3. 识别它相对于当前有效方案的变化。
4. 执行必要的约束与现实校验。
5. 判断是否涉及用户尚未授权的重要新取舍。
6. 按既有确认机制应用合法修改。
7. 形成新的有效旅行版本并保留必要依据。

### 与“选择即确认”的关系

用户明确采用已经充分说明取舍的方案时，不应再增加无意义的普通二次确认。

但如果存在尚未呈现的新重要牺牲，仍需交还用户判断。

【F3 后期设计已收敛｜B】

# 5.5 F5 的端到端主流程：编辑草稿中的假设

这是 F5 区别于普通方案比较的关键场景。

## 5.5.1 初始状态

当前有效方案 A：

- 开罗三天。
- 卢克索三天。
- 阿斯旺两天。

用户进入 F4 编辑会话。

随后完成两项未提交的修改：

- 开罗：3 → 2 天。
- 卢克索：3 → 4 天。

形成编辑草稿 B：

开罗两天、卢克索四天、阿斯旺两天。

用户还没有点击「完成编辑」。

## 5.5.2 F5-S10｜用户提出假设

用户：

> 如果这次不去阿斯旺，整趟旅行是不是会更舒服？

### 系统需要理解

用户正在讨论的是当前编辑成果的另一种可能性。

因此，应当依据当前正确的工作上下文决定假设基准。

本例基于 B。

### 不应发生

- 不使用未包含编辑变化的旧方案 A 直接代替 B。
- 不删除 B 中的阿斯旺。
- 不自动完成本轮编辑。

## 5.5.3 F5-S11｜生成假设 C

C 基于 B：

- 已包含开罗两天。
- 已包含卢克索四天。
- 假设取消阿斯旺。
- 对整趟旅行重新分析相关收益与代价。

### 核心关系

```
有效方案 A
开罗 3 / 卢克索 3 / 阿斯旺 2
          │
          ▼
编辑草稿 B
开罗 2 / 卢克索 4 / 阿斯旺 2
          │
          ▼
假设预览 C
开罗 2 / 卢克索 4 / 不去阿斯旺
剩余时间如何安排仍需分析
```

这里没有把原阿斯旺两天自动分配给其他城市。

因为那不是用户明确指定的全部操作。

## 5.5.4 F5-S12｜展示 C 相对于 B 的差异

系统应比较：

- B 中已完成的修改。
- 假设新增的删除阿斯旺变化。
- 相关时间重新分配空间。
- 可能改变的体验安排。
- 新的交通与现实条件。
- 是否会影响已确认的其他决定。

### 用户应当清楚

当前看到的是假设预览 C，不是正在编辑的草稿 B 已被修改。

这项区别必须在交互行为上成立。

具体视觉呈现由 UX-04 验证。

## 5.5.5 F5-S13｜用户放弃假设

用户：

> 还是保留阿斯旺吧。

系统应返回 B。

### 正确状态

A 保持不变。

B 仍然是：

开罗两天、卢克索四天、阿斯旺两天。

C 不再作为当前查看焦点。

### 错误行为

把阿斯旺从 B 中删除后，又试图凭语言模型重新生成 B。

正确设计是始终没有用 C 覆盖 B。

## 5.5.6 F5-S14｜用户明确把假设纳入草稿

用户：

> 不去阿斯旺这个调整也加到当前编辑里。

### 正确处理

此时用户表达了明确的草稿修改意图。

系统应：

1. 定位当前编辑草稿 B。
2. 确认用户要应用的假设变化。
3. 将该变化纳入同一编辑会话。
4. 更新地图和时间轴中的草稿。
5. 更新本轮修改记录。
6. 立即呈现可以确定的结构变化。
7. 将复杂影响保留到适当分析或完成编辑阶段。
8. 不自动提交有效方案 A。

### 关键边界

用户把 C 纳入 B，不是用户已经完成整个编辑会话。

## 5.5.7 F5-S15｜用户继续编辑

用户随后可能说：

> 那把释放出来的时间多安排给卢克索。

系统应继续修改当前草稿。

如果原假设只有“删除阿斯旺”，此时新增的停留分配也需要正确记录。

### 必须防止

- 前一项假设操作没有进入草稿，导致后续指令基准错误。
- 同一修改执行两次。
- 其他已经完成的草稿修改丢失。
- 将草稿变化误写成有效方案变化。

## 5.5.8 F5-S16｜完成编辑

用户点击：

完成编辑。

这时进入 F4/F6 的整组修改校验与合法提交流程。

如果发现阻断冲突：

- 原有效方案保留。
- 编辑草稿保留。
- 相关问题就地说明。
- 必要时提供修复建议。

如果满足相应权限和校验要求：

- 应用获授权的整组修改。
- 保存新的有效版本。
- 保留相关历史与依据。

# 5.6 多轮假设与连续比较机制

## 5.6.1 用户可能连续提出不同假设

例如用户已经有八天三城方案。

第一轮：

> 如果不去阿斯旺呢？

第二轮：

> 如果保留阿斯旺，但卢克索只住两天呢？

第三轮：

> 哪个方案能保留更多历史文化体验？

系统不能因为第二轮出现，就直接把第一轮的假设视为正式决定。

## 5.6.2 必须正确区分假设之间的关系

至少存在以下几种情况。

### 情况 A｜后一个假设替代前一个假设

用户：

> 不对，刚才那个假设改成卢克索只住两天。

应当根据明确指代修改对应的假设分析。

### 情况 B｜后一个假设与前一个并列比较

用户：

> 另外再看看保留阿斯旺的情况。

此时可能需要保留两种假设作为比较对象。

### 情况 C｜后一个假设基于前一个假设继续修改

用户：

> 在刚才不去阿斯旺的基础上，把卢克索增加一天。

应基于对应假设继续推演。

### 情况 D｜用户回到最初有效方案

用户：

> 不考虑刚才那些假设了，还是看原来的安排。

应返回原来的有效方案或明确指定的编辑草稿。

### 工程意义

系统需要正确理解“刚才那个”“另一个”“在这个基础上”等上下文指代。

不能仅通过最近一条自然语言消息判断全部方案关系。

【设计原则来源 B；以上四类为对已知多轮机制的场景化展开，未取得各类场景的原始逐轮裁决】

## 5.6.3 多个假设是否都应保存为历史版本？

这是一个必须谨慎处理的边界。

F3 后期已经形成：

重要、用户可见的历史方案应当可以回顾。

但也明确：

不应把 AI 内部的所有临时生成结果都强制纳入用户可见版本历史。

因此，F5 不应自行宣布：

> 每提出一个假设，就必须生成新的正式旅行版本。

### 已经能够确定的要求

- 当前假设必须与有效方案或草稿区分。
- 用户需要能够在当前比较任务中理解不同假设。
- 对用户有实质决策价值的重要历史方案，应具备相应回顾能力。
- 被用户明确采用的方案必须按正式版本规则处理。
- 普通内部推演不要求全部进入用户可见历史。

### 尚待核查

假设何时进入用户可回看历史、何时仅作为临时比较结果保留，以及跨会话持久化的具体粒度。

【工程待核查／UX 细化待验证】

不能擅自制造“每个 What-if 自动永久保存”的新正式规则。

# 5.7 纠错：F5 不只是生成另一种方案

## 5.7.1 为什么纠错需要与假设区分？

用户说：

> 如果开罗少一天呢？

与：

> 我刚才说错了，不是少两天，是少一天。

虽然都涉及天数变化，但含义不同。

前者是条件推演。

后者可能在纠正此前已经表达的操作。

如果系统一律按新方案生成处理，就可能产生重复修改或错误覆盖。

## 5.7.2 纠错需要识别什么？

【设计已收敛｜B、C】

至少需要识别：

- 纠错针对哪个对象。
- 用户纠正的是哪个原有表达。
- 原操作是否已经执行。
- 原操作是否已经成为当前草稿。
- 原操作是否已经正式确认。
- 纠正会影响哪些后续结果。
- 哪些其他内容不应该改变。

## 5.7.3 场景 A｜尚未执行的指令纠错

用户：

> 卢克索减少两天。

系统准备执行时，用户立即纠正：

> 不是减少两天，是减少一天。

### 正确行为

以用户明确的纠正为依据，避免继续执行已经被撤销的错误意图。

### 不应发生

先执行减少两天，再把“减少一天”解释为额外减少一天。

否则会出现累计减少三天的错误。

### 技术要求

需要能够识别修正操作与新增操作之间的区别。

## 5.7.4 场景 B｜编辑草稿中的纠错

用户在编辑草稿 B 中已将开罗三天改成一天。

随后说：

> 我改错了，开罗应该是两天。

### 正确行为

- 定位 B 中开罗的当前停留。
- 将目标修改为两天。
- 保留本轮其他城市的编辑。
- 更新草稿显示。
- 更新或关联相关修改依据。
- 对受到影响的分析进行必要更新。
- 不直接改变有效方案 A。

### 不应发生

简单再次把当前天数减少或增加某个未正确解释的增量。

应结合用户的实际表达判断目标值与增量语义。

## 5.7.5 场景 C｜已确认方案中的纠错

用户此前已经正式采用一套行程。

之后说：

> 我之前确定卢克索四天是考虑错了，我想改回三天。

### 正确行为

这已不只是草稿内的修正。

因为当前有效版本可能已经包含卢克索四天。

系统需要：

1. 识别新的明确修改目标。
2. 对照当前有效旅行。
3. 检查相关影响。
4. 按既有权限和确认机制处理。
5. 成功后生成新的有效版本。
6. 保留先前决定及变更依据。

### 不应发生

为了“纠错”，直接擦除之前的正式采用记录，让历史看起来从未发生过。

这与 F3 的版本演化和恢复原则一致。

## 5.7.6 场景 D｜偏好理解纠错

用户：

> 不是说我不喜欢阿斯旺，我只是担心时间不够。

这里主要纠正的是系统理解。

### 正确行为

- 保留阿斯旺的真实兴趣。
- 修正错误排斥判断。
- 将时间不足作为顾虑或约束相关信息。
- 不自动增加阿斯旺停留。
- 重新判断当前需要比较什么。

### 为什么重要？

纠正偏好语义与编辑旅行结构，不是同一件事。

即使用户纠正了“不喜欢阿斯旺”的误解，也不表示他已经决定将阿斯旺加入旅行。

## 5.7.7 场景 E｜已核验事实发生变化

例如：

系统之前基于某日期的交通数据判断一段连接可行。

后来用户改变日期，或者取得更新的信息。

### 正确行为

需要判断旧证据是否仍适用。

必要时重新检查受影响的安排。

如果出现已确认的现实冲突，应在相关位置标注。

如果只是暂时无法重新核验，应标记待核验。

### 不应发生

把工具查询失败当作用户旅行决定错误。

也不能因事实变化就清空所有用户偏好。

# 5.8 重算：为什么强调有限范围，而不是每次重做整趟旅行？

## 5.8.1 最初的产品问题

旅行规划具有明显的关联关系。

调整一座城市，可能影响整趟旅行。

因此系统需要重算。

但如果任何小变化都重新生成全程安排，又可能引起：

- 无关城市被修改。
- 用户确认的体验被删除。
- 计算时间增加。
- 模型输出前后不一致。
- 用户难以追踪到底改了什么。
- 无法有效保留历史决定。

### PRD-006 的基线

在 MVP 可覆盖范围内：

优先识别受影响关系，进行有限范围重算；必要时可重算整份骨架。

不是永远只能局部，也不是每次必须全局。

【正式资料旁证｜C】

## 5.8.2 变更影响分析的基本逻辑

例如用户把卢克索从三天增加为四天。

需要判断：

直接受影响：

卢克索停留。

可能关联受影响：

- 整趟旅行总天数。
- 其他城市的可分配时间。
- 卢克索相关体验安排。
- 相邻交通连接。
- 受日期影响的活动或班次。

通常不应无故改变：

- 与本次变化无关的旅行兴趣。
- 无关城市已经确认的体验。
- 用户此前明确的硬约束。
- 不受影响且仍然有效的事实。

### 核心原则

重算是为了识别和处理必要变化，不是为了重新发明用户的整个旅行。

【设计已收敛｜B、C】

## 5.8.3 哪些变化适合局部重算？

典型例子：

- 某城市增加或减少停留。
- 某个体验顺序调整。
- 某段交通条件变化。
- 某项费用数据更新。
- 某座城市的局部规划恢复。

这些变化可以先识别直接影响及依赖关系。

如果依赖关系证明影响范围较小，可以保留无关部分。

## 5.8.4 哪些情况可能需要扩大分析范围？

例如：

- 总旅行天数大幅缩短。
- 城市组合发生变化。
- 已确认的入离境条件改变。
- 某个关键交通连接不再可行。
- 多座城市的停留相互竞争。
- 历史恢复导致多重依赖冲突。

系统可能需要重新评估较大范围甚至整份旅行骨架。

### 重要限制

扩大计算范围，不等于可以自动扩大业务修改授权。

系统可以分析整趟旅行，但仍须保护用户未授权改变的有效决定。

## 5.8.5 重算结果需要向用户解释什么？

至少包括：

- 用户提出的原始改变。
- 哪些内容确实发生变化。
- 哪些其他安排受到影响。
- 哪些重要体验被保留。
- 哪些体验可能需要牺牲。
- 哪些事实需要重新核验。
- 是否出现已知冲突。
- 哪些地方需要用户判断。

### 不应仅回答

> 已重新计算，新的方案更合理。

因为用户无法验证“更合理”具体意味着什么。

## 5.8.6 编辑中的计算节奏

F4 后期已经明确：

简单确定性反馈即时进行，复杂整体分析在合适节点执行。

因此 F5 需要区分两类重算。

### 类型 A｜用户明确请求假设分析

例如：

> 如果不去阿斯旺，会影响什么？

系统应当提供这次假设所需要的分析。

不必等待用户点击完成编辑。

### 类型 B｜用户连续编辑时的系统处理

例如：

用户先修改卢克索，再修改开罗。

系统即时处理确定性变化。

不应在每次修改后自动执行全套 AI 分析。

完成编辑时，对整组草稿进行必要的综合核验。

### 两者的区别

用户主动要求分析时，应回应用户当前需求。

用户只是连续操作时，不应无意义地打断编辑。

# 5.9 已确认体验与重要决定的保护

## 5.9.1 假设可以影响重要决定，但不能静默应用

例如用户此前已经确认：

卢克索的核心历史文化体验需要保留。

现在提出：

> 如果卢克索只待一天呢？

系统可以推演这种安排。

但如果实际安排无法保留原有核心体验，应明确说明。

### 假设分析阶段

可以展示：

- 哪些体验可能无法继续安排。
- 是否存在不同的修复方式。
- 减少停留的收益与代价。

### 正式修改阶段

如果用户希望真正采用该变化，系统需要检查用户是否已经理解相关重要牺牲。

不能仅为了满足“一天”的数字要求，就自行删除核心体验且不说明。

【设计已收敛｜B】

## 5.9.2 用户可以主动改变原有价值取舍

保护已确认体验，不等于永远不允许修改。

用户可能明确说：

> 我知道这样就看不了某项遗迹，但我愿意把时间留给阿斯旺。

在符合实际约束的情况下，系统应尊重用户新的价值判断。

### 产品边界

AI 的职责是：

- 提供清楚的影响分析。
- 发现未告知的重要牺牲。
- 必要时准备可行修复方案。
- 保留版本与决定依据。

不是替用户永久锁定某项偏好。

# 5.10 日期、预算和现实条件变化引发的重算

## 5.10.1 日期未知时可以进行什么假设？

用户可能问：

> 如果我冬天去埃及，这套安排会有什么不同？

如果缺少具体日期，系统可以：

- 解释有可靠依据的一般性季节差异。
- 判断是否存在重要日期依赖。
- 指出哪些安排需要具体日期核验。
- 在当前可支持范围内进行结构性比较。

但不能凭空给出指定日期的真实交通班次和预订结果。

## 5.10.2 用户后来提供具体日期

【Owner 已确认｜A：F6 后期】

需要重新核验日期相关的事实。

例如：

- 相关活动是否适用该日期。
- 已有交通信息是否仍然适用。
- 时间衔接是否存在现实问题。

### 核心规则

重新核验受影响部分。

保留没有受到新条件影响的旅行决定。

### 如果出现冲突

AI 可以准备尽量保留原有规划价值的修复建议。

但涉及放弃重要体验时，仍需要用户判断。

## 5.10.3 用户修改预算

用户：

> 如果我把预算从两万提高到三万，会有什么变化？

这属于假设性预算变化。

系统不应立即把有效预算上限改成三万。

### 正确行为

- 识别假设。
- 判断原有两万是预算意向还是明确硬上限。
- 在当前费用来源和覆盖范围内分析变化。
- 区分新增可考虑选项与实际已核验费用。
- 保留当前有效预算判断，直到用户明确修改。

### 后续正式修改

如果用户明确说：

> 我决定把预算上限改为三万。

系统应按正式预算与约束变更机制处理。

### 重要边界

用户可以在合法范围内改变自己的预算决定。

但 AI 不能自行放宽用户明确的硬上限。

【正式资料旁证｜C：PRD-009】

## 5.10.4 外部事实变化不自动产生用户决定

假设某段交通条件改变。

系统可以：

- 标记旧结果失效。
- 重新核验。
- 发现相关冲突。
- 准备替代安排。

但不能仅因外部数据变化，就擅自把用户选择的城市删除。

事实改变与用户价值改变是两回事。

这项区别是 F5、F6 共同依赖的重要规则。

# 5.11 F5 与历史版本、城市级恢复的关系

## 5.11.1 假设与历史版本不能混为一谈

F3 后期明确提出，用户应该能够回看重要历史版本。

但 F5 中的假设不一定都是正式历史版本。

例如：

用户只是问：

> 如果不去阿斯旺，会怎么样？

系统提供了一次条件化分析。

这并不代表用户采用过这个方案。

因此需要区分：

当前有效版本： 当前正式采用的旅行安排。

历史有效版本： 过去曾经采用过的旅行安排。

重要历史候选： 曾对用户产生实际比较价值、值得回看的方案。

假设预览： 为当前问题生成的可能性分析，尚未采用。

### 已知产品要求

- 重要的用户可见历史方案应具备可回顾性。
- 普通内部推演不应全部堆进用户版本历史。
- 查看历史不自动恢复。
- 假设不自动成为已确认决定。

【设计已收敛｜B】

## 5.11.2 用户以历史版本作为假设基准

### 场景

用户当前有效方案是 V4。

但想问：

> 如果在最初的两城方案基础上，再给卢克索增加一天，会怎么样？

### 需要的系统行为

1. 识别用户明确指向的历史版本。
2. 读取该版本中的旅行安排。
3. 理解用户提出的是假设而非直接恢复。
4. 基于正确历史内容形成预览。
5. 检查当前相关条件是否发生变化。
6. 展示假设结果及其与所选比较对象的差异。
7. 不覆盖当前有效版本 V4。

### 不能发生

先自动恢复旧版，然后再增加卢克索一天。

因为用户原本只是想了解一种可能性。

### 证据状态

【基于已收敛的假设隔离、历史查看与版本恢复规则进行的场景化展开｜B】

目前未取得该具体场景的原始逐轮裁决，不应将其标记为已独立批准的完整新流程。

## 5.11.3 用户想恢复历史方案

用户：

> 我还是喜欢之前的两城版本，就恢复那个吧。

这已经超出普通假设分析。

应转入 F3 的历史恢复机制。

需要：

- 确定恢复来源。
- 对照当前有效方案。
- 检查相关约束与事实。
- 解释重要差异。
- 按权限执行恢复。
- 成功后建立新的有效版本。
- 保留旧版本及后续历史。

不能简单将版本指针倒回，使后续历史消失。

## 5.11.4 用户只想恢复某座城市

用户：

> 我只想恢复卢克索以前的安排，其他城市保持现在这样。

这属于 F3 后期的城市级恢复。

但其实现依赖 F5 的影响分析能力。

### 系统需要完成

- 确定历史城市安排。
- 确定当前旅行中的对应对象。
- 识别局部差异。
- 分析相关时间、交通和体验影响。
- 保留无关决定。
- 识别重大冲突。
- 在必要时准备修复建议。
- 不自动牺牲其他城市已确认的体验。

### 重要边界

局部恢复的操作范围是城市，但分析范围可能需要延伸到整趟旅行。

不能因为用户只恢复卢克索，就只检查卢克索内部。

同样，不能因为分析了整趟旅行，就擅自修改整趟旅行。

# 5.12 F5 的 AI 主动性、停止与授权边界

## 5.12.1 用户提出假设时，AI 应主动完成什么？

在必要条件与工具能力支持下，可以主动：

1. 确定假设基准。
2. 识别变化对象。
3. 分析结构影响。
4. 检查相关硬约束。
5. 查询会改变当前判断的重要事实。
6. 比较获得与放弃。
7. 识别关联风险。
8. 解释值得用户判断的取舍。

用户不需要逐条指示 AI：

> 先查交通，再算停留，再比较景点。

这属于 ANTU 希望节省的规划劳动。

【设计已收敛｜B、C】

## 5.12.2 什么时候不应继续深入分析？

如果当前假设问题已经可以在合理依据下回答，而继续计算只会增加成本或延迟，系统应允许停止。

例如：

用户只问：

> 去掉阿斯旺会少一座城市吗？

系统不需要为了回答这个简单问题，立即执行完整交通核验与所有体验重排。

### 工程依据

项目机制审视资料提出过：

根据继续行动的增量价值、用户成本、系统成本、可靠性和权限判断是否值得继续准备。

但其完整运行策略和验证状况仍应以正式 NAP 为准。

【正式资料旁证｜C】

## 5.12.3 用户明确请求与系统额外建议的优先级

如果用户只是要求比较两种安排，AI 不应未经请求把旅行正式修改。

如果用户明确要求采用其中一种安排，系统也不应无意义地要求继续探索。

### 统一原则

AI 负责准备、解释与建议；用户拥有重要价值取舍和正式业务修改的控制权。

## 5.12.4 用户拒绝某项假设

例如：

> 两城方案还是算了。

系统不应因此推断：

- 用户永远不考虑两城。
- 用户永久喜欢阿斯旺。
- 用户拒绝两城方案中的所有体验。
- 相关城市应从所有历史版本中删除。

拒绝的范围应以当前明确对象和上下文为准。

# 5.13 UX-02.5 对 F5 的补充机制

## 5.13.1 UX-02.5-A｜跨会话恢复

【Owner 已确认｜A】

用户可能在假设比较中暂停。

例如：

用户编辑旅行草稿 B，同时提出假设 C。

尚未决定是否把 C 纳入 B，便退出。

### 已确认的恢复目标

用户重新进入后，应尽可能恢复：

- 当前有效旅行 A。
- 尚未提交的编辑草稿 B。
- 上次成功保存的操作位置。
- 与未完成任务有关的决策上下文。
- 已表达的用户条件和顾虑。
- 相关事实核验的当前适用性。

### 对假设 C 的准确要求

如果 C 是上次尚未完成工作的重要部分，系统需要具备继续相应讨论的上下文能力。

但目前没有足够证据表明：

所有临时假设预览都必须永久持久化为独立旅行版本。

因此，工程侧应重点核查：

- 能否识别上次未完成的假设任务。
- 能否恢复或必要时重新构造对应预览。
- 能否确保重新构造的结果基于正确版本。
- 是否会意外覆盖 B 或 A。
- 相关事实是否需要重新核验。

具体持久化与重建策略，尚待正式技术规格审查。

## 5.13.2 UX-02.5-B｜跨流程切换与状态一致性

【Owner 已确认｜A：用户明确认可该阶段的补充规则】

### 原讨论形成的统一原则

工作上下文与业务修改分离。

对 F5 具有直接影响。

用户可以：

1. 在 F4 编辑草稿。
2. 进入 F5 假设比较。
3. 返回 F1 了解体验。
4. 打开 F3 历史方案。
5. 返回原编辑草稿。
6. 再次讨论此前假设。

### 不同操作的效果

- 切换浏览对象，不修改草稿。
- 查看假设，不自动采用。
- 查看历史版本，不自动恢复。
- 右滑体验表示兴趣，不自动加入行程。
- 只有明确修改指令才进入相应业务编辑。
- 页面切换不自动结束编辑会话。
- 恢复讨论必须关联正确的旅行和版本。

### 重要技术风险

系统如果只用“最近查看的方案”作为所有操作的默认目标，很容易发生错误。

例如用户查看历史版本后说：

> 把卢克索多加一天。

系统需要依据当前任务和具体指代，判断这是：

- 修改当前有效方案；
- 修改当前草稿；
- 还是对历史版本提出假设。

如果存在会导致重要状态错误的歧义，应当澄清，而不是猜测后直接写入。

## 5.13.3 UX-02.5-C｜异常失败与成果保护

【后期设计已收敛｜A；C 各项细则的独立 Owner 批准依据待补证】

### 异常一：假设计算失败

用户问：

> 如果不去阿斯旺呢？

系统分析到一半失败。

### 正确行为

- 不修改当前有效方案。
- 不删除编辑草稿。
- 不伪造完整比较结果。
- 对未完成部分标记失败或待处理。
- 在适当条件下允许重新分析。

### 异常二：部分事实查询失败

例如交通来源无法返回可靠数据。

系统可保留已经正确完成、且仍然适用的结构分析。

但未核验的交通部分不能被标记为已经通过。

### 异常三：纠错过程中出现网络故障

如果用户明确纠正了草稿中的天数，但保存失败：

系统不能直接假装修正已成功持久化。

需要保留可恢复成果，并让用户理解实际保存状态。

### 异常四：用户将假设加入草稿后退出

下次回来应恢复已成功保存的编辑进度。

不能因为曾经显示过假设预览，就将该预览直接当作正式有效行程。

### 异常五：用户采用假设时提交结果未知

用户执行正式采用后，请求超时。

系统不能立即认定提交失败，也不能直接再次写入。

需要核实权威状态，并避免重复执行相同业务修改。

### 异常六：假设基准已经过期

用户之前基于有效版本 V3 形成了假设。

后来当前有效版本已更新至 V4。

用户再尝试采用旧假设时：

- 不应直接覆盖 V4。
- 需要识别版本差异。
- 保留原假设意图。
- 判断是否需要重新计算或协调冲突。
- 对新的重要取舍交还用户决定。

### 重要说明

上述版本并发与幂等保护，是后期 UX-02.5 对提交安全性的要求。

并不意味着 F5 必须独立建设第二套提交服务。

应复用正式的旅行修改、版本和授权机制。

# 5.14 F5 的全部可恢复初步 UI 设计

F5 后期形成的一个重要方向是：

不另建独立 What-if 页面，而是在现有地图、时间轴、对话、方案比较和历史版本能力中承接假设与重算。

因此，本节不应凭空发明新的完整页面架构。

用户在对话中输入：

## UI-F5-02｜假设预览与当前方案对比

来源：F3 比较能力、F5 假设讨论｜B

### 设计目的

用户提出假设后，需要看到具体变化，而不是只收到一句“这样会更轻松”。

### 比较内容

- 原方案。
- 假设方案。
- 城市顺序与停留差异。
- 体验获得与放弃。
- 时间和转场变化。
- 预算差异（有可靠数据时）。
- 相关现实冲突。
- 待核验条件。

### 低保真信息结构

```
────────────────         ────────────────
开罗 3 天                  开罗 3 天
卢克索 3 天                卢克索待重新分配
阿斯旺 2 天                不安排阿斯旺

主要变化
────────────────────────────────────────

```

### 重要边界

不能因为预览 C 被展示，就让当前有效方案 A 自动变化。

## UI-F5-03｜编辑草稿 B 与假设预览 C 的区分

来源：F4/F5 后期｜B

### 场景

用户已经编辑了 B，再提出假设 C。

### 产品要求

用户必须能够理解：

- B 是当前未提交的编辑成果。
- C 是在 B 基础上进一步提出的可能方案。
- 查看 C 不会覆盖 B。
- 可以返回 B 继续编辑。
- 明确将 C 的改变加入 B 后，B 才更新。

### 初步文字示意

```
当前工作：旅行编辑

草稿 B

如果不去阿斯旺

假设变化：
移除阿斯旺，其他影响待分析

返回当前编辑
将该假设加入当前编辑
```

### 设计状态

工作语义已收敛。

具体视觉结构待 UX-04。

不能直接将上述两个操作标签视为已批准的最终按钮文案。

## UI-F5-04｜地图上的假设预览

来源：F5 复用 F4 地图工作空间｜B

### 需要表达

如果假设改变城市组合或连接，地图应有能力展示对应的预览。

例如：

- 某座城市在假设中被移除。
- 某条连接在假设中改变。
- 不同城市组合产生不同空间结构。

### 重要区别

地图上的假设路线不能被误认为：

- 当前已经正式采用的路线。
- 已核验可执行的交通连接。
- 用户正在编辑草稿中的实际修改。

### UX-04 待验证

- 假设路线与有效路线如何视觉区分。
- 是否同时展示两套路线。
- 是否在地图上切换预览。
- 多个假设怎样选择。
- 如何避免线路重叠导致混乱。

当前没有足够原始资料证明具体采用过虚线、颜色或特定图标，因此不应自行指定。

## UI-F5-05｜顶部时间轴上的假设预览

来源：F4 顶部时间轴设计与 F5 复用要求｜B

### 功能

用户提出天数或顺序假设后，时间轴可以显示对应的暂定分配。

### 示例

```
当前编辑草稿 B
开罗 2 天 ─ 卢克索 4 天 ─ 阿斯旺 2 天

假设预览 C
开罗 2 天 ─ 卢克索 4 天 ─ 剩余时间待分配
```

### 重要边界

如果用户没有明确指定释放时间的分配方法，时间轴不能擅自把剩余时间填给某座城市并当成唯一结果。

### UX-04 待验证

- 原时间轴与假设时间轴的对照方式。
- 预览切换操作。
- 未分配时间的表达。
- 假设中的已知冲突。
- 编辑草稿与假设的返回路径。

## UI-F5-06｜右侧整体影响摘要

来源：F4 工作空间与 F5 比较机制｜B

F5 的影响分析应能够融入右侧上下文信息区。

### 主要内容

当前假设改变了什么。

保留什么。

获得什么。

失去什么。

影响哪些其他城市。

有哪些未知。

需要用户判断什么。

### 为什么需要？

地图和时间轴更适合展示空间、顺序与天数变化。

右侧信息区可以解释这些变化对整趟旅行意味着什么。

### 设计状态

【交互协作方向已收敛｜B】

但“假设一定显示在右侧”尚无完整独立裁决证据，应交由 UX-04 结合整体工作空间验证。

## UI-F5-07｜多假设比较

来源：F3 比较能力与 F5 连续假设要求｜B

### 用户需求

用户提出多个可能方案后，希望直接比较其差异。

### 可以复用的组件

- F3 方案比较视图。
- 地图。
- 时间轴。
- 整体影响摘要。
- 相关事实及未知信息。

### 需要保护的交互

- 不同假设有正确基准。
- 用户知道正在比较哪几份内容。
- 切换假设不改有效方案。
- 不为无意义的细微内部变化生成大量历史卡片。

### UX-04 待验证

- 并排还是切换展示。
- 是否允许暂时固定某个比较对象。
- 多个假设如何命名和识别。
- 复杂比较时如何控制信息密度。

## UI-F5-08｜纠错反馈

来源：PRD-002、006 与 F5 纠错机制｜B、C

### 场景

用户说：

> 不是减少两天，是减少一天。

### 用户应该看到

当前具体修改被正确纠正。

例如：

- 开罗停留从错误草稿值调整到用户明确要求的目标值。
- 其他未受影响的草稿内容保持。
- 本轮修改记录反映正确结果。
- 如相关分析失效，说明需要重新检查。

### 不应发生

系统把纠错当作新的追加操作，使停留进一步错误减少。

### UX-04 待验证

- 纠错成功如何反馈。
- 原操作是否在修改记录中显示为已撤销或已修正。
- 错误结果已经影响多个对象时怎样提示。
- 是否需要在历史中查看原修改依据。

## UI-F5-09｜局部重算影响提示

来源：F3 影响分析、F4 即时反馈及 PRD-006｜B、C

### 产品要求

当用户只改变一个对象时，系统应优先展示相关变化。

例如：

用户将卢克索从三天增加到四天。

可以就地显示：

- 停留增加一天。
- 总天数是否变化。
- 哪些城市或连接可能受影响。
- 哪些体验安排需要进一步分析。

### 注意

“可能受影响”与“已经确认发生冲突”不能显示成相同结论。

### UX-04 待验证

- 受影响对象的视觉提示。
- 简单变化和复杂重算结果的层级。
- 哪些信息默认展开。
- 多个关联变化如何汇总。

## UI-F5-10｜假设采用入口

来源：F5 采用机制及 F3“选择即确认”｜B

### 场景

用户看完假设之后，决定采用相应改变。

### 两种不同上下文

当前有编辑会话：

将假设中的明确改变纳入当前编辑草稿。

当前没有编辑会话：

进入既有的正式方案采用或修改流程。

### 为什么不能统一成一个无条件“确认”按钮？

因为两种操作的后果不同。

一种只是继续编辑。

另一种可能正式改变有效旅行。

### UX-04 待验证

- 如何明确区分“纳入编辑”和“正式采用”。
- 用户选择对象不明确时的反馈。
- 是否存在需要先展示的重要新取舍。
- 如何避免多余确认。

## UI-F5-11｜假设中的事实和冲突标注

来源：F5/F6、UX-02.5｜A、B

### 需要区分

- 假设导致的结构问题。
- 假设涉及的已知现实冲突。
- 当前没有日期而无法核验的事项。
- 工具失败。
- 旧事实已经不适用。

### 适用位置

- 地图相关城市或连接。
- 时间轴相关段落。
- 右侧影响摘要。
- 假设比较内容。

### 关键要求

假设中的冲突不能被误报为当前有效旅行的冲突。

例如当前 A 没有问题，但假设 C 存在天数冲突。

应明确冲突属于 C。

## UI-F5-12｜历史方案与假设回看

来源：F3 版本历史与 F5 比较｜B

### 功能要求

用户应能够回看重要历史方案，并在适用范围内继续比较。

### 必须避免

- 查看历史即恢复。
- 所有临时假设都自动进入正式历史。
- 旧版本的事实无条件被视为当前有效。
- 从历史返回时错误覆盖编辑草稿。

### 未定事项

- 重要假设的保存门槛。
- 何时显示为临时比较记录。
- 是否有独立的假设历史入口。
- 跨会话如何继续未完成的假设讨论。

这些属于后续 UX-04 与工程核查内容，不得在本轮自行定稿。

# 5.15 F5 的关键设计演化

## 5.15.1 E-F5-01｜从“提出变化就重新生成”到独立假设预览

### 初始问题

用户提出“如果怎样”，系统容易将其直接当作修改指令。

### 风险

- 覆盖有效方案。
- 破坏已有草稿。
- 导致用户反复恢复原安排。
- 混淆探索与确认。

### 后期方向

识别假设意图，生成独立预览。

### 当前结果

假设不自动修改有效方案或编辑草稿。

【设计已收敛｜B】

## 5.15.2 E-F5-02｜从独立 What-if 功能到复用现有工作空间

### 曾经面对的设计选择

是否为假设建立独立的页面或专门模式？

### 后期判断

独立体系容易增加：

- 页面复杂度。
- 用户切换成本。
- 状态维护难度。
- 与编辑草稿和方案比较重复的机制。

### 最终方向

不建立新的 What-if 页面或模式。

复用：

- 地图。
- 时间轴。
- 对话。
- F3 方案比较。
- F4 编辑会话。
- 现有确认与版本能力。

【设计已收敛｜B】

### 不应误解

复用交互入口不意味着省略假设与有效状态的隔离。

## 5.15.3 E-F5-03｜从单一当前方案到 A/B/C 三层关系

### 新问题

用户在编辑草稿 B 时提出假设。

此时假设应基于哪份方案？

### 风险

如果系统只认为存在一个“当前方案”，可能把假设建立在 A 上，或者直接覆盖 B。

### 后期方案

区分：

- A：有效方案。
- B：编辑草稿。
- C：基于正确对象的假设预览。

### 当前结果

C 不自动覆盖 B，B 不自动覆盖 A。

【设计已收敛｜B】

## 5.15.4 E-F5-04｜从看过假设就视为接受，到明确采用

### 问题

用户可能只是查看一种可能性。

### 修正

浏览、比较、提问和采用具有不同语义。

### 当前规则

只有明确将假设加入草稿或采用为旅行安排时，才进入相应业务修改流程。

### 与其他 Flow 的关系

F1：浏览不等于兴趣。

F3：查看不等于采用。

F4：问题不等于编辑。

F5：假设不等于修改。

这些构成一致的授权边界。

## 5.15.5 E-F5-05｜从全局重生成到有限范围重算

### 初始风险

任何修改都重新生成整趟旅行。

### 问题

- 修改范围过大。
- 无关决定容易丢失。
- 影响难以追踪。
- 生成与计算成本高。
- 用户已确认体验缺少保护。

### 后期方向

优先识别受影响对象及依赖。

在当前可行范围内进行局部重算。

必要时扩大到整趟旅行分析。

### 当前结果

分析范围由实际影响决定，业务修改范围由用户意图和授权决定。

【设计已收敛｜B、C】

## 5.15.6 E-F5-06｜从重算得出“更优方案”到解释用户取舍

### 问题

系统可能生成一份更省时的方案，却删除用户重视的体验。

### 修正

重算必须解释：

- 获得。
- 保留。
- 失去。
- 时间及转场代价。
- 约束和未知。

### 当前结果

AI 可以推荐，但重要价值取舍仍属于用户。

【设计已收敛｜B、C】

## 5.15.7 E-F5-07｜从纠错直接覆盖到保留变化依据

### 初始问题

用户可能纠正之前已经采用的决定。

### 风险

如果系统直接覆盖，就丢失正式旅行的演化历史。

### 后期方向

依据纠错范围分别处理：

- 未执行指令。
- 当前草稿。
- 当前有效决定。
- 用户偏好理解。
- 外部事实。

### 当前结果

纠错应维护正确的当前有效状态，并保留必要依据。

【设计已收敛｜B、C】

## 5.15.8 E-F5-08｜从一次假设到多轮连续比较

### 设计问题

用户可能连续提出多个假设，并用“刚才那个”“另一个方案”等方式引用。

### 后期能力要求

保持正确的假设基准和对比关系。

### 当前结果

不必为每个假设建立永久版本，但不能在多轮讨论中混淆对象。

【设计已收敛｜B；具体复杂场景的原始裁决待补证】

## 5.15.9 E-F5-09｜从日期未知阻断，到条件依赖重算

### 后期发现的问题

用户可能不确定日期，但已经完成大量有效旅行规划。

### 风险

如果加入日期后整份行程被无条件重生成，之前规划成果会丢失。

### 修正

- 允许当前可行范围内的规划。
- 标记日期依赖。
- 现实条件确定后重新核验受影响部分。
- 尽可能保留不受影响的决定。
- 发生重大冲突时交由用户裁决。

【Owner 已确认｜A：F6 后期】

## 5.16.2 语义理解需要承接什么？

【工程待核查】

F5 对语义理解提出了较高要求。

需要区分：

假设

> 如果减少一天呢？

明确修改

> 就减少一天。

纠正

> 不是减少两天，是减少一天。

拒绝

> 刚才那个方案不要。

放弃假设

> 还是按照原来的安排。

采用假设

> 就按刚才那套来。

历史恢复

> 恢复到之前的版本。

条件变更

> 我确定可以旅行十天了。

还要正确理解：

- “刚才那个”。
- “另一种安排”。
- “在这个基础上”。
- “原来的版本”。
- “这座城市”。
- “刚才删掉的那一项”。

### 关键要求

不能把语言模型的猜测直接用于高影响状态修改。

当指代歧义会导致修改错误版本、删除重要体验或错误确认时，需要必要澄清。

普通低风险信息问题则不应过度追问。

## 5.16.3 Trip State 需要承接什么？

【工程待核查】

需要核查正式规格是否能够支持：

- 当前有效方案。
- 有效旅行版本。
- 正在编辑的草稿。
- 假设与正式修改的业务区别。
- 用户已确认决定。
- 变更来源和适用范围。
- 纠错后的有效判断。
- 重要版本历史。
- 城市级恢复。
- 条件化偏好和硬约束。
- 现实事实的有效性。
- 相关变更依据。

### 为什么需要？

假设、编辑和正式采用会涉及相同的城市、停留和体验对象。

但它们的业务意义不同。

如果系统只维护一份随对话变化的行程文本，就无法可靠保证状态隔离。

### 不允许的工程推断

本章不创建新的正式 Schema 状态或字段名称。

应由工程映射到现有规格，再判断是否存在缺口。

## 5.16.4 Decision Context 需要承接什么？

【工程待核查】

F5 需要正确维护：

1. 当前用户意图。
2. 当前旅行任务。
3. 当前假设的比较目标。
4. 当前假设基于哪份方案。
5. 用户此前已明确的约束。
6. 当前分析使用了哪些证据。
7. 哪些条件属于假设。
8. 哪些条件是有效旅行决定。
9. 哪些问题还未解决。
10. 多轮讨论中的正确指代。
11. 恢复时哪些上下文已经过期。

### 重要例子

用户在编辑 B 中提出 C，又返回地图查看 A。

之后说：

> 那刚才不去阿斯旺的方案呢？

系统必须能够关联原来的假设 C，而不是直接重新解释为新的有效方案修改。

### 重要边界

Decision Context 负责解释当前讨论，不应另行成为权威旅行状态。

## 5.16.5 NAP 需要承接什么？

【工程待核查】

重点包括：

- 识别假设、信息请求、明确修改和正式采用。
- 判断当前行动是否需要澄清。
- 判断哪些假设分析可以自主执行。
- 判断何时调用规划计算。
- 判断何时查询现实事实。
- 判断何时停止继续准备。
- 判断用户拒绝和改道后的正确行为。
- 判断正式修改是否取得授权。
- 检测重要新取舍是否需要用户决定。
- 不让假设绕过 Candidate 和 Proposal 生命周期规则。
- 不把回答交付解释为用户确认完成。

### 特别说明

NAP 负责行动选择和权限边界。

但不能仅靠 NAP 的自然语言指令，替代必要的数值计算、状态校验和版本检查。

## 5.16.6 前端需要承接什么？

【工程待核查】

需要支持：

方案焦点

- 当前有效方案。
- 当前草稿。
- 当前假设。
- 当前历史预览。

视觉联动

- 地图。
- 时间轴。
- 右侧整体摘要。
- 对话。
- 方案比较。

用户操作

- 进入假设。
- 查看差异。
- 返回原方案或草稿。
- 明确纳入草稿。
- 正式采用。
- 纠错。
- 查看相关事实与冲突。

异常反馈

- 生成中。
- 计算失败。
- 事实待核验。
- 已证实冲突。
- 保存失败。
- 版本已变化。

### 核心验收要求

用户应能理解：

现在看到的是哪一份旅行安排，它是否已经正式生效。

## 5.16.7 规划与校验执行能力需要承接什么？

【工程待核查】

这是 F5 对计算系统最直接的要求。

需要具备：

- 对正确基准进行假设推演。
- 明确识别变更对象。
- 检查城市停留和总天数。
- 分析连接变化。
- 识别体验获得与损失。
- 检查预算和硬约束。
- 识别受影响依赖。
- 必要时局部重算。
- 复杂情况下扩大全程分析。
- 保留不受影响的决定。
- 识别事实核验的适用条件。
- 检查旧事实是否过期。
- 生成能够解释的差异。
- 必要时准备可行修复方案。
- 在数据缺失时正确标记未知。

### 关键技术风险

分析的影响范围是否完整，以及未受影响部分是否得到保护。

如果系统少算一段关联交通，可能得出错误的方案结论。

如果系统过度重算，也可能损害已有决定。

因此，需要可检查的状态和计算机制，而不是只由模型生成“应该没有问题”的说明。

## 5.16.8 后端、版本与运行记录需要承接什么？

【工程待核查】

至少需要核查：

- 当前假设与正确基准的关联方式。
- 用户明确将假设纳入草稿的操作是否可追溯。
- 正式采用时是否检查最新有效版本。
- 是否可以避免重复提交。
- 纠错是否有正确变更依据。
- 历史恢复是否创建新版本。
- 跨会话是否能恢复未完成工作。
- 工具失败后如何保留已有结果。
- 用户确认和外部事实核验是否独立记录。

### 不应提前规定

- 必须使用哪种数据库。
- 必须采用事件溯源架构。
- 必须新增独立 What-if API。
- 必须建立专用 What-if Agent。
- 必须为每次假设永久保存一份完整快照。

这些属于工程方案选择，现有源资料不足以直接裁决。

## 5.17.1 评测层级

语义评测： 是否正确区分假设、纠错、采用、拒绝和历史恢复。

状态评测： A、B、C 与历史版本之间是否正确隔离。

计算评测： 受影响范围、天数、约束和变化结果是否正确。

权限评测： 是否避免未经授权牺牲已确认决定。

事实评测： 日期适用性、数据来源、未知和失败是否表达正确。

故障评测： 中断、恢复、旧版本和重复提交是否得到保护。

用户体验评测： 用户是否理解当前操作的实际后果，是否能够轻松比较并回到原安排。

机制正确性通过，不等于用户体验价值已被验证。

# 5.19 F5 完整设计结论

F5 的核心成果不是另外建设一个专门的“假设规划器”，而是让 ANTU 已有的旅行工作空间能够承接用户真实、反复、非线性的旅行思考。

最终能够恢复的主要机制如下。

第一：假设与正式修改必须分离。

用户说“如果怎样”，系统应推演，而不是直接改行程。

第二：不建立独立 What-if 页面或模式。

尽可能复用地图、时间轴、对话、方案比较、编辑和版本能力。

第三：有效方案 A、编辑草稿 B、假设预览 C 保持隔离。

假设 C 不自动覆盖 B，B 不自动覆盖 A。

第四：用户明确采用时，才进入相应修改流程。

编辑中可以将假设纳入草稿；编辑外使用现有合法采用与确认机制。

第五：纠错需要正确识别对象与范围。

纠正错误操作，不等于发起新的累计修改；纠正偏好理解，也不等于修改旅行方案。

第六：重算应以受影响范围为依据。

优先局部计算，必要时扩大全程分析，但不无故修改无关决定。

第七：比较必须解释真实的旅行价值变化。

包括体验获得、保留、失去、时间、交通、费用、约束和未知。

第八：重要价值取舍仍由用户决定。

AI 可以准备修复和推荐，但不能擅自牺牲已经确认的体验。

第九：事实变化需要重新核验，而非直接推翻全部规划。

日期、交通、费用和其他条件必须按适用范围管理。

第十：跨会话、异常和版本安全需要完整承接。

恢复未完成工作，防止假设覆盖、重复提交、事实误报和陈旧版本覆盖。
