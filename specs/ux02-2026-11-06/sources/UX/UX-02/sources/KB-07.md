### 7.0.1 为什么需要 UX-02.5？

F1–F6 已经分别设计了探索、推荐、方案比较、地图编辑、假设重算和确认保存。

但将六条 Flow 连接起来之后，会暴露出一些不能只靠单条流程解决的问题。

例如：

用户在 F4 编辑了一半，进入 F1 探索体验，再到 F5 比较假设，随后离开应用。几天后返回时，原来未完成的编辑是否还在？

因此，UX-02 后期增加了 UX-02.5 补充设计，主要检查：

F1–F6 的单独行为已经设计清楚之后，它们组合在一起是否仍能保持正确、连续和安全的产品行为。

UX-02.5 不是重新设计 F1–F6，也不是另建一套独立业务系统。

# 7.1 UX-02.5 的共用问题：用户在一个持续变化的旅行中工作

## 7.1.1 六条 Flow 不是六个独立业务系统

ANTU 中，同一位用户可能连续经历：

```
F1｜了解卢克索的体验
    ↓
F2｜了解增加卢克索的旅行代价
    ↓
F3｜比较两城和三城骨架
    ↓
F4｜编辑城市停留
    ↓
F5｜假设不去阿斯旺
    ↓
F6｜正式采用一组修改
    ↓
返回 F1｜继续探索新体验
```

虽然交互入口不同，但这些操作都围绕同一趟旅行及其不断演化的决定。

### 已形成的产品要求

- 用户不需要每进入一个 Flow 就重新建立旅行。
- 已确认决定不能因切换入口而丢失。
- 当前草稿不能因浏览行为而自动提交。
- 假设不能覆盖有效旅行。
- 历史版本不能被误当成最新有效版本。
- 用户兴趣和正式采用不能混淆。
- 外部事实核验不能代替用户确认。

【设计已收敛｜B；PRD 正式旁证 C】

## 7.1.2 五种必须区分的工作对象

UX-02.5-B 后期明确要求区分以下内容。

| 工作对象      | 主要作用            | 不代表什么         |
| --------- | --------------- | ------------- |
| 当前有效旅行    | 维护已经正式生效的安排     | 不代表全部现实条件均已核验 |
| 当前编辑草稿    | 保存尚未提交的修改       | 不代表已经成为有效旅行   |
| 当前假设预览    | 推演某种可能性         | 不代表用户已经采用     |
| 正在查看的历史版本 | 回看或比较旧安排        | 不代表已经恢复       |
| 当前浏览焦点    | 用户此刻查看的城市、体验或连接 | 不代表业务修改目标     |

### 核心产品结论

工作上下文与业务修改分离。

用户看到什么、当前讨论什么、正在编辑什么、真正生效的是什么，需要能够正确关联，但不能被混为同一个状态。

【UX-02.5-B｜B；Owner 对进入后续阶段的同意可见 A】

## 7.1.3 不能用“当前页面”代替业务状态

例如：

用户在编辑卢克索时打开阿斯旺体验卡。

此时：

- 当前页面可能显示阿斯旺。
- 当前浏览焦点是阿斯旺。
- 当前编辑草稿仍属于同一趟埃及旅行。
- 本轮正在修改的业务内容可能是卢克索停留。
- 当前有效旅行仍然是编辑前的版本。

如果系统只保存一个“当前城市”，就可能把后续自然语言修改错误作用到阿斯旺。

因此，跨 Flow 状态一致性要求不仅是前端显示正确，还包括后续 AI 行动使用正确的业务上下文。

# 7.2 UX-02.5-A｜跨会话恢复与编辑续接

原阶段编号：UX-02.5-A

设计主题：用户离开旅行规划后，能否从原来的实际工作位置继续，而不是重新开始？

来源等级：B 为主；PRD 状态保存要求提供 C 类旁证。

## 7.2.1 原始问题背景

用户可能花较长时间形成一趟旅行。

先完成 F3 骨架选择，随后在 F4 中连续调整城市停留。

例如：

当前有效方案 A：

开罗三天 → 卢克索三天 → 阿斯旺两天。

用户开始编辑：

- 开罗减少一天。
- 卢克索增加一天。

形成尚未提交的草稿 B。

随后用户查看了一次阿斯旺体验，和 AI 讨论了旅行节奏。

但没有点击「完成编辑」，就关闭应用。

三天之后重新进入。

### 如果系统只恢复最后一条聊天

可能出现：

- 有效方案恢复，但草稿丢失。
- 只知道用户想修改卢克索，不知道已经修改了什么。
- 地图显示旧安排，聊天却继续讨论新安排。
- 之前的确认与顾虑不再被正确读取。
- AI 重新问已经回答过的问题。
- 旧现实数据未经检查就被当成当前事实。

因此，跨会话恢复不应只是恢复聊天文本。

## 7.2.2 A-01｜恢复最后成功保存的工作进度

### 产品方向

历史摘要记载，Owner 要求：

重新进入后，应尽可能恢复上次操作到的最后一个步骤。

【历史摘要记载 Owner 要求｜B，原始逐字裁决待补证】

### 需要恢复的内容

有效旅行：

用户此前已经正式采用的安排。

未完成草稿：

已经成功保存的编辑变化。

编辑会话：

当前是否仍有未完成的工作。

当前焦点：

用户上次正在查看或操作的城市、体验、连接或其他对象。

操作进度：

用户已经完成什么，接下来还准备处理什么。

未解决问题：

此前已经发现、但尚未处理的冲突或重要取舍。

### 具体例子

用户回来后，仍然可以看到：

开罗 2 天、卢克索 4 天、阿斯旺 2 天的编辑草稿。

与此同时，原来的有效旅行 A 仍然保留。

### 必须避免

系统把恢复的草稿直接当作已确认旅行。

恢复草稿不是提交草稿。

## 7.2.3 A-02｜恢复决策上下文，而不只是恢复可见页面

### 为什么需要？

用户之前可能说过：

> 我希望多留一些时间看卢克索的遗迹，不想让旅行太赶。

随后才调整城市停留。

如果恢复时只保留数字：

卢克索 3 → 4 天。

却丢失此前的真实理由，AI 后续可能错误理解这次修改的目的。

### 需要恢复

- 当前旅行目标。
- 用户明确条件。
- 重要偏好与顾虑。
- 当前决策问题。
- 已讨论的主要取舍。
- 用户明确拒绝或暂缓的方案。
- 尚未解决的认知缺口。
- 本轮操作关联的事实与假设。

### 工程边界

这些信息需要从权威旅行状态和当前决策上下文中取得正确依据。

不能仅依赖模型重新总结聊天记录。

也不能让 Decision Context 成为另一份可以覆盖 Trip State 的权威旅行状态。

【B；PRD-002 旁证 C】

## 7.2.4 A-03｜跨会话恢复时重新检查现实事实

这是 A 阶段后期的重要新增要求。

### 原讨论问题

用户此前可能已经完成过现实条件检查。

但三天后回来：

- 出发日期可能已经改变。
- 原查询结果可能过期。
- 某项交通条件可能变化。
- 当时尚未取得的数据现在可能可以核验。

### 形成的产品要求

恢复历史工作成果的同时，需要重新判断相关现实核验结果是否仍然适用。

【历史摘要记载 Owner 明确要求｜B】

### 处理逻辑

1. 恢复上次工作成果。
2. 识别此前用过的现实核验依据。
3. 判断适用日期、条件与时效。
4. 找出需要更新的事实。
5. 在工具和数据条件允许时重新核验。
6. 把新的实际结果关联到正确对象。
7. 对冲突、未知和失败分别处理。

### 不应发生

- 因为重新打开会话，就认定原行程必然不可行。
- 无条件删除之前的有效决定。
- 将旧事实永久视为当前有效。
- 查询失败后直接显示“交通不存在”。
- 每次恢复都无条件全量重算整趟旅行。

### 需要保留的边界

恢复时的现实核验，应以相关性和事实适用条件决定。

具体缓存、时间阈值或后台执行方式，不在本轮 UX-02 中定稿。

## 7.2.5 A-04｜发现现实冲突后，必须定位问题

### 示例

用户此前保存了某段具体日期的交通安排。

重新进入后，更新后的可靠事实表明该安排与后续活动无法衔接。

### 正确反馈

系统应指出：

- 哪个安排出现问题。
- 问题关联哪座城市或哪段连接。
- 哪个事实发生变化。
- 对整趟旅行有什么影响。
- 哪些其他决定仍然有效。
- 可能怎样修复。

### 对 UI 的要求

冲突应关联到：

- 地图对象。
- 顶部时间轴。
- 右侧相关信息区。

不能只用一句：

> 您的行程出现问题。

### 必须区分

真实冲突： 已有充分证据证明实际不兼容。

待核验： 尚无足够证据判断。

核验失败： 工具未能提供有效结果。

【B；PRD-007 旁证 C】

## 7.2.6 A-05｜旧草稿与新版本之间的安全关系

### 场景

用户在 V3 版本上开始编辑，随后退出。

之后另一设备或合法操作形成 V4。

用户重新进入，继续原来基于 V3 的草稿。

### 风险

如果系统直接提交旧草稿，就可能覆盖 V4 中后来确认的内容。

### 产品要求

- 保留旧草稿及其用户意图。
- 识别草稿原本基于什么版本。
- 识别当前有效版本已经变化。
- 不静默覆盖新版本。
- 必要时对比新旧差异。
- 对冲突或新的重要取舍取得用户授权。

### 不能推断

此处不意味着已经决定必须自动合并两个版本。

自动合并是否适用、哪些范围可以安全合并，需要后续工程规格及实际产品场景判断。

## 7.2.7 A-06｜恢复失败时的成果保护

### 场景

用户重新进入时，地图服务加载失败。

或草稿的部分展示信息无法取得。

### 产品要求

已确认有效旅行不应因此丢失。

系统应尽可能：

- 恢复可取得的有效内容。
- 说明哪些内容尚未恢复。
- 保护原有编辑成果。
- 保留其他可用交互入口。
- 避免生成虚假的完整恢复结果。

### 重要边界

页面恢复失败不等于业务状态已经丢失。

前端展示层和权威保存结果需要分开判断。

## 7.2.8 A 阶段的初步 UI

历史讨论保留了一个恢复未完成编辑的入口方向。

### 说明性结构

```
发现上次未完成的旅行编辑

已保存的修改：
开罗 3 → 2 天
卢克索 3 → 4 天

当前状态：
编辑尚未完成
部分现实条件需要重新核验

继续上次编辑
查看当前有效方案
```

来源等级：B。

这段低保真文字是本次归档基于讨论规则重新组织的示意，不是原始截图。

### 已形成的行为要求

- 用户能够继续上次编辑。
- 原有效方案受到保护。
- 未完成草稿不会自动丢弃。
- 恢复后能识别需要重新检查的事实。

### 尚未最终定稿的 UI

- 是否必须先出现恢复提示。
- 是否自动进入上次编辑位置。
- 是否在旅行主工作空间内显示轻量提示。
- “继续编辑”和“查看当前方案”的具体控件位置。
- 网络暂时不可用时的入口形式。

这些交由 UX-04 验证。

# 7.3 UX-02.5-B｜跨流程切换与状态一致性

原阶段编号：UX-02.5-B

设计主题：用户在 F1–F6 之间不断切换时，如何确保浏览、编辑、假设、历史和有效旅行不会互相污染？

来源等级：B 为主；Owner 同意进入下一阶段的信息为 A；PRD 相关机制为 C。

## 7.3.1 B 阶段的核心问题

用户不可能始终沿着 F1→F2→F3→F4→F5→F6 的固定顺序前进。

例如：

1. 已经采用旅行骨架。
2. 进入 F4 开始编辑。
3. 返回 F1 查看某个体验。
4. 右滑体验，表示感兴趣。
5. 向 AI 询问相关交通。
6. 进入 F5 比较假设。
7. 查看 F3 的历史方案。
8. 返回 F4 继续编辑。

这条路径中既有：

- 内容浏览；
- 兴趣反馈；
- 问答；
- 假设；
- 历史浏览；
- 真正编辑。

如果系统不能区分它们，很容易发生错误状态变化。

### 典型错误

用户只想浏览阿斯旺体验，系统却自动将其加入编辑草稿。

或者用户查看旧版本后，AI 把后续修改作用于旧版，而不是原来的编辑草稿。

因此 B 阶段的核心不是设计更多页面，而是建立跨入口共享状态时的操作语义边界。

## 7.3.2 B-01｜查看焦点与业务修改目标分离

### 已形成的规则

切换浏览对象，不等于切换业务修改目标。

【设计已收敛｜B】

### 示例

用户正在编辑卢克索停留。

随后点击阿斯旺。

正确行为：

- 地图聚焦阿斯旺。
- 城市浮层展示阿斯旺。
- 右侧信息区切换到阿斯旺摘要。
- 原来卢克索的编辑成果保留。
- 用户不需要重新进入编辑。
- 不自动修改阿斯旺安排。

### 为什么重要？

“当前查看阿斯旺”只是一项浏览上下文。

不能因此把所有尚未完成的业务操作都重新指向阿斯旺。

## 7.3.3 B-02｜页面切换不结束编辑会话

### 原问题

用户进入编辑态后，为了做出决定，可能需要查看其他城市、交通、体验或历史方案。

如果一离开编辑界面就自动结束草稿，会造成大量返工。

### 已形成的规则

切换页面或 Flow，不等于完成编辑，也不等于放弃编辑。

### 示例

```
开始编辑 B
    ↓
修改卢克索停留
    ↓
进入 F1 浏览开罗体验
    ↓
进入 F5 比较假设 C
    ↓
返回 F4
    ↓
继续原草稿 B
```

### 正确状态

- 有效旅行 A 保持。
- 编辑草稿 B 保持。
- 假设 C 不自动覆盖 B。
- 浏览行为不产生正式采用。
- 返回时不需要重新执行已经完成的修改。

## 7.3.4 B-03｜兴趣反馈与行程采用分离

这是 B 阶段特别讨论过的跨 Flow 案例。

### 场景

用户正在编辑旅行草稿。

随后进入 F1。

在卢克索的体验卡上右滑，表示感兴趣。

### 正确行为

可以按 F1 规则记录该体验的兴趣反馈。

但：

- 不自动加入旅行。
- 不自动修改城市停留。
- 不自动改变已确认体验。
- 不自动把用户兴趣升级为正式采用。
- 不结束当前编辑会话。

### 后续情况

用户明确说：

> 把刚才那个体验加到这次编辑里。

这才是明确修改意图。

系统应识别正确对象，并按现有编辑机制处理。

### 重要边界

对内容感兴趣，与决定将该内容纳入旅行，是不同的产品行为。

【设计已收敛｜B；PRD-002 旁证 C】

## 7.3.5 B-04｜假设与编辑草稿分离

### 场景

用户正在编辑草稿 B。

随后提出：

> 如果不去阿斯旺呢？

### 正确行为

生成假设 C。

B 继续保留。

用户可以：

- 查看 C。
- 比较 B 与 C。
- 继续讨论 C。
- 返回 B。
- 明确将 C 的修改加入 B。

### 不能发生

仅因用户提出假设，系统就删除 B 中的阿斯旺。

这与 F5 的 A/B/C 关系一致。

## 7.3.6 B-05｜历史浏览与版本恢复分离

### 场景

用户正在编辑 V3 版本。

随后打开旅行历史，查看 V1。

### 正确行为

- 展示 V1。
- 明确当前是在查看旧版。
- 不覆盖 V3。
- 不覆盖正在编辑的草稿。
- 允许返回当前工作。
- 只有明确恢复意图才进入版本恢复流程。

### 进一步问题

如果用户在查看 V1 时说：

> 把卢克索增加一天。

系统需要判断：

用户是想：

- 在当前有效方案上修改；
- 在正在编辑的草稿中修改；
- 还是基于 V1 提出新的假设？

如果当前上下文不足以确定高影响修改对象，必须进行必要澄清。

### 不能简单采用的规则

> 用户最后查看哪份方案，就修改哪份方案。

这种做法会造成严重版本误写。

## 7.3.7 B-06｜对话与地图可以有不同焦点，但不能有不同的权威旅行

### 典型场景

地图正在显示卢克索。

用户向 AI 问：

> 如果把开罗减少一天，会影响什么？

### 正确行为

AI 应根据用户明确指向的开罗分析。

而不是因为地图当前聚焦卢克索，就把开罗修改解释为卢克索修改。

### 相反情况

用户在地图上选中了某个交通连接，随后说：

> 这段要多久？

此时可以利用可靠的当前指代上下文，识别其询问的是对应连接。

### 要求

系统需要维护：

- 当前地图焦点。
- 当前对话指代。
- 当前任务。
- 当前编辑目标。
- 当前旅行版本。

但并不需要为每个入口复制一份旅行权威状态。

## 7.3.8 B-07｜跨 Flow 拒绝不能被错误放大

### 场景

用户在 F3 拒绝某套三城方案。

随后在 F1 继续浏览阿斯旺。

### 正确行为

用户仍然可以正常探索阿斯旺。

不能因为拒绝三城方案，就认定：

- 用户不喜欢阿斯旺。
- 阿斯旺永久排除。
- 以后不允许重新比较阿斯旺。
- 相关体验需要从所有历史中删除。

### 原因

拒绝的作用范围必须与用户实际表达的对象一致。

拒绝一份方案不等于拒绝其中每个组成对象。

## 7.3.9 B-08｜跨 Flow 的确认操作必须作用于正确版本

### 场景

用户先在 F5 生成了一个假设。

随后切回 F3 的历史比较。

再说：

> 就按刚才那个来。

### 风险

“刚才那个”可能指向：

- F5 假设；
- F3 历史候选；
- 当前正在编辑的草稿；
- 其他最近查看的对象。

### 正确行为

在正式应用之前，需要可靠确定：

- 用户指定的方案。
- 对应来源版本。
- 实际修改范围。
- 当前有效旅行。
- 相关授权和约束。

### 不应发生

用户一句模糊的“就这样”，系统就随意选择最近的内部方案提交。

## 7.3.10 B-09｜跨 Flow 的事实状态也需要一致

### 场景

F3 比较中，一段交通仍然是概略估算。

用户进入 F4 后，系统不应该把它显示成指定日期已核验班次。

随后又到 F6，仍应保持事实核验层级准确。

### 形成的要求

事实需要关联：

- 对应对象。
- 来源。
- 查询条件。
- 日期适用性。
- 时效。
- 实际核验层级。

改变查看入口，不能改变事实本身的可信程度。

【B；PRD-007 旁证 C】

## 7.3.11 B 阶段的初步 UI 要求

本阶段没有证据表明 Owner 最终批准了一套全新的页面布局。

B 主要提出了状态呈现和跨入口连续性的要求。

### UI-B-01｜明确当前工作内容

用户需要知道现在是：

- 查看当前有效旅行。
- 编辑未完成草稿。
- 查看假设预览。
- 浏览历史版本。
- 普通内容探索。

### UI-B-02｜切换浏览焦点时保留编辑反馈

例如用户编辑中打开另一座城市：

- 草稿不消失。
- 编辑入口仍可恢复。
- 当前未提交状态不会被错误隐藏为已完成。

### UI-B-03｜假设与草稿视觉区分

假设预览不能与正在编辑的正式草稿混淆。

### UI-B-04｜历史版本只读提示

用户查看历史时，应能知道：

当前打开的是旧版本。

### UI-B-05｜当前有效方案回看入口

用户可以从历史或假设返回当前有效旅行。

### 状态

上述为已经形成的交互信息要求。

具体标签、色彩、切换控件、浮层和响应式布局仍待 UX-04 验证。

# 7.4 UX-02.5-C｜异常失败与用户成果保护

原阶段编号：UX-02.5-C

设计主题：当 AI、网络、数据、校验或提交发生异常时，怎样保护用户已有旅行成果，避免错误提交或虚报成功？

来源等级：B 为主；当前可见 Owner 指示开始 C 为 A；PRD-005、007、008、§5.4 为 C 类旁证。

### 证据特别说明

当前直接可见的 Owner 原话是：

> 我同意。进行异常失败与成果保护。

这能够证明 Owner 要求进入 C 阶段。

当前历史摘要还保留了 C 阶段的主要讨论方向，但不包含每项细则的完整原始裁决。

因此，不能将以下所有 C 规则逐条标记为“Owner 原始裁决已复核”。

## 7.4.1 C 阶段的核心问题

用户完成旅行规划，需要经历很多可能失败的操作：

- 地图和时间轴编辑。
- AI 生成或重算旅行方案。
- 查询交通与活动事实。
- 保存草稿。
- 完成编辑。
- 采用候选。
- 恢复旧版本。
- 跨会话恢复。

如果系统只考虑成功路径，就可能出现：

用户看到修改成功，但实际没有保存。

或者：

用户看到提交失败，实际上服务端已经成功。

还可能出现：

AI 计算失败后，把尚未完成的核验错误显示为通过。

因此，C 阶段形成的基本原则是：

失败不等于用户撤销；请求已发送不等于提交成功；状态未知不能被伪装为确定成功或失败。

【后期设计原则可由历史摘要恢复｜B】

## 7.4.2 C-01｜编辑过程中断网

### 典型场景

用户正在调整开罗和卢克索的停留。

已经修改多个对象。

此时网络中断。

### 用户最关心的问题

此前的编辑是否丢失？

### 正确的产品行为

系统需要区分：

- 已成功持久化的草稿修改。
- 当前前端仍然保留、但尚未确认持久化的修改。
- 已经正式提交的有效旅行修改。

### 必须保护的内容

- 原有效旅行。
- 已成功保存的草稿。
- 当前能够安全保留的用户操作成果。
- 已有版本与决定依据。

### 不能发生

- 一断网就清空全部草稿。
- 把尚未成功保存的修改提示为“已保存”。
- 因为草稿暂时无法同步，就改变原有效方案。
- 用户重新进入后，将部分成功的修改误当成全部完成。

### 工程待核查

是否支持离线操作及其具体范围，不由本轮 UX-02 直接确定。

但如果系统允许用户在断网期间继续编辑，就必须正确表达其保存与同步状态。

## 7.4.3 C-02｜AI 规划或重算失败

### 场景

用户完成多项编辑后，系统开始进行影响分析。

AI 或计算服务在中途失败。

### 正确行为

1. 不自动提交未经必要检查的草稿。
2. 保留当前有效方案。
3. 保留已成功保存的编辑草稿。
4. 说明哪些分析尚未完成。
5. 保留仍然适用的部分结果。
6. 允许在必要范围内重新分析。
7. 不把失败当作用户撤销修改。

### 为什么不能直接丢弃草稿？

因为用户编辑的成果和系统校验失败，是两回事。

用户已经完成的编辑操作不应该因为 AI 服务不稳定而消失。

### 为什么不能直接提交？

因为系统可能尚未完成必要约束检查。

如果直接提交，会把未完成验证的内容伪装为合法有效结果。

### 需要区分

规划内容已保存： 用户修改成果存在。

整体校验已完成： 相关检查已经执行并取得有效结果。

二者不能用一个“成功”状态代替。

## 7.4.4 C-03｜部分计算成功、部分失败

### 场景

系统已经完成：

- 城市停留加总。
- 城市顺序更新。
- 一部分交通影响判断。

但外部交通查询失败。

### 正确行为

已成功完成的结构计算可以继续作为有效分析结果使用，前提是其输入和适用条件仍然成立。

尚未取得结果的部分应标记为未完成或待核验。

### 不应发生

错误一：

只因为某个接口失败，就把所有用户操作成果清空。

错误二：

因为大部分计算成功，就显示全部校验通过。

### 测试要求

系统必须能够区分：

- 结果已经可靠完成的范围。
- 当前仍未完成的范围。
- 哪些前序结果因输入变化而需要作废。

## 7.4.5 C-04｜现实数据查询失败与确认无服务不同

PRD-007 和 §5.4 已经明确要求区分：

- 查询超时。
- 空结果。
- 字段缺失。
- 数据过期。
- 查询条件不适用。
- 有依据确认不存在相应服务。

AI Native旅行产品｜PRD V0.1.md

### 场景

用户希望确认某段交通。

外部工具没有返回结果。

### 错误行为

系统回答：

> 这段没有交通服务。

### 正确行为

如果仅仅是工具超时，应说明：

当前无法取得可靠核验结果。

不能从请求失败推断现实中没有服务。

### 对旅行状态的影响

已有旅行决定不应因为接口失败自动失效。

但对应的现实条件也不能继续被冒充为已经完成当前核验。

## 7.4.6 C-05｜已知现实冲突与未知必须区分

### 场景 A：已证实冲突

某段具体时间安排经过有效核验，确认不能成立。

### 正确行为

- 关联实际受影响对象。
- 标明冲突原因。
- 展示影响范围。
- 在适用工作空间中持续保留提示。
- 提供必要的修复方向。

### 场景 B：尚未核验

用户没有具体出发日期。

系统不知道相关班次是否成立。

### 正确行为

标记待核验。

不能直接显示为严重冲突。

### 场景 C：旧事实已经过期

之前的班次结果不再适用于新日期。

### 正确行为

标记需要重新检查。

不能继续当作当前条件下已核验。

### 关键规则

缺少证据，不等于发现冲突。

## 7.4.7 C-06｜提交请求超时：结果未知

这是 C 阶段必须重点保留的机制。

### 场景

用户点击：

完成编辑。

请求已经发送到服务端。

随后网络断开。

前端没有收到最终结果。

### 可能存在的真实情况

情况 A：

服务端已经成功处理并更新有效旅行。

情况 B：

服务端尚未处理成功。

情况 C：

服务端处理状态仍未确定或暂时无法查询。

### 为什么不能立即显示“失败”？

因为服务端可能已经成功。

如果用户据此前端提示再次提交，可能重复执行同一修改。

### 为什么不能立即显示“成功”？

因为系统尚未取得权威成功依据。

如果直接显示成功，会制造虚假的业务状态。

### 正确产品行为

1. 保留当前用户操作上下文。
2. 不以网络超时直接判定业务结果。
3. 重新取得权威旅行状态。
4. 识别本次业务操作是否已经生效。
5. 根据实际结果给出反馈。
6. 避免重复执行同一次业务修改。

### 不能在 UX 中直接指定

- 必须采用某个具体消息队列。
- 必须使用某个数据库事务协议。
- 必须设置固定次数重试。
- 必须使用某个具体 API 路径。

这些属于工程实现。

但结果未知与提交安全是必须承接的产品要求。

## 7.4.8 C-07｜重复点击与重复提交保护

### 场景

用户要把卢克索从三天改成四天。

点击一次「完成编辑」。

因为没有立即看到反馈，又点击一次。

### 错误情况

系统把两次请求解释成两个独立的“增加一天”动作。

最终卢克索从三天变成五天。

### 正确行为

同一次明确业务提交不应因网络重试或重复点击而重复应用。

### 产品要求

- 能识别重复执行风险。
- 对同一次业务意图避免重复效果。
- 不依赖用户一定只点击一次。
- 允许在结果未知时安全核实状态。

### 工程待核查

具体需要怎样标识业务操作、维护提交结果和实现幂等，由正式后端机制决定。

## 7.4.9 C-08｜并发版本变化与旧草稿保护

### 场景

设备一：

用户基于 V3 开始编辑。

设备二：

用户随后合法采用新方案，形成 V4。

设备一：

用户点击完成编辑。

### 风险

如果设备一直接提交旧草稿，可能覆盖 V4 中的新决定。

### 正确行为

- 识别草稿基础版本。
- 判断当前最新有效版本。
- 检查相关变化是否冲突。
- 保留设备一上的用户编辑成果。
- 不静默覆盖新有效版本。
- 在需要新的价值判断时交还用户决定。

### 不应直接推定

所有并发修改都可以自动合并。

例如两个设备同时修改同一城市的停留，可能涉及实际互相矛盾的决定。

系统不能只因为数值可以合并，就认定用户已授权合并。

## 7.4.10 C-09｜历史版本恢复失败

### 场景

用户尝试恢复旧版旅行。

恢复过程发现：

- 当前日期条件已改变。
- 历史连接不再适用。
- 旧版本涉及的核心安排与当前约束冲突。

### 正确行为

- 原有效方案保持。
- 用户恢复意图被保留。
- 说明具体冲突。
- 尽量识别可恢复的部分。
- AI 可以准备修复建议。
- 需要重要新取舍时交由用户判断。
- 不将恢复预览错误标记为已经生效。

### 城市级恢复的特殊要求

局部城市恢复失败，不应导致整趟旅行的其他城市错误回滚。

## 7.4.11 C-10｜用户拒绝、暂停与失败不能混为一谈

这三个结果具有不同语义。

| 情况       | 真实含义          | 应有处理          |
| -------- | ------------- | ------------- |
| 用户拒绝     | 用户明确不接受某项改变   | 按拒绝范围保持有效状态   |
| 用户暂停     | 用户暂时不继续处理     | 保留未完成工作和适用上下文 |
| 系统失败     | 系统未能完成某项操作    | 保护成果，说明实际失败范围 |
| 提交结果未知   | 尚不能确定业务是否生效   | 核实权威状态        |
| 用户明确放弃草稿 | 用户不再保留本轮未提交编辑 | 按合法放弃流程处理     |

### 核心边界

不能因为系统失败就记录“用户拒绝”。

也不能因为用户暂停就自动放弃草稿。

## 7.4.12 C 阶段的初步 UI

本阶段主要新增的是状态反馈要求，并没有足够证据证明已定稿专门的错误处理页面。

### UI-C-01｜草稿保存状态

需要区分：

- 修改正在保存。
- 修改已成功保存。
- 当前修改尚未确认保存。
- 保存发生失败。

### UI-C-02｜整体校验状态

需要区分：

- 尚未开始必要校验。
- 正在校验。
- 已完成当前可执行的检查。
- 部分核验失败。
- 存在已知冲突。
- 仍有待核验事项。

### UI-C-03｜正式提交状态

需要区分：

- 提交中。
- 权威确认成功。
- 权威确认失败。
- 提交结果未知。

### UI-C-04｜版本冲突

用户应能知道：

当前草稿所依据的旅行版本已经变化。

在问题处理前，旧草稿不会直接覆盖新版本。

### UI-C-05｜错误定位

地图、时间轴、右侧信息区应能关联受影响对象。

### UI-C-06｜恢复结果

用户应知道：

- 哪些成果已经恢复。
- 哪些尚未恢复。
- 哪些现实事实需要重新检查。

### 低保真结构示意

```
本次修改的提交结果暂时无法确认

当前情况：
网络连接中断，尚未取得最终提交结果

已保护：
本轮编辑内容
当前有效旅行版本

后续处理：
核实服务端最终状态
避免重复应用相同修改
```

这只是归档重构的说明性信息结构，不是原始 UI 文案，也不代表已经确定具体按钮或弹窗。

### C 阶段结论

用户成果保护必须覆盖编辑、计算、事实核验和正式提交整个过程。

尤其需要保证：

- 用户修改不会因为工具故障无故丢失。
- 未校验的结果不会被显示成已通过。
- 系统失败不会被解释成用户拒绝。
- 网络超时不会被直接判定为业务失败。
- 重复请求不会重复应用。
- 旧草稿不会覆盖新版本。
- UI 成功反馈必须有权威业务结果支撑。

当前状态：产品规则可恢复；对应实现、正式接口及端到端测试均待工程核查。

# 7.5 UX-02.5-D｜规格一致性与工程交接检查

原阶段编号：UX-02.5-D

阶段性质：设计完成后的核查与交接，不是继续新增 F1–F6 产品行为。

来源等级：A｜当前可见 Owner 关于“UX-02 设计已完成，只剩规格一致性和工程交接检查”的明确表述；B｜此前对 D 任务的解释；C｜现有 PRD 和机制资料。

## 7.5.1 D 阶段的定位

Owner 曾直接提出一个关键问题：

> 所以整个我们 UX02 这一个环节的所有工作都结束了，现在只剩下规格一致性和工程交接的检查。那在这一步你刚刚是想进行什么操作呢？

这明确区分了两件事情：

第一：F1–F6 及后期补充行为设计已经完成讨论。

第二：还需要检查这些设计与正式产品、技术规格之间的关系，并形成后续交接。

### 不能将 D 阶段理解为

- 重新选择 F1–F6 的产品方案。
- 为每个 Flow 再做一轮完整探索。
- 直接修改 Trip State、Decision Context 或 NAP。
- 直接宣布 UX 设计已经由工程实现。
- 不保存正式知识底稿就进入开发。
- 自动把所有后期设计加入 MVP 范围。

## 7.5.2 D 阶段应该检查什么？

核心是：

UX-02 的行为规则是否与已有正式规格兼容，工程模块是否具备承接这些行为的明确责任和可验证要求。

需要对照：

- PRD V0.1。
- Trip State Schema V0.1.0。
- Decision Context V0.1.0。
- NAP V0.1.0。
- 规划与校验执行相关设计。
- 前端状态与交互能力。
- 后端保存、读取和版本机制。
- 外部事实和计算工具。
- AI Evaluation。
- 已存在的工程实现与运行证据。

### 最重要的区别

规格一致性检查： 设计的行为规则与现有正式规范是否存在差异或冲突。

工程能力覆盖检查： 现有设计或实现是否能够承接相关要求。

UX 设计完整性检查： 是否存在遗漏、矛盾或未定义的交互行为。

这三种检查不能互相替代。

## 7.5.3 D 阶段如何判断规格覆盖？

建议对每条关键规则形成以下结果之一。

| 结果   | 含义                    |
| ---- | --------------------- |
| 已覆盖  | 正式规格中存在可定位、语义一致的机制要求  |
| 部分覆盖 | 正式规格已有部分责任，但不足以完全覆盖设计 |
| 缺失   | 经正式规格检查，确认没有必要的承接规范   |
| 存在冲突 | UX 规则与正式规格的行为要求不一致    |
| 待验证  | 无足够资料或测试证据，暂不能下结论     |

这是一组建议的审查结果标签，不是宣布正式工程包已经采用此分类。

### 重要边界

如果 UX 设计出现了某项新增要求，但还没有核对正式技术包：

只能标记为：

工程待核查。

不能直接标记“工程缺失”。

反过来，正式规格已经描述某项能力，也不能直接宣布工程代码已经实现。

## 7.5.4 D-01｜Trip State 一致性核查

重点确认：

- 用户目标、偏好、候选、约束、决定和外部事实是否保持区分。
- 浏览与兴趣反馈是否不会直接升级为正式决定。
- 假设是否不会自动写入有效旅行。
- 当前有效方案、草稿和历史版本是否能够正确区分。
- 重要变更是否能够保留来源和依据。
- 整份与城市级历史恢复是否有合法承接方式。
- 修改是否保留不受影响的决定。
- 跨会话恢复时是否能够取得必要权威状态。

### 不允许直接执行的动作

UX-02-D 不能因发现行为差异，就擅自修改正式 Trip State 对象、字段或状态转换。

应先记录差异，再由对应规格维护工作处理。

## 7.5.5 D-02｜Decision Context 一致性核查

重点确认：

- 当前任务和决策缺口。
- 用户当前明确意图。
- 相关的偏好、顾虑和硬约束。
- 当前浏览对象与修改目标。
- 当前假设的基准。
- 历史版本引用。
- 已完成和未完成的工作。
- 事实失效及待重核验。
- 跨会话恢复上下文。

### 重要版本注意事项

项目此前曾出现过：

跨会话恢复接口需求一度以 0.2.0 标记，后来要求统一按 Decision Context V0.1.0 的正式范围处理。

因此，工程核查必须特别注意：

不能因为仍有旧的 0.2.0 引用，就遗漏当前 V0.1.0 的恢复接口要求。

这属于既有规格维护风险，不意味着本轮已读取并完成了所有对应原包改动。

## 7.5.6 D-03｜NAP 一致性核查

重点确认：

- 用户主动请求和系统推荐的优先关系。
- 浏览、问题、假设、编辑、确认和恢复的不同动作语义。
- 低风险探索的许可范围。
- 重要决定的权限与确认。
- “选择即确认”与正式 Proposal 生命周期是否兼容。
- 用户拒绝后的处理。
- 用户不回应时的等待和停止。
- 已交付回答但未确认任务完成时如何维持正确生命周期。
- Candidate 不满足重入条件时，是否仍可进行合法的只读探索。
- 异常失败后是否能选择安全的下一步行动。

### 已有的重要产品边界

项目此前明确讨论：

允许只读探索，不代表允许 Candidate 非法重入。

以及：

回答交付，不代表用户已经确认或完成业务执行。

这些应作为正式 NAP 规格核对事项，而不是在 UX-02 中再创建新的顶层 Policy。

## 7.5.7 D-04｜规划与校验执行能力核查

重点确认：

- 能否生成实质不同的旅行骨架。
- 能否检查明确约束。
- 能否识别体验得失。
- 能否计算城市停留与连接影响。
- 能否进行有限范围重算。
- 能否检测日期依赖。
- 能否识别外部事实过期。
- 能否区分冲突与未知。
- 能否针对局部问题准备修复。
- 能否保留用户已确认的重要决定。
- 计算失败时是否会保留原有效状态。

### 技术实现边界

UX-02 描述的是系统应该具有的行为能力。

不能因此要求一定建立某个特定名称的独立 Agent 或执行框架。

## 7.5.8 D-05｜前端与交互工程核查

重点确认：

- 地图、时间轴和对话是否共享正确的旅行状态。
- 浏览与编辑是否能够区分。
- 编辑草稿是否能够持续显示。
- 假设和历史预览是否不会误写有效状态。
- 右侧整体和城市信息区是否能正确切换。
- 已知冲突是否能定位到具体对象。
- 待核验和已知冲突是否能区分。
- 完成编辑、撤销、放弃和暂停是否具有不同效果。
- 跨会话是否能恢复最后成功保存的位置。
- 失败和提交结果未知是否能正确反馈。

### UX-04 与 D 的区别

D 负责检查：

这些行为是否有明确工程承接。

UX-04 负责进一步决定：

这些行为具体通过什么页面、组件、状态和视觉方式让用户理解。

不能把 D 的覆盖检查当作最终 UI 定稿。

## 7.5.9 D-06｜后端、数据与运行机制核查

重点确认：

- 草稿保存与读取。
- 正式提交与权威状态核实。
- 版本关系。
- 提交幂等。
- 并发版本保护。
- 恢复接口。
- 外部事实来源、适用范围和时效。
- 查询失败分类。
- 操作、工具结果和确认依据的可追溯性。
- 异常中断后的恢复能力。

### 测试边界

必须通过具体运行证据确认工程能力。

不能只凭设计说明或 API 名称推断功能完整。

## 7.5.10 D 阶段的正确交付内容

D 最终应形成：

UX 行为规则 → 正式规格位置 → 差异或兼容性结论 → 工程承接责任 → 测试要求。

例如：

| UX 规则    | 需要核对的正式规格                 | 需要取得的证据       |
| -------- | ------------------------- | ------------- |
| 选择即确认    | NAP、PRD-008、Proposal 生命周期 | 规则条款、正反例与运行结果 |
| 跨会话恢复编辑  | TS、DC、恢复接口                | 恢复测试及对象关联证据   |
| 城市级恢复    | TS、版本与影响计算                | 局部恢复和连锁检查结果   |
| 假设不覆盖草稿  | TS、DC、NAP、运行编排            | 多轮状态对照        |
| 提交结果未知   | 后端提交与版本机制                 | 断网、重复请求的回归测试  |
| 日期依赖重新核验 | DC、事实数据与规划校验              | 条件变更后的检查结果    |

不得把以上检查项标记成“已经通过”。

# 7.6 其他跨 Flow 的后期补充机制

以下机制在 F1–F6 中分别形成或深化，但因影响多个 Flow，需要作为独立索引保留。

## 7.6.1 X-01｜选择即确认

主要来源：F3 后期｜B

涉及：

- F3 骨架采用。
- F4 完成编辑。
- F5 假设正式采用。
- F6 重要决定保存。

### 统一边界

用户已经明确表达对具体方案或修改的正式采用意图，且重要影响已经充分呈现时，不要求重复进行普通确认。

### 不取消

- 新重要取舍的必要授权。
- 事实核验。
- 硬约束检查。
- 版本校验。
- 高风险交易权限。

这是跨 Flow 的确认语义优化，不是无条件自动提交。

## 7.6.2 X-02｜重要历史版本及恢复

主要来源：F3 后期｜B

涉及：

- F3 方案历史。
- F4 编辑提交。
- F5 基于历史方案提出假设。
- F6 保存、回顾与恢复。
- UX-02.5-A/C 的恢复和安全保护。

### 统一边界

- 重要用户可见方案具有历史回顾价值。
- 不要求保存所有 AI 内部中间方案。
- 查看历史不自动恢复。
- 恢复旧安排形成新有效版本。
- 不能擦除后续历史。
- 恢复时须核查当前约束和事实适用性。

## 7.6.3 X-03｜城市级恢复

主要来源：F3 后期｜B

涉及：

- F3 版本比较。
- F4 局部编辑。
- F5 连锁影响分析。
- F6 正式应用。
- UX-02.5-C 异常保护。

### 统一边界

用户可以只针对某座城市请求恢复历史安排。

但系统必须检查相关联的其他城市、连接、停留和体验。

局部恢复范围不等于局部分析范围。

分析可以扩大，但未经授权的业务修改不能随之扩大。

## 7.6.4 X-04｜A/B/C 方案隔离

主要来源：F4、F5｜B

三类内容：

- A：有效旅行。
- B：编辑草稿。
- C：假设预览。

### 统一边界

- B 不自动覆盖 A。
- C 不自动覆盖 B。
- 普通浏览不修改任何一个业务目标。
- 明确应用假设到 B，才更新草稿。
- 正式采用需要使用相应合法流程。

这套 A/B/C 是设计解释模型，不是已确认的正式 Schema 枚举。

## 7.6.5 X-05｜即时反馈与整体校验分层

主要来源：F4｜B

涉及：

- 地图操作。
- 时间轴编辑。
- 自然语言编辑。
- F5 重算。
- F6 完成编辑。

### 统一边界

即时反馈：

显示能够直接计算的结构变化及已知问题。

完整分析：

在必要节点检查整体影响、现实条件与重要取舍。

### 不应发生

每一次简单操作都触发全程重新规划。

但如果当前已经存在明显重大冲突，也不应故意延迟到最终提交后才提示。

## 7.6.6 X-06｜规划与现实核验双维度

主要来源：F6 后期｜B；PRD-007、008 旁证 C

### 统一边界

用户确认旅行选择，不等于外部现实条件自动成立。

无日期时可以进行当前范围内的规划和确认。

存在高影响日期依赖时，应尽早识别。

加入真实日期后，对受影响事项进行必要核验。

### 关键分类

- 规划已采用。
- 事实已核验。
- 事实待核验。
- 事实失效。
- 已知冲突。
- 工具失败。

这些不能混成单个“行程完成”状态。

## 7.6.7 X-07｜最小必要修改与复杂连锁影响

主要来源：F3、F5、F6｜B

### 统一边界

旅行中某项变化，可能影响多个对象。

系统应计算实际依赖，并尽可能保护不受影响的决定。

### 重要限制

“最小修改”不是最高优先级的绝对规则。

如果用户明确愿意改变更大范围以获得更喜欢的体验，系统仍应尊重合法价值取舍。

### 不应发生

只因为系统找到一个技术上容易的修复方式，就未经授权删除用户的重要体验。

## 7.6.8 X-08｜用户纠错、拒绝和恢复讨论

主要来源：F1、F2、F5、F6｜B；PRD-002 旁证 C

需要区分：

- 用户修正系统对偏好的理解。
- 用户拒绝某个候选。
- 用户暂停当前讨论。
- 用户重新打开已经讨论过的对象。
- 用户正式改变已确认决定。

### 统一边界

不能将拒绝一次方案扩大为永久排斥其所有对象。

不能把条件性的“如果”升级为正式决定。

不能把重新探索候选自动视为满足 Candidate 合法重入条件。

## 7.6.9 X-09｜AI 回答交付与任务完成分离

主要来源：NAP 后期产品裁决｜B

### 场景

用户要求 AI 解释一项交通选择。

AI 已经提供有依据的解释。

但用户没有表示是否接受某个旅行调整。

### 正确行为

- 可以将解释交付记录为已经发生。
- 不伪造用户已确认方案。
- 不将业务执行标记为成功。
- 不反复催问相同确认。
- 保持后续任务能够正确恢复。

### 工程交接

需要核对 NAP 和 Decision Context 的任务生命周期。

不要求因为这项 UX 规则新增另一套顶层 Policy。

## 7.6.10 X-10｜用户成果与业务状态的分层保护

主要来源：UX-02.5-A/C｜B

需要区分：

- 用户已经正式确认的旅行成果。
- 正在编辑但未提交的草稿。
- 已经成功保存的草稿操作。
- 只存在于当前交互中的临时预览。
- 已完成但可能过期的事实核验结果。
- 已发送但结果未知的业务提交。

### 核心目标

系统故障、页面切换或长期离开，不应错误破坏已形成的合法成果。

但也不能因为用户在屏幕上看到某项预览，就假装它已经成功保存。

# 7.7 UX-02.5 的设计演化与 Owner 裁决索引

本节不重新叙述 F1–F6 的全部设计历史，而是集中说明后期为什么必须增加 UX-02.5，以及哪些原有认识被深化。

## 7.7.1 E-2.5-01｜从单条 Flow 正确到跨 Flow 连续性

### 原有设计

F1–F6 已分别形成明确的进入、操作、确认和退出规则。

### 后期发现

单条流程正确，并不能保证跨流程状态正确。

例如：

F4 编辑过程本身没有问题，但用户进入 F5 后可能错误覆盖原草稿。

### 补充方向

建立跨流程工作上下文与业务修改的隔离要求。

### 最终收敛

切换查看内容不改变实际业务修改目标。

【设计已收敛｜B；B 阶段 Owner 同意后续推进的信息可见 A】

## 7.7.2 E-2.5-02｜从聊天历史恢复到实际工作续接

### 原有能力目标

长期保存用户旅行状态和决定依据。

### 后期发现

恢复已确认旅行还不够。

用户可能正在编辑一组尚未提交的修改。

### 补充要求

恢复：

- 当前有效方案。
- 未完成草稿。
- 最后成功保存的操作进度。
- 相关决策上下文。
- 需要重新核验的现实条件。

### 最终方向

跨会话恢复应服务于任务继续，而不仅是回顾聊天。

【历史摘要记载 Owner 明确要求｜B】

## 7.7.3 E-2.5-03｜从恢复旧状态到检查旧事实适用性

### 原有风险

用户三天后回来，系统直接沿用上次的交通和活动核验结果。

### 新问题

某些现实条件可能已经变化或不再适用。

### 补充方向

恢复后判断哪些事实需要重新核验。

### 最终结果

业务成果可以恢复，事实可信性需要按当前条件重新判断。

【设计已收敛｜B；PRD-007 旁证 C】

## 7.7.4 E-2.5-04｜从点击或切换触发状态变化，到意图分离

### 原有风险

系统可能把最近查看的对象当作最近确认的对象。

### 后期补充

浏览、兴趣、假设、草稿、历史和有效方案分别处理。

### 最终结果

用户的查看行为不能无意触发高影响业务改变。

【设计已收敛｜B】

## 7.7.5 E-2.5-05｜从错误提示到用户成果保护

### 原有问题

设计异常分支时，容易只考虑显示错误文案。

### 后期发现

对旅行规划而言，更重要的是：

用户修改是否丢失、原有效方案是否受到破坏、提交是否重复执行。

### 补充方向

- 保护有效方案。
- 保护已保存草稿。
- 标明实际失败范围。
- 确保必要校验完成。
- 核实提交结果。
- 防止重复业务修改。

### 最终结果

异常处理不仅是错误反馈，更是状态与成果安全。

【后期设计可恢复｜B】

## 7.7.6 E-2.5-06｜从“请求失败”到“结果可能未知”

### 原有风险

网络超时后直接显示提交失败。

### 问题

服务端可能已经成功处理。

### 补充方向

通过权威业务状态核实实际结果。

### 最终结果

前端未收到成功响应，不足以证明业务更新失败。

【后期设计可恢复｜B】

## 7.7.7 E-2.5-07｜从单设备编辑到版本一致性保护

### 原有风险

草稿可能建立在旧版本上。

### 后期补充

提交前检查草稿基础版本与当前有效版本。

### 最终结果

不能让旧草稿静默覆盖新的有效旅行。

【后期设计可恢复｜B；工程待核查】

## 7.7.8 E-2.5-08｜从 UX 设计继续扩张到工程规格核对

### 后期阶段变化

Owner 明确指出：

UX-02 的全部设计讨论已经结束，剩余是规格一致性与工程交接检查。

### 对任务范围的影响

不再继续把正常工程接口问题当成需要重新裁决的 UX 问题。

而是：

1. 固化已形成的产品行为。
2. 保存设计知识与演化依据。
3. 对照正式规格。
4. 识别工程责任与差异。
5. 交接测试要求。
6. 只在真正需要新的产品 trade-off 时交由 Owner 判断。

【Owner 原始表述可见｜A】

## 7.9.2 需要保留的测试轨迹

后续工程检查不能只依赖单个静态样例。

至少应准备以下连续业务轨迹。

### T-2.5-01｜编辑—探索—返回

```
采用有效方案 A
→ 开始编辑 B
→ 修改卢克索
→ 进入 F1 浏览阿斯旺
→ 右滑一项体验
→ 返回 F4
→ 继续编辑 B
```

验证： 兴趣正确记录，草稿不丢失，不自动加入行程。

### T-2.5-02｜编辑—假设—返回

```
有效方案 A
→ 编辑草稿 B
→ 生成假设 C
→ 查看 C
→ 返回 B
→ 完成编辑
```

验证： C 不覆盖 B，B 未获合法提交前不覆盖 A。

### T-2.5-03｜编辑—跨会话恢复

```
采用 A
→ 连续修改形成 B
→ 退出
→ 现实事实可能变化
→ 重新进入
→ 恢复 B
→ 检查相关事实
```

验证： 恢复最后成功保存的成果，事实适用性正确。

```

→ 查看 V1

→ 处理必要取舍
→ 合法形成 V4
```

```
→ 用户再次尝试
→ 查询权威状态
```

验证： 不因超时误判，不重复应用修改。

### T-2.5-06｜并发版本冲突

```

```

验证： 正确检测版本变化，V4 不被静默覆盖。

### T-2.5-07｜日期变化后的局部修复

```
→ 后来补充具体日期
→ 旧核验结果不再适用
→ 重新核验相关安排
→ 定位冲突
→ AI 提出修复
→ 用户决定重要取舍
```

验证： 不伪造事实，不自动推翻整趟旅行。

### T-2.5-08｜回答交付但业务未确认

```
→ 用户转向其他任务
→ 之后恢复讨论
```

验证： 回答交付不等于用户已确认修改，不持续催问。

## 7.11.2 本阶段最重要的产品结论

UX-02.5 解决的不是六条 Flow 各自怎样工作，而是：

当用户在不同 Flow、不同会话、不同版本和不同系统状态之间来回切换时，ANTU 怎样保证旅行决定始终正确，编辑成果不丢失，假设不被误用，事实不被虚报，失败不会破坏用户已经形成的成果。

其主要设计成果可归结为四个方面。

一、持续工作能力。

用户离开后可以尽可能恢复最后成功保存的工作成果、相关上下文和操作位置。

二、跨入口状态一致性。

浏览、编辑、假设、历史与有效旅行拥有不同业务语义，不能因页面或交互入口切换而互相覆盖。

三、异常与成果保护。

系统失败、查询超时、提交结果未知、重复请求和版本冲突，不得导致错误业务状态或无依据的成功反馈。

四、正式规格与工程交接。

产品设计已形成的规则，需要逐项映射到正式 TS、DC、NAP、计算、前后端及 Evals，确认真实承接与验证情况。
