## 9.0 本章定位与使用说明

### 9.0.1 本章要解决的问题

F1–F6 和 UX-02.5 的详细设计已经在前八部分分别恢复。

但对于正式归档，仅保存当前设计规则仍然不够。

Work 还需要理解：

- 为什么最初提出某种方案。
- 它试图解决什么用户问题。
- 后来发现了什么不足。
- 是否讨论过其他解决方式。
- 最终为什么改变方向。
- 哪些原则已经收敛。
- 哪些属于 Owner 明确裁决。
- 哪些方案曾被明确放弃。
- 哪些仅仅是讨论中识别出的风险。
- 哪些问题仍需要 UX 或工程验证。

本章的核心目标是：

保留 UX-02 的设计决策历史，使后续团队不仅知道“应该怎样做”，还知道“为什么这样做、哪些做法不应该重新引入”。

### 9.0.2 不重新裁决已经完成的产品设计

本章不会重新选择 F1–F6 的交互方案。

若发现历史资料不完整，采用以下处理方式：

已有明确结论，但原始裁决无法直接查看：

保留结论，标记历史摘要恢复与待补证。

已有正式 PRD 要求：

作为正式资料旁证，保留对应章节编号。

存在不同阶段的设计变化：

按已知时间顺序保留，不静默覆盖旧方案。

只知道最终排除了某种做法，却不知道它是否曾被正式提出：

将其列为“明确不采用的行为／应避免的风险”，而不是伪造一次历史方案讨论。

确实存在尚未解决的问题：

保留为待验证或工程待核查，不要求 Owner 重新裁决已经讨论过的内容。

# 9.1 历史来源、裁决证据与废弃方案分类

## 9.1.1 证据等级

| 等级          | 证据来源                             | 可以支持的结论                             |
| ----------- | -------------------------------- | ----------------------------------- |
| A｜原始消息可直接读取 | 当前实际可见的用户消息、Owner 原话             | 可以确认该消息明确表达的意图、要求或裁决                |
| B｜历史摘要恢复    | UX-02 历史上下文摘要、前述恢复底稿             | 可以恢复设计规则和演化线索，但不能冒充完整原始裁决           |
| C｜正式资料旁证    | PRD V0.1、项目思考总纲 V2、《产品机制审视与迭代计划》 | 可以确认正式资料中的产品机制和需求，但不等于 UX-02 聊天原始记录 |

### 本章特别注意

前八部分中部分机制被表述为：

> 历史摘要记载 Owner 明确认可。

本章继续保留这一信息，但统一标为：

【B｜历史摘要记载 Owner 已确认，原始裁决待补证】

不能因为前八部分已经重复描述某项机制，就把它提升为 A 级证据。

同样，P01 机制已经在正式项目资料中记录为产品方向已裁决，只能据此证明 P01 的正式机制状态，不能声称 UX-02 中也逐字完成过同一裁决。

## 9.1.2 设计状态分类

本章使用以下六类标签。

| 标签          | 判定方式                           |
| ----------- | ------------------------------ |
| 【Owner 已确认】 | 有直接可定位的 Owner 裁决，或明确注明仅由历史摘要记载 |
| 【设计已收敛】     | 多轮讨论形成稳定规则，但独立批准依据不完整          |
| 【候选方案】      | 仍在探索、验证或等待最终交互形式确定             |
| 【待解决】       | 仍存在尚未回答的产品问题或确认依赖              |
| 【已推翻】       | 有证据证明曾提出的方案后来被明确替换或否定          |
| 【工程待核查】     | 需要与正式规格、实际实现和测试结果对照            |

### 对“已推翻”的进一步限制

本章区分两种情况。

D 类：有演化证据的废弃方向。

可以说明原来采用过或认真考虑过什么、后来如何修正。

R 类：明确禁止或应避免的实现方式。

可以确认当前规则不允许这种行为，但不一定有证据证明它曾经作为正式设计提案存在。

这两类不能合并成一份虚假的“被推翻方案历史”。

## 9.1.3 当前可恢复的整体演化顺序

1. F1｜降低启动门槛

   从目的地意愿进入地图与体验探索，渐进形成用户认知和偏好。
2. F2｜由决策缺口引导下一步

   AI 根据当前任务选择有意义的帮助，同时保留用户改道和跳过权。
3. F3｜从探索进入可比较的旅行骨架

   通过实际体验得失、停留与交通代价支持用户选择，并逐渐补充确认与版本历史。
4. F4｜从方案展示发展为持续可编辑工作空间

   形成顶部时间轴、主地图、右侧信息区，以及连续编辑和统一草稿机制。
5. F5｜支持非破坏性假设、纠错和有限重算

   将假设与有效方案、编辑草稿区分，避免每次变化都重建整趟旅行。
6. F6｜从确认保存扩展到渐进式确认与现实核验管理

   区分用户决定和事实核验，允许无日期规划，同时保护高影响条件和历史版本。
7. UX-02.5｜补齐跨流程连续性与异常保护

   形成跨会话恢复、工作上下文隔离、提交安全、版本冲突保护和工程一致性检查范围。

证据说明： 上述是根据已恢复设计阶段建立的高层演化顺序，不是全部原始聊天消息的精确时间序列。

# 9.2 F1｜意愿启动与探索的设计演化

原讨论阶段：UX-02｜F1

主要来源：B；PRD-001、002、007 提供 C 类旁证。

## E-F1-01｜从收集旅行条件到低门槛认知启动

### 设计问题

用户可能只知道：

> 我想去埃及。

但不知道：

- 埃及有哪些值得旅行的城市。
- 不同城市体验有什么区别。
- 自己到底喜欢哪些内容。
- 应该安排多少天。
- 需要多少预算。
- 城市之间如何移动。

如果产品一开始要求用户填写完整日期、预算和旅行天数，会迫使用户在缺乏认知基础时作出决定。

### 当前正式方向

仅凭目的地意愿就可以开始。

系统优先帮助用户建立：

- 城市地理位置的参照。
- 城市体验差异的参照。
- 可能的旅行价值。
- 相关条件和代价。

用户可以在探索过程中逐渐形成偏好和限制。

### 设计演化意义

从“先收齐条件再规划”，转向“通过探索帮助用户形成条件”。

### 被排除的做法

`必须填写完整日期和预算 → 才能查看目的地`

【R｜明确不采用的交互行为】

### 证据状态

【设计已收敛｜B】

【PRD-001 正式旁证｜C】

目前没有完整原始讨论证明“强制问卷”曾被正式选定为 F1 的第一版方案，因此不能把它写成一个已经实施、后来被推翻的版本。

## E-F1-02｜从纯文字介绍到地图与体验共同建立认知

### 最初要解决的问题

传统文字旅游介绍可以提供信息，但不一定让用户形成清楚的空间和体验参照。

例如：

用户知道开罗、卢克索、阿斯旺的名称，却仍然不清楚：

- 它们在哪里。
- 城市之间是什么空间关系。
- 每座城市代表怎样的旅行体验。
- 增加一座城市可能带来什么移动代价。

### 形成的设计方向

F1 通过：

城市地图 + 体验内容 + 图片 + 轻量反馈 + AI 对话

共同帮助用户探索陌生目的地。

### 初步 UI

- 地图城市节点。
- 城市信息浮层。
- 体验卡。
- 图片和背景说明。
- 交通连接入口。
- 相关事实说明。

### 收益

用户不需要先掌握旅行地理知识，才能开始理解不同选择。

### 代价与风险

- 内容过多可能增加认知负担。
- 地图可能过度占用阅读空间。
- 用户可能把地图连接误解成已核验交通。
- 图片吸引力可能被错误推断为正式旅行偏好。

### 当前结论

地图与体验共同建立认知，是已形成的产品方向。

但具体卡片尺寸、滑动布局和视觉风格仍待 UX-04。

【设计已收敛｜B、C】

## E-F1-03｜从轻量反馈到条件化偏好理解

### 设计初衷

用户在探索体验时，可以通过简单操作表达：

- 感兴趣。
- 不感兴趣。
- 想再了解。
- 有某种顾虑。

历史讨论涉及右滑／左滑体验卡的具体形式。

### 后来需要明确的问题

用户右滑某个体验，是否意味着：

- 已经喜欢该体验？
- 旅行一定要包含它？
- 已确认该城市？
- 将来不允许改变？

这些含义不能混淆。

### 形成的规则

轻量反馈主要是偏好或兴趣证据。

它不自动成为：

- 稳定的跨场景偏好。
- 已确认旅行决定。
- 草稿修改。
- 城市正式采用。

### 代表性案例

用户：

> 卢克索的文化体验很吸引我，但我担心转场太累。

正确理解应同时保留：

兴趣： 历史文化体验具有吸引力。

顾虑： 转场负担可能影响采用。

不能简化为：

> 用户一定要去卢克索。

也不能简化为：

> 用户不喜欢卢克索。

### 当前结论

反馈的方向和反馈所包含的条件必须分开保留。

【设计已收敛｜B；PRD-001、002 旁证 C】

## E-F1-04｜从浏览内容到适时揭示旅行代价

### 设计问题

用户可能因为某个体验产生强烈兴趣。

但该体验是否值得纳入旅行，还可能取决于：

- 交通。
- 所需停留。
- 与其他体验之间的冲突。
- 现实日期。
- 费用。
- 疲劳与转场复杂度。

### 形成的设计

探索界面允许用户查看城市间相关交通信息。

当事实会实质改变当前兴趣或选择时，AI 可以在有数据和权限的条件下进行必要核验。

### 当前边界

不能把所有交通细节都前置给用户。

也不能为了保持体验沉浸感而隐藏重要已知代价。

### 形成的取舍

探索以认知为中心，重大现实条件应在相关时机进入判断。

### 初步 UI 状态

交通连接卡、弹层及事实层级说明已讨论。

具体呈现方式仍待 UX-04 验证。

【设计已收敛｜B、C】

## E-F1-05｜卡片滑动的最终设计地位

这是需要避免错误归档的细节。

### 可以恢复的事实

F1 讨论过左右滑动体验卡的操作形式。

其目的是降低表达兴趣的交互成本。

### 同时存在的正式边界

PRD-001 没有把卡片形式设为不可改变的 P0 组件。

PRD 明确允许根据实际体验验证交互形式。

### 因此不能写成

> Owner 最终确认，ANTU 必须使用左右滑卡作为唯一探索机制。

### 当前正确状态

轻量反馈的业务行为：已收敛。

左右滑卡作为具体 UI：曾讨论的初步方案，仍需 UX-04 验证。

【候选 UI｜B、C】

# 9.3 F2｜决策缺口推荐与改道的设计演化

原讨论阶段：UX-02｜F2

相关正式机制：PRD-003、P01 下一步行动价值判断。

## E-F2-01｜从发现信息缺口到识别真实决策缺口

### 初始设计方向

用户当前不清楚什么，系统可以帮助补足什么。

例如：

- 不知道城市差异 → 解释差异。
- 喜欢多个城市但时间不够 → 比较取舍。
- 不清楚转场代价 → 查询或计算。
- 误解了旅行条件 → 优先纠错。

这一机制是 PRD-003 的核心。

### 后期发现的问题

系统不知道某项信息，并不意味着用户现在需要补齐它。

例如：

用户正在阅读古埃及文化内容。

系统尚不知道出发日期。

但用户可能完全没有进入具体行程安排阶段。

### 机制深化

需要区分：

1. 信息缺失。
2. 实际阻碍当前判断的决策缺口。
3. 值得现在解决的高优先级问题。

### 当前结论

决策缺口不是缺失字段清单。

缺口必须与用户当前真实目标有关。

【设计已收敛｜B；P01 旁证 C】

## E-F2-02｜从“按缺口推荐行动”到行动价值与成本比较

这是 F2 相关机制中证据最清晰的一条项目级演化链路。

### 原有机制

根据决策缺口推荐下一步行动。

### P01 机制审视发现的问题

即使正确识别了缺口，也可能存在多个合理动作。

例如用户担心转场太累，可以：

- 解释交通耗时。
- 查询现实交通。
- 比较两城和三城。
- 展示时间轴差异。
- 先询问用户最担心什么。
- 暂时不打断用户。

原有逻辑尚不能充分解释：

为什么现在应当执行其中某一个，而不是其他动作？

### 讨论过的竞争方向

| 方案        | 收益           | 代价            |
| --------- | ------------ | ------------- |
| 只按决策缺口选动作 | 简单、容易解释      | 难以比较多个合理行动    |
| 相对价值与成本判断 | 能考虑实际收益和用户负担 | 预测价值具有不确定性    |
| 每轮固定提供推荐  | 持续推动任务       | 可能产生重复打扰      |
| 后台准备、按需呈现 | 减少即时用户劳动     | 可能增加系统成本与过期结果 |
| 草案优先      | 较快形成具体讨论对象   | 可能造成锚定和返工     |

### 正式采用方向

P01 选择：

A｜行动资格和边界检查。

B｜相对价值与成本比较。

C｜反馈验证与策略迭代。

其中 B 是下一步行动选择的核心产品依据。

### 与 F2 的关系

这不是推翻 F2 的决策缺口机制。

而是将其从“行动选择的唯一依据”调整为“行动判断的重要输入”。

【P01 产品方向已裁决｜C】

### 重要限制

这是正式机制资料中的裁决，不能冒充已复核的 F2 原始 Owner 裁决。

## E-F2-03｜从持续主动推荐到允许不介入

### 原有设计追求

AI 应主动推动旅行规划，不只是被动聊天。

### 后来识别的问题

如果 AI 每轮都附加：

> 接下来可以比较交通。

用户可能持续只想了解文化，系统仍反复推送同一建议。

主动性会变成打扰。

### 当前方向

允许以下行动成为合法选择：

- 直接回答。
- 继续准备有价值的信息。
- 推荐下一步。
- 询问真正关键的条件。
- 延迟行动。
- 不额外介入。

### 明确不采用

每轮必须提供下一步建议。

P01 正式资料已经明确排除该强制规则。

【D｜有正式资料证据的不采用方向｜C】

### 尚未定稿

具体推荐触发阈值、忽略后的抑制规则、推荐呈现位置仍需 UX 验证。

【候选 UX｜C】

## E-F2-04｜从推荐下一步到允许随时改道

### 设计问题

AI 当前推荐：

> 先比较两城和三城交通代价。

但用户想：

> 我还是想先了解卢克索的历史。

如果系统坚持完成推荐任务，用户会失去对规划过程的控制权。

### 已形成规则

用户可以：

- 跳过推荐。
- 不响应。
- 改用地图。
- 改用对话。
- 直接请求旅行方案。
- 返回探索。
- 继续修改已经存在的方案。

### 推荐状态变化

根据 PRD-003：

用户跳过并改用其他入口时，原推荐应退出突出态，系统处理新输入并重新判断缺口。

### 当前结论

AI 可以推荐路径，但不能把推荐变成强制流程。

【设计已收敛｜B、C】

## E-F2-05｜双层响应的地位：候选而非最终控件规范

### 提出的 UI 思路

第一层回应用户明确需求。

第二层在有实际价值时，提供额外下一步建议。

### 它试图解决的问题

避免 AI 因过度关注长期规划而忽略眼前问题。

同时保留必要主动性。

### 尚待验证的问题

- 什么时候展示额外建议。
- 连续忽略后如何停止。
- 推荐是否只在对话底部。
- 是否每轮检查行动价值。
- 已在后台准备的内容还应不应该推荐。
- 何时完全不提供额外建议。

### 当前结论

明确需求优先是稳定原则。

双层响应的具体 UI 和触发策略仍是候选。

【候选方案｜C】

### 不得在后续归档中升级为

> AI 每次回答都必须显示一张下一步推荐卡。

## F2 演化小结

| 主题     | 初期方向    | 后期修正           | 当前状态    |
| ------ | ------- | -------------- | ------- |
| 缺口识别   | 找到未知信息  | 判断是否实际阻碍当前决策   | 已收敛     |
| 行动选择   | 缺口对应动作  | 比较合法动作的相对价值与成本 | P01 已裁决 |
| AI 主动性 | 主动推动规划  | 允许延迟、等待和不介入    | 已收敛     |
| 用户路径   | 系统推荐下一步 | 用户可跳过、拒绝和改道    | 已收敛     |
| 推荐 UI  | 条件化双层响应 | 需验证触发、抑制和展示    | 候选      |

# 9.4 F3｜骨架比较与取舍的设计演化

原讨论阶段：UX-02｜F3

主要来源：B；PRD-004、006、008 为 C 类旁证。

F3 的演化不仅涉及方案比较，还涉及三个后期重要补充：

选择即确认、重要版本历史、城市级恢复。

这三项不能因为它们并非最初 F3 的基础内容，就从归档中删除。

## E-F3-01｜从生成行程到生成具有实质差异的候选

### 最初需要解决的问题

当用户提出：

> 我有八天，想去开罗、卢克索和阿斯旺，怎么安排比较好？

AI 可以生成一套旅行骨架。

但单套生成方案容易产生两个问题：

- 用户缺乏理解其他选择的参照。
- AI 的首个方案可能对用户形成过强锚定。

### 形成的设计方向

当存在多种有意义的安排时，提供少量具有实质差异的完整骨架。

PRD-004 的基线是：

默认先比较两项有实质差异的候选，用户可以进一步展开更多。

### 这里的“实质差异”包括

- 城市组合。
- 城市顺序。
- 停留分配。
- 核心体验。
- 时间和转场代价。
- 已知费用。
- 与当前用户偏好的匹配关系。
- 需要承担的关键取舍。

### 当前规则

不是为了凑出两个方案而生成两个看起来不同、实际没有意义的变体。

如果只有一个有意义的可行方向，应如实说明。

如果当前硬约束下没有可行方案，应展示冲突，而不是编造解决方案。

【设计已收敛｜B、C】

### 不应重新引入

无论条件怎样，都强制生成固定数量的完整方案。

【R｜当前规则排除的行为；不证明它曾是被批准的旧方案】

## E-F3-02｜从方案优劣排序到解释旅行价值取舍

### 初期容易产生的问题

方案比较可能简化为：

> A 最推荐，B 次推荐。

或：

> A 更轻松，B 更丰富。

但用户未必知道这些结论究竟来自什么安排。

### 形成的机制

系统需要向用户解释：

获得什么。

放弃什么。

保留什么。

为了这些体验要付出什么代价。

### 代表性案例

八天埃及旅行：

方案 A： 两城，开罗与卢克索。

方案 B： 三城，增加阿斯旺。

比较应说明：

- 阿斯旺带来的体验类型。
- 增加阿斯旺可能产生的转场。
- 其他城市的停留是否被压缩。
- 哪些核心体验可以保留。
- 哪些体验可能因此被放弃。
- 哪些交通和费用信息尚未核验。

这里的内容属于比较机制示例，不是对实际埃及交通或费用的事实判断。

### 重要取舍

AI 可以提供有依据的推荐倾向，但不应以一个不透明的综合分数替代用户自己的价值选择。

### 当前结论

方案比较的核心不是“AI 认为哪个最好”，而是让用户理解每个方案的实际旅行代价和价值。

【设计已收敛｜B、C】

## E-F3-03｜从“先生成候选”到尊重用户明确请求

### 设计问题

有些用户希望深入探索。

另一些用户直接说：

> 给我安排一套八天的埃及旅行。

如果系统强制要求后者先完成所有体验卡和偏好探索，就违背其明确目标。

### 形成的方向

当已有条件足以产生有意义的骨架时，系统应提供实质性的规划结果。

必要未知可以标注，关键缺失可以澄清。

但不能把 F1 探索变成 F3 的强制前置步骤。

### 对 AI 主动性的影响

用户明确请求规划时，应优先准备实际方案。

只有在某项缺失确实阻碍当前重要判断时，才进行必要澄清。

【设计已收敛｜B、C】

## E-F3-04｜从候选选择到“选择即确认”

### 原讨论问题

用户看完两套方案，明确点击：

采用方案 B。

此时是否还需要系统弹窗：

> 确定采用方案 B 吗？

### 新增确认的收益

理论上可以减少误操作。

### 新增确认的代价

- 重复表达已经明确的决定。
- 增加点击成本。
- 打断连续规划。
- 把所有选择都当成高风险交易。
- 容易让用户误以为前一次采用没有正式含义。

### 后期收敛方向

当用户已经理解当前方案的重要取舍，并执行明确采用动作时：

选择本身表达确认意图。

### 保留的例外

- 对象不明确。
- 出现新的重要价值牺牲。
- 当前存在必须处理的硬约束。
- 必要事实核验不足以支持所声称的执行级结果。
- 提交基准版本发生变化。
- 涉及额外高风险权限。

### 当前状态

【B｜历史摘要记载 Owner 明确批准，原始裁决待补证】

### 被替换的默认方式

```
明确选择方案
    ↓
普通二次确认
    ↓
正式采用
```

转为：

```
明确选择方案
    ↓
满足必要权限与校验
    ↓
正式采用
```

如果发现新的重大取舍，应插入必要裁决，而不是恢复所有场景通用的二次确认弹窗。

## E-F3-05｜从“只保存当前方案”到重要历史版本可回看

### 新问题

旅行规划可能经历多轮明显改变。

例如：

V1：两城旅行。

V2：增加阿斯旺。

V3：重新调整城市停留。

用户后来可能想问：

> 我之前那个不去阿斯旺的方案是什么样的？

如果系统只保留当前方案，就难以恢复此前选择。

### 后期方向

重要的用户可见方案演化需要可回看。

但不要求所有 AI 内部临时推演都成为正式历史版本。

### 形成的区分

- 当前有效版本。
- 历史有效版本。
- 有回顾价值的重要候选。
- 临时假设与内部中间结果。

### 当前规则

有历史回顾价值，不等于一切中间计算都必须永久保存为用户可见版本。

【设计已收敛｜B】

### 工程影响

需要核查正式版本关系、快照或变更记录能否承接。

不能由 UX-02 直接指定存储结构。

## E-F3-06｜从旧版本回看扩展到旧版本恢复

### 新问题

用户打开旧方案，并不一定只是想了解过去。

他可能希望：

> 还是恢复以前的两城方案。

### 需要区分的动作

查看旧版： 不修改任何有效内容。

比较旧版： 分析差异。

恢复旧版： 发起正式业务修改。

### 后期形成的规则

恢复历史版本时，应当形成新的有效版本，而不是抹除后续历史。

例如：

```
V1 → V2 → V3
             │
             └── 恢复 V1 的内容
                      ↓
                      V4
```

V2、V3 仍保留。

### 为什么不能简单把历史指针倒回？

因为用户在 V2、V3 时可能作出过真实决定。

这些决定及其理由具有历史意义。

直接删除，会使系统无法解释旅行为什么发生了变化。

### 当前状态

【B｜历史摘要记载后期已确认，原始裁决待补证】

## E-F3-07｜从整份恢复扩展到城市级恢复

### 新场景

用户说：

> 我只想恢复卢克索之前的安排，其他城市都保持现在这样。

### 整份恢复为什么不够？

如果为了恢复卢克索而将整份旅行回到旧版：

- 开罗的新决定可能丢失。
- 阿斯旺的新安排可能被覆盖。
- 已确认的重要体验可能被删除。

### 后期补充

支持以某一城市为范围的历史恢复意图。

### 但发现另一项风险

虽然用户只修改卢克索，实际影响可能延伸到：

- 总天数。
- 相邻城市。
- 城市连接。
- 已确认体验。
- 交通和日期条件。

### 最终规则

恢复对象可以是局部的，但影响分析不能机械限制为局部。

### 授权边界

影响分析覆盖整趟旅行，不意味着系统可以自动修改整趟旅行。

如果修复需要牺牲其他已确认的重要体验，仍需要用户裁决。

【B｜历史摘要记载后期已确认，原始裁决待补证】

## E-F3-08｜从“恢复旧内容”到“恢复时重新检查现实条件”

### 新问题

旧版本可能基于之前的日期和交通信息形成。

用户现在恢复时，这些条件可能已经变化。

### 后期衔接

F6 和 UX-02.5 进一步明确：

- 读取历史内容。
- 判断旧事实是否适用于当前条件。
- 对相关部分重新核验。
- 标记已知冲突。
- 保留没有受到影响的决定。

### 当前结论

历史安排可以被重新采用，但旧事实不能因历史恢复而自动获得当前有效性。

【设计已收敛｜B、C】

## F3 演化小结

| 编号      | 关键改变            | 当前结论          |
| ------- | --------------- | ------------- |
| E-F3-01 | 生成方案 → 实质差异比较   | 默认先比较少量有意义候选  |
| E-F3-02 | 方案排名 → 解释得失     | 不透明评分不能替代价值判断 |
| E-F3-03 | 固定探索前置 → 明确需求优先 | 用户可直接请求骨架     |
| E-F3-04 | 选择后重复确认 → 选择即确认 | 校验与重要授权仍保留    |
| E-F3-05 | 只看当前方案 → 历史可回看  | 重要版本可追溯       |
| E-F3-06 | 历史回看 → 整份恢复     | 恢复形成新版本       |
| E-F3-07 | 整份恢复 → 城市级恢复    | 局部意图、关联检查     |
| E-F3-08 | 恢复旧内容 → 条件重核验   | 不复用不适用的旧事实    |

# 9.5 F4｜地图与时间轴编辑的设计演化

原讨论阶段：UX-02｜F4

主要来源：B；PRD-005、006、008 提供 C 类旁证。

F4 是交互形式、工作空间布局和业务操作机制同时发生明显收敛的阶段。

## E-F4-01｜从可视化行程展示到可操作旅行工作空间

### 起始问题

地图可以展示地理位置。

时间轴可以展示旅行顺序。

但如果它们只能阅读，用户仍然需要通过聊天反复描述每一次调整。

### 产品目标

用户能够直接通过地图和时间轴修改旅行骨架。

例如：

- 调整城市顺序。
- 增加或减少城市停留。
- 在相关位置查看交通代价。
- 查看编辑影响。

### 形成的规则

地图、时间轴和 AI 对话应共享正确的旅行状态。

同一修改应在相关视图中得到一致反馈。

### 当前状态

【设计已收敛｜B、C】

## E-F4-02｜从普通地图交互到浏览与编辑分离

### 新问题

地图上大量操作只是浏览。

例如：

- 点击城市。
- 查看体验。
- 打开交通信息。
- 切换城市浮层。

如果普通点击和真实修改混用，用户无法确定有没有改变行程。

### 形成的设计

默认允许自由浏览。

直接修改旅行时，通过明确编辑入口或具有清晰修改语义的操作进行。

### 被排除的做法

用户每次点击城市就自动把该城市加入行程。

### 产品理由

浏览和学习本身应当是低风险、低成本的。

正式旅行修改需要明确意图。

【设计已收敛｜B】

## E-F4-03｜从连续操作中的逐项分析到编辑会话

### 初期需要处理的问题

用户连续修改：

1. 卢克索增加一天。
2. 开罗减少一天。

最终总天数仍然保持八天。

如果第一步就要求进行完整全程重算，系统会对尚未完成的中间状态反复分析。

### 识别出的代价

- 增加等待。
- 增加系统调用。
- 打断用户。
- 对暂时不完整的草稿过早确认。
- 每次修改产生大量重复解释。

### 后期形成的机制

一个编辑会话中可以连续修改同一份草稿。

能够直接计算的变化即时显示。

整体影响在适当时机集中校验。

### 当前结论

即时确定性反馈与复杂影响分析分层。

【B｜历史摘要记载 Owner 明确认可，原始裁决待补证】

### 被替换的默认处理方式

不是每次修改后都必须完整重算和确认。

但已知重大冲突仍然需要及时提示。

## E-F4-04｜从地图和聊天分别处理，到统一草稿

### 新问题

用户可能先在时间轴操作，再用自然语言继续修改。

如果两个入口分别维护旅行，状态会互相冲突。

### 后期形成的规则

在同一编辑会话中：

- 地图操作。
- 时间轴操作。
- 明确的自然语言编辑指令。

都应修改同一正确草稿。

### 重要例外

普通问答和假设不进入草稿。

例如：

> 卢克索四天会不会太多？

不等于：

> 把卢克索缩短一天。

### 当前结论

多入口共享编辑对象，语义决定是否写入。

【设计已收敛｜B】

## E-F4-05｜从平均分屏到地图主工作空间

### 可恢复的早期布局问题

地图、内容、对话和旅行摘要都需要展示。

不同区域如何分配空间，是后期专门讨论的问题。

### 历史摘要记载的 Owner 要求

地图不应被右侧信息区挤压成五五分屏。

地图应占据更大的主要工作区域。

### 后期形成的布局

- 顶部横向旅行时间轴。
- 左侧／中央大地图。
- 右侧相对紧凑的信息区。
- 地图内部城市浮层。
- 可持续使用的 AI 对话。

### 产品理由

旅行的地理关系与直接编辑，需要足够可操作空间。

右侧信息区承担解释旅行价值的职责，而不应与地图平均争夺面积。

### 当前状态

【B｜历史摘要记载 Owner 明确提出，原始布局裁决待补证】

### 尚未确定

具体尺寸、响应式断点、对话面板形态和移动端布局。

不能将文字原型变成最终像素级规格。

## E-F4-06｜从城市信息侧栏到整体／城市双焦点摘要

### 初期问题

用户点击卢克索，右侧应该显示什么？

如果只显示景点介绍，会与地图浮层产生内容重复。

### 后期形成的方向

右侧信息区具有两个主要焦点。

整趟旅行摘要：

- 当前旅行骨架。
- 核心体验收益。
- 时间和交通代价。
- 当前未知和问题。
- 与用户目标相关的取舍。

当前城市摘要：

- 城市停留。
- 重要体验。
- 用户相关顾虑。
- 城市局部问题。
- 对整趟旅行的影响。

### 切换机制

- 点击城市，切换城市摘要。
- 关闭城市浮层，可返回整体摘要。
- 从信息区返回整体，不必强制关闭地图浮层。

### 当前结论

信息焦点和浏览焦点可以相关联，但不必完全绑定。

【设计已收敛｜B】

## E-F4-07｜从“修改后再次确认”到完成编辑表达提交意图

### 问题

用户已在编辑会话中明确进行了多项修改。

如果完成编辑后再出现一个通用确认弹窗，会再次重复用户已表达的意图。

### 后期方向

「完成编辑」本身是本轮修改的正式提交意图。

满足必要权限和校验后，不增加普通二次确认。

### 必须保留的边界

- 当前草稿与有效方案的基础版本检查。
- 硬约束检查。
- 新重大价值牺牲的必要授权。
- 当前事实核验的适用范围。
- 提交失败时的成果保护。

### 当前状态

【设计已收敛｜B】

### 不得错误推导

> 点击完成编辑之后，任何影响都可以直接提交。

“完成编辑”并不是无限授权。

## E-F4-08｜从编辑中的假设提问到非破坏性预览

### 新问题

用户正在编辑草稿 B 时问：

> 如果不去阿斯旺呢？

这是一项假设，而不是明确删除操作。

### 后期衔接

F5 进一步形成 A/B/C 关系。

### 最终规则

- B 保留。
- C 基于 B 推演。
- 只有用户明确要求时，才把 C 的改变纳入 B。
- C 不自动成为有效方案 A。

### 当前状态

【设计已收敛｜B】

## E-F4-09｜从当前页面操作到跨会话可恢复编辑

### 后期新问题

用户可能编辑到一半退出。

如果草稿只存在于前端临时交互中，之前的工作会丢失。

### UX-02.5-A 补充

需要恢复：

- 已保存草稿。
- 最后成功保存的操作进度。
- 当前任务上下文。
- 必要的事实重核验。

### 当前结论

暂停工作不等于完成或放弃编辑。

【设计已收敛｜B】

## E-F4-10｜从普通提交到异常安全提交

### 后期发现

提交期间可能断网、重复点击或存在并发版本变化。

### UX-02.5-C 补充

- 结果未知应核实权威状态。
- 重复请求不能造成重复修改。
- 旧草稿不能静默覆盖新有效版本。
- 校验失败保留草稿和原有效方案。

### 当前结论

编辑安全不仅涉及 UI 撤销，也涉及权威提交结果和版本一致性。

【后期设计已收敛｜B；工程待核查】

## F4 演化小结

| 主题   | 后期有效规则          | 必须避免的回退      |
| ---- | --------------- | ------------ |
| 地图定位 | 主工作空间，可浏览与编辑    | 地图仅作静态装饰     |
| 工作模式 | 默认浏览，明确编辑       | 点击即修改        |
| 编辑过程 | 连续操作同一草稿        | 每项都全面重算、重复确认 |
| 多入口  | 地图、时间轴、对话共享草稿   | 各入口维护不同方案    |
| 布局   | 顶部时间轴＋大地图＋右侧信息区 | 无依据地回到机械五五分屏 |
| 右侧内容 | 整趟旅行／城市摘要       | 只重复城市列表      |
| 假设   | 独立预览            | 假设覆盖草稿       |
| 完成编辑 | 表达整组提交意图        | 普通重复确认       |
| 恢复   | 保存和恢复未完成工作      | 离开页面即丢失      |
| 异常   | 保留成果、核实提交状态     | 超时就认定失败      |

# 9.6 F5｜假设、纠错与重算的设计演化

原讨论阶段：UX-02｜F5

主要来源：B；PRD-002、006、008 提供 C 类旁证。

F5 最重要的演化是：

从将用户的新想法理解为新的规划修改，转向支持非破坏性假设，并对真正需要修改的内容进行有限范围重算。

## E-F5-01｜从“如果怎样”到独立假设语义

### 设计问题

用户说：

> 如果不去阿斯旺呢？

可能只是想了解这种安排的结果。

如果系统立即删除阿斯旺，就错误扩大了用户意图。

### 已形成的区分

假设：

> 如果不去阿斯旺呢？

明确修改：

> 这次确定不去阿斯旺，把它从当前方案里移除。

纠错：

> 我刚才不是说要删除阿斯旺，只是想比较一下。

三者不具有相同的状态效果。

### 当前规则

假设可以触发分析、比较和临时预览。

但不自动修改有效旅行。

### 重要原因

用户应该能够安全地讨论各种可能性，而不担心每次提问都会破坏之前的决定。

### 当前状态

【设计已收敛｜B、C】

## E-F5-02｜从独立 What-if 功能到复用现有工作空间

### 曾讨论的设计问题

是否需要为假设建立专门的页面或模式？

### 独立方案的潜在收益

- 可以集中展示假设。
- 可以与普通编辑进行视觉隔离。
- 可以组织多个可能版本。

### 代价

- 与 F3 方案比较重复。
- 与 F4 编辑机制重复。
- 增加模式切换。
- 可能形成第二套临时方案管理逻辑。
- 用户需要理解更多页面和状态。

### 后期收敛

不专门建立独立 What-if 页面或业务模式。

假设功能复用已有：

- AI 对话。
- 地图。
- 时间轴。
- 方案比较。
- 编辑草稿。
- 确认和版本管理。

### 必须保留的区别

不建立独立页面，不意味着不需要隔离假设状态。

### 当前状态

【设计已收敛｜B，原始方案取舍过程待补证】

### 废弃方向

独立 What-if 页面作为 F5 默认必经入口。

【B｜历史摘要可恢复其被排除的最终方向，原始候选细节待补证】

## E-F5-03｜从单一“当前方案”到 A/B/C 关系

### 新问题

用户可能同时存在：

- 已经正式采用的旅行。
- 尚未提交的编辑草稿。
- 正在讨论的假设。

如果统一叫“当前方案”，系统可能把三种内容互相覆盖。

### 后期机制

A：有效方案。

B：当前编辑草稿。

C：基于正确对象形成的假设预览。

### 核心关系

```
有效方案 A
    │
    └── 编辑草稿 B
            │
            └── 假设预览 C
```

### 正确行为

- 用户查看 C，B 不变。
- 用户放弃 C，返回 B。
- 用户把 C 加入编辑，才更新 B。
- 用户完成编辑，才按相应流程更新有效旅行。
- 没有编辑会话时，假设可以直接基于 A。

### 关键价值

保护用户自由探索可能性的空间，同时维持正式旅行的权威性。

### 当前状态

【设计已收敛｜B】

### 重要工程限制

A/B/C 是解释业务关系的设计代号，不能直接认定为正式 Schema 中三个独立状态名称。

## E-F5-04｜从假设比较到多轮假设连续性

### 新用户行为

用户先问：

> 如果不去阿斯旺呢？

随后：

> 如果保留阿斯旺，但卢克索只待两天呢？

再问：

> 哪个更适合我？

### 新的机制要求

系统需要知道：

- 第一种假设的基准是什么。
- 第二种假设是否替代第一种。
- 两者是否应该并列比较。
- 当前正在讨论哪一个。
- 哪些条件已经被用户明确改变。
- 哪些只是临时推演。

### 风险

如果只依赖最后一句话，可能出现：

- 将两个假设混成一个。
- 错误使用有效版本。
- 将假设性预算写成硬约束变化。
- 自动删除用户原本要保留的城市。

### 当前方向

多轮假设需要正确的基准与指代管理。

### 仍待补证

原讨论中究竟尝试过哪些具体多假设 UI，以及它们的取舍顺序，目前原始消息不足。

因此不能声称已裁决固定的多假设标签、命名或展示结构。

【设计机制已收敛｜B；具体 UI 待验证】

## E-F5-05｜从纠错作为新指令到纠正原操作

### 典型问题

用户：

> 开罗减少两天。

随后：

> 不对，我说的是减少一天。

如果系统把第二句话当作新的增量命令，就可能累计减少三天。

### 正确机制

系统应识别：

这是对原意图的纠正，而不是新增一次减少操作。

### 需要进一步区分

- 原操作尚未执行。
- 原操作已写入草稿。
- 原操作已正式采用。
- 原来错误的是用户偏好理解。
- 原来错误的是外部事实。

### 不同情况的后果

尚未执行： 修正待处理意图。

草稿内： 修正草稿中的对应变化。

已确认： 通过合法变更形成新的有效版本。

偏好理解： 修正相关语义，不自动改变行程。

外部事实： 更新证据和受影响核验结果。

### 当前结论

纠错范围必须与真正被纠正的对象一致。

【设计已收敛｜B、C】

## E-F5-06｜从全局重新生成到有限范围重算

### 起始问题

旅行安排之间存在连锁影响。

用户改变卢克索停留，可能影响总天数和相邻交通。

如果每次都重新生成整份行程，会造成大量无关修改。

### 全局重生成的潜在收益

- 可以重新优化整体方案。
- 计算逻辑表面上较简单。
- 在结构大幅改变时可能有必要。

### 代价

- 用户已确认的无关决定可能丢失。
- 新旧差异难以解释。
- 计算与等待成本高。
- AI 可能重新解释此前偏好。
- 用户容易陷入重复规划。

### 正式 PRD 方向

优先识别受影响关系。

在 MVP 可支持范围内重算相关部分，必要时重算整份骨架。

### 重要取舍

有限重算不是禁止全局分析。

如果修改影响整趟旅行，仍可能需要扩大分析范围。

但：

扩大分析范围，不自动扩大实际修改权限。

### 当前状态

【设计已收敛｜B、C】

### 被排除的默认方式

任何小变化都不加区别地完全重生成整趟旅行。

## E-F5-07｜从 AI 自动选择最优修复到保留用户价值取舍

### 新问题

用户缩短旅行天数。

AI 可能找到一种技术上方便的修复：

删除某项已确认的重要体验。

### 为什么不可以直接执行？

因为：

系统优化的时间或计算成本，不一定是用户最重视的价值。

用户可能宁愿：

- 牺牲一座城市。
- 提高预算。
- 接受更长转场。
- 保留某项核心体验。

### 后期规则

AI 可以：

- 识别冲突。
- 准备修复。
- 比较修复的代价。
- 推荐有依据的方案。

但重要价值牺牲仍需用户授权。

### 当前状态

【设计已收敛｜B、C】

## E-F5-08｜从用户假设到事实变化触发相关重算

### 新问题

重算不仅由用户主动修改触发。

例如：

用户后来提供具体日期。

此前与日期相关的交通事实可能不再适用。

### 后期补充

- 识别条件依赖。
- 重新核验受影响的事实。
- 对相关安排重新计算。
- 保留仍然成立的决定。
- 将新冲突关联正确对象。

### 当前结论

用户选择变化与外部事实变化，都会影响规划，但不拥有相同的授权语义。

外部事实变化不能直接替用户作出新的价值决定。

【设计已收敛｜B、C】

## F5 演化小结

| 编号      | 关键演化                   | 当前结论         |
| ------- | ---------------------- | ------------ |
| E-F5-01 | 假设提问 → 独立推演            | 不自动修改有效旅行    |
| E-F5-02 | 独立 What-if 页面 → 复用工作空间 | 无专用必经模式      |
| E-F5-03 | 单一当前方案 → A/B/C         | 草稿、假设、有效方案隔离 |
| E-F5-04 | 单轮假设 → 多轮连续比较          | 正确维护基准与指代    |
| E-F5-05 | 纠错作为新命令 → 定位原操作        | 不错误累计修改      |
| E-F5-06 | 全局重生成 → 有限重算           | 必要时扩大分析      |
| E-F5-07 | AI 自动优化 → 用户保留重要取舍     | 不擅自牺牲体验      |
| E-F5-08 | 仅用户修改触发 → 条件变化也触发      | 事实重核验不等于用户确认 |

# 9.7 F6｜关键确认、保存与回顾的设计演化

原讨论阶段：UX-02｜F6

主要来源：B；PRD-007、008、009 提供 C 类旁证。

F6 的设计演化主要集中在：

确认语义、规划深度、现实依赖、日期变化、版本历史及异常安全。

## E-F6-01｜从重要决定确认到避免重复确认

### 最初的合理要求

重要旅行决定不能由 AI 擅自修改。

### 实际产生的问题

如果用户每次明确选择之后还需要完成一次普通确认，系统会变成高摩擦的多级审批流程。

### F3/F4 的后期影响

- F3 形成“选择即确认”。
- F4 形成“完成编辑作为本轮提交意图”。

### F6 最终承接

确认应当关注真实的重要决定，而不是机械增加确认次数。

### 当前规则

对象明确、重要影响已呈现、必要条件满足时，可以根据明确采用动作完成合法提交。

有新的重大牺牲时，仍须取得相应授权。

【设计已收敛｜B】

## E-F6-02｜从“确认行程”到规划与现实核验双维度

### 起始问题

用户确认一套旅行骨架。

但具体日期和交通条件仍然未知。

### 两种错误处理

过度阻断：

没有全部现实核验，就不能确认任何规划。

过度承诺：

用户已经确认骨架，因此所有安排都可执行。

### 后期机制

将以下两者区分：

规划决定是否已采用。

现实条件核验到了什么程度。

### 核心规则

已确认骨架可以同时存在待核验的现实条件。

但不能冒充全程执行已被证实。

【设计已收敛｜B；PRD-008 旁证 C】

## E-F6-03｜L1/L2/L3 从规划深度分析到非强制关卡

### 曾采用的分析框架

历史摘要记录，讨论中曾使用三个规划深度：

L1： 城市骨架层次。

L2： 体验和活动安排层次。

L3： 具体日期和执行细节层次。

这些是恢复出的概略含义，完整原始定义待补证。

### 曾面对的设计取舍

是否按照三个层级设置依次完成的确认和核验流程？

### 固定层级机制的收益

- 容易解释规划进度。
- 可以在较粗层次降低细节负担。
- 方便区分不同阶段需要的事实。

### 后来发现的问题

- 用户不按固定顺序规划。
- 某些 L2 内容也可能高度依赖日期。
- 某些具体信息可以提前使用。
- 强制层级确认会增加操作成本。
- 无法解决后来现实条件变化的问题。

### 后期方向

保留 L1/L2/L3 作为理解规划深度的分析工具。

不设为三个必须依次通过的确认关卡。

### 当前结论

按当前决定的条件依赖进行必要确认，不以固定层级阻断规划。

【设计已收敛｜B，原始 Owner 裁决待补证】

### 特别注意

规划深度 L1/L2/L3 与 PRD §5.3 的权限分级 L0–L3 完全不同。

不能在技术规格中混用。

## E-F6-04｜从要求确定日期到允许无日期渐进规划

### 新问题

用户可能已经明确城市、体验与停留，但仍不知道出发日期。

### 原本可能采取的严格方式

要求先确定日期，再允许形成比较完整的旅行安排。

### 代价

用户会被迫过早决定日期。

同时大量与日期无关的规划无法保存。

### 后期形成的规则

没有具体日期，不是所有旅行规划的阻断条件。

可以在当前条件允许的范围内：

- 探索。
- 比较骨架。
- 分配停留。
- 讨论重要体验。
- 形成条件化安排。
- 确认当前层次的旅行决定。

### 仍需保留

具体班次、开放时间和其他依赖日期的执行事实不能被伪装为已核验。

【B｜历史摘要记载 F6 后期 Owner 认可】

## E-F6-05｜从“日期以后再查”到提前识别高影响日期依赖

### 新的风险

假设用户为了某项重要体验，决定增加一座城市。

但这项体验高度依赖日期。

如果系统直到用户最终确定日期时才发现不成立，可能导致大量规划返工。

### 两种极端方案

全部前置：

所有活动和交通都必须先核验日期。

缺点是严重增加前期负担。

全部后置：

等用户确定日期后再检查所有执行条件。

缺点是重大问题可能发现过晚。

### 后期形成的取舍

高影响日期依赖前置识别。

低影响未知可以保留到更合适的阶段。

### 判断依据

- 当前用户正在作出的决定。
- 事实是否可能显著改变该决定。
- 是否具备可靠数据。
- 用户是否能够提供必要条件。
- 提前处理能否避免重大返工。

### 当前结论

需要提前的是会改变当前重要判断的条件，而不是所有未知细节。

【B｜历史摘要记载 Owner 认可，原始裁决待补证】

## E-F6-06｜从日期变化后全程重做，到受影响部分重核验

### 新问题

用户已经完成较多规划，后来才确定日期。

### 全程重做的代价

- 丢失有效的城市选择。
- 破坏此前确认的重要体验。
- 重复计算与搜索。
- 让用户重新解释相同偏好。
- 增加不必要的选择负担。

### 后期方向

1. 识别日期相关依赖。
2. 检查旧事实适用性。
3. 重新核验受影响部分。
4. 保留不受影响的决定。
5. 对新冲突进行对象级标注。
6. AI 准备必要修复建议。
7. 重要新取舍交还用户。

### 当前结论

现实变化触发变更影响管理，不自动清空整趟旅行。

【设计已收敛｜B、C】

## E-F6-07｜从单一“是否可行”到事实状态分层

### 新问题

用户看到某段交通信息时，实际可能属于：

- 地图上的地理连接。
- 有依据的概略耗时。
- 指定日期已核验的班次。
- 真实可购买交通。
- 数据暂时未知。
- 旧来源已经失效。
- 已经确认存在冲突。

如果统一显示为“可行／不可行”，容易误导。

### 后期形成的原则

事实应显示当前实际达到的核验层级和适用条件。

### 特别区分

查询失败不是无服务。

没有日期不是已知冲突。

用户确认不是现实事实成立。

### 当前状态

【设计已收敛｜B；PRD-007 正式旁证 C】

## E-F6-08｜从一次性警告到持续定位冲突

### 设计问题

某段交通存在真实冲突。

系统只弹出一次警告。

用户关闭后继续浏览，可能不再知道问题在哪里。

### 后期方向

冲突与相关业务对象关联。

在适用工作空间中持续可见：

- 地图。
- 时间轴。
- 右侧整体信息区。
- 城市摘要。
- 相关修改或方案比较。

### 需要同时防止

- 已解决问题继续显示。
- 草稿冲突误报为有效方案冲突。
- 未知条件全部标成严重错误。
- 切换页面后冲突无故消失。

### 当前结论

冲突属于旅行状态与事实管理的一部分，而不仅是一次性提示文案。

【设计已收敛｜B】

## E-F6-09｜从保存当前结果到保存决定与演化依据

### 起始问题

如果系统只保存一份当前旅行文本，很难解释：

- 用户之前为什么排除某座城市。
- 哪些体验已经确认。
- 什么时候改变过天数。
- 哪些事实影响过原决定。
- 当前版本从哪一份历史安排演化而来。

### 后期方向

保留：

- 当前有效安排。
- 重要决定范围。
- 用户授权依据。
- 版本关系。
- 相关变化。
- 未解决问题。
- 事实核验的适用范围。

### 重要价值

帮助用户在长期规划中回看和修改。

同时为 AI 继续理解用户提供真实依据。

### 当前结论

保存的是持续旅行决策成果，而不只是最终一段行程文字。

【设计已收敛｜B、C】

## E-F6-10｜从普通确认结果到提交安全与成果保护

### 后期 UX-02.5 新增问题

- 提交超时。
- 用户重复点击。
- 旧草稿覆盖新版本。
- AI 校验失败。
- 事实工具不可用。
- 跨会话恢复不完整。

### 形成的保护方向

系统要以权威业务状态判断实际提交结果。

不能因为网络超时就直接宣称失败。

也不能让同一次业务修改重复生效。

### 当前结论

保存与确认的正确性不仅取决于用户点击，还取决于实际状态更新是否可靠完成。

【后期设计已收敛｜B；工程待核查】

# 9.8 UX-02.5｜后期补充机制的设计演化

原讨论阶段：UX-02.5-A/B/C/D

本阶段与前面六条 Flow 不同。

它不是从零开始设计一种新的用户任务，而是检查：

当已有六条 Flow 被组合使用，并遇到中断、失败、版本变化和现实数据变化时，原来的设计是否依然成立。

## E-2.5-01｜从恢复对话到恢复实际旅行工作

原阶段：UX-02.5-A

### 起始问题

用户退出后再回来，系统是否只需要恢复聊天和当前旅行？

### 新场景

用户已经完成多次编辑，但尚未点击「完成编辑」。

三天后回来。

### 发现的问题

只恢复聊天可能无法恢复：

- 未提交草稿。
- 草稿的基础版本。
- 用户本轮修改。
- 最后操作对象。
- 尚未完成的决策问题。

### 后期要求

恢复最后成功保存的工作进度。

既要恢复旅行成果，也要恢复当前任务所需的上下文。

### 当前结论

跨会话恢复是任务续接，不是简单的聊天记录回放。

【B｜历史摘要记载 Owner 明确要求】

### 原始证据缺口

恢复最后一步的完整 Owner 原话和对应 UI 讨论待补证。

## E-2.5-02｜从恢复旧结论到检查现实事实是否仍然适用

原阶段：UX-02.5-A

### 新问题

上次会话已经核验过交通。

但用户几天后回来，相关事实可能已经失效。

### 两种错误方式

完全不核验：

沿用过期事实。

每次全量重算：

耗费大量资源，甚至造成无关结果变化。

### 后期形成的方向

恢复旅行成果。

独立判断相关事实的适用性。

对需要重新确认的部分进行核验。

### 重要区别

恢复业务决定，不意味着恢复旧事实的当前有效性。

### 当前状态

【设计已收敛｜B】

## E-2.5-03｜从每条 Flow 独立运行到跨流程状态隔离

原阶段：UX-02.5-B

### 新场景

用户正在 F4 编辑。

进入 F1 右滑体验。

再进入 F5 比较假设。

最后返回 F4。

### 风险

- 兴趣被误加入行程。
- 假设覆盖草稿。
- 浏览焦点成为编辑目标。
- 旧版本被当作当前有效版本。
- 原编辑任务丢失。

### 后期形成的规则

工作上下文与业务修改分离。

### 具体效果

- 查看不等于修改。
- 兴趣不等于采用。
- 假设不等于草稿修改。
- 历史查看不等于恢复。
- 页面切换不等于编辑完成。
- AI 回答不等于用户确认。

### 当前状态

【设计已收敛｜B】

当前可见历史材料中，Owner 曾同意进入后续异常保护阶段，但不能据此自动推断 B 中每项子规则的原始批准文本均已取得。

## E-2.5-04｜从错误提示到真正保护用户成果

原阶段：UX-02.5-C

### 原来容易忽略的问题

设计异常时只考虑：

> 网络错误，请重试。

但用户更关心：

- 刚才编辑的内容还在不在？
- 旅行有没有被改掉？
- 提交实际上成功了吗？
- 再次提交会不会重复修改？
- 之前确认的方案能否恢复？

### 新的机制要求

异常处理必须保护：

- 当前有效旅行。
- 已成功保存的编辑草稿。
- 未解决的任务状态。
- 正确的事实核验结果。
- 版本关系。
- 用户实际授权的范围。

### 当前结论

异常处理不只是 UI 文案，而是业务状态安全。

【后期设计已收敛｜B】

## E-2.5-05｜从“请求超时＝失败”到“提交结果未知”

原阶段：UX-02.5-C

### 新问题

用户点击完成编辑，网络随后断开。

但服务端可能已经提交成功。

### 识别出的风险

如果前端直接显示失败，用户可能再次提交同一修改。

如果前端直接显示成功，则可能虚报业务结果。

### 后期规则

- 不根据网络超时直接判断业务结果。
- 查询权威状态。
- 防止重复业务效果。
- 根据实际情况反馈成功、失败或尚不能确定。

### 当前结论

前端没有收到结果，不等于服务端没有执行。

【后期设计已收敛｜B；工程待核查】

## E-2.5-06｜从单设备编辑到旧草稿与新版本冲突保护

原阶段：UX-02.5-C

### 新场景

设备一基于 V3 编辑。

设备二形成 V4。

设备一再次提交旧草稿。

### 风险

旧草稿可能覆盖最新有效决定。

### 后期规则

- 保留用户旧草稿。
- 检查当前有效版本。
- 识别不兼容变化。
- 不静默覆盖新版本。
- 对重大取舍要求必要授权。

### 不应额外推断

所有并发修改都必须自动合并。

自动合并不一定尊重用户的真实价值判断。

【后期设计已收敛｜B；工程待核查】

## E-2.5-07｜从单项机制设计到正式规格一致性检查

F1–F6 及后期补充已基本完成产品行为讨论。

### 早期问题

- 待核验条件。

地图负责空间与直接操作。

右侧信息区负责解释当前安排意味着什么。

### 需要验证的代价

信息区可能承载内容过多，需要控制展示层级。

### 当前状态

【交互职责已收敛｜B；视觉组织待 UX-04】

# 9.16 第 9 部分最终归档结论

UX-02 的演化，可以概括为五条持续强化的主线。

第一条：从系统驱动的规划步骤，转向以用户当前目标为中心的持续决策。

用户不必先填完整问卷，也不必沿 F1–F6 的固定顺序前进。AI 可以主动帮助，但推荐必须有价值且允许跳过。

第二条：从信息展示和方案生成，转向可理解、可比较的旅行价值取舍。

地图、体验、交通、时间轴和方案比较共同帮助用户理解真实得失，而不是只接受模型输出的“最佳方案”。

第三条：从一次性方案结果，转向持续可编辑、可回顾的旅行状态。

用户可以连续修改、提出假设、纠错、查看历史，必要时整份或局部恢复，而不丢失已确认的重要决定。

第四条：从简单确认，转向确认、事实和授权的清晰分离。

选择即确认不是取消校验。无日期规划可以进行，但不能伪造现实可执行性。重要新取舍仍然属于用户。

第五条：从成功路径设计，转向跨 Flow、跨会话和异常情况下的成果保护。

用户已经形成的旅行成果不能因为切换页面、AI 失败、网络中断或版本变化而被错误覆盖。

### 本章最重要的历史保存原则

后期明确结论优先，但早期方案及被修正原因仍应保留。

已确认的行为规则继续有效，但没有取得原始消息的 Owner 裁决必须如实标记。

尚待验证的 UI 和工程能力，不应被伪装成最终定稿或已经实现。
