# 3.1 F3 的产品定位与任务目标

## 3.1.1 F3 要解决什么问题？

经过 F1、F2，用户已经对目的地形成一定认知，也可能表达了具体的兴趣、顾虑和旅行条件。

但是：

知道自己喜欢哪些地方，不等于知道怎样把它们安排成一趟旅行。

例如，用户可能希望：

- 去开罗看金字塔和其他古埃及历史文化内容。
- 去卢克索体验卡纳克神庙、帝王谷。
- 考虑阿斯旺的尼罗河相关体验。
- 整趟旅行大约八天。
- 不希望转场过于频繁。
- 尽量保留重要体验。

此时存在实际取舍：

- 是否需要三座城市？
- 如果只去两座城市，会放弃什么？
- 如果去三座城市，会压缩哪些停留？
- 城市顺序是否影响交通负担？
- 增加一座城市后，其他城市的体验时间如何变化？
- 哪些安排只是暂定，哪些已经经过现实条件核验？

传统行程生成容易直接提供一份“八天埃及游”。

但这不能充分回答用户：

为什么应该这样安排，而不是另一种安排？

因此 F3 的核心职责是：

把旅行选择转换为具体、可比较、可修改的旅行骨架，让用户理解每种安排对整趟旅行的实际收益与代价，并能够作出明确取舍。

【设计已收敛｜B、C】

## 3.1.2 什么是旅行骨架？

在 F3 的语境中，旅行骨架主要包括：

- 旅行的城市组合。
- 城市之间的顺序。
- 各城市的大致停留天数。
- 主要跨城连接或交通方式。
- 需要保留的核心体验方向。
- 相关约束、假设及待核验条件。

旅行骨架并不必然包含：

- 所有景点的精确小时安排。
- 具体酒店预订。
- 国际航班的实时联合优化。
- 实际购买的交通票。
- 完整逐项预算。
- 全部活动的预订确认。

旅行骨架是用户逐步建立和维护整趟旅行的重要规划对象，不等于已经具备完整执行条件的旅行订单。

### 既有 PRD 的首版边界

PRD V0.1 明确将 MVP 聚焦于有限埃及城市集合的城市组合、顺序、停留和主要跨城交通。

完整逐日景点排程、交易、住宿深选等并非该 PRD 的首版承诺。

# 3.2 F3 的进入条件与用户场景

F3 不要求用户必须完整完成 F1 或 F2。

## 3.2.1 场景 A｜用户主动要求生成旅行骨架

典型输入：

> 这些地方我都挺喜欢的，帮我看看怎么安排吧。

用户已经形成一定城市兴趣，但尚未确定最终组合。

### 系统应做什么？

1. 读取现有有效旅行信息。
2. 识别当前想解决的旅行安排问题。
3. 判断是否有足够条件进行初步规划。
4. 必要时澄清真正影响骨架的关键条件。
5. 在当前已知范围内形成有意义的候选方案。
6. 解释每个方案的实际旅行取舍。

### 不应发生

- 要求用户先完成全部体验卡。
- 只根据热门路线生成一个默认方案。
- 把用户对城市的兴趣当作城市已经确认。
- 在没有日期时伪造精确交通班次。

【设计已收敛｜B、C】

## 3.2.2 场景 B｜用户已有明确旅行天数

例如：

> 我只有八天，想去开罗、卢克索，阿斯旺也想考虑一下。

此时系统已经知道一个重要资源边界。

但仍需要正确区分：

- 八天是明确的总天数，还是大概估计？
- 三座城市都是用户已确认的，还是只是感兴趣？
- 哪些体验更重要？
- 是否已有入离境条件？
- 哪些交通信息可以核验？

如果信息足够，可以直接比较。

如果只有一个关键条件会显著改变方案，才需要针对性澄清。

## 3.2.3 场景 C｜用户已有一份有效旅行骨架

用户可能已经确认过：

开罗 → 卢克索。

现在希望考虑增加阿斯旺。

此时 F3 不是从零开始。

系统需要：

1. 读取当前有效骨架。
2. 识别用户正在考虑的变化。
3. 以原方案作为比较基准。
4. 计算增加阿斯旺后会改变哪些安排。
5. 解释新增收益以及被挤占的体验和时间。
6. 保留原有效骨架，直到新的改变获得必要授权。

【设计已收敛｜B、C】

## 3.2.4 场景 D｜用户从 F4 编辑回到方案比较

用户正在编辑旅行草稿，发现某次调整产生了重要取舍。

例如：

> 如果把卢克索增加一天，整趟旅行会有什么不同？

F3 的比较能力需要能够围绕当前正确的基准工作。

可能的比较基准包括：

- 当前有效方案。
- 正在编辑的草稿。
- 某个假设预览。
- 用户明确指定的历史版本。

不能默认所有比较都基于最新有效方案，也不能把任何预览当作已经应用的修改。

这一边界在 F4、F5 后期得到进一步细化。

【设计已收敛｜B】

## 3.2.5 场景 E｜用户恢复历史方案

例如：

> 我还是觉得前一个八天方案比较舒服。

或：

> 我想把卢克索恢复成之前三天的安排，但其他城市保持现在这样。

这会触发不同的恢复范围：

- 整趟旅行版本恢复。
- 局部城市级恢复。

F3 后期对此形成较完整的交互与冲突管理要求。

【历史摘要记载 Owner 已确认｜B】

## 3.2.6 场景 F｜用户暂时没有具体旅行日期

用户可能已知道：

- 想去哪些城市。
- 最重视哪些体验。
- 想怎样分配停留天数。
- 大概接受什么旅行节奏。

但仍不知道具体出发日期。

后期 F6 明确：

日期未知不应该普遍阻断旅行骨架及有条件的深度规划。

系统可以在可验证的范围内进行结构性检查，保留与具体日期相关的待核验事项。

【Owner 已确认｜A：F6 后期】

# 3.3 F3 的端到端主流程：从规划请求到明确取舍

本节还原 F3 的完整代表性路径。

以下埃及八天案例用于说明产品机制，不代表已经完成真实交通、费用或活动开放核验。

## 3.3.1 F3-S01｜用户提出规划请求

### 用户输入

> 我有八天，开罗和卢克索比较想去，阿斯旺也挺感兴趣。帮我看看怎么安排。

### 系统理解

识别：

明确需求： 生成或比较旅行骨架。

旅行时间： 八天。

兴趣对象： 开罗、卢克索和阿斯旺。

确认情况： 需要从现有旅行状态核实，不能只根据本轮“比较想去”直接升级为正式采用。

可能的关键顾虑： 如果之前用户曾表达转场疲劳顾虑，应纳入判断。

### 状态要求

- 读取已有旅行状态。
- 保留用户原话和明确条件。
- 正确关联当前决策焦点。
- 不因一次生成请求就改变已确认旅行方案。

### AI 的下一步

判断目前是否具备形成有意义骨架比较的条件。

## 3.3.2 F3-S02｜读取已有状态及决策上下文

系统不能只看最近一句话。

需要整合：

- 目的地与旅行目标。
- 已知旅行天数。
- 日期或时间窗口。
- 国际入离境条件，如果用户提供过。
- 已确认城市。
- 正在考虑的候选城市。
- 用户已表达的体验兴趣。
- 明确顾虑。
- 预算意向或硬上限。
- 既有有效骨架。
- 相关现实事实。
- 当前未解决的决策缺口。

### 为什么需要？

例如用户之前说过：

> 我不希望为了多去一个城市而牺牲太多真正想看的遗迹。

如果系统只根据最新一句“阿斯旺也挺感兴趣”，可能会错误地生成一个压缩卢克索核心体验的方案。

### 工程边界

这些业务信息应通过权威状态与决策上下文获取。

不能只依赖模型对长期聊天记录的模糊记忆。

【设计已收敛｜B、C】

## 3.3.3 F3-S03｜识别影响骨架的关键约束和未知

系统需要识别三类不同性质的信息。

### A. 明确约束

例如：

> 我最多只有八天。

或：

> 总预算不能超过两万元。

这些需要按照用户实际表达的约束强度处理。

### B. 偏好与顾虑

例如：

> 我不想太赶。

> 我更喜欢历史文化体验。

这些会影响方案比较，但不能自动转换成未经确认的硬阈值。

### C. 未知条件

例如：

- 尚未确定具体出发日期。
- 尚未确定国际抵达地点。
- 未核验某段交通。
- 某项体验的实际开放日期未知。

### 系统行为

判断哪些未知会显著改变当前的骨架比较。

必要时提出针对性问题。

但不要求所有信息完全确定后才能生成初步骨架。

### 关键原则

缺少信息，不等于必须停止；具备信息，也不等于可以宣称全部可执行。

【设计已收敛｜B、C；F6 后期补充 A】

## 3.3.4 F3-S04｜形成具有实质差异的候选方案

系统需要生成真正不同的旅行选择。

### 示例

针对八天埃及旅行，可以讨论：

方案 A：开罗 + 卢克索

保留两座城市，给核心历史文化体验分配更多停留时间。

方案 B：开罗 + 卢克索 + 阿斯旺

加入第三座城市，增加不同的体验方向，但需要重新分配城市停留和跨城转场时间。

这只是概念示例，不代表两套方案经过完整现实校验。

### 为什么不是只生成不同排列？

如果系统生成：

- A：开罗三天、卢克索三天、阿斯旺两天。
- B：开罗两天、卢克索四天、阿斯旺两天。

但不解释这一天差异具体带来什么体验变化，用户仍然缺乏判断依据。

因此，候选之间的差异应能映射到：

- 实际体验获得与放弃；
- 城市顺序和停留变化；
- 转场负担；
- 时间资源；
- 有依据的费用；
- 重要约束；
- 未核验条件。

### 方案数量

PRD-004 提出：

存在多个有意义候选时，默认先比较两项，用户可以查看更多。

AI Native旅行产品｜PRD V0.1.md



后续 UX-02 进一步强调：

不能为了凑数强行生成三个方案，甚至不应在只有一种有意义方案时强造第二种。

【设计已收敛｜B、C】

候选数量服务于有效比较，而不是固定展示格式。

## 3.3.5 F3-S05｜进行必要的规划计算与现实核验

生成候选骨架之后，不能只依赖模型编写自然语言解释。

系统需要在实际能力范围内检查：

1. 已知旅行总天数与城市停留是否一致。
2. 城市顺序是否存在明显不合理的结构问题。
3. 是否违反明确硬约束。
4. 城市之间的交通代价是否有依据。
5. 体验分配是否与用户重要兴趣相符。
6. 增加一个城市会影响哪些其他安排。
7. 预算比较是否具备一致的费用口径。
8. 仍然缺少哪些现实条件。

### 日期未知时

可以检查与日期无关的结构约束，以及有来源的一般交通条件。

但不能将实际班次、预订可用性或具体开放时间写为已经核验。

### 约束冲突时

如果某套候选违反明确硬约束：

系统不能自动放宽限制，然后声称该方案可行。

应说明冲突，并在必要时提出调整方向。

### 查询失败时

不能将无结果、超时或信息缺失解释成确定不存在相应交通服务。

【设计已收敛｜B、C】

## 3.3.6 F3-S06｜计算每套骨架对整趟旅行的影响

这是 F3 讨论中最重要的设计要求之一。

旅行骨架不能只按局部城市数量、顺序或停留天数比较，而必须说明这些变化会给整趟旅行带来什么。

### 例如加入阿斯旺

用户真正关心的不是：

> 从两座城市变成三座城市。

而是：

- 增加了哪些独特体验？
- 开罗会损失哪些时间？
- 卢克索原计划的重要体验是否还能保留？
- 是否增加新的转场？
- 整体旅行节奏是否明显变紧？
- 哪些体验需要被压缩或调整？
- 哪些现实条件尚未核验？

### 需要明确区分的影响

直接变化：

增加、删除、调整的城市或停留。

连锁变化：

其他城市停留、旅行节奏、交通连接和体验时间受到的影响。

重要的用户价值变化：

获得或失去了用户明确重视的体验。

现实风险或未知：

交通条件、活动日期、具体衔接是否成立。

### 不能采用的简化方式

> 方案 A：两城，比较轻松。\
> 方案 B：三城，比较丰富。

这种比较过于抽象。

也不能仅根据城市数量就断言哪个方案一定轻松，因为真实转场方式、时间分配和安排细节可能改变结论。

【设计已收敛｜B；PRD-004、006 为 C 类旁证】

## 3.3.7 F3-S07｜向用户展示骨架比较

系统应让用户直接理解：

每个方案怎么安排、获得什么、放弃什么，以及为什么存在这些差异。

### 内容结构

比较内容至少应围绕：

- 城市组合。
- 城市顺序。
- 停留分配。
- 核心体验。
- 重要交通与转场。
- 时间负担。
- 相关费用。
- 已知约束冲突。
- 当前假设和未知。
- 对其他城市的影响。

### 说明性比较

| 比较维度 | 两城骨架         | 三城骨架           |
| ---- | ------------ | -------------- |
| 城市组合 | 开罗、卢克索       | 开罗、卢克索、阿斯旺     |
| 体验收益 | 更集中地安排两城核心体验 | 增加阿斯旺相关体验      |
| 停留取舍 | 两城可分配更多停留    | 需要重新分配八天       |
| 转场   | 连接数量相对较少     | 需要处理新增连接       |
| 可能牺牲 | 阿斯旺相关体验      | 部分既有城市停留与体验时间  |
| 现实核验 | 根据实际条件核验     | 新增连接和活动条件也需要核验 |

此表只展示已讨论的比较机制，不包含真实交通时间、真实费用或经过核验的可行性结果。

### 进一步展开

如果用户需要深入比较，应该能看到：

- 某项体验为什么被保留或牺牲。
- 增加某座城市的具体代价。
- 哪些差异来自用户偏好。
- 哪些差异来自现实约束。
- 哪些条件仍然不确定。

【设计已收敛｜B、C】

## 3.3.8 F3-S08｜AI 给出有依据的建议

F3 允许 AI 提出推荐意见。

但推荐必须能够解释。

### 例如

如果用户明确重视历史文化体验，也担心转场过多：

AI 可以说明某个骨架更有利于保留深入游览时间，另一个骨架则能获得新的体验类型。

但不应使用：

> 方案 A 综合评分 92，方案 B 综合评分 86，所以你应该选 A。

如果评分没有清楚的依据及价值解释，就不能替代用户的选择。

### 用户可以选择更费时的方案

用户可能明确表示：

> 我就是想去阿斯旺，即使会比较赶也愿意。

只要不违反不能突破的现实条件与明确硬约束，系统应尊重其价值取舍。

AI 负责准备与解释 trade-off，用户保留重要的价值决定。

【设计已收敛｜B、C】

## 3.3.9 F3-S09｜用户查看、询问或比较方案

用户可以：

- 查看 A。
- 查看 B。
- 展开某项差异。
- 询问某座城市被压缩的原因。
- 了解特定体验的影响。
- 请求再比较另一种安排。
- 返回 F1 探索城市。
- 进入 F5 提出假设。
- 明确采用某个方案。

### 必须区分行为语义

查看方案： 浏览行为。

询问方案： 获取信息。

提出假设： 探索可能的变化。

请求修改方案： 产生新的方案或草稿。

选择采用： 对明确对象作出正式采用意图。

不能把这些动作混成同一个状态转换。

【设计已收敛｜B】

## 3.3.10 F3-S10｜用户明确选择一个方案

例如：

> 就选方案 B。

或者在明确标注为采用操作的 UI 中，点击：

采用此方案。

### 后期形成的关键规则

选择即确认。

也就是说：

如果用户已清楚理解当前方案及其重要取舍，并执行明确的采用操作，系统不应再制造一个独立的“已选择、等待第二次确认”的普通中间流程。

【历史摘要记载 Owner 已确认｜B，原始裁决待补证】

### 注意适用条件

“选择即确认”不意味着：

- 可以跳过必要的业务约束校验。
- 可以自动接受用户未被告知的重大牺牲。
- 可以确认虚构的交通班次。
- 可以突破不能更改的现实条件。
- 可以自动授权订票、支付或其他交易行为。

它解决的是重复确认带来的无意义交互成本，不是取消授权和校验机制。

这一机制将在本章后续专节详细归档。

## 3.3.11 F3-S11｜应用决定并保留历史

在符合既有权限和校验要求的情况下，用户明确采用方案后：

- 被采用的方案形成当前有效旅行安排。
- 保留必要的决策依据。
- 保留此前版本或重要方案历史。
- 正确记录哪些内容已经确认。
- 正确记录哪些现实条件仍待核验。
- 不把用户尚未确认的其他方案当作有效方案。

### 为什么要保留历史？

后期 F3 讨论明确发现：

旅行规划不是一次性生成，而是用户不断认识、比较、采用和修改的过程。

因此，用户需要能够回顾：

- 之前有哪些重要方案。
- 为什么采用过某个版本。
- 当前版本相较之前改变了什么。
- 哪些曾经喜欢的体验被牺牲。
- 能否恢复旧安排。

【设计已收敛｜B】

## 3.3.12 F3-S12｜用户继续修改或返回探索

采用某个方案，不代表旅行规划永久结束。

用户之后可能：

> 我想再给卢克索增加一天。

或者：

> 我还是想看看阿斯旺有没有更值得去的体验。

这时：

- 明确修改应进入既有编辑与授权机制。
- 浏览城市不自动改变有效方案。
- 假设讨论不覆盖有效方案。
- 新的重要用户可见变化需要正确保存与比较。
- 后续恢复历史版本时也不能抹除已有历史。

F3 因此与 F4、F5、F6 形成持续的旅行决策循环。

# 3.4 F3 最关键的比较规则：整趟旅行的实际收益与代价

## 3.4.1 为什么不能只比较城市数量？

用户不是在购买城市数量。

他真正选择的是：

怎样在有限的时间、预算、精力和现实条件下，获得最符合自己期待的旅行体验。

因此，“两城还是三城”只是方案结构上的差异。

真正有决策价值的是这种结构差异导致的体验变化。

## 3.4.2 体验必须区分获得、保留与失去

对方案 B 相对于方案 A，应当能够说明：

获得：

新增哪些原方案没有的体验。

保留：

哪些用户明确重视的体验仍然可以保留。

失去：

哪些原方案中的体验因时间、顺序或其他限制无法继续安排。

被调整：

哪些体验仍在，但停留时间、顺序或负担发生变化。

未知：

哪些体验的实际可行性尚未核验。

【设计已收敛｜B】

### 案例

原方案：

开罗三天、卢克索五天。

新方案：

开罗三天、卢克索三天、阿斯旺两天。

系统不应只说：

> 卢克索减少两天，阿斯旺增加两天。

而应进一步分析：

- 卢克索原本准备安排的体验有哪些受到影响。
- 这些体验是否仍可保留。
- 新增阿斯旺可以提供哪些不同体验。
- 总体转场负担是否增加。
- 是否需要舍弃用户明确喜欢的内容。
- 哪些结论需要进一步的现实条件才能确定。

具体删去哪项体验必须来自实际规划和校验，不能在没有依据时直接编造。

## 3.4.3 时间代价不仅是天数

系统还需要考虑：

- 城市停留。
- 跨城移动。
- 等待和换乘。
- 必要的门到门时间。
- 活动之间的时间衔接。
- 可能造成的连续疲劳。
- 对其他城市体验安排的挤占。

但是：

不能凭城市数量或地理距离直接制造精确的旅行时间和疲劳结论。

应尽可能利用有依据的交通与规划条件进行计算。

## 3.4.4 预算比较必须保持口径一致

如果只有部分交通或体验费用有可靠依据：

系统可以比较这些分项。

但不能将它们伪装为完整旅行总预算。

需要注意：

- 人数。
- 币种。
- 日期。
- 费用是否包含往返。
- 费用包含哪些项目。
- 哪些项目尚未知。
- 哪些价格只是参考而非实时可购买金额。

### 用户预算本身也有语义差异

例如：

> 大概准备两万。

与：

> 最多不能超过两万。

不能当作同一种硬约束。

后期即使用户愿意提高预算，也应保留相应修改依据。

【设计已收敛｜C，PRD-009】

## 3.4.5 现实可行性与方案价值分开

用户可以确认：

> 我愿意为了阿斯旺多安排一段转场。

但不代表：

> 我确认某个尚未查到的交通班次一定存在。

因此需要区分：

价值取舍： 用户愿不愿意接受某种安排与代价。

事实核验： 现实交通、开放时间和其他外部条件是否支持执行。

这一原则既属于 F3 的比较要求，也在后期 F6 被进一步细化。

【设计已收敛｜B、C；F6 补充 A】

# 3.5 「规划与校验执行能力」：F3 对 AI 的核心新增要求

这是 F3 后期形成的一项高价值设计成果。

历史摘要明确记录，用户要求将其作为后续工程交付必须承接的产品能力：

规划与校验执行能力。

【历史摘要记载 Owner 明确要求保留｜B，原始逐轮消息待补证】

它不是一个已经决定采用的独立 Agent 名称，也不是某个具体技术模块的正式名称。

它描述的是：

ANTU 不仅要生成旅行建议，还要能够在可靠约束、事实和用户价值基础上准备、比较、检查和修复旅行方案。

## 3.5.1 为什么需要这项能力？

如果 F3 只依赖语言模型生成文本，可能出现以下问题：

- 候选方案表面不同，实际旅行价值相近。
- 时间分配加总不一致。
- 新增城市后没有更新其他城市停留。
- 删除一项体验时没有说明代价。
- 违反用户明确约束。
- 使用没有可靠来源的交通时间。
- 只在局部调整，却遗漏整体连锁影响。
- 用户选择后才发现该方案存在重大冲突。
- 为了让方案看起来可行，擅自删除用户重视的体验。

因此，F3 需要将方案生成、现实条件检查、旅行影响分析和取舍解释结合起来。

## 3.5.2 能力一｜多策略候选生成

### 用户需求

用户需要比较具有实际差异的旅行选择。

### 系统应具备的能力

能够围绕当前目标、约束和偏好，形成几种真正有区别的规划策略。

例如：

策略 A：优先保留核心体验。

把更多停留时间分配给用户已经明确重视的城市和体验。

策略 B：优先扩大体验覆盖。

增加新的城市或体验类型，同时显示需要承担的时间和交通代价。

策略 C：优先控制转场负担。

在不擅自突破用户重要偏好的前提下，尝试减少不必要的城市移动。

这些是可用于说明能力的策略类型，不是 F3 已经确认必须同时展示的三个固定方案模板。

### 重要规则

不应该机械生成三套方案。

若只有两套有意义方案，展示两套。

若只有一套满足已知重要条件，应解释为什么没有更多有价值的候选。

若所有候选都违反硬约束，应显示冲突，而不是制造一个看似可行的虚假方案。

【设计已收敛｜B、C】

## 3.5.3 能力二｜硬约束校验

### 需要检查的事项

例如：

- 总旅行天数。
- 已明确不能突破的预算上限。
- 用户已确认且不能被静默删除的城市或体验决定。
- 已知的入离境条件。
- 相关对象的合法状态与权限。
- 已知现实条件中的明确矛盾。

### 例子

用户明确：

> 这趟旅行最多八天。

系统生成：

开罗三天、卢克索四天、阿斯旺三天。

如果这些都是独立的完整停留天数，就已经超出八天。

系统不能仍将其描述为满足八天限制的方案。

### 关键边界

不能靠用户喜欢某个方案，就宣布明显违反硬约束的安排变得可行。

如果硬约束是用户可以改变的条件，需要由用户明确调整。

如果属于不可改变的现实条件，不能通过用户确认消除事实冲突。

【设计已收敛｜B、C】

## 3.5.4 能力三｜现实事实核验

F3 需要使用可靠事实支持旅行骨架比较。

相关事实可能包括：

- 两座城市之间存在何种交通方式。
- 已知条件下的交通耗时。
- 某项体验的适用日期。
- 重要交通连接的现实可行性。
- 已有费用信息的口径。
- 已知活动条件。

### 四项重要要求

第一：来源明确。

系统需要知道事实来自何处。

第二：适用条件明确。

例如交通班次是否只适用于某个日期。

第三：核验层级明确。

地理位置、一般交通、指定日期班次与实际可购买性不能混淆。

第四：失败和未知明确。

没有取得数据不等于确认现实中不存在服务。

### 后期补充

加入具体日期后，必须重新核验原本依赖日期的安排。

不能把旧日期的结果永久当作有效事实。

【设计已收敛｜B、C；F6 补充 A】

## 3.5.5 能力四｜整趟旅行的连锁影响分析

这是 F3 最重要的计算要求之一。

### 为什么局部修改需要整体检查？

用户增加一个城市，并不是简单在地图上增加一个地点。

它可能引起：

- 新的交通连接。
- 城市顺序变化。
- 原有城市停留压缩。
- 原有体验时间变化。
- 新的费用。
- 已有交通安排失效。
- 新的活动时间冲突。
- 旅行节奏改变。

### 示例

原方案：

开罗三天 → 卢克索五天。

用户希望：

> 加上阿斯旺两天。

系统不能简单生成：

开罗三天 → 卢克索五天 → 阿斯旺两天。

因为总天数可能已经超出用户八天的限制。

系统需要先识别：

- 哪两天会从原安排中腾出来？
- 是否必须缩短开罗或卢克索？
- 哪些重要体验因此受影响？
- 是否有其他结构性调整方式？
- 哪些变化会损害用户此前明确的取舍？

### 产品要求

AI 应主动准备可能的修复方案，但不能为了满足新增意图，就静默删除用户重视的其他体验。

【历史摘要记载为后期重要收敛规则｜B】

## 3.5.6 能力五｜有意义的差异过滤

生成多种候选并不意味着全部值得展示。

### 典型问题

系统内部可能生成五套旅行方案。

其中三套只是：

- 城市停留的细微变化；
- 交通方式描述不同；
- 核心体验没有实质差异；
- 实际代价几乎相同。

这些方案全部展示，会增加用户判断负担。

### 形成的方向

系统应优先提供：

在体验收益、旅行节奏、重要资源消耗或风险上具有实质差异的候选。

### 必须保留的边界

不因内部生成数量较多，就把所有中间方案写进用户可见历史版本。

只有真正对用户产生比较、判断或恢复价值的重要方案，才需要进入相应的可回顾记录。

【设计已收敛｜B】

## 3.5.7 能力六｜可解释的取舍分析

系统需要能够解释：

- 为什么某项体验被保留。
- 为什么某个城市停留减少。
- 新方案增加了什么价值。
- 原方案有哪些优势。
- 哪些代价无法同时消除。
- 哪些判断依赖用户主观价值。
- 哪些事实还没有核验。

### 重要边界

AI 不能以不可追溯的综合评分取代用户选择。

可以有推荐理由，但推荐理由必须与实际方案差异和已有用户信息相联系。

## 3.5.8 能力七｜条件依赖与不确定性管理

这项能力在 F6 后期进一步得到明确。

### 原始问题

用户可能在日期未知时，已经充分规划了城市与体验。

未来加入具体日期后，某些安排可能无法执行。

### 后期方向

系统需要识别：

- 哪些决定相对稳定。
- 哪些安排依赖具体日期。
- 哪些安排依赖真实班次或开放时间。
- 哪些条件可能导致局部调整。
- 哪些关键依赖可能改变整份骨架。

### 对 F3 的意义

在方案比较时，应尽早揭示有可能改变重要取舍的条件。

但不因所有细节尚未确定就阻止骨架比较。

【Owner 已确认｜A：F6 后期】

## 3.5.9 这项能力不等于必须建立多个 Agent

历史摘要明确记录：

规划与校验执行能力可以由不同的技术组件共同实现，不要求一定拆成多个 Agent。

产品侧关注的是可验证的行为结果：

- 能否生成有意义的候选。
- 能否检查约束。
- 能否识别影响。
- 能否正确使用事实。
- 能否解释差异。
- 能否在失败时保护状态。

具体使用规则引擎、计算服务、工具调用或其他架构，属于后续工程设计。

【设计已收敛｜B；工程待核查】

# 3.6 「选择即确认」：F3 中后期的重要产品裁决

## 3.6.1 最初需要解决的问题

用户看到了两个经过比较的旅行方案。

系统已经向用户解释：

- 每个方案有哪些城市。
- 哪些体验能够保留。
- 哪些体验需要牺牲。
- 主要时间和交通代价。
- 已知的约束和未知条件。

用户点击：

选择方案 B。

此时系统是否还需要要求用户点击一次：

确认采用方案 B？

### 原有候选思路

可以将选择与正式确认分成两个步骤：

1. 用户先选择某方案。
2. 系统再请求确认。
3. 用户确认后应用。

### 发现的问题

在用户已经充分理解取舍、操作语义也明确的情况下，增加第二次确认可能只是重复用户刚刚表达的决定。

它带来：

- 额外交互成本。
- 不必要的流程复杂度。
- 选择后状态含义不清。
- 用户不知道自己到底已经决定了什么。

## 3.6.2 后期裁决

选择即确认。

【历史摘要记载 Owner 已明确确认｜B，原始裁决待补证】

准确理解：

当用户对清楚呈现的具体方案执行明确采用操作时，这个操作本身就是针对该方案的确认意图。

不需要再引入一个通用的：

`已选择 → 等待再次确认 → 已采用`

中间状态。

## 3.6.3 不能误解为取消全部校验

例如方案 B 存在一个此前未展示的重要问题：

采用该方案会导致用户已经确认的核心体验无法保留。

如果用户之前没有被清楚告知这一取舍，不能仅凭“选择 B”就认为用户已经授权牺牲该体验。

系统必须：

1. 识别新发现的重要影响。
2. 向用户解释变化。
3. 在需要新的价值决定时交还用户判断。
4. 保留原有效方案，直到新的修改获得必要授权。

同样，用户确认不能让实际不存在的班次变成存在。

### 重要区别

重复确认： 用户已经明确知道并接受某个取舍，系统又问一遍是否确定。

新的必要裁决： 系统发现之前没有呈现的新重要牺牲，需要用户进一步判断。

后者不是前者的重复。

## 3.6.4 什么行为不适用“选择即确认”？

| 用户行为            | 是否构成方案采用             |
| --------------- | -------------------- |
| 点击查看方案 B        | 否                    |
| 展开方案 B 的交通信息    | 否                    |
| 询问“方案 B 会不会太赶”  | 否                    |
| 说“如果按 B 会怎样”    | 否，属于假设               |
| 说“我比较倾向 B，再看看”  | 不应直接视为正式采用           |
| 在明确采用入口点击“采用 B” | 是，表达正式采用意图           |
| 明确说“就按 B 来”     | 是，表达正式采用意图，但仍须执行必要校验 |

### 与技术规格的关系

UX-02 不因此自行新增或删除 Trip State 的具体状态字段。

需要在工程核查中确保：

- 用户操作表达的是明确采用意图。
- 对应方案和版本没有歧义。
- 必要校验已经执行。
- 适用权限得到满足。
- 不重复设置普通确认步骤。
- 需要新裁决的重大影响不会被绕过。

【工程待核查】

# 3.7 方案版本历史：从一次选择到持续规划

这是 F3 后期较大的一项设计扩展。

## 3.7.1 为什么需要版本历史？

用户规划旅行时，可能经历：

1. 首次采用两城方案。
2. 后来想增加阿斯旺。
3. 比较后采用三城方案。
4. 再次调整卢克索停留。
5. 因交通问题恢复之前的安排。
6. 之后又想借鉴旧版本某个城市的规划。

如果系统只保存最新方案，就会产生以下问题：

- 用户不知道以前怎么安排。
- 无法理解后来改变了什么。
- 曾经放弃的体验难以找回。
- 想恢复旧方案时只能重新描述。
- AI 可能错误重构旧版本。
- 用户缺少对复杂修改的掌控感。

### 形成的产品方向

保留具有重要用户意义的旅行方案历史，让用户能够查看、比较和恢复过去的安排。

【历史摘要记载 Owner 已确认｜B】

## 3.7.2 哪些变化应该形成历史记录？

历史摘要记录的后期要求：

重要的用户可见旅行方案迭代，都应具有可回顾性。

具体包括：

- 用户采用的旅行骨架。
- 用户后来正式修改并采用的新方案。
- 对用户有实际比较价值的重要候选版本。
- 可以被用户重新查看和选择的重要历史安排。
- 基于旧版本恢复后形成的新有效版本。

### 必须区分

用户可见的重要方案： 对用户实际决策有意义，应可追溯。

AI 内部临时生成的候选： 仅用于内部搜索、计算或筛选，不要求全部进入用户可见历史。

### 未定的工程细节

“重要用户可见版本”的精确归档粒度，仍需要映射到正式版本机制。

不能在 UX 底稿中擅自规定每条模型生成文本都必须建立独立版本。

【设计已收敛｜B；工程待核查】

## 3.7.3 版本历史至少需要让用户理解什么？

用户打开历史后，应能知道：

- 当时采用或讨论的城市组合。
- 城市顺序。
- 停留分配。
- 主要体验安排。
- 当时有哪些重要假设。
- 与当前版本的差异。
- 相关决定及理由。
- 哪些事实可能已经过期。
- 能否恢复该版本。

### 关键原则

版本历史不是简单的聊天消息历史。

系统不能仅保存：

> 用户说过“把卢克索增加一天”。

还需要能够关联当时实际形成的旅行安排及其重要依据。

## 3.7.4 用户查看历史版本

### 用户操作

打开某个过去的旅行版本。

### 正确系统行为

1. 读取指定历史版本。
2. 展示该版本的旅行内容。
3. 明确让用户知道当前查看的是历史方案。
4. 不自动覆盖当前有效方案。
5. 允许与当前方案比较。
6. 允许用户进一步请求恢复。

### 重要边界

查看历史版本不等于恢复历史版本。

这与 F1 的“浏览不等于喜欢”、F5 的“假设不等于修改”具有同样的语义隔离要求。

# 3.8 整趟旅行版本恢复

## 3.8.1 典型场景

用户当前已经采用了 V3 方案。

此前有一个 V1 方案，安排更简单。

用户说：

> 我还是觉得最开始那套方案比较舒服，想恢复那个版本。

以上 V1/V3 只是用于说明历史顺序的示例编号，不代表正式 Trip State 版本 ID。

## 3.8.2 用户恢复前，系统需要做什么？

不能直接把旧版本数据覆盖到当前有效方案。

需要考虑：

- 当前版本相较旧版本新增了什么。
- 旧版本原来的条件是否仍然适用。
- 当前是否存在新的硬约束。
- 是否增加了新的已确认决定。
- 旧版本依赖的现实事实是否已经过期。
- 恢复会不会带来新的重要取舍。

### 例如

旧版本还没有明确旅行日期。

用户现在已经确定了具体日期。

恢复旧版本时，不能直接认为旧版本当时成立的交通信息仍然适用。

## 3.8.3 恢复后的版本处理

【历史摘要记载 Owner 已确认｜B】

恢复历史版本，应产生一个新的有效版本，而不是擦除后续历史、让系统时间倒退。

### 示例

历史：

V1 → V2 → V3

用户决定采用 V1 的安排。

正确结果可以概念化为：

V1 → V2 → V3 → V4（恢复自 V1）

V2 和 V3 仍然保留。

### 为什么？

用户需要理解：

- 曾经发生过哪些规划演化。
- 现在为什么恢复。
- 当前版本基于哪个旧版本。
- 后续还能否查看 V2/V3。

### 重要边界

这不要求一定使用名为 `restored_from_version_id` 的字段。

具体版本关系如何表达，由正式 Trip State Schema 和工程设计确定。

UX 要求的是能够保留版本来源和恢复依据。

## 3.8.4 恢复时发现新冲突

例如用户恢复旧版城市顺序，但当前日期已经无法支持其中某段具体交通安排。

系统应当：

1. 保留当前有效方案。
2. 对拟恢复内容进行必要校验。
3. 说明哪些旧安排仍然适用。
4. 标明已发现的冲突。
5. AI 主动准备合理修复建议。
6. 对涉及新的重要取舍的修复请求用户判断。
7. 不自动将不可执行的具体安排标记为有效。

### 对用户的体验要求

系统不应该简单拒绝：

> 旧版本不可恢复。

而应解释：

哪个部分可以恢复，哪个部分与当前条件冲突，以及怎样调整可能保留原来的旅行价值。

【设计已收敛｜B；F6 后期规则 A】

# 3.9 城市级恢复：F3 后期新增的重要能力

这一项不能被普通的整份版本回滚替代。

## 3.9.1 用户实际需求

用户可能喜欢当前旅行的大部分安排，只是想恢复某座城市之前的规划。

例如：

> 我想把卢克索恢复成之前的三天安排，但开罗和阿斯旺保持现在这样。

### 如果只提供整份回滚

用户必须放弃所有后续修改，才能恢复卢克索。

这与用户的实际意图不符。

### 形成的设计方向

支持在整趟旅行的当前上下文中，选择性恢复历史版本中的某座城市安排。

【历史摘要记载 Owner 已确认｜B】

## 3.9.2 城市级恢复的对象是什么？

用户选择的不是简单的文字片段，而是历史版本中某个城市对应的规划内容。

它可能包括：

- 城市停留分配。
- 该城市的重要体验安排。
- 与该城市相关的顺序或时间关系。
- 必要的城市内规划内容。
- 影响该城市安排的已知条件。

### 重要问题

城市并不是完全独立的对象。

恢复卢克索三天，可能会影响：

- 整趟旅行总天数。
- 开罗和阿斯旺的时间分配。
- 与卢克索相邻的交通连接。
- 某些体验日期。
- 旅行节奏。
- 已确认的其他安排。

因此，城市级恢复不能被实现为单纯复制旧数据。

## 3.9.3 城市级恢复的交互流程

### 步骤一：用户指定恢复对象

例如：

> 恢复旧版本的卢克索安排。

如果用户没有明确指定旧版本，应结合上下文判断是否有唯一明确对象。

如存在影响重要决定的歧义，应进行必要澄清。

### 步骤二：系统读取两种内容

当前有效旅行：

需要保护的整趟旅行当前安排。

指定历史城市安排：

用户希望恢复的内容。

### 步骤三：比较局部差异

系统应知道：

- 卢克索的停留天数变化。
- 哪些体验恢复。
- 哪些当前体验被移除或调整。
- 城市间连接可能如何变化。
- 对其他城市产生哪些影响。

### 步骤四：分析连锁影响

例如原来卢克索四天，用户恢复成三天。

这一变化可能释放一天。

但系统不能在没有明确依据时，直接决定把这一天交给阿斯旺、开罗或其他城市。

反过来，如果恢复会增加一天，也不能自动从另一个已经确认的城市中夺走一天。

### 步骤五：AI 准备必要修复

AI 可以分析：

- 是否能够直接恢复且不影响其他重要安排。
- 是否需要调整相邻交通。
- 是否有几种不同的时间分配方法。
- 哪种调整能够更好地保留用户已确认的体验。

### 步骤六：用户决定重要取舍

如果恢复会改变其他已确认内容，必须说明代价并遵守相应授权规则。

### 步骤七：生成新版本

成功采用后，形成具有正确来源关系的新有效版本。

原有当前版本和历史版本不被擦除。

【设计已收敛｜B】

## 3.9.4 城市级恢复中的核心保护边界

第一：局部恢复不等于整份旅行恢复。

用户只指定卢克索时，不应顺便回滚开罗和阿斯旺的所有安排。

第二：城市局部变化可能触发整体影响检查。

不能因为恢复范围是单城市，就跳过其他城市的关联校验。

第三：AI 可以主动准备修复，但不能擅自作出新的重要价值牺牲。

第四：恢复必须保留版本与修改依据。

第五：恢复过程中尚未提交的预览不应覆盖有效旅行。

这些规则需要由版本管理、影响分析、权限校验和编辑机制共同支持。

# 3.10 多重冲突与复杂修改：F3 后期的重要深化

## 3.10.1 为什么需要讨论复杂冲突？

简单场景中，用户增加或删除一座城市，系统只需要调整相关停留。

但真实旅行规划常常涉及多项相互依赖的安排。

例如：

用户已经确认：

- 开罗的某些核心体验。
- 卢克索的某些重点参观项目。
- 阿斯旺的某项体验。
- 总旅行天数。
- 特定的城市顺序。

之后又决定恢复旧版卢克索安排。

这可能同时引发：

- 总天数不一致。
- 某个城市被压缩。
- 跨城交通需要重新安排。
- 体验时间发生冲突。
- 某项已确认体验无法继续保持。

此时的关键问题不只是有没有冲突，而是谁有权决定牺牲什么。

## 3.10.2 冲突需要区分性质

### A. 结构或硬约束冲突

例如：

用户明确限定八天，当前安排合计十天。

系统不能将其视为已经可执行。

### B. 现实事实冲突

例如：

在指定日期条件下，某项已核验的交通安排与其他活动发生明确时间冲突。

这种冲突需要基于实际可靠数据，而不能凭语言模型猜测。

### C. 用户价值取舍冲突

例如：

恢复旧版卢克索的停留分配，可能要求减少阿斯旺某项用户喜欢的体验。

这不一定是现实上绝对不可执行，而是涉及用户个人价值选择。

### D. 条件未知

例如：

未提供具体日期，当前无法核验指定班次。

未知不能被自动标成存在现实冲突。

以上区分结合了 F3 的历史讨论、PRD 基线和 F6 后期进一步明确的规则。

## 3.10.3 AI 应先做什么？

面对复杂修改，AI 应当主动进行必要的影响分析。

主要步骤：

1. 确定用户明确提出的目标。
2. 识别受影响的城市、体验、连接和时间安排。
3. 对照当前有效方案。
4. 检查明确硬约束。
5. 检查相关现实条件。
6. 区分可保留内容与受影响内容。
7. 寻找可行的局部调整方式。
8. 将重要取舍整理为用户能够判断的候选。

### 不能采取的方式

- 为了生成可行解，直接删除用户喜欢的体验。
- 发现硬约束冲突后静默修改用户上限。
- 因某一段交通未知，就宣布整趟旅行不成立。
- 每发现一个问题就向用户提出一个琐碎问题。
- 把全部计算和排错责任交给用户。

## 3.10.4 修复优先级：尽量保留原有旅行价值

后期 F3 讨论明确强调：

AI 应尽可能寻找减少无关牺牲的修复方式，而不是每次出现问题就重新生成整趟旅行。

这在后期 F6 被进一步表达为：

变更影响管理与最小必要修改。

### 举例

用户希望恢复卢克索旧版三天安排。

假设这一操作导致相关转场时间需要变化。

系统可以尝试：

- 调整同一城市内部的体验顺序。
- 调整某段交通的安排。
- 检查是否需要变化停留分配。
- 比较不同修复方式对其他已确认体验的影响。

但是：

最小修改不是比用户明确价值更高的绝对目标。

如果用户愿意调整更多内容以换取更喜欢的体验，系统仍应允许用户作出这样的取舍。

## 3.10.5 不应自动牺牲其他已确认体验

### 典型问题

用户：

> 把卢克索恢复成之前的安排。

系统发现若按原时间分配，会减少阿斯旺的停留。

### 错误行为

自动删除阿斯旺已确认的某项体验。

然后告诉用户：

> 已恢复卢克索。

### 正确行为

应当说明：

- 卢克索恢复会改变什么。
- 阿斯旺哪些安排可能受到影响。
- 是否存在不牺牲重要体验的替代调整。
- 如果必须发生取舍，具体有哪些选择。
- 哪些现实条件还需要核验。

### 用户控制权

用户提出局部恢复，并不意味着授权系统重新决定全部旅行中的体验优先级。

【设计已收敛｜B】

## 3.10.6 如果存在多个修复方案怎么办？

系统可以准备几个具有实际差异的修复方向。

例如：

方案一：保留所有关键体验，调整城市停留。

方案二：保持城市停留，改变部分体验安排。

方案三：保留当前方案，暂不进行历史恢复。

以上为说明性的修复方向，不代表任何特定埃及行程实际满足这些条件。

比较应说明：

- 保留什么。
- 改变什么。
- 牺牲什么。
- 需要用户决定什么。
- 哪些事实已核验。
- 哪些条件仍未知。

不为了凑齐三个方向而制造无意义的候选。

## 3.10.7 如果没有可行修复怎么办？

系统必须能够诚实说明：

在当前已知且不可突破的条件下，暂时无法找到满足全部要求的安排。

此时需要：

- 保留当前有效方案。
- 保留用户的修改或恢复意图。
- 解释冲突来源。
- 在许可范围内提出可能的条件调整。
- 不擅自删除用户已确认安排。
- 不将失败结果伪装为有效更新。

如果用户愿意明确修改可由其控制的硬约束，可以据此重新计算。

但外部事实和不可更改的现实条件不能因为用户确认就失效。

【设计已收敛｜B、C】

# 3.11 F3 中不同方案、决定与历史的状态边界

## 3.11.1 为什么要严格区分？

F3 中可能同时存在：

- 当前有效旅行方案。
- AI 正在生成的候选。
- 用户正在查看的比较方案。
- 尚未提交的修改草稿。
- 用户提出的假设。
- 历史有效版本。
- 用户正在预览的恢复结果。

它们虽然都可能表现为旅行地图和时间轴，但业务含义完全不同。

不能因为用户在界面上看到了某份旅行安排，就认为这份安排已经成为当前有效方案。

【设计已收敛｜B、C】

## 3.11.2 关键操作语义

| 用户行为      | 应当产生的业务效果         | 不得发生的错误         |
| --------- | ----------------- | --------------- |
| 查看候选 A    | 展示候选内容            | 自动采用 A          |
| 展开候选交通信息  | 显示证据              | 将交通方式确认为已选择     |
| 请求生成另一方案  | 形成新候选或比较结果        | 覆盖当前有效方案        |
| “如果增加阿斯旺” | 创建假设分析            | 直接修改有效方案        |
| 明确采用候选 B  | 发起对 B 的正式采用       | 再设置无意义的二次普通确认   |
| 拒绝候选 B    | 不采用这套方案           | 认定用户不喜欢 B 中全部城市 |
| 查看旧版本     | 读取历史              | 自动执行恢复          |
| 请求恢复旧版本   | 启动恢复与必要校验         | 静默覆盖当前方案        |
| 只恢复卢克索    | 针对指定城市准备局部恢复      | 整趟旅行全部回滚        |
| 恢复过程中遇到冲突 | 保留原有效方案，解释冲突和调整方向 | 未解决冲突却显示恢复成功    |

### 关于“拒绝”的重要范围限制

例如：

用户拒绝一套包含阿斯旺的方案。

不能因此推断：

- 用户永远不想去阿斯旺；
- 阿斯旺应从所有候选中排除；
- 用户不喜欢尼罗河体验；
- 以后不允许继续比较三城方案。

拒绝一套方案，只对这次明确的方案选择具有相应意义。

【设计已收敛｜B】

## 3.11.3 当前有效方案与其他方案

当前有效方案应当具有明确的业务依据。

候选、假设和历史预览不能直接作为有效方案使用。

例如：

当前有效方案是两城安排。

用户在 F3 正在查看三城候选。

当他返回当前旅行总览时，系统不能因为三城候选刚刚被打开，就把三城显示为已经正式采用。

### 交互要求

用户需要能够理解：

- 现在有效的旅行是什么。
- 当前正在比较什么。
- 哪些内容尚未采用。
- 哪些变更只是草稿或假设。
- 哪个历史版本正在被查看。

具体状态名称和数据字段应以正式 Trip State Schema 为准。

## 3.11.4 版本关系不应混同于业务确认

F3 后期提出的“保留用户可见重要版本”，并不等于：

所有历史方案都是已确认方案。

用户可能曾经认真比较过一个重要候选，但最终没有采用。

它仍可能具有回看价值。

因此需要区分：

历史可回看性： 能否恢复此前讨论或展示过的方案内容。

正式有效性： 该方案是否获得过必要的用户确认。

现实核验状态： 某个方案中的具体安排是否经过相关事实核验。

这些语义不能由单一的“版本存在”推断。

【设计已收敛｜B；工程待核查】

## 3.12.2 UI-F3-02｜整趟旅行差异说明

### 设计问题

早期骨架比较可能过度强调：

- 城市数量；
- 停留天数；
- 路线形状。

但用户真正需要知道的是：

具体体验得失以及整趟旅行负担怎样变化。

### 后期形成的内容要求

差异区应当尽可能包含：

获得： 新增的体验价值。

保留： 原有重要体验中仍然得到保护的部分。

失去： 被删除、压缩或无法继续安排的体验。

调整： 时间、顺序、交通和旅行节奏发生的变化。

风险与未知： 已知冲突及待核验条件。

### 初步结构

```
从方案 A 改为方案 B

新增：
  阿斯旺相关体验

保留：
  开罗的核心体验
  卢克索仍可安排的核心体验

可能减少：
  某些城市的停留时间
  部分原有体验的安排空间

新增代价：
  跨城连接
  对旅行节奏的影响

需要核验：
  具体日期的交通与活动条件
```

这里的“保留”或“减少”必须由真实方案数据和分析结果支持。

不能把该结构中的示意内容直接当作埃及八天旅行的事实。

### 设计状态

【设计已收敛｜B】

# 3.13 F3 与 F4、F5、F6 的边界和衔接

## 3.13.1 F3 与 F4｜方案选择后进入连续编辑

F3 帮助用户比较和采用旅行骨架。

F4 负责在地图、时间轴及对话中继续调整骨架。

### 后期 F4 的新增设计

【设计已收敛｜B】

用户进入一个明确的编辑会话后：

- 可以连续修改多个城市。
- 每次操作只更新同一份编辑草稿。
- 地图和时间轴同步显示暂定变化。
- 不每点击一次就启动完整 AI 分析。
- 完成编辑时对整组变化进行必要校验。
- 在允许应用的范围内完成提交。
- 若发现阻断冲突，则保留草稿与原有效方案。

### 对 F3 的影响

F3 的骨架比较和采用机制，需要能够承接后续多轮编辑与版本变更。

不能把一次采用当作不可修改的终点。

## 3.13.2 F3 与 F5｜假设比较

用户可能已经有当前有效方案 A。

然后提出：

> 如果不去阿斯旺呢？

这种输入应被理解为假设，而不是正式删除阿斯旺。

系统可以基于正确方案形成假设预览，并比较：

- 失去什么；
- 获得什么；
- 旅行节奏如何变化；
- 哪些其他城市安排会改变。

### 后期 F5 补充

如果用户处于编辑会话：

- 有效方案 A。
- 正在编辑的草稿 B。
- 基于 B 提出的假设 C。

C 不能自动覆盖 B。

如果用户明确要求把假设加入当前编辑，才进入对应草稿。

【设计已收敛｜B】

## 3.13.3 F3 与 F6｜确认、保存与现实核验

F3 的“选择即确认”解决用户采用方案的交互语义。

F6 进一步处理：

- 当前确认的具体范围。
- 现实条件核验。
- 日期未知时的规划采用。
- 已知冲突的阻断。
- 保存草稿与保存有效方案的区别。
- 旧事实变化后的重新核验。

### 后期核心原则

规划确认与现实可行性核验，是两个不同的维度。

用户可以确认当前层次的旅行骨架，而某些具体交通安排仍待核验。

但不能把已知阻断当前执行安排的冲突，伪装成可以直接执行。

【Owner 已确认｜A：F6 后期】

# 3.14 UX-02.5 对 F3 的补充

## 3.14.1 UX-02.5-A｜跨会话恢复

【Owner 已确认｜A】

### 场景

用户正在比较或编辑旅行方案，尚未完成，就退出。

几天后回来。

### F3 需要承接的内容

- 当前有效骨架。
- 正在比较或编辑的内容。
- 重要历史版本。
- 用户上次关注的方案。
- 之前已经形成的取舍依据。
- 尚未解决的决策问题。
- 需要重新校验的现实事实。

### 重要安全要求

恢复工作进度不等于自动采用此前未确认的方案。

用户可以继续原任务，但必须保持当前有效方案与未完成草稿之间的区别。

## 3.14.2 UX-02.5-B｜跨流程一致性

【Owner 已确认｜A】

用户可能在：

- 骨架比较；
- 地图浏览；
- 编辑草稿；
- 假设预览；
- 历史版本；

之间来回切换。

系统需要正确区分：

- 当前查看对象。
- 当前比较对象。
- 当前编辑目标。
- 当前有效版本。
- 用户是否正在执行正式采用或恢复。

### 已确认原则

工作上下文与业务修改分离。

切换浏览对象，不等于切换业务修改目标。

切换页面，不等于自动完成或放弃编辑。

查看历史版本，不等于执行版本恢复。

## 3.14.3 UX-02.5-C｜异常失败与成果保护

【后期产品设计已收敛｜A；独立逐项 Owner 批准依据待补证】

### 对 F3 的影响

方案生成失败：

不得破坏当前有效方案。

比较计算失败：

可以保留已完成且仍适用的结果，明确说明未完成部分。

历史版本读取失败：

不能将读取失败解释为该版本已被删除。

恢复时校验失败：

保留原有效版本与用户的恢复意图。

提交时网络中断：

不能直接认定成功或失败，应核实权威状态。

重复提交：

应避免同一次采用或恢复动作被重复执行。

当前版本发生并发变化：

旧草稿不能直接覆盖新的有效版本。

# 3.15 F3 的设计演化与重要 Owner 裁决

## 3.15.1 E-F3-01｜从直接生成行程到先识别关键取舍

早期候选：

- 先完整收集信息。
- 立即生成完整方案。
- 识别关键条件后尽快形成有意义比较。

发现的问题：

前两者分别存在问卷成本高、假设过多和过早锚定的问题。

最终方向：

历史摘要记载 Owner 选择第三种方向。

【B｜原始裁决待补证】

## 3.15.2 E-F3-02｜从比较结构到比较整趟旅行价值

初期方案：

展示城市数量、顺序与停留。

问题：

用户仍然不知道某项变化会给实际旅行体验带来什么。

修正：

加入获得、保留、失去、时间代价、转场影响、费用和未知条件。

最终结果：

比较必须具备整趟旅行视角。

【设计已收敛｜B、C】

## 3.15.3 E-F3-03｜从固定候选数量到实质差异优先

初期方向：

提供多种方案供用户选择。

问题：

数量可能增加但决策价值没有增加。

修正：

优先展示有意义的差异。

最终结果：

不强制凑齐三个方案；只有一种有意义方案时可以只提供一种并解释限制。

【设计已收敛｜B、C】

## 3.15.4 E-F3-04｜从选择后再次确认，到选择即确认

曾经的方向：

用户先选择，再进入单独确认。

问题：

如果取舍已经明确，重复确认增加成本并制造不必要状态。

最终方向：

明确采用操作本身表达确认意图。

保留的边界：

不能绕过重要新取舍、约束校验或业务权限。

【历史摘要记载 Owner 已确认｜B】

## 3.15.5 E-F3-05｜从只保留最新方案，到用户可回顾的重要历史

原有风险：

只保留最新方案导致旧安排无法找回。

修正：

重要用户可见方案具备历史回顾价值。

进一步限制：

不要求所有 AI 内部中间候选都进入用户可见历史。

【历史摘要记载 Owner 已确认｜B】

## 3.15.6 E-F3-06｜从整份版本恢复到城市级恢复

早期方向：

恢复整趟旅行的历史方案。

发现的问题：

用户可能只想恢复一座城市，而希望保留其他后续修改。

补充：

允许指定城市级历史安排进行恢复。

新问题：

局部恢复可能导致整趟旅行的时间和交通冲突。

后续要求：

必须执行相关影响分析和必要校验。

【历史摘要记载 Owner 已确认｜B】

## 3.15.7 E-F3-07｜从直接覆盖旧版本，到新版本继承历史

风险：

恢复旧版本时擦除后来发生的规划过程。

修正：

恢复后产生新的有效版本，保留版本来源和此前历史。

结果：

用户能够持续追溯规划过程。

【设计已收敛｜B】

## 3.15.8 E-F3-08｜从局部修改到复杂连锁影响分析

初期能力：

调整城市停留或组合。

发现的问题：

局部变化可能影响多个城市、体验和交通连接。

修正：

规划与校验执行能力必须能够计算相关连锁影响。

重要限制：

不能自动牺牲其他已经确认的核心体验。

【设计已收敛｜B】

## 3.15.9 E-F3-09｜从日期缺失阻断，到渐进式规划确认

后期发现的问题：

用户可能在无日期时已经完成深入规划，加入真实日期后可能发生较大返工。

曾讨论的分析框架：

L1 骨架、L2 体验安排、L3 具体日期与执行安排。

发现的不足：

同一规划深度内部也存在不同的日期依赖；不能把三个层级当成强制确认关卡。

修正方向：

- 渐进式规划确认。
- 延迟绑定具体执行条件。
- 尽早识别重要日期依赖。
- 加入具体日期后进行变更影响分析。
- 尽量局部修复，不默认推翻整个方案。

最终结果：

无日期的深度旅行规划可以形成可确认的规划内容，但不能假装所有现实执行条件已经核验。

【Owner 已确认｜A：F6 后期】

## 3.16.2 Trip State 需要承接的业务语义

【工程待核查】

需要核查能否表达：

- 当前有效旅行骨架。
- 尚未采用的候选。
- 已确认的重要决定。
- 假设及其与有效方案的关系。
- 用户重要方案版本。
- 修改依据。
- 恢复来源。
- 城市级局部恢复。
- 与版本有关的现实条件。
- 用户确认范围。
- 受影响对象和历史关系。

这里不直接指定新增 Schema 对象或字段。

正式 Trip State Schema V0.1.0 的对象与状态转换必须另行核对。

## 3.16.3 Decision Context 需要承接什么？

【工程待核查】

主要包括：

- 当前正在比较什么。
- 比较基准是哪份方案。
- 当前用户最重要的取舍是什么。
- 相关偏好、顾虑和约束。
- 还缺少什么条件。
- 当前结论依赖哪些证据。
- 是否正在讨论旧版本恢复。
- 当前假设基于什么。
- 哪些问题尚未解决。
- 恢复任务的必要上下文。

尤其需要保证：

Decision Context 不会因为聚焦一份历史方案，就将其误当作 Trip State 的当前有效版本。

## 3.16.4 NAP 需要承接什么？

【工程待核查】

需要核查以下行为：

- 什么时候可以自主生成候选。
- 什么时候需要澄清。
- 什么时候主动查询事实。
- 什么时候进行影响计算。
- 什么时候给出推荐。
- 什么时候必须停止自动修改。
- 什么时候需要用户判断。
- 用户明确选择后如何处理确认。
- 遇到新重大牺牲如何交还用户裁决。
- 用户拒绝后如何保留原方案。
- 恢复旧版本时如何处理权限和冲突。
- 工具失败时如何降级。
- 用户切换任务后如何停止不再适用的行动。

不自行新增 NAP 顶层规则。

## 3.16.5 规划与校验执行能力需要承接什么？

【工程待核查】

这一能力应支持：

1. 生成具有真实差异的候选。
2. 正确执行基本约束计算。
3. 识别用户价值影响。
4. 检查现实事实。
5. 分析局部变化的连锁影响。
6. 过滤无意义的候选。
7. 输出可解释差异。
8. 识别新冲突。
9. 在许可范围内准备修复方案。
10. 保留未核验条件。
11. 对日期和其他关键条件变化进行必要重算。
12. 在失败时保留已完成的有效成果。

### 实现边界

产品侧不要求其一定由单独 Agent 实现。

但不能仅用 Prompt 宣称能够保证：

- 旅行天数正确。
- 事实可靠。
- 连锁影响完整。
- 约束永不突破。
- 版本恢复无冲突。

这些需要可检查的计算、状态与评测依据。

### 需要区分的评测层级

机制正确性： 状态、确认、恢复、权限和结果是否正确。

规划计算正确性： 天数、连接、影响和约束是否一致。

事实可靠性： 来源、条件、时效与未知是否正确。

用户体验： 用户是否真正理解不同方案的代价，是否能掌控复杂修改。

不能因为机制测试通过，就声称真实用户价值或实际数据覆盖已经验证。

# 3.20 F3 完整设计结论

F3 的设计已经从最初的“生成与比较城市旅行骨架”，扩展为一套支持持续规划和用户重要取舍的交互体系。

其核心成果包括：

第一：有意义的骨架比较。

用户比较的是整趟旅行的体验获得、保留、失去、时间、交通、费用和未知，不只是城市数量。

第二：规划与校验执行能力。

AI 需要有能力生成、检查、比较和修复方案，而不是只依赖自然语言生成。

第三：选择即确认。

用户明确采用一个已经清楚呈现取舍的方案，不需要再经历无意义的重复确认。

第四：重要方案历史。

用户能够回顾重要的旅行规划演化，而不是只保留最新方案。

第五：整份与城市级恢复。

用户可以恢复过去的整趟旅行，也可以仅恢复一座城市的旧安排。

第六：复杂冲突保护。

局部恢复可能影响整趟旅行，AI 应主动计算和准备修复，但不能擅自牺牲其他已确认的旅行价值。

第七：渐进式规划确认。

日期未知时仍可以深入规划，但必须保留现实条件依赖，未来加入具体日期时进行必要重核验和局部修复。

这些设计成果共同决定：

ANTU 的 F3 不是一次性行程生成器，而是支持用户逐步形成、理解、比较、修改和恢复旅行决策的核心规划机制。
