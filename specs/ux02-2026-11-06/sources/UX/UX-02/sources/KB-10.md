Work 进行正式归档和工程交接时，还需要回答五个问题：

第一：每项关键交互究竟需要系统做什么？

不能只写“支持智能推荐”“支持保存”“支持重算”。

第二：业务状态应该怎样变化，哪些状态必须保持不变？

例如用户右滑体验，兴趣可以变化，但有效旅行不能因此变化。

包括语义理解、Trip State、Decision Context、NAP、前端、后端、外部数据、计算、Evals 与运行记录。

第四：怎样证明交互行为真正正确？

不能仅根据模型输出或者技术规格中的描述宣布通过。

第五：当前归档究竟恢复了多少历史内容，还缺少什么？

必须区分已经恢复的设计知识与尚未取得的原始历史证据。

1. 全量设计资料目录与来源覆盖。

## 10.1.3 源资料中的三类不同结论

正式交接时，应把以下三类结论分开。

| 层次          | 可以得出的结论             | 不能直接得出的结论           |
| ----------- | ------------------- | ------------------- |
| UX-02 历史设计  | 产品希望用户如何操作、系统应如何回应  | 具体 API 和 Schema 已存在 |
| PRD 或正式机制资料 | 当前产品需求和机制边界是什么      | 所有需求均已进入当前工程版本      |
| 工程规格与运行结果   | 通过逐项检查可确认设计、实现和测试覆盖 | 未检查前不能直接假设通过        |

### 例子

UX-02.5 要求：

> 用户回来后能够恢复上次未完成的编辑。

这是设计要求。

Decision Context 可能包含跨会话恢复机制。

这是需要对照的工程设计。

但只有进一步检查实际接口、状态读写及运行测试，才能判断它是否真正支持：

- 已保存草稿恢复。
- 正确版本关联。
- 上次操作位置恢复。
- 决策上下文恢复。
- 旧事实重新核验。
- 并发版本安全。

需求存在、规格存在、实现存在、测试通过，是四种不同事实。

## 10.3.1 F1｜意愿启动与探索

需求来源：UX-02 F1；PRD-001、002、007；验收 A01、A02、A07。

| 编号        | 用户操作         | 所需系统行为              | 状态变化与保护          | 工程模块            | 测试重点        |
| --------- | ------------ | ------------------- | ---------------- | --------------- | ----------- |
| F1-REQ-01 | “我想去埃及”      | 识别目的地意愿，提供有限城市与体验参照 | 建立旅行目标，不强造已确认城市  | 语义、TS、DC、NAP、前端 | 无日期预算可开始    |
| F1-REQ-02 | 点击地图城市       | 展示城市位置、体验和相关内容      | 改变浏览焦点，不修改有效旅行   | 前端、DC、内容数据      | 点击不产生正式采用   |
| F1-REQ-03 | 打开体验卡        | 展示体验内容与可靠背景         | 普通浏览不直接形成稳定偏好    | 前端、内容数据、DC      | 浏览与兴趣区分     |
| F1-REQ-04 | 对体验右滑        | 识别正面兴趣反馈            | 记录有范围的兴趣，不自动加入行程 | 前端、语义、TS        | 兴趣不等于决定     |
| F1-REQ-05 | 对体验左滑        | 识别当前排斥或暂不感兴趣的反馈     | 保留作用范围，不永久排除整个城市 | 前端、语义、TS        | 拒绝不错误放大     |
| F1-REQ-06 | “喜欢文化，但怕转场累” | 分别理解兴趣与顾虑           | 条件性偏好保留，不强造疲劳硬阈值 | 语义、TS、DC        | 不推断不存在的数字约束 |

| F1-REQ-08 | 交通信息仅为估算     | 显示来源、条件和核验层级        | 外部事实按实际可靠性记录     | 数据、TS、前端        | 估算与班次区别     |
| F1-REQ-09 | 用户纠正兴趣       | 修正对应理解              | 保留原表达及必要变更依据     | 语义、TS、DC        | 纠错不自动改旅行    |
| F1-REQ-10 | 用户跳过探索直接要方案  | 转入 F3 所需规划行动        | 已有兴趣与条件保留        | NAP、DC、计算       | 不强制完成探索     |

### F1 最重要的技术要求

F1 不只是内容展示前端。

它要求系统同时具有：

- 地图对象与体验内容关联。
- 用户反馈事件的语义区分。
- 兴趣和条件的状态维护。
- 用户原话及适用范围保留。
- 不将行为推断自动升级为正式决定。
- 当前认知问题与相关现实事实关联。
- 允许随时转入其他 Flow。

### 不应自行增加的技术假设

不要求为每个滑卡动作调用一次完整 LLM 推理。

不要求每次查看体验都产生永久偏好。

不要求使用某种固定卡片技术架构。

### F2 与 P01 的特殊关系

PRD-003 的正式基线仍描述为根据决策缺口推荐下一步。

P01 后期机制进一步补充：

当前明确目标、决策缺口、行动资格、预期增量价值和综合成本应该共同影响下一步行动选择。

P01 还明确：

- 不能只看模型自评。
- 不能每轮强制推荐。
- 用户采纳不等于行动真正有效。
- 推荐后的结果需要反馈验证。

### 工程交接限制

P01 已形成正式机制方向，但其模块调整是否已经同步进最新 PRD、DC 和 NAP，需要进一步核查。

不能将 P01 文档提出的所有技术建议直接宣布为已经生效的 NAP 实现规则。

### F4 最重要的技术能力

统一草稿是 F4 的核心工程约束。

用户通过：

- 地图。
- 时间轴。
- AI 对话。

实施的明确修改，必须正确作用于同一业务草稿。

但：

- 普通浏览。
- 体验兴趣。
- 信息询问。
- What-if 假设。
- 历史版本查看。

不能错误写入该草稿。

### 需要特别核查

“地图和时间轴都能展示行程”不等于它们已经支持统一编辑会话。

“Trip State 能保存有效骨架”不等于它已经支持未完成草稿的连续编辑和跨会话恢复。

但系统不能因此生成：

- 虚假的交通班次。
- 虚假的可购买性。
- 虚假的预算总价。
- 虚假的事实核验成功记录。

同时，日期或现实事实后来变化时，系统不能直接推翻用户此前全部价值判断。

# 10.5 按工程模块汇总的能力要求

这部分是 Work 交给工程团队时最重要的检索入口。

它将前面的用户操作要求映射到技术模块，但不代替正式工程设计。

## 10.5.1 模块 M01｜用户语义理解

### 模块需要解决什么？

用户使用自然语言、地图、卡片和时间轴表达旅行意图。

系统必须判断用户究竟在：

- 探索。
- 询问。
- 表达兴趣。
- 表达顾虑。
- 比较。
- 提出假设。
- 请求修改。
- 纠错。
- 拒绝。
- 暂停。
- 采用方案。
- 恢复历史。

### 需要重点支持的语义能力

| 编号     | 具体能力         | 为什么需要            | 主要 Flow |
| ------ | ------------ | ---------------- | ------- |
| SEM-01 | 当前明确请求识别     | 避免系统偏离用户目标       | F1、F2   |
| SEM-02 | 指代解析         | 理解“这个城市”“刚才那套方案” | F2–F6   |
| SEM-03 | 操作对象定位       | 避免改错城市或版本        | F3–F6   |
| SEM-04 | 假设与明确修改区分    | 防止“如果”直接变成有效修改   | F5      |
| SEM-05 | 兴趣与采用区分      | 防止体验反馈升级为决定      | F1、F3   |
| SEM-06 | 明确约束与可调整意向区分 | 避免预算或天数被错误锁定     | F1、F6   |
| SEM-07 | 纠错与新增操作区分    | 避免重复累计修改         | F5      |
| SEM-08 | 拒绝作用范围识别     | 避免局部拒绝被全局扩大      | F2、F3   |
| SEM-09 | 条件化表达理解      | 保留“如果交通不太累”      | F1、F2   |
| SEM-10 | 高影响歧义识别      | 修改对象不明确时安全澄清     | F3–F6   |

### 一个必要的评测案例

用户依次说：

> 开罗减少两天。

> 不对，是减少一天。

系统应判断第二句是否在纠正前一项操作。

不能无条件把第二句解释成再次减少一天。

### 工程边界

不应为语义理解单独创建未经正式设计的“用户心理状态模型”。

也不能仅靠模型自报置信度证明提取正确。

需要以实际业务语义、对象关联和状态结果进行验证。

## 10.5.2 模块 M02｜Trip State

### Trip State 的职责

维护整趟旅行的权威业务信息及其变化依据。

UX-02 对 TS 的要求可以分为六组。

### 第一组：旅行基本对象

需要能正确承接：

- 旅行目标。
- 城市候选。
- 用户偏好与顾虑。
- 时间与预算约束。
- 城市组合。
- 顺序和停留。
- 主要跨城交通。
- 重要体验。
- 已确认决定。
- 相关外部事实。

### 第二组：不同业务语义

需要正确区分：

- 普通探索。
- 兴趣反馈。
- 候选。
- 暂定编辑。
- 已确认旅行。
- 假设。
- 历史记录。
- 待核验事实。

### 第三组：变化与历史

需要承接：

- 用户明确修改。
- 纠错。
- 新的确认决定。
- 重要版本关系。
- 旧版本恢复。
- 城市级恢复。
- 相关变更依据。

### 第四组：状态保护

需要支持：

- 推断不覆盖确认。
- 假设不直接生效。
- 未提交草稿不覆盖有效方案。
- 不受影响的决定保留。
- 更新失败时保留原状态。

### 第五组：现实事实

需要关联：

- 事实来源。
- 查询条件。
- 适用日期。
- 核验层级。
- 有效性。
- 当前未知与冲突。
- 受影响的旅行对象。

### 第六组：跨会话与版本安全

需要核查是否支持：

- 读取当前有效版本。
- 恢复已保存草稿。
- 追踪草稿基准。
- 检查陈旧版本。
- 保留重要变更依据。

### TS 最重要的边界

Trip State 是权威旅行状态，不是下一步行动评分器，也不是所有 UI 焦点的唯一保存位置。

需要与 Decision Context 和前端工作上下文协同。

### 不得自行新增的工程结论

当前不规定：

- 必须新增什么字段。
- 必须新增什么对象。
- 必须采用什么数据库。
- 必须使用事件溯源。
- 必须建立三份独立的 A/B/C 持久化对象。

应先映射到现有 TS 正式对象与合法转换。

## 10.5.3 模块 M03｜Decision Context

### Decision Context 的职责

组织当前决策所需要的上下文，而不是维护第二份独立的有效旅行。

### 需要支持的上下文

| 需求     | 具体含义         | 关联场景      |
| ------ | ------------ | --------- |
| 当前任务   | 用户现在在做什么     | F1–F6     |
| 当前明确请求 | 用户希望系统立即回答什么 | F2        |
| 当前决策问题 | 哪项取舍尚未解决     | F2、F3     |
| 当前浏览焦点 | 正在查看哪个城市或体验  | F1、F4     |
| 当前编辑对象 | 现在应修改哪个草稿    | F4        |
| 当前方案基准 | 假设和比较来自哪份内容  | F3、F5     |
| 相关用户证据 | 偏好、顾虑、限制及来源  | F1–F6     |
| 相关硬约束  | 当前行动必须遵守的条件  | F3–F6     |
| 决策缺口   | 当前阻碍判断的未知或冲突 | F2        |
| 已完成的分析 | 避免重复工作       | F2、F5     |
| 未完成问题  | 后续需要继续的任务    | F2、F6     |
| 事实失效   | 旧核验何时需要重新检查  | F6        |
| 跨会话恢复  | 正确恢复未完成任务上下文 | UX-02.5-A |

### 必须区分的三类“当前”

一个用户可能：

- 当前查看阿斯旺。
- 当前编辑埃及旅行草稿。
- 当前讨论卢克索时间分配。

它们不必指向同一个城市。

### 核心边界

不能让一次浏览焦点切换，把当前编辑基准或用户正式决定错误覆盖。

### 特别需要工程核查

Decision Context V0.1.0 中的跨会话恢复接口，是否真正覆盖 UX-02.5-A 所需的全部恢复信息。

同时检查历史上 0.1.0／0.2.0 的版本引用是否已统一。

## 10.5.4 模块 M04｜Next Action Policy

### NAP 的职责

在当前目标、状态、权限和事实条件下，决定下一步应该采取什么行动。

但它不能代替权威状态保存、真实事实查询和确定性约束计算。

### UX-02 提出的行动类别

- 直接回答。
- 展示信息或体验。
- 解释方案差异。
- 生成候选。
- 查询交通或活动事实。
- 判断重要缺口。
- 提出澄清。
- 推荐下一步。
- 暂时不额外行动。
- 准备修改提案。
- 执行合法草稿修改。
- 请求必要授权。
- 等待用户。
- 处理拒绝。
- 处理失败。
- 恢复未完成讨论。

### 重点 Policy 需求

| 编号         | 行动边界                      | 对应产品问题   |
| ---------- | ------------------------- | -------- |
| NAP-REQ-01 | 用户明确请求优先                  | 不强迫问卷    |
| NAP-REQ-02 | 重要行动先检查权限                 | 不越权改旅行   |
| NAP-REQ-03 | 缺口不直接等于行动价值               | 不过度推荐    |
| NAP-REQ-04 | 允许等待或不介入                  | 不重复打扰    |
| NAP-REQ-05 | 只读探索不改变 Candidate 合法状态    | 不非法重入    |
| NAP-REQ-06 | 假设不等于采用                   | 不误触发业务写入 |
| NAP-REQ-07 | 选择即确认应与合法 Proposal 生命周期兼容 | 不增加无意义确认 |
| NAP-REQ-08 | 重要新取舍必须有授权                | 不静默牺牲体验  |
| NAP-REQ-09 | 回答交付不等于任务确认完成             | 不伪造用户决定  |
| NAP-REQ-10 | 失败后选择安全行动                 | 不重复错误提交  |
| NAP-REQ-11 | 日期依赖有实际决策价值时及时核验          | 不遗漏重大条件  |
| NAP-REQ-12 | 用户拒绝或改道后调整策略              | 不强制原流程   |

### 与 P01 的关系

P01 正式机制提出：

A｜行动资格与边界检查。

B｜相对行动价值与成本比较。

C｜行动效果反馈验证。

其中 B 是下一步行动选择需要补强的关键责任。

但这不要求一定建立三个 Agent。

### 必须核查

P01 正式机制是否已完整同步到当前 NAP 工程原包。

不能仅因 P01 归档中存在调整建议，就宣布当前 NAP 运行时已经采用这些规则。

## 10.5.5 模块 M05｜前端与交互状态

前端不仅需要显示旅行，还需要让用户理解：

目前看到的是什么业务内容，操作会产生什么后果。

### 主要工作空间

历史摘要恢复的后期布局方向：

- 顶部横向时间轴。
- 左侧／中央大地图。
- 右侧整体或城市信息区。
- 地图城市浮层。
- 可持续调用的 AI 对话。
- 候选与历史的必要比较界面。

### 必须承接的状态维度

工作模式：

浏览、编辑、假设、历史查看。

业务内容：

有效旅行、草稿、候选、假设、历史版本。

保存结果：

未保存、保存中、已保存、保存失败。

核验结果：

待核验、已完成当前范围核验、事实失效、已知冲突、工具失败。

提交结果：

提交中、权威确认成功、确认失败、结果未知。

### 跨视图一致性

地图、时间轴、信息区和 AI 对话不能使用彼此矛盾的旅行版本或事实状态。

### 当前仍待 UX-04 验证

- 具体组件。
- 页面尺寸。
- 弹层和侧栏组织。
- 推荐呈现方式。
- 移动端布局。
- 状态颜色与图标。
- 编辑历史和差异视觉。
- 冲突与未知信息层级。

## 10.5.6 模块 M06｜后端、保存与接口

### 后端需要解决的实际问题

用户的交互必须最终对应可检查的真实业务结果。

### 重点能力

1. 读取当前有效旅行。
2. 读取正确的历史版本。
3. 保存未提交草稿。
4. 读取已保存的草稿。
5. 合法应用已确认修改。
6. 维护版本关联。
7. 核查提交基础版本。
8. 避免重复提交产生重复效果。
9. 查询权威提交结果。
10. 支持必要的跨会话恢复。
11. 保存重要决定与变更依据。
12. 在异常情况下保护原有效状态。

### 最关键的两个问题

提交幂等：

用户重复点击或网络重试，不能让同一业务意图重复执行。

版本一致性：

旧草稿不能直接覆盖较新的有效方案。

### 工程设计仍需决定

- 使用什么存储结构。
- 如何标识业务请求。
- 怎样关联草稿与版本。
- 用什么接口查询结果。
- 如何进行安全重试。
- 并发冲突如何协调。
- 失败时如何恢复。

UX-02 只规定需要满足的行为，不擅自规定具体接口名称。

## 10.5.7 模块 M07｜外部数据与工具

### 主要数据类型

- 城市与地理位置。
- 体验内容。
- 交通连接。
- 概略耗时。
- 指定日期的交通条件。
- 体验适用日期与开放信息。
- 有依据的费用。
- 必要的现实约束。

### 事实可靠性要求

系统必须知道：

- 事实来自哪里。
- 查询时用了什么条件。
- 信息适用于什么日期。
- 数据何时取得。
- 结果覆盖什么范围。
- 是否仍然有效。
- 能证明到什么程度。

### 尤其需要区分交通层级

| 层级       | 能支持的结论         | 不能自动推出  |
| -------- | -------------- | ------- |
| 地理连接     | 城市间可能存在地理或路线关联 | 真实交通班次  |
| 有依据的概略时间 | 可以讨论一般时间代价     | 指定日期可执行 |
| 指定日期核验   | 查询条件下有相应事实依据   | 一定可购买   |
| 实际可购买性   | 需要进一步来源和交易条件   | 已完成购买   |

### 数据异常

需要分别处理：

- 超时。
- 空结果。
- 字段不完整。
- 数据失效。
- 条件不适用。
- 经过可靠核验确认无相应服务。

### MVP 范围限制

PRD V0.1 不承诺：

- 全目的地覆盖。
- 全交通方式实时覆盖。
- 全日期实时数据。
- 国际航班联合优化。
- 完整酒店深选。
- 交易和订单执行。

## 10.5.8 模块 M08｜规划、约束与影响计算

### 需要的计算能力

- 城市组合与顺序检查。
- 总天数和停留分配计算。
- 明确硬约束检查。
- 城市连接影响。
- 交通时间和复杂度分析。
- 重要体验保留与损失识别。
- 有依据费用的分项比较。
- 修改的直接与连锁影响。
- 必要范围重算。
- 局部恢复后的关联影响。
- 日期变化后的条件重新核验。
- 冲突及修复方案比较。

### 一个典型例子

用户将卢克索从三天增加到四天。

系统需要判断：

- 总天数是否改变。
- 是否有其他城市被压缩。
- 已确认体验是否受到影响。
- 相邻交通是否需要变化。
- 相关日期条件是否仍适用。

### 重要边界

计算范围可以扩大，但业务修改范围必须受到用户授权约束。

不能因为计算系统认为另一种安排更优，就直接覆盖用户的确认决定。

### 不应默认采用的工程方式

每次编辑都由大模型重新生成完整行程文本。

需要可检查的对象、依赖和计算结果。

## 10.5.9 模块 M09｜AI Evaluation

### 为什么需要？

UX-02 包含许多难以只靠文本示例发现的错误。

例如：

- 模型语言看似正确，但草稿改错了。
- 地图显示正确，但后端未保存。
- AI 推荐合理，但违反用户明确拒绝。
- 交通说明流畅，但依据只是过期估算。
- 提交反馈成功，但权威旅行没有改变。

因此，评测必须同时检查：

模型理解。

业务动作。

状态变化。

事实依据。

用户体验结果。

### 正式 PRD 的基础

PRD §7.6 已要求 AI Evaluation Dataset 覆盖：

- 初始旅行状态。
- 用户输入或操作。
- 工具返回条件。
- 预期状态变化。
- 可接受行动。
- 禁止行为。
- 判断理由。

### 后期 UX-02 增加的重点

- 连续编辑。
- 跨 Flow 状态隔离。
- 跨会话恢复。
- 历史版本恢复。
- 城市级恢复。
- 假设基准。
- 提交结果未知。
- 重复提交。
- 并发版本。
- 事实失效与对象级冲突。

### 状态

【工程待核查】

不能因前述 F1–F6 编写了测试案例，就宣布当前测试集已经包含或运行了这些场景。

## 10.5.10 模块 M10｜运行记录与可观测性

### 为什么需要？

用户旅行状态的错误，往往发生在多个系统协作过程中。

例如：

用户说：

> 开罗减少一天。

系统正确识别了对象，但更新了错误版本。

如果只保存模型输出，很难知道问题发生在哪里。

### 需要能够追踪的内容

| 记录维度      | 作用                  |
| --------- | ------------------- |
| 用户输入或操作   | 知道真实意图来自什么          |
| 当时工作上下文   | 知道处于哪个 Flow、草稿或历史预览 |
| 当前有效版本    | 检查修改基准              |
| 模型解释与候选动作 | 检查语义是否正确            |
| 规则和权限判断   | 检查是否越权              |
| 工具调用条件及结果 | 检查事实来源与失败           |
| 结构计算结果    | 检查天数和影响范围           |
| 状态变更前后差异  | 检查实际更新了什么           |
| 用户确认依据    | 检查修改授权范围            |
| 提交结果      | 区分成功、失败与未知          |
| 恢复或重试关系   | 检查是否重复执行            |
| 评测结果      | 支持回归和错误归因           |

### 重要边界

这些要求是可追溯能力需求，不意味着必须记录或展示模型内部私有推理过程。

也不意味着可以无限保存用户敏感信息。

具体隐私保留期限、数据脱敏和日志策略需要正式工程与合规设计。

# 10.6 工程能力覆盖分类与 MVP 范围边界

这一部分必须严格区分：

产品设计需要什么、PRD 当前承诺什么、正式工程规格写了什么、实际系统实现了什么。

当前只核对了 PRD 和项目机制资料，尚不能完成后两项判断。

## 10.6.1 分类口径

本章将工程要求划分为四类。

| 分类              | 含义                          | 当前如何处理             |
| --------------- | --------------------------- | ------------------ |
| S1｜PRD 已有正式需求   | PRD V0.1 已明确提出对应产品能力        | 保留 PRD 编号，工程仍待核查   |
| S2｜后期 UX 细化要求   | UX-02 对 PRD 已有能力给出更具体行为     | 映射原 PRD，检查是否需补充规格  |
| S3｜后期新增或增强能力    | UX-02 提出新要求，当前无法证明已进入正式工程范围 | 作为范围差异候选，待工程及产品侧核查 |
| S4｜PRD 明确延后或不承诺 | 超出当前 MVP 默认范围               | 保留长期设计价值，不自动纳入本期开发 |

### 关键边界

S3 不是“工程确定缺失”。

S4 也不是“产品永远不需要”。

这两类都要完整保留，但不能误认为当前工程已经承诺。

### 为什么仍然要核查？

因为 PRD 是产品需求文件。

例如：

PRD-005 已明确要求连续地图／时间轴操作累积为暂定骨架。

但尚需工程核查：

- 是否真正支持跨入口编辑。
- 暂定骨架是否可持久化。
- 复杂编辑操作是否可撤销。
- 退出后能否恢复。
- 当前有效版本是否受到保护。

不能用 PRD 条文替代这些验收。

## 10.6.3 S2｜后期 UX 对已有需求的具体化

### 容易混淆的两种“异常”

UX-02.5-C：产品运行异常。

例如编辑保存失败、网络断开、AI 计算失败。

PRD 延后的旅行中异常处理：

例如用户旅行途中航班取消、酒店订单改退及实时应急处置。

两者不是同一范围。

不能因 PRD 延后“旅行中异常处理”，就删除 UX-02.5-C 对编辑成果和系统提交安全的要求。

# 10.7 AI Evaluation 与端到端工程验收计划

本节只提取测试要求，不宣称测试已经执行。

## 10.7.1 测试应该如何组织？

不能只把 F1–F6 每条流程分别测试一遍。

还必须验证跨流程连续轨迹。

建议按四层组织。

### 第一层：单项交互机制

测试：

- 语义提取。
- 兴趣反馈。
- 候选比较。
- 草稿编辑。
- 假设区分。
- 明确采用。
- 事实核验。

### 第二层：连续多轮业务轨迹

测试：

- 多次修改。
- 纠错。
- 拒绝。
- 改道。
- 假设比较。
- 历史查看和恢复。

### 第三层：跨会话与异常

测试：

- 网络断开。
- 页面刷新。
- 重新进入。
- AI 计算中断。
- 外部数据失败。
- 提交结果未知。
- 重复提交。
- 并发版本变化。

### 第四层：真实用户任务价值

测试：

- 是否真正减少用户重复劳动。
- 是否帮助用户理解取舍。
- 是否造成新的认知负担。
- AI 推荐是否恰当。
- 用户是否理解当前业务状态。
- 系统是否可靠保护用户已形成的决定。

工程机制正确，不等于用户体验价值已验证。

## 10.7.2 每个测试用例至少需要哪些信息？

以下是交接所需的测试描述结构，不是规定必须使用同名工程字段。

| 信息          | 为什么需要       |
| ----------- | ----------- |
| 用例编号        | 能定位测试       |
| 需求和 Flow 来源 | 关联 UX 与 PRD |
| 初始有效旅行      | 判断修改是否正确    |
| 初始草稿／假设／历史  | 测试正确工作上下文   |
| 用户原话或操作事件   | 验证真实触发      |
| 用户操作所在入口    | 区分地图、时间轴、对话 |
| 外部数据与工具条件   | 验证事实可靠性     |
| 可接受的系统行动    | 不要求只有一种模型回复 |
| 预期状态变化      | 检查实际业务效果    |
| 必须保持不变的状态   | 检查是否越权      |
| 禁止行为        | 明确关键失败      |

开放式语言任务可以存在多个合理回答。

但关键业务边界不能放宽。

例如：

用户提出“如果不去阿斯旺”，AI 可以用不同措辞解释假设。

但无论措辞怎样，均不能未经授权删除当前有效方案中的阿斯旺。

## 10.7.4 E2E-01｜从陌生目的地探索到正式采用

### 初始状态

用户仅表达：

> 想去埃及。

### 操作轨迹

1. 系统提供有限城市与体验内容。
2. 用户查看开罗和卢克索。
3. 用户对某个卢克索体验表达兴趣。
4. 用户补充担心转场太累。
5. AI 在适当时机提供相关差异和交通代价。
6. 用户请求旅行骨架。
7. 系统形成有意义的候选比较。
8. 用户明确采用其中一套。

### 必须验证

- 初始无需完整日期预算。
- 兴趣和顾虑正确保存。
- 不错误形成硬约束。
- AI 不强制完成固定探索流程。
- 比较内容具有实际差异。
- 正式采用前有效状态受到保护。
- 采用后保存正确旅行和依据。
- 未核验事实仍然标明未知。

### 禁止行为

首次右滑就自动采用城市。

## 10.7.5 E2E-02｜连续编辑与即时反馈

### 初始状态

有效旅行：

开罗三天、卢克索三天、阿斯旺两天。

### 操作轨迹

1. 进入编辑。
2. 卢克索增加一天。
3. 系统即时显示相关变化。
4. 开罗减少一天。
5. 草稿更新为新的八天分配。
6. 用户查看阿斯旺。
7. 返回编辑。
8. 点击完成编辑。

### 必须验证

- 两次修改进入同一草稿。
- 中间状态可继续编辑。
- 地图、时间轴与信息区一致。
- 浏览其他城市不结束编辑。
- 完成编辑前原有效方案不变。
- 完成编辑后执行整组必要校验。
- 无重大新取舍时不要求普通重复确认。

### 禁止行为

第一步修改后，系统强制结束编辑并覆盖有效旅行。

## 10.7.6 E2E-03｜编辑中的假设与返回

### 初始状态

已有有效方案 A 和编辑草稿 B。

### 操作轨迹

1. 用户在 B 上修改停留。
2. 用户说：“如果不去阿斯旺呢？”
3. 系统产生 C。
4. 用户查看 C 的差异。
5. 用户说：“还是保留阿斯旺。”
6. 返回 B。
7. 用户继续原编辑。

### 必须验证

- C 基于正确的 B。
- B 没有被 C 覆盖。
- A 始终保持。
- 用户放弃 C 时不需要重新生成 B。
- 当前草稿原有操作记录仍正确。

### 禁止行为

提出假设就删除草稿中的阿斯旺。

## 10.7.7 E2E-04｜纠错与重要决定保护

### 初始状态

用户已建立若干明确城市停留决定。

### 操作轨迹

1. 用户提出减少两天。
2. 系统形成对应草稿操作。
3. 用户立即纠正：“不是两天，是一天。”
4. 系统修正相关变化。
5. 重新检查受影响结果。
6. 用户最终采用合法修改。

### 必须验证

- 纠错指向原操作。
- 不累计错误增量。
- 无关已确认决定保留。
- 正式采用的变化与用户最终意图一致。
- 必要历史依据可追溯。

### 禁止行为

因为两条指令都出现过，就累计减少三天。

## 10.7.8 E2E-05｜整体版本恢复

### 初始状态

已有：

V1 → V2 → V3。

V3 为当前有效版本。

### 操作轨迹

1. 用户打开 V1。
2. 查看主要差异。
3. 决定恢复 V1。
4. 系统检查当前条件和重要影响。
5. 用户完成必要取舍。
6. 成功形成 V4。

### 必须验证

- 查看 V1 时 V3 不变。
- V1 的旧事实不自动被当作当前有效。
- 恢复操作经过合法授权。
- V4 具有正确历史来源。
- V2、V3 仍可回看。

### 禁止行为

恢复 V1 后删除 V2、V3 的历史。

## 10.7.9 E2E-06｜城市级历史恢复

### 初始状态

用户想恢复卢克索旧版安排。

其他城市已有较新的确认内容。

### 操作轨迹

1. 选择历史来源。
2. 指定只恢复卢克索。
3. 识别局部差异。
4. 检查全程关联影响。
5. 说明是否影响其他体验和交通。
6. 必要时取得用户的新取舍授权。
7. 合法应用恢复。

### 必须验证

- 恢复对象正确。
- 不自动回滚其他城市。
- 没有遗漏重要连接影响。
- 需要扩大分析时不自动扩大修改范围。
- 新版本保存正确依据。

### 禁止行为

用户只恢复卢克索，系统却将开罗和阿斯旺全部恢复为旧版。

## 10.7.10 E2E-07｜无日期采用与补充日期

### 初始状态

用户已选择城市和停留，但日期未知。

### 操作轨迹

1. 用户采用当前骨架。
2. 系统保存当前规划决定。
3. 相关具体交通保持待核验。
4. 用户后来补充日期。
5. 系统识别相关依赖。
6. 重新核验必要部分。
7. 某项事实若出现冲突，进行准确标注。
8. AI 准备修复方向。
9. 用户决定重要调整。

### 必须验证

- 无日期可采用当前规划层次。
- 未知不能被标记为已核验。
- 新日期只触发相关核验。
- 原重要决定不会无故丢失。
- 冲突有对象、来源和影响范围。
- 新重大取舍由用户判断。

### 禁止行为

用户补充日期后，系统自动清空此前所有规划成果。

## 10.7.11 E2E-08｜跨 Flow 编辑连续性

### 操作轨迹

```
F3 正式采用 A
→ F4 编辑 B
→ F1 浏览体验并右滑
→ F5 提出假设 C
→ F3 查看历史方案
→ 返回 F4
→ 继续原编辑 B
```

### 必须验证

- A 保持权威有效。
- B 保留全部合法修改。
- 右滑只记录兴趣。
- C 不覆盖 B。
- 历史查看不自动恢复。
- 返回 F4 后使用正确草稿基准。
- 各视图未出现状态互相污染。

### 禁止行为

将最后查看的历史方案自动作为正在编辑的有效对象。

## 10.7.12 E2E-09｜跨会话恢复与旧事实重核验

### 操作轨迹

1. 用户进入 F4 连续编辑。
2. 草稿成功保存。
3. 用户退出。
4. 过一段时间重新进入。
5. 系统恢复旅行与草稿。
6. 读取当前任务背景。
7. 判断旧现实核验是否仍然适用。
8. 对需要重查的部分进行处理。
9. 用户继续编辑。

### 必须验证

- 已保存草稿不丢失。
- 当前有效方案不被草稿覆盖。
- 恢复后不重新询问已经明确的基础条件。
- 旧事实适用性正确。
- 发现冲突时关联对应对象。
- 工具失败不被显示成已知冲突。

### 禁止行为

只恢复聊天文本，丢弃此前已保存的旅行编辑成果。

## 10.7.13 E2E-10｜正式提交结果未知

### 操作轨迹

1. 用户完成编辑。
2. 系统提交。
3. 网络中断。
4. 用户没有收到成功反馈。
5. 系统尝试核实权威状态。
6. 用户可能再次尝试同一提交。

### 必须验证

- 不立即断言失败。
- 不立即断言成功。
- 保留可恢复的操作信息。
- 不重复应用相同业务改变。
- 最终反馈与权威结果一致。

### 禁止行为

同一次卢克索增加一天的修改被执行两次。

## 10.7.14 E2E-11｜旧草稿与新有效版本并发

### 操作轨迹

1. 设备一基于 V3 编辑。
2. 设备二形成 V4。
3. 设备一恢复旧草稿。
4. 用户尝试提交。
5. 系统发现版本差异。
6. 保留草稿并处理必要冲突。

### 必须验证

- V4 不被静默覆盖。
- 旧草稿的用户意图仍然保留。
- 需要重要取舍时交还用户。
- 不因冲突直接丢弃整轮修改。

## 10.7.15 E2E-12｜回答已交付但用户未确认决定

### 操作轨迹

1. 用户询问两套方案的差异。
2. AI 给出实质性比较。
3. 用户没有选择。
4. 用户转入其他任务。
5. 之后重新讨论该方案。

### 必须验证

- 信息回答已交付。
- 用户尚未采用任何新方案。
- 当前有效旅行保持。
- AI 不反复催问。
- 后续讨论遵守 Candidate 和 Proposal 的合法生命周期。

### 禁止行为

把完整回答的输出，写成用户已经确认或完成业务修改的依据。

# 10.8 AI Evaluation 的错误严重性与验收报告

## 10.8.1 为什么不能只统计总体准确率？

UX-02 中有些错误只是表达不够清楚。

另一些错误会直接破坏用户旅行成果。

例如：

较低风险：

城市介绍不够吸引人。

较高风险：

错误理解用户要修改的城市。

关键风险：

未经授权删除已确认城市，或虚报真实交通班次。

因此，评测需要分类汇报关键失败，而不应将所有结果混成单个平均分。

## 10.8.2 建议保留的错误分类

以下为测试归档建议分类，不代表正式工程评测体系已经采用这些名称。

| 类别         | 错误表现             | 对应 Flow         |
| ---------- | ---------------- | --------------- |
| EV-SEM     | 用户意图或指代错误        | F1–F6           |
| EV-STATE   | 兴趣、候选、草稿、有效状态混淆  | F1、F3–F6        |
| EV-PERM    | 未经授权改变重要决定       | F3–F6           |
| EV-FACT    | 事实来源、适用条件或核验层级错误 | F1、F3、F6        |
| EV-CALC    | 天数、顺序、费用或影响计算错误  | F3–F6           |
| EV-CONTEXT | 跨 Flow 或跨会话上下文错误 | UX-02.5-A/B     |
| EV-VERSION | 历史、恢复或并发版本错误     | F3、F6、UX-02.5   |
| EV-COMMIT  | 提交结果或重复执行错误      | F4、F6、UX-02.5-C |
| EV-ACTION  | 推荐行动不符合目标或价值     | F2              |
| EV-UX      | 用户无法理解当前状态或操作后果  | 所有 Flow         |

### 特别需要单独报告的关键失败

- 已确认决定未经授权被覆盖。
- 用户硬约束被静默放宽。
- 假设直接写入有效状态。
- 查询失败被写成事实不存在。
- 估算被显示成真实班次。
- 部分费用被冒充全程费用。
- 保存失败被显示为成功。
- 同一业务操作重复执行。
- 旧草稿覆盖最新有效版本。
- 已保存的合法旅行成果丢失。

这些不能简单被其他正确回答抵消。

## 10.8.3 行动价值与用户体验的独立验证

P01 已明确提出：

行动前预测 + 行动后轻量验证 + 关键任务结果校验。

因此还需要观察：

- 用户是否更容易理解当前旅行取舍。
- AI 是否减少了用户自行搜索和比较的劳动。
- 推荐是否恰当。
- 是否造成重复打扰。
- 用户是否能够忽略推荐。
- 用户是否可以顺利完成关键任务。
- 用户是否理解已经确认与尚未核验的区别。
- 长期规划成果是否能够稳定续接。

### 不能直接推断

用户点击了推荐，就一定说明推荐有价值。

用户结束对话，就一定说明任务完成。

模型认为自己回答正确，就一定说明用户理解了取舍。
