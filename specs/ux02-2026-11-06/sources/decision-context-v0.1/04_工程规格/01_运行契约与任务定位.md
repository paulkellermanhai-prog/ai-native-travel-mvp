## 1. 分层与版本

运行合同 `runtime_contract_version=0.1.0` 使用独立命名空间 `https://decision-context.example/runtime/0.1/`；它不是 Trip State 的 schema_version，也不是修改已有 DecisionContext 的许可。跨会话恢复接口属于同一首版合同。

- 权威业务层仍是九个持久对象、只读 DecisionContext、两类系统记录和根采用引用。
- 运行层有 Turn、Task Interpretation、Read Packet 等**传输/会话封装**，不进入 state.objects，不新增业务类别，不拥有预算/偏好/采用真值。
- 解释器产出任务理解；运行程序验证形状、引用、来源定位、身份延续和进度边界；程序不能从字符匹配证明语义正确。
- Policy 以组装结果选择动作，不成为首次任务定位的前提；没有在本包实现行动排序、自动提醒或入口路由。

## 2. 基础读取与解释器前置协议

宿主鉴权与旅行访问授权 → 读取 GET state 的固定版本 → 解释器同时读取本轮事件、该版本状态和本会话任务线索 → 输出结构化任务解释 → `open-turn` 校验/注册 → 组装 → Policy/Agent 消费。

基础读取先用完整有限 MVP 状态作为确定性下限，不再做一个依赖 Policy 的“初始 Context”。窗口不足时解释器可受控按 ID 查询；生产实现必须保持同版与保护边界，不得因模型窗口缺省就假造理解。本文不承诺任意大旅行状态均可一次进入模型。

解释器逻辑接口：`interpret(event, authorized_state_snapshot, runtime_focus) -> tasks, focus_keys`。职责包括：多问题拆分、继续/细化/分叉/新题/歧义、候选退出/探索/条件取舍的区别、假设与有效变更意图、适用对象种子和原话证据。模型供应商与提示词实现可替换，但输出必须满足此合同；**本包参考实现接收合成解释结果，不实现真实自然语言解释器**。

## 3. open-turn 请求与字段归属

所有列出字段必填；未知项只能使用合同允许的 null/空列表，不猜值。所有对象拒绝额外字段。

| 字段 | 含义/来源/所有者 | 规则 |
|---|---|---|
| runtime_contract_version | 调用方声明运行协议 | 只接受 0.1.0 |
| trip_id / expected_revision | 宿主定位、解释器所读状态版本 | 必须是授权旅行和当前版本；否则刷新定位 |
| event | 本轮原始输入，宿主采集，不由模型改写 | 结构见下表 |
| tasks | 解释器提出的问题集合 | 至少一个，可宽泛/ambiguous；不是先要求用户明确决策 |
| focus_keys | 本轮主焦点集合 | 非空、不重复，引用本轮 tasks；组装仍每包一个任务 |

| event 字段 | 定义 |
|---|---|
| event_id | 主体内输入事件幂等 ID；同 ID 同请求返回原 Turn，不同内容拒绝 |
| entry | dialogue/map/timeline/comparison；表示入口，不表示用户已确认 |
| text / reference | 原始表达或操作描述、来源定位符；变更命令绑定这两个原值 |
| received_at | 带时区时刻，不得晚于运行时钟；不是事实 observed_at |

## 4. Task Interpretation 的完整业务语义

| 字段 | 规则 |
|---|---|
| task_key | 调用方提出、当前 Runtime 会话/主体内稳定的 ASCII ID；注册器验证，不用 Context.id/Decision.id 代替 |
| question | 当前问题说明；可为尚未成形的探索，不能由其内容自动写业务状态 |
| kind | explore / candidate_tradeoff / skeleton_choice / constraint_adjustment；这是运行分类，不是 Decision.decision_kind |
| target_ids | 同旅行已存在对象；初始探索可为空，不造不存在城市引用 |
| branch | actual / hypothetical；同一身份不跨分支换含义 |
| relation | new / continue / refine / resume / reopen / focus；表示与已有语义问题的关系 |
| related_task_keys | 已定位问题的普通组织关联，不驱动业务传播；同请求只可关联前面已验证的问题或原会话问题，无自关联 |
| certainty | explicit / inferred / ambiguous，描述任务解释；不提升 Preference.certainty 或外部核验 |
| evidence | 非空原话区段列表，每项 start/end 为 Unicode 码点偏移、左闭右开，quote 必须与原文切片相等 |
| progress | open / paused / handled；是会话语义，不写 Context.status 或 Decision.status |
| progress_evidence | open 可为 null；暂停/本次已处理必须有明确表达的区段且 certainty=explicit |

多任务校验全部完成后才注册：任何一项失败不留下半批任务。继续身份必须已存在且 kind/branch 不变；候选集合可变但须有本轮来源。handled 重新推进只能用 reopen；paused 变 open 需要 resume/reopen，不能因 focus 自动恢复。程序只验证这些必要条件；用户实际是否换了目标需解释器评测。

E/Q/S 为不同粒度的相关问题；细化到 Q/S 不关闭 E。焦点切 A/B 不新建 S。原话未给原因，退出原因只能保留未知/原退出表达，不能由相邻顾虑生成确定因果。

P03/P05 的当轮解释仍使用上述原字段：`certainty=ambiguous` 表示问题理解未定，`question` 说明当前有依据的替代解释及尚不明确的对象/范围，`evidence` 精确定位本轮原话；没有可唯一确定的业务对象时 `target_ids=[]`。多个独立问题才拆成多个 Task，不把同一问题的候选解释伪装成已确认的独立任务。`explicit` 只描述解释依据，不是写入授权。解释器应把新反馈与旧原话、对象、范围、时间和条件对照，区分纠错、真实变化、细化或仍不可分；运行程序只验证结构与身份，语义分类需独立评测。

**受信宿主证据读取边界（DC-AC8-PROTOCOL-01，技术方案已裁决，E03 待实现）：**宿主先以当前认证会话和 TripMembership 保存原话、生成可信 `event_id`；**这一步不依赖尚未产生的 `task_key`**。解释器随后提出 Task，DC `open_turn` 验证，宿主再将同一事件与一个或多个已验证任务建立可审计关联；纠错只追加关联修订，不覆盖旧事件。跨轮纠错/指代读取使用当前受信主体、旅行、工作区、已恢复的 `task_key` 与有界时间窗/游标；读时重验会话和成员资格，不采信模型或客户端自报的 owner、trip、task。每条旧证据须有受信记录 ID、原文、来源/入口、服务器时间、主体/旅行及已验证任务关联；旧轮片段只供解释器对照，现行 `Task.evidence` 仍须精确指向**本轮** event，不能把旧文区段伪装成当轮区段。未关联、缺页、乱序、删除/到期、读取失败或权限撤回均不得伪造历史或提升确定性；保留当前输入和已保存 Task 的未知，可继续安全的低风险探索，重要写入仍走当前 Turn/Packet/Grant 与 TS 守卫。记录、关联、幂等/并发、分页和失败细则见[独立宿主数据契约](../03_评审与工程衔接/16_E11宿主交互证据数据契约与验收轨迹.md)。当前 Python 参考 Runtime 没有宿主接口，只验证当轮结构和现有恢复保护。

P04 的未知兴趣不阻止 `explore`。只有目的地意愿也可建立 Task；新偏好须由 TS 合法写入后在新包中读取，弱局部证据不得由任务解释扩大到其他对象。未展示或无反馈不进入否定证据，真实曝光记录由宿主/UX 负责。用户改道可按现有 `new/continue/refine/focus` 关系重定位，不能要求完成固定探索步骤。

## 5. 待处理输入和有效状态双通道

`packet.context + objects` 是当前提交状态的读取表示；`packet.pending_input` 是本轮输入处理结果，两者不得合并成一个“已生效摘要”。

| pending_input 字段 | 定义/更新 |
|---|---|
| event / base_revision | 原事件及解释发生时状态版本，打开本轮时冻结 |
| processing_status | unprocessed 初始；提交后取原变更响应 pending_confirmation/applied/rejected/conflict；proposed 保留给明确的预览集成，参考正常路径不持久生成 |
| proposal_id | 没有提案时 null；原状态系统返回后设置；不是 ChangeRecord.id |
| result_revision | 最后处理响应版本，不把它当输入发生时版本 |
| errors | 原提交错误的 code/message；失败保留请求和原状态，不宣称成功 |

本包不设置“待处理预算=10000”的独立值权威。用户“预算改成一万元”可以被理解、解释拟议影响；只有合法提交成功才改有效 Constraint，再重新组装。明确范围授权无需重复泛化确认。范围/币种/人数关键不明时保留歧义；不能凭“少打扰”自动猜金额或放宽固定条件。

合法更新后重新读取当前状态，重建 Context 和正文；Task Identity 可以延续，但新依据必须校验。若其他入口更新了状态而本轮尚未提交，包提供 `input_based_on_older_revision_revalidate_before_write`，写入还必须绑定当前包与当前版本，不自动重放原提案。

P05 的澄清回答只更新理解与对象定位；若要撤销已确认城市、采用骨架或改硬条件，仍须新的当前输入、当前 Packet 和相应宿主授权。跳过、未回答或拒绝候选解释时，未决任务可以保持 `open/ambiguous`；不得把沉默变成有效状态、授权或 `handled`。等价追问抑制和少量中立选项属于 NAP/UX，不由 DC 运行合同生成。

## 6. 写入授权不是解释器自述

宿主注入 Principal（主体 ID、允许旅行集合），不接受 JSON 中 actor/permissions。`WriteGrant` 是宿主内存的不可变能力参数，绑定主体、event_id、原 change-request 摘要、revision 和到期时刻；持久模式还必须绑定当前 runtime_id 授权代次。它不是远程可自行签发的 JSON 字段。

turn 响应的 runtime_id 由运行层生成，恢复时轮换；checkpoint_ack 在配置持久后端且成功保存时为真实回执，无后端测试模式为 null。宿主不能根据客户端自报 runtime_id 签发授权，仍需验证用户实际指令与当前服务器代次。

- 有精确且有效的宿主 Grant：以 User Actor 走原 submit；原有硬约束/固定条件/确认范围守卫照常执行。
- 无 Grant：以 Model Actor 提案；受保护范围由原系统返回 pending_confirmation，低风险写入遵守原权限。
- 确认只由宿主确认用户点击/指令来源后调用 confirm；原摘要、主体、范围、revision、TTL 与幂等规则均保留。
- 参考实现能验证 Grant 绑定，不验证用户是否真的说了某种语义、也不提供签名/鉴权系统；宿主必须承担这条信任边界。

## 7. 生命周期与 O1

Runtime 实例绑定一个用户/旅行/工作区会话。配置 CheckpointRepository 后，任务/本轮源线索、焦点和草稿跨实例/进程恢复；Packet 与写入授权不恢复。未配置后端的测试模式仍只用内存，返回 recovery_available=false，不满足首版 P0。

当前已实现事务检查点、保存确认、并发与恢复协议，见恢复规格和独立进程/SIGKILL 验收。生产系统仍须落实真实前端、鉴权、会话回收、容量和保留策略；原业务状态/提案/审计的生产持久化按继承规格建设，不由运行检查点代替。
