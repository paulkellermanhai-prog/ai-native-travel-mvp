# 读取、组装与有效性规格｜工程候选 V0.1

日期：2026-10-23。规范实现：[runtime.py](../90_可运行工程包/context_runtime/runtime.py)。继承 Context 形状不变；新增的正文、覆盖与说明只属于运行 Packet。

## 1. 组装的确定性顺序

1. 验证 Principal、turn_id 所有权和 task_key 属于该轮解释。
2. 读取权威 state 快照 A，以 task.target_ids 作显式种子。
3. 为有限 MVP 的可靠召回，额外纳入所有 active/revised TripGoal、所有 active Preference，**不依赖 Candidate 是否已建立 preference_ids 反链**。这选择牺牲少量规模效率，避免新偏好漏入；不采用模型相关性剪枝。
4. 调用原 Store.context；它加入所有活动约束、confirmed 决定、当前根骨架、所有非 resolved 问题，并扩展原引用闭包。不重写这段已确认规则。
5. 读取快照 B，只有 A.revision=Context.state_revision=B.revision 才接受；每个引用版本必须与 A 正文版本一致。最多三次，仍竞争则 SNAPSHOT_BUSY，不无限重试。
6. 用同一份 A 解引用全部 selected IDs，保存完整包快照的摘要、生成时刻及当前证据限制；消费时刻不得已超过 Context.expires_at。
7. 根据正文预算形成完整/分层/受限表示，校验 Packet Schema 后保存会话内包，返回深复制。读取不写 Trip State/业务历史。

保守的全 active Preference 种子是本轮局部实现选择：现有有限数据下不需要新增排序/反向索引服务。未来按适用性减少正文之前，须证明保护/相关性召回完整，不能只看 Token 下降。

P04/P16 沿用这一步：冷启动可没有 Preference；一旦 TS 有合法、仍有效的局部弱兴趣或明确兴趣，它会进入原对象正文并保留 `scope/certainty/support/source`，不能因未与 Candidate 建反链而漏读。DC 不从未展示、无反馈或普通点击构造否定偏好，也不记录 C0/C1/C2、完整曝光和交互负担流水。用户改道或 TS revision 变化时重新定位并组装，旧包不继续作为当前任务依据。

## 2. 同版本读取和并发

参考实现使用原公开 get_state/context/get_state 和单调 revision 的乐观快照协议，不侵入旧 Store 私有锁，也不改原代码。A/B 不一致就丢弃该轮读取。主体/同旅行验证在之前执行。

生产存储适配器应在 MVCC/只读事务或等价固定版本读取中取 state、投影和正文；原子写/鉴权仍由原状态服务负责。必须保持旅行 revision 单调、同 revision 内容不被外部原位改写。不得使用“不报 revision 的数据修复”绕过契约。

每包 snapshot_digest 是确定性 JSON（sorted keys、UTF-8、无多余空白）的 SHA-256，用作内容完整性校验，不是权限凭证、加密或事实真实性证明。当前资源与返回值深复制，客户端改显示摘要不影响存储。

## 3. 阅读包字段

完整结构见 [packet.schema.json](../90_可运行工程包/schemas/packet.schema.json) 和生成字段字典，关键语义如下：

| 字段 | 所有者/含义 |
|---|---|
| runtime_contract_version | 运行协议版本，与 Trip State 独立 |
| packet_id / turn_id | 本次快照与本轮输入的关联；不能跨主体/轮次用于变更 |
| task | 对当前问题解释的复制，仍是解释，不是业务状态 |
| context | 未扩展的正式 DecisionContext，只保存原合同字段 |
| pending_input | 原输入与实际处理结果，不能当有效业务值 |
| objects | 由固定快照解引用的完整原对象，不是改写后的摘要 |
| deferred_ids | 清单中尚未进入首包正文的 ID，明确列出，不静默遗漏 |
| coverage | complete / layered / limited，描述初次正文交付；不会因翻页自动改写原包 |
| evidence_checked_at | 本包证据限制的计算时刻；不替代事实 observed_at 或 expires_at |
| snapshot_digest | state 快照内容摘要；不当事实来源 |
| annotations | 四维消费说明，按以下规则生成，禁止回写成业务值 |
| support | decision_support 或 information_only，是读取支持等级，不是用户确认/事实核验/采用许可 |
| warnings | 过期依据、未完整解引用、原输入版本较旧等限制说明码 |

`task.question/certainty/evidence` 可向 NAP 提供当前暂定问题和当轮原话；跨轮未提交原话只在宿主按[任务证据读取边界](01_运行契约与任务定位.md)验证后供解释器局部校准，不塞入 Packet 或 `objects` 冒充 TS 证据。`pending_input` 明示尚未生效的请求，`context` 与对象正文提供当前目标、保护集合、问题、证据和未知。消费者不得把字段为空机械解释为高价值澄清，也不得从 DC 的注释直接得到 V/C/E 或介入时机裁决。

## 4. 保留、适用、限制、呈现的规则

| 维度 | 当前确定性规则 | 不得推论 |
|---|---|---|
| retained | 正式清单内对象均保留，不因局部焦点移除底座 | 保留等于要立即展示 |
| applicability | trip 范围通常适用；entity 按目标实体/候选 subject/骨架 stops 交集；skeleton 按目标 ID；date/traveler 或不足证据为 unknown。Preference.condition 用原三值计算。Decision 未直接指向目标、Issue 未直接关联目标时为 unknown，不强定等适用 | unknown=false；全部 confirmed 都同等权重 |
| restriction | 不可用事实/未完成评估/未解决问题/非当前授权提示 decision_limit；原骨架 assessment=blocked 提示 known_conflict | 说明码本身是全量硬约束求解器；一个问题阻止全部探索 |
| presentation | 默认为 policy_judgment；dismissed 为 suppressed_unchanged 并带“用于相关结论时需披露”；其他限制可标 limitation_if_used | 已经实现自动提醒策略；dismissed 已解决或能绕过守卫 |

理由码和 evidence_ids 保留说明依据，evidence_ids 当前来自对象 dependencies；原 source/evidence_refs/原事实仍在完整正文。任何新未知不会补造概率分或用户偏好权重。

限制规则是保守消费提示，完整硬冲突判定仍调用原 assess/采用守卫。状态新增硬约束使全部适用骨架复核的既有机制不变。注释判断不覆盖原 scope/condition，不将局部偏好泛化。date/traveler 的精细计算未实现时保留 unknown，不擅自宣称其已满足。

## 5. 状态一致性与证据有效性独立检查

状态检查：旅行、revision、正文摘要、对象版本、原 Context 的保护集合/版本清单/事实状态一致。

证据检查：消费时钟小于包 expires_at；原事实 fact_usable 检查 lifecycle、query_status、核验、freshness、适用性、observed_at、缺字段、到期和查询日期；运行注释另外按当前全程活动 date_window 检查适用性。多个全程日期条件全部符合才作为适用，不擅自选一个忽略另一个。

原 context.stale_fact_ids 按旧合同原样返回；运行发现的“当前日期不适用”等限制在 annotations 追加，不偷偷改原字段语义。引用事实不等于用其支持结论；verification 未达所需级别即限制。用户承认未知不提升核验层级。

P10/C12：当前 TS 投影已把争议而不可消费的事实列入 `stale_fact_ids`，即使该事实单独通过 `fact_usable`。DC 对该清单中的每个事实给出 `decision_limit`；单条事实仍可用时用 `fact_contested` 说明理由，否则用原 `fact_unusable`。这两个理由只是读取注释，不重算 TS 的争议判定；正式新采用仍由 TS 返回 `HARD_CONFLICT` 或其他实际结果。旧 confirmed Decision 仍在保护清单内，`review_state=stale` 只限制当前授权资格，不删除决定或改写根。

失效触发：任何 revision 变化、正文摘要变化、Context 到期、事实/保护集合重新检查不一致。默认 TTL 沿用最多五分钟且不晚于引用事实的下一未来到期，不由新包延长事实生命。页读取前后再次检查；即使本轮无提交，事实过期也拒绝旧页/旧包写入。

## 6. 分层、窗口与降级的精确定义

`body_budget_bytes` 为 objects 数组确定性 UTF-8 JSON 的首包预算，2–10,000,000 字节；不是模型 Token、全部 HTTP 响应字节或完整 Context 清单上限。最小 2 能容纳空数组。没有声称已达到任何性能 SLA。

- 全部正文能放下：complete，support=decision_support，但所有未知/事实/确认/硬约束守卫仍在。
- 放不下：按“任务目标优先、其余 ID 字典序”尝试装完整对象，未放下的逐 ID 列 deferred；有正文为 layered，无正文为 limited，初包 support=information_only。
- 不截对象字段，不删除原引用/硬约束。完整清单、注释和运行原话可能也很长，因此 Packet 是**给宿主编排器的传输包，不是可直接全量塞入模型的 Prompt**。模型端按页读取并显式声明所用范围。
- `pages` 只按原清单读取原快照的完整对象；每次重验 revision/TTL，返回 remaining_ids；服务器记录 delivered。客户端自行声称已读无效。
- delivered 只证明服务器发送过正文，不证明模型理解或用户理解；测模型语义和用户理解仍需独立评测。
- 单个对象也超模型窗口时，本版不提供字段级裁切。只能继续有足够独立依据的低风险信息说明，明确未作全旅行可行性判断；不能把受限服务称为全程个性化推荐。

adopt_skeleton/decide_candidate/withdraw_decision 三类重要选择要求该包完整正文已交付（首包或分页），再走原程序全部守卫与精确授权。非决定性探索可继续；明确用户的约束修正不因包分层被机械阻止，但仍由原全状态守卫校验。不得借此在旧 Context 中把预算先改成新值。

## 7. 重建与错误恢复

快照竞争自动在只读阶段尝试三次；写入/确认不自动重基、不自动换幂等键重试业务动作。包过期/状态变化时必须重新定位仍有效的对象范围、组装、预览并在必要时获得对应新范围授权。问题身份可延续，但旧授权不续期。

读取失败不改变 state/history；页失败不新增 delivered；写入守卫失败保留原状态，pending_input 按真实响应保留失败。缓存不提供完整事件溯源；历史恢复按既有规则创建新暂定版本，不能恢复旧 adopted 资格。

## UX-02：历史比较与当前依据

历史comparison_refs固定对象版本供只读解释；历史旧verified/assessment不成为当前现实事实。恢复准备读取当前TS重新装配硬约束、已确认体验、相邻连接、全程夜数、部分费用与unknowns。异步结果须由宿主绑定trip/task/目标/base_revision/操作代次，不把旧回包写入新草稿。历史与当前焦点分离；分页未完整消费时不授予重要写入。详见[UX02映射](../03_评审与工程衔接/18_UX02行为落实与E03开发验收映射.md)。
