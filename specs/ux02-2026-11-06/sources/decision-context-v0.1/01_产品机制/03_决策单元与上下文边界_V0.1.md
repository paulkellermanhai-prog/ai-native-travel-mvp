## 1. 四种身份不能混用

| 概念 | 身份含义 | 当前是否已有持久契约 |
|---|---|---|
| 决策单元 Decision Unit | 用户正在推进的一个可辨识问题；包括探索性判断 | 本轮语义定义，不新增业务对象 |
| task_id | 一次任务读取的调用方标识，可用于关联同一问题 | 现有接口接受字符串，不提供身份注册和恢复保证 |
| Decision.id | 一条候选选择或骨架采用的价值决定记录 | 有正式对象、版本、确认和替代规则 |
| DecisionContext.id | 某时刻某 revision 的只读投影实例 | 有正式形状与有效期；每次组装可不同 |

一个决策单元可跨多轮、多份 Context；可以没有 Decision，也可以关联多条 Decision。task_id 的字符串相同不能证明用户问题相同；字符串不同也不能证明用户问题一定不同。[S05 §7；S13；C07–C08]

“探索阶段存在决策”与“已有 confirmed Decision 对象”是两个命题。前者包括用户逐渐形成判断，以及系统根据缺口选择交互；后者只有既有合同规定的价值确认。[U02]

## 2. 决策单元的最小业务定义

**决策单元是：在同一旅行目标范围内，围绕一个可解释的主问题持续组织探索、依据和取舍的语义单位。** 它不要求一开始就有有限候选，也不要求以确认结束。[C07]

其识别需要理解四件事，不是本轮新增四个 Schema 字段：

1. 用户想推进什么问题：了解差异、形成偏好、取舍城市、选择骨架，还是调整条件。
2. 问题作用在哪个旅行、对象范围和方案/假设分支。
3. 怎样算暂时推进了问题：更清楚差异、表达出顾虑、作出选择，或明确知道当前阻碍。不是统一的“确认按钮”。
4. 与已有问题的关系：继续、细化、依赖、改换目标、重审，还是新任务。

例：“想去埃及，先看看有什么不同”可有一个探索性问题；“这两个骨架该选哪个”是明确比较问题。前者逐渐收敛到后者时，要保留讨论来源关联，但不声称两者在全部粒度上必须拥有同一个 task_id。

### 2.1 V04 的 E、Q、S 身份收口【U03；C22】

本用例中 **E、Q、S 是三个不同粒度、相互关联的判断问题，不是同一身份的三个生命周期状态**：E 是形成认知/偏好的宽探索问题，Q 是某城市是否纳入的局部取舍，S 是哪版整体骨架被采用。它们可以共存；Q 对 S 提供依据，二者继承 E 的适用偏好与来源，不继承不适用的授权。

V04 在同一问题内的焦点变化不新建身份，例如在 S 内从 A 切 B；从 E 细化到 Q 只表示当前焦点变化，不说明 E 已完成。只有用户明确不再推进原问题，或存在有依据的当次完成条件，才描述该问题本次已处理；不能从“打开骨架页”推断探索结束。形成中边界不清时允许暂定关联，不强迫每句话唯一归类。

H 是 Q 关联的假设分支读取，不是第四类新增业务对象。E/Q/S/H 都只是用例标签，不是持久 ID 格式或需要新增的正式 enum。运行 task_id 如何表达这些身份与关系仍由下一轮封装设计决定，不能用标签替代实现。

## 3. 连续性规则：不依赖词面或候选数量

| 用户变化 | 建议身份判断 | 保留什么、重新检查什么 |
|---|---|---|
| 比较 A/B，用户从 A 点开 B | 同一主问题 | 比较目的、偏好和条件保留；视图焦点变化 |
| 比较 A/B 后换成 B/C，仍解决同一城市组合问题 | 通常同一问题的新候选集合 | 新引用与版本；不能抹去 A 的退出原因 |
| “先了解一下卢克索”后“卢克索与阿斯旺怎么取舍” | 原探索的收敛/细化，可关联新的比较单元 | 保留来源和已形成判断；避免无限复用一个大任务 |
| “八天改六天，仍做这次埃及旅行” | 通常同一骨架问题的重审 | 新约束与失效传播；旧事实不默认适用 |
| “不是改行程，只看看少两天会怎样” | 原问题关联的独立假设分支 | scenario 隔离；不覆盖原问题的有效条件 |
| “不去埃及了，改成另一趟日本旅行” | 新旅行/新目标问题，不静默迁移 | 旧旅行保留；跨旅行偏好复用需另有依据和授权 |
| “这次还是埃及，但由文化为主改成陪老人慢游” | 同旅行目标发生实质变化；建议新主问题并关联旧问题 | 走明确目标变更；旧决定保留待复核，不隐式撤销 |
| “接着昨天那两个方案” | 候选与原问题可唯一定位才恢复；不唯一则保留歧义 | 当前状态、旧选择及变化记录；不复用昨天 Context |
| 用户明确撤回采用，仍想比较原两个方案 | 原问题重开 | 撤回后的根引用与决定状态；不自动回退旧方案 |

这些是语义判据，不是已实现的意图分类器或绝对相似度阈值。证据不足且误合并会改变重要范围时，才需要针对性澄清；纯阅读焦点可先采取不写状态的可逆处理。[C08]

### 3.1 为什么修改约束通常不新开问题

用户仍想解决“本次旅行怎样安排”，约束改变的是解空间而非必然改变目标。每次改日期就新建互不关联的任务，会丢失先前价值权衡。反过来，把“目的地和同行目的全换了”仍当原题，会把旧决定错误带入新旅行。

问题身份应相对稳定，依据与确认版本必须严格更新。这种不对称是连续性的核心。

## 4. 并行问题、拆分与依赖

一趟旅行可同时存在“是否去卢克索”“哪版骨架合适”“预算是否愿意调整”。一句话也可同时涉及它们。例如：“保留卢克索，预算可以多一点，但别动回程。”

应识别多个受影响范围：候选价值选择、预算表达、回程约束。不得用一条笼统确认覆盖所有变化；能否在同一原子命令批次提交由既有合同决定。

本轮推荐：**允许多个语义问题共存；每份 Context 对外说明一个主问题，其他问题以相关依据、保护边界或待解决依赖出现。** 一次输入可以形成多个任务读取，但不能因此并行写入互相冲突的状态。[C11]

当子问题能够独立表达、可单独暂停，或其完成条件显著不同，就值得拆分；否则保留为原问题的条件，避免把每个缺字段都建成任务。

依赖至少区分两类：

- 业务影响依赖：已有 typed dependencies、条件引用、骨架/决定关联及隐式传播负责；不新建完整决策图。
- 用户问题的组织关系：某骨架比较受预算判断影响，或探索问题逐渐收敛成比较。这是运行层关联，不得拿普通任务关联驱动业务失效。

尚无预算上限时，不必机械阻止所有探索。某连接事实缺失时，会限制骨架可行性判断，但不必阻止用户表达喜欢某体验。何者先处理是 Policy 问题，不在本轮制定排序。

## 5. 问题进程与投影生命周期分离

以下是业务解释词，不发布新 enum：

- **形成中**：已有探索需求，尚不能准确表达主问题或比较对象。
- **处理中**：当前围绕问题积累认知、偏好、候选或选择。
- **暂时受阻**：有明确缺失、证据冲突或能力限制；不等于必须停止全部交互。
- **暂停**：当前不继续该问题；不撤销任何既有决定。
- **本次已处理**：探索已达到当前认知目的、选择已表达，或用户明确不再推进；不等于现实全部核验。
- **重审**：相关依据/目标改变，重新评估原问题；不自动撤销 Decision。

其中当前焦点、暂停、是否需要新交互，由用户行为和上层任务/交互管理承担；Context 只为选定问题提供读取。系统不能在 Context 内偷偷维护一套权威进度，再让 Policy 盲从。[C07、C11]

TripGoal.current_task 是既有用户目标表达，不是每次点击、短暂切换的运行焦点字段。不能为方便任务导航而让 AI 反复覆写它。[S06、S08]

输入理解/任务定位先从本轮事件、基础状态和已有焦点线索识别这些问题及关系，再由组装器读取；Policy 不承担首次定位的唯一前提。完整前置契约见主文档 §3.2。问题定位只提出范围/关系，不自动产生退出原因或改写业务状态。

### 5.1 少打扰与精确授权不冲突【U03；C23】

不为每次认识变化、浏览、焦点切换、普通说明或合法的明确范围修改重复询问。程序自动完成能够确定的形状、版本、权限与依赖检查；探索内容可保留暂定解释，不为填满内部字段打断用户。

只有歧义会影响重要范围、拟议变更没有相应用户授权、与固定现实条件/确认决定有实质冲突等，才需要针对性澄清或正式确认。已有明确授权不重复收集；新版本/提案摘要变化导致旧确认不能复用时，才按既定规则重新预览。用户拒绝不应导致系统换一种问法不断施压。

因此“保持原因未知”和“问用户为什么”不是同一个动作：V04 阶段 3 完全可以先合法记录退出与原因未表达，继续探索，不必强问是否因为转场。

## 6. 切换、暂停与恢复的操作语义

### 6.1 切换

用户从比较切到地图或说明页，如果仍解决同一问题，只改变入口/焦点；依据对象与确认范围不随 UI 标签改变。用户主动改道不应丢状态，也不应被强制拉回原推荐入口。

### 6.2 暂停

暂停意味着不再主动围绕该问题持续交互，不等于 Candidate.excluded、Decision.revoked 或 OpenIssue.resolved。尚未消费的旧 Context 不因为“暂存”而延长有效期；旧确认提案也不延长。

### 6.3 恢复

恢复需要辨认原问题与对象，再从当前 Trip State 重建依据，说明会实质影响当前判断的变化。旧决定若已撤销，只能作为历史；旧事实若过期，保留其历史解释用途，不能支持当前可行性。根引用为空时，不因找到了旧方案就恢复采用。

若中断时只存在未提交的模型草案或本地编辑，现有权威状态不能保证恢复。不能声称“有 Chat History 就能无损还原”。未提交内容的恢复是额外产品/工程承诺，需要单独设计。

## 7. 跨会话恢复：必须公开的缺口与推荐

目前已有证据保证业务状态与历史可表达，**没有证据保证 task_id 的语义身份、暂停书签、未提交内容或生产重启后的会话恢复已经实现**。[S05 §10；S13]

备选方案：

| 方案 | 能力 | 代价/风险 | 建议 |
|---|---|---|---|
| R0：仅本会话焦点；重新进入靠当前状态/历史定位 | 无新增任务持久机制 | 无法保证精确回到暂停问题；可能需用户澄清 | P0 的保守下限，不包装成无缝恢复 |
| R1：轻量持久任务书签，保存身份与权威引用，不复制业务值 | 可更可靠定位原问题 | 新增运行存储、权限、删除/保留和陈旧指针处理；尚未批准 | 若无缝跨会话是发布必要承诺，再选；第二阶段评估 |
| R2：完整任务状态机和可回放工作流 | 可管理复杂并行与长任务 | 迁移、同步、恢复、冲突和运维成本高 | V0.1 不推荐 |

**推荐评审立场**：P0 先保证“业务状态连续、可基于当前状态恢复讨论”，不承诺“精确回到每个暂停点”。若 Owner 认为后者是核心差异化，转向 R1，而不是悄悄在 Context 或 ChangeRecord 中塞一套任务业务状态。[C12；待 Owner 审核 O1]

R1 即使不新增业务对象，也增加真实工程成本；“只是元信息”不能作为免评审理由。任何扩展都不得把新字段塞进严格拒绝额外字段的 0.1.0 合同。

## 8. Context 自有元信息与外部依据

继承的自有元信息：投影 id、trip_id、task_id、status、state_revision、assembled_at、expires_at 和版本引用清单。它们描述这次读取，不承载用户价值真值。

当前主问题的自然语言说明、问题关系、缺口解释、焦点来源，属于本轮需求；并非现有 Context 已有字段。第二阶段需决定作为读取封装/运行输入还是经版本化的合同扩展，不能直接加入旧对象。

缺口也分层：有确切事实的“日期未提供”“条件结果 unknown”可确定描述；“用户可能缺少文化体验参照”是推断，应带来源和可纠正标识；“下一步应该展示地图”是行动判断，归 Policy。

## 9. Product / Business Sense：身份边界为何影响成本

拆分过细，用户每次点一下都像新任务，系统要维护大量进度；合并过粗，所有探索都变成“规划埃及”一大团，无法判断何时换了问题。好的粒度不是最整齐的层级，而是既能解释用户行为、又能防止跨问题错误应用依据的最小单位。

业务状态恢复与工作现场恢复也是不同服务承诺。前者复用已完成的 State System；后者还需要保存焦点、草稿和导航关系。先明确要替用户省哪一种劳动，才能判断多一套持久机制是否值得投入。
