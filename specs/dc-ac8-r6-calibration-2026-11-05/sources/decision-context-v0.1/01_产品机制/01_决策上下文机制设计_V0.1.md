## 1. 从什么用户失败出发

目标用户是希望掌控重要取舍、但不愿自己连接全部资料和规划细节的轻量自主旅行者。MVP 是有限埃及城市范围的旅行骨架，而不是全球自动预订助手。[S01 §2.3–2.5；S02 §1–3]

典型失败不是“模型记不住一句话”，而是：

1. 用户说“卢克索这次先不去，但我仍喜欢文化体验”，系统下一轮把文化偏好一起丢掉。
2. 用户回来继续比较两个骨架，系统沿用上周的交通观察，误称旧方案现在仍可行。
3. 用户在比较中拖动停留，系统把暂定编辑解释为已采用，覆盖当前方案。
4. 用户问“少两天会怎样”，系统直接修改有效日期并围绕一个假设推进。
5. 用户已经更正预算，系统仍从旧聊天摘要提取“两万硬上限”，重复澄清或错误拒绝方案。

这些失败损害的是**受约束的决策连续性**：用户能保留已形成的理解与价值选择，同时知道什么因新条件需要重审。连续性不等于永远维持旧结论，而是能解释“问题为何还在、依据哪里变了、哪些决定没有被改动”。[本轮推导 C01]

## 2. 可检验的职责定义

决策上下文（Decision Context）是：**面向当前旅行判断任务——包括尚未完全识别、尚未形成明确选择或正式 Decision 的探索性问题——基于同一旅行版本与消费时刻组装的只读依据视图；它把相关对象、确认边界、现实限制和未解决条件连接起来，让消费者知道能据什么判断、不能把什么当成事实或授权。** 未完全识别的问题允许以有来源的暂定理解进入，不能以“请先明确决策”作为探索服务的前置门槛。

其价值顺序是：

1. 正确延续用户正在解决的问题，并保留重要价值选择的自主权。
2. 防止过期、不适用、推断或待确认内容污染当前判断。
3. 减少用户重新解释与纠错的劳动，支持在探索和规划间来回移动。
4. 在上述前提下，降低无关内容和模型阅读成本。

“缩短 Prompt”“减少 Token”是可能的工程收益，不是成立的产品理由；现有保守投影甚至可能比一段摘要更大。[C01、C02]

可检验标准：恢复旧讨论时不重复询问已明确且仍有效的条件；候选退出不丢跨候选偏好；版本或时效变化不继续消费旧依据；暂定、假设、确认、核验分别可辨；任一重要结论可定位对象版本和来源。实际改善幅度待评测，不预报提升百分比。

补充标准【U03】：**用户在探索中形成、修正、否定或重新确认的认知与偏好，必须能够在合法状态更新后反映到后续决策上下文；同时保留来源、适用范围和确认边界，避免把暂时的想法升级为稳定偏好。** 认知变化不意味着新增一个“认知真值对象”：按内容归入已有目标、偏好、候选、事实或问题；未能合法映射的理解保留为可纠正的运行解释，不冒充已提交业务状态。

## 3. Chat History、Trip State 和其他系统各管什么

| 层 | 解决的问题 | 不应承担的职责 |
|---|---|---|
| 对话历史 Chat History | 用户当时怎样表达、指代、解释或纠正；还原语境 | 按最后一句话决定权威值；把模型叙述当确认或外部证据 |
| 输入理解与任务定位 Input Interpretation & Task Resolution | 在受控读取基础状态后，辨认本轮涉及的问题、关系、分支与待处理变更，提出有来源的暂定焦点 | 不选择最终下一行动；不直接写业务真值；不要求先有完整任务专用 Context |
| 完整旅行状态 Trip State | 当前业务真值、对象关系、有效选择、约束、证据与变更历史 | 自己决定眼前要展示或优先处理哪个用户问题 |
| 决策上下文 Decision Context | 为当前任务提供可解释、可追溯、时效受控的依据与限制 | 保存另一份偏好、预算、事实或采用结果；决定下一行动 |
| 既有决定 Decision | 谁在何时、对哪个候选或骨架版本作了什么价值选择 | 代表全部讨论过程；保存预算修改或所有任务的完成状态 |
| 下一行动策略 Next Action Policy | 根据缺口、权限、能力与成本选择行动及交互方式 | 重写事实、绕过状态守卫，或把缺口本身当行动指令 |
| 业务命令、校验和确认链路 | 校验并应用合法写入，维护原子性与授权 | 依赖模型口头承诺“用户大概同意了” |

2026-11-05/DC-AC8-PROTOCOL-01 技术裁决：跨轮未提交原话及解释证据优先由**受信宿主交互记录**承载；可信事件先于任务解释保存，随后建立有依据的 `event_id → task_key` 关联。DC 按当前任务、主体和旅行按需读取并组织有来源的解释，不在 TS 或 Checkpoint 写完整对话流水。当前宿主尚无可授权、可追溯的交互证据读取实现，故此处是职责与 E03 接入要求，不能称完整解释证据链已恢复；证据缺失时保留未知，仍按原 0.1.0 Checkpoint 恢复现有任务现场。具体输入校验见[运行契约 §4](../04_工程规格/01_运行契约与任务定位.md)，恢复失败边界见[恢复规格 §6](../04_工程规格/05_持久检查点与跨会话恢复规格.md)。

DecisionContext 本身已属于十类对象之一，但只作派生投影。九个持久业务对象、两类系统记录和根采用引用保持原样。[S05 §1、3、7；S10 I02–I03]

重要区别：探索阶段也有用户判断和系统交互决策，并不在决策之外；但当前问题可以尚未产生任何正式 Decision 记录。一个问题也可能产生多个候选选择和一个骨架采用决定。反过来，已确认 Decision 的依据改变后，该问题可重新打开，而 Decision 只变待复核，不自动撤销。[S05 §3、5；S07；U02；C08]

例如用户“不知道两座城市有什么区别”，Context 应提供当前理解、已有反馈、差异资料和认知缺口；选择用说明、探索、澄清还是核验，由 Policy 负责。识别缺口和选择交互都是探索阶段必要能力，不能因为尚无 confirmed Decision 就跳过它们。

### 3.1 不该靠 Context 修的问题

- 偏好范围错误：修 Preference 及证据，不在 Context 摘要中偷偷纠正。
- 用户真正更改日期：走 Constraint 变更及传播，不只替换当前提示词中的日期。
- 交通事实失效：由事实消费检查、状态维护和有限重算处理；Context 不能将旧事实重新核验。
- 新骨架采用：走 Decision 与根引用原子更新，不写“本轮已确定”标签替代。
- 用户说“暂不管”：保留 OpenIssue 的限制，不把 dismissed 改写为 resolved。
- 工具或计算不覆盖：明确能力缺口，增加上下文不能创造数据或可行性证据。

### 3.2 任务识别与上下文组装的前置契约【U03；C17】

任务识别归**运行层的输入理解与任务定位职责**，位于任务专用 Context 组装之前；这是逻辑职责，不要求新增 Agent、服务或持久业务对象。不能交给只读 Context 自己管理焦点，也不要求 Policy 先拿到完整任务 Context 才能识别任务。

职责链：输入与事件 → 基础状态读取 → 输入理解/任务定位 → 合法变更处理（如需要）→ 以新版本重新定位/组装 → Policy 消费并选择行动。合法写入无需每轮发生；无写入时用原有效版本继续。Policy 可以提出后续焦点调整，但不得倒过来成为首次任务定位的唯一前提。

| 前置契约 | 本轮确定的业务含义 | 后续工程细化 |
|---|---|---|
| 输入 | 经鉴权的 trip_id/入口/本轮原话或操作；当前旅行 revision；运行焦点/可用历史定位线索；最小基础状态与必要按 ID 读取 | 读取权限、容量、来源定位、并发处理 |
| 输出 | 一组暂定问题及关系、主焦点或尚不唯一的范围、已有对象种子、假设/有效变更之别、待处理输入与拟议变更及其证据/歧义 | 运行封装形状与验证；不是向 0.1.0 塞新字段 |
| 约束 | 允许问题尚未成形；不伪造身份、因果或授权；最新输入与有效状态分开；不把任务识别结果直接变成业务状态 | 识别评测与失败信号 |
| 写入后 | 只以提交响应和当前状态确定是否生效；revision 变化须重新验证焦点/种子并重建 Context | 重建/重试合同；不无限循环 |
| 证据不足 | 可逆的探索解释可先继续；只有歧义会影响保护范围或不可逆/重要变更时才针对性澄清 | 不预定 Policy 行动排序 |

基础读取不是“另一个业务 Context”：它复用状态读取、权限及保护规则，为输入定位提供足够依据；其阅读范围与任务专用投影不同，具体容量与读取契约待设计，不能无限读取聊天替代状态。

八项机制融合后的任务定位沿用同一前置链：`Task Interpretation` 是可修正的当前理解，不是用户意图真值。解释器须区分当前任务、对象、范围、条件和关键不确定性；仅当有证据的替代解释会改变当前回应、重要写入范围或授权后果时，才将其作为当前任务的未决部分传给消费者。新反馈应先比较原话、对象、范围、时间和条件，再局部修正相关任务；合法业务变更交给 Trip State，其他任务和已确认决定不随解释改写。现行 `question/certainty/evidence/target_ids` 可承载一个暂定问题及其当轮原话；跨轮未提交证据按上节宿主边界处理，不扩大 Checkpoint 或假报已联通宿主记录。

例：“我不想去大阪了，东京怎么样？对了，预算能不能再低一些？”应识别：大阪退出表达、东京探索、降低预算的可行性/取舍问题；它们共享旅行预算和部分偏好，但不是同一笔无条件写入。东京尚未被接受，“能不能再低”没有给出新预算值，不能直接改 Constraint。“不想去大阪”若触及已确认采用或外部承诺，要走既有影响/守卫；否则按明确范围处理，不强加额外确认。日本仅用于语义压力测试，不扩张埃及 MVP 数据覆盖。

## 4. 三种架构的实质比较

比较不是重新投票推翻既有合同。B 或含新业务真值的 C 若要落地，必须作为另一次明确的规格变更评审。本轮只证明推荐是否有足够理由维持约束。

| 维度 | A：动态派生视图 | B：独立维护的上下文状态 | C：引用、动态组装与持久记录组合 |
|---|---|---|---|
| 真值与一致性 | 业务值归 Trip State，重建可消除旧投影 | 同值两处维护，需合并与冲突协议 | 若只复用既有业务记录，与 A 一致；若复制则退化为 B |
| 跨轮行为 | 当前依据可恢复；单凭视图不能保证任务身份 | 易表达任务进展，但会混入业务值与任务状态 | 任务身份可由运行层辅助；事实仍重建 |
| 传播 | 复用 revision、版本和依赖失效 | 需再维护一套失效/补丁/补偿链 | 持久依据复用既有传播；新增元信息须独立界定 |
| 生命周期 | 单次投影的有效/失效/释放 | 长寿命对象，需迁移、过期和并发控制 | 区分业务历史、任务连续性和投影有效期 |
| 成本与性能 | 每次闭包和解引用有开销，可测后优化 | 读快的可能性伴随写放大、锁与恢复成本 | 可缓存但不免校验；按需诊断，不保存所有完整快照 |
| 可解释性 | 清单、版本、来源明确 | 若只存总结，难解释旧值从哪来 | 引用与历史可解释；仍需记录组装器/模板版本 |
| 交付复杂性 | 现有合同已支持主体，任务与消费语义仍缺 | 增加写接口、权限、对象生命周期、迁移和一致性测试 | 受限组合可增量交付；无限扩张则复杂度最高 |
| 本项目判断 | 作为 Context 对象实现方式采用 | V0.1 不采用 | 只采用“现有持久记录 + A”的组合解释，不另建 Context 真值库 |

### 4.1 推荐的准确含义

**A 是投影实现，受限 C 是系统组成，二者不是相互竞争的持久模型。**

持久保存的“已经决定”“为何改变”“哪个事实取代旧事实”仍分别由 Decision、OperationIntent、ChangeRecord、ExternalFact 等承担。按 task_id 生成的 Context 只引用它们。决策单元是本轮提出的任务语义，不自动成为持久对象。[C03]

为什么不选 B：眼前的痛点是识别任务与正确取证，不是缺少另一处存预算和偏好。B 要承担跨入口双写、事实过期传播、确认撤回同步和历史恢复的维护成本，却没有当前证据表明必须如此。若未来出现独立于旅行状态的长期协作任务、多人责任分配或大量非业务工作进度，再以真实失败证据审视任务服务，不能在 V0.1 提前建设。

为什么不只说“A 已有所以完事”：当前请求只有 task_id 和种子对象，尚无语义身份规则、跨会话可靠恢复承诺、反向相关性召回保证和同版本解引用契约。它能输出合法投影，不证明 Agent 能正确延续问题。新增设计价值在这些缺口，而非更换存储范式。[S13；C04–C06]

### 4.2 独立生命周期到底有没有

- 投影有已定义的生命周期：assembled → active → stale → released；参考实现直接创建 active，通过检查发现失效，不将这些状态逐一持久化。
- 用户问题有不同的语义进程：形成中、处理中、暂停、重新评估等，是本轮待审核的运行层概念，不能拿 Context.status 来承载。
- Decision 有自己的确认、修订和撤销生命周期；事实失效不等于用户问题结束，也不等于 Decision.revoked。

所以“Context 有有效期”与“Context 是独立业务真值”没有逻辑蕴含关系。[S06–S07；C07]

## 5. 读取内容的边界

### 5.1 继承的安全底座，不能由相关性裁剪

当前正式实现会加入所有活动 Constraint、所有 confirmed Decision、当前有效骨架、所有非 resolved OpenIssue（包括 dismissed），再沿引用闭包扩展。其中所有活动 hard Constraint 单列为 must_include_constraints。[S05 §7；S13 context]

不能把“任务聚焦”偷换为删掉这些底座。可以在展示或消费说明中区分“当前任务直接相关”和“全旅行保护条件”，但要保留约束的 scope、condition 和未知，不把局部约束错误用于每一候选。跨旅行数据不进入。[C05]

**保留、适用、阻塞、呈现是四个独立问题**，不是统一权重或四个新增业务字段：[U03；C18]

| 判断 | 谁负责、依据什么 | 不允许的推论 |
|---|---|---|
| 必须保留吗 | 正式投影/引用合同保证底座和来源完整 | 保留就应每轮展示 |
| 当前适用吗 | 基于 scope、condition、对象/分支、确认范围和当前证据判断；不确定则保留 unknown | 历史 confirmed 在任何任务都一律适用 |
| 阻碍什么推进吗 | 既有程序守卫判断已知硬冲突；缺证据限制特定结论，Context 只表达限制 | 有 OpenIssue 就阻止一切探索；dismissed 就可绕过硬守卫 |
| 值得主动呈现吗 | Policy 根据用户暂缓意图、影响变化和当前任务决定，Context 提供依据 | 因保留一个 dismissed 问题就每轮催办 |

dismissed 问题没有新相关变化、用户未重开、也不影响当前判断时，不应仅因“仍在底座”重复打断。若其限制现在直接影响用户要作的采用/可行性判断，应说明该限制而不假装已解决；新依赖变化可按原规则重开。具体提醒频率/路由留给 Policy，不在 Context 设定优先级分数。

### 5.2 任务相关内容

按需补齐：当前目标、比较对象及其版本、适用偏好与顾虑、条件依据、候选退出/重入原因、受影响骨架与确认范围、费用口径及缺项、历史中与本问题相关的纠正或替代关系。

冷启动只知道目的地时，兴趣保持未知，探索任务可以没有候选、偏好或正式 Decision。已记录的局部轻量兴趣仍按原 `scope/condition/certainty/support/source` 读取；未展示、无反馈、点击或浏览本身不能推出稳定、排他或相反兴趣。用户明确改道时重定位焦点并重建相关包，不把探索固定成问卷。是否深化、提供哪种参照及个性化强度由 NAP/UX 根据证据决定，DC 只提供当前任务和有界依据。

这里“补齐”是后续种子选择与读取需求，不声称现有闭包已经自动找到全部内容。特别是：TripGoal 不保证自动入选；只沿 Candidate.preference_ids 正向查找可能漏掉尚未关联的新偏好；未写入 Trip State 的最新输入是待解释材料，不应伪装为已生效状态。[C04]

**本轮输入的双通道消费契约**：[U03；C19]

- 已提交权威通道：现有 Trip State 及只读 Context，明确 revision、来源、范围和时效。
- 待处理输入通道：本轮原话/操作、发生时版本、正在解释/拟议/等待确认/失败的处理结果，与已生效值分开。它是运行输入封装，不是第二份业务状态，不能直接并入已确认摘要。
- 消费者必须阅读两者：能理解“用户正要求改预算”，但在提交成功前不能声称“预算已改”。可说明拟议影响/条件，不能依赖未生效值作正式采用判断。
- “预算改成一万元”若币种、人数、范围可从现有状态唯一解析且用户有权修改，明确指令可授权该范围写入，合法提交后重建 Context；不再问一遍泛化“是否确认”。若与固定条件冲突、范围关键不明或提交失败，保留原状态并说明具体阻碍，不能忽略新输入或假报成功。
- 不在读取时隐式写入，也不将模型解析出的“可能已经同意”当提交响应。待确认差异与失败输入均不得被下一轮摘要升级为已生效值。

歧义未解时，保留原话、`ambiguous` 任务和未知对象/范围；能够安全服务多个解释的阅读任务可以继续。对象、范围或权限不明的重要变更不得由 DC 猜测执行；定向澄清只帮助理解，不构成变更授权。用户跳过、不回答或自由更正后，解释器按新证据继续或重定位任务；是否追问、选项文案、重复抑制由 NAP/UX 决定。当前合同只保证最近成功保存的任务事件与明确草稿可跨会话恢复，不宣称拥有完整交互流水。

### 5.3 需要排除或隔离的内容

排除无关历史长文、其他旅行的信息、隐私凭据、不能说明来源的总结。隔离假设场景、待确认差异、已撤回选择和旧日期事实：必要时可作为历史解释，但必须标清不能作为当前授权或可行性依据。排除无关历史不等于删历史，也不允许删除安全底座闭包要求的引用。[C05、C12]

### 5.4 引用还不是模型可消费的正文

现有投影返回引用和版本，并没有自动包含每一对象的业务值。后续需要同一 revision 下的解引用读取（Hydration），保留原对象身份、来源和适用条件。正文是读出的表示，不是另一份可独立编辑的真相。

若先取得 Context，再拿到更新后的对象正文，二者版本不同就不得混用。[C06]

安全底座超过模型消费窗口时，**不静默截断，也不让全部对话停摆**。引用投影保持完整，可通过分层解引用/按需读取，将任务正文与保护信息区分；程序校验与模型阅读分别记录覆盖，不能把未读内容声称为已读。[U03；C21]

若仍无法完整消费：允许继续有足够独立资料支持的城市差异说明、偏好探索或其他低风险非决定性任务，同时标明未进行全量个性化/可行性判断；不把它说成适合本次旅行的已确认推荐，不作全程可行结论或正式采用。若局部任务本身可能触及尚未检查的关键约束，就限制该结论，而不是用“探索”标签豁免。正式采用仍须通过全部既定程序守卫与有效确认；分层读取的工程协议和降级行动选择留后续设计。

### 5.5 状态一致性与证据有效性必须分别成立【U03；C20】

| 维度 | 检查问题 | 不保证什么 |
|---|---|---|
| 状态一致性 State Consistency | trip_id/revision、对象版本、投影清单与正文是否一致 | 同版本不保证现实观察至今有效 |
| 证据有效性 Evidence Validity | 消费时刻是否过期，日期/人数/条件是否适用，查询结果/核验层级是否足以支持当前结论 | 未过期也不保证字段完整、适用或已核验 |

两者独立检查；组合通过也只支持证据覆盖内的结论。价格、航班、酒店可订状态、营业信息等动态事实不能单靠 revision 判断；这些类别是有效性要求示例，不代表首版已提供相关搜索或库存能力。上周保存的价格今天即使 revision 未变，也不能自动作为当前可靠报价。沿用已有 expires_at/事实四轴与消费检查，不另造 Context 事实核验权威。

争议事实即使各自未过期，也以当前 Trip State 投影的 `stale_fact_ids` 作为不可直接消费信号；DC 注释只说明限制，不重新裁定事实真伪。旧已确认 Decision 及其 `review_state=stale` 保留在保护底座中，不能由过期 Packet 或恢复现场重新授予当前采用资格。DC 提供任务、目标、缺口、证据和时效输入；P01/P15/P16/P19 的 V/C/E、累计用户负担与立即/延后/后台准备/不介入仍由 NAP 裁决，行动效果由运行记录和评测验证。

## 6. 版本、持久化、快照与审计

| 信息 | 本轮立场 | 原因 |
|---|---|---|
| 用户选择、偏好、约束、事实与更改原因 | 继续持久于原权威对象与两类系统记录 | 业务连续性的基础，不能只留在 Prompt |
| Context 投影本身 | 默认按需重建，不写业务历史 | 读操作不应变成业务变更；避免快照堆积 |
| 对象版本、state_revision、组装/到期时刻 | 使用既有合同 | 能判断依据是否仍可消费 |
| 任务身份/暂停指针 | 语义建议见第三份文件；保存位置待设计 | 当前 task_id 没有持久任务注册契约 |
| 问题诊断的读取清单 | 条件性建议记录运行关联 ID、清单、组装器/模板版本和错误 | 定位当时“读到了什么”；不新增业务事件类型 |
| 完整模型输入快照 | 非默认；仅在确有评测或争议复现需要、取得相应数据保留许可时考虑 | 费用、敏感信息和提供方内容许可负担较大 |

正式合同要求任一 revision 改变或到期后重建；当前默认到期至多五分钟，且不晚于被引用的下一项未来事实到期。仅时间经过也会使事实不可用；不能只比较 revision。stale_fact_ids 实际是“不可消费事实集合”，不仅是 freshness=stale。[S05 §5、7；S13]

历史确认用原本的 Decision、提案摘要、确认范围与 ChangeRecord 追溯；诊断快照不能代替确认凭据。审计重建回答“当时基于什么”；恢复讨论回答“现在应基于什么”，两个问题不能共用一份旧 Context。[C09]

## 7. 设计原则与业务收益

1. **同一问题，新的依据。** 延续身份不等于复用过期 Context，减少重讲成本同时避免错误确定性。
2. **偏好保留，适用性重算。** 尊重机制 B，既不遗忘用户，也不将局部兴趣泛化。
3. **问题状态不等于决定状态。** 用户暂停比较不是撤销选择，事实失效不是用户反悔。
4. **描述缺口，不安排动作。** Context 可表达某连接缺日期证据；何时查询、先解释还是先澄清由 Policy 决定。
5. **优先复用已验证守卫。** 防错依赖程序与授权链路，不依赖模型看过一段告诫。
6. **不把连续性承诺扩成全功能任务系统。** 先验证有限骨架问题的收益，再决定持久书签、复杂并行或更细粒度追踪的投入。

## 8. Product / Business Sense：本轮核心判断

一个机制值得增加，不是因为它让系统图更完整，而是因为它能消除具体用户失败，并能找到可测的反例。这里增加“问题身份和恢复规则”可以防止反复重问与错误延续；增加第二份业务状态反而创造新的失败面。

商业上最值得验证的不是用户是否觉得“记忆很强”，而是是否更少自己重新查资料和修复规划，能否理解并认可取舍，是否愿意继续使用。当前没有足够依据推断付费意愿、转化率或留存提升；先做有限任务对照评测，见第五份文件。
