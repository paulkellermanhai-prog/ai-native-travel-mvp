# 跨会话精确恢复｜工程收口报告

日期：2026-10-24。对应 U05/O1 首版 P0 与 U06 正式工程完成要求。状态：**该新增需求已在工程包内实现并通过本地验收；完整规格仍待 Owner 最终审核，不代表生产应用已上线。**

## 1. 这次真正增加了什么

| 用户要求 | 实现与证据 |
|---|---|
| 回来不用重讲正在处理什么 | 持久任务/关系/焦点；新 Runtime 与独立进程重开验证，不依赖旧内存 |
| 找回比较和未提交编辑 | 比较对象/当时版本、选中对象、展开问题、草稿/假设原话和结构提案保存恢复 |
| 保留搁置状态但少打扰 | 暂停问题与 dismissed 引用保存；恢复按当前状态区分仍暂缓/已经重开，不把恢复当重新催办 |
| 事实/约束变了也不误推进 | 当前状态重新组装与时效检查，旧比较/草稿明确陈旧，缺失对象不造替代 |
| 不复活旧决定和旧授权 | 根与 Decision 仍读原权威；恢复输入只读、Grant 绑定新授权代次、旧提案不恢复，草稿不执行 |
| 多会话不会互相覆盖 | SQLite 事务、检查点版本 CAS、主体/旅行/工作区隔离；两进程同基线保存只有一份成功 |
| 失败不能假报保存成功 | 保存确认只在提交后；提交前/后强制终止进程、丢回执幂等重试、状态查询与删除反重放均有测试 |

## 3. 工程边界没有被偷换

- Trip State 0.1.0、机制 B、状态传播、唯一权威、AI 写入和确认守卫不变。
- Decision Context 首版运行合同保持 0.1.0；新增的是同一首版合同内的持久运行检查点，不新增业务对象类别、不复制有效旅行状态。
- 使用 SQLite 作为本地事务参考适配，不以 iCloud 同步 SQLite 文件实现跨设备并发。
- 精确性以最后成功保存的现场为界；未收到确认的前端输入不能假报已保存。
- 页面恢复是语义入口/对象/展开焦点，不承诺像素、动画帧还原。

## 6. Product / Business Sense

恢复的价值是让用户不用重复组织自己的判断劳动，而不是让系统执着于昨天的结论。因此持久的是“我在想什么、看到哪、改到哪”，重新计算的是“今天什么仍成立”，必须重新授权的是“现在要改变什么”。三者分开，才能同时做到连续、省心与可靠。
