# 持久检查点与跨会话恢复规格

日期：2026-10-24。运行合同 **0.1.0**；检查点 payload 格式 **1**；SQLite 存储格式 user_version **1**；Trip State 仍为 **0.1.0**。状态：工程参考实现与本地恢复验收已完成，待人工联合评审；不是生产网络/前端/鉴权或物理断电已验收。

继承 U05 首版 P0 范围，U06 要求正式补齐工程包。本文覆盖旧稿中“仅会话内存、不提供精确恢复”的范围假设，不重开机制 B、原传播与 AI 写入边界。

## 1. 完成的范围与所有者

Runtime 配置 `CheckpointRepository(path)` 后，任务、问题关联/进程、当前焦点、比较对象版本、页面语义视图、未提交/假设草稿及原话、暂缓问题引用可跨实例/进程找回。恢复点是最后一个收到持久保存确认的完整检查点，不是客户端所有尚未发送/尚未收到确认的键盘输入。

- 原 Trip State 独占已生效目标、偏好、约束、候选、事实、骨架、决定、根采用和业务历史。
- 检查点独占运行现场元信息；业务内容只保存 ID/版本。未提交内容只在明确 draft 域，不能成为第二份有效业务值。
- 检查点不保存 Read Packet、模型交付回执、Grant、待确认提案 token 或可重放写缓存。
- DC-AC8-PROTOCOL-01 已裁决：跨轮未提交原话及解释证据优先留在受信宿主交互记录，Checkpoint 格式 1 仍只保留每个任务最近成功保存的 event/现场，不保存完整对话流水；宿主记录不得用来回填 TS 真值。
- 当前代码保留无后端的 Runtime 模式供共用单元测试；`scene-status.recovery_available=false` 时不能宣称满足首版 P0，恢复接口明确返回 503。

参考接入（数据库位置由宿主配置，不放在工程源码或网盘同步目录）：

```python
repository = CheckpointRepository(trusted_local_database_path)
runtime = Runtime(authoritative_trip_store, checkpoints=repository,
                  workspace_key="workspace")
```

运行实例按用户/旅行/工作区会话隔离。持久行键为 `(owner, trip, workspace)`；owner 来自经鉴权 Principal，不接受客户端或模型 JSON 中的 owner/actor。重新进入时先调用 restore 或由 open_turn 首次自动装载任务身份，不要求用户重新解释上次的比较。

## 2. 为什么使用 SQLite，为什么不复制整趟状态

本次选择标准库 SQLite 做可运行持久适配器：无需新增服务依赖，真实事务、跨进程比较更新和进程终止可直接测试。文件以 0600 创建，初始化和写入事务均使用数据库锁，非只靠 Python RLock；synchronous=FULL，删除启用 secure_delete。摘要用于检测意外内容损坏，不是加密或抵御拥有文件权限的恶意管理员的签名。

这不是为生产分布式系统定数据库。SQLite 文件须在一个受控本地文件系统，由服务访问；**不能通过 iCloud/网盘多设备同步该文件充当分布式锁**。工程包放在 iCloud 不影响源码交付，但真实运行数据库应由宿主放在受控数据目录。生产多设备应访问中心化服务/等价事务适配器，仍保持本契约。

复制完整 state/已采用标记或旧 Packet 会形成第二份真值、延长旧证据和授权的生命，因此明确不保存。恢复只保存工作现场，再向原权威状态请求当前读取包。

## 3. 保存协议、自动保存与确认体验

1. `open_turn` 在有持久后端时自动保存任务与原话，返回 `turn.checkpoint_ack`；未收到该确认不宣称这轮现场已持久保存。保存失败时回滚本次会话注册，不留“注册成功且假装保存了”的半状态。
2. 前端/宿主在比较、选择焦点、展开讨论、草稿编辑、暂缓意图变化后后台调用 `checkpoints/save`。这不是让用户每步手动保存或确认；前端可对输入做短防抖，但离开页面/会话前应尝试 flush。真实 UI 定时与导航适配不在本包中，服务端协议与故障结果已经可测。
3. 用户的合法业务提交/确认后自动尝试更新现场中的处理结果。业务状态与现场存储是两个提交边界：业务已成功、现场保存失败时，不把原业务响应改成失败，也不重放业务写入；`checkpoints/status` 和后续 Packet warning 明确现场未确认保存。
4. `checkpoints/retry` 仅重试本实例保留的原检查点 payload/版本/键；不会重放任何业务命令。若实例已重启，先读取数据库最后成功点，再从原业务状态/历史核对，不执行旧输入。
5. UI 应区分“正在保存”“已保存到版本 N”“现场未确认保存/冲突”。用户关掉程序前没有确认保存的内容，不保证在强制关闭后找回；这是显式的可靠性边界，不能显示虚假的已保存。

## 4. 机器合同与字段含义

全部请求/响应/嵌套字段由 contracts.py 生成，见 FIELD_DICTIONARY.md 与当前 schemas/。所有封装拒绝额外字段，继承 command/业务对象 `$id` 不变。

| 接口/Schema | 输入 | 输出与语义 |
|---|---|---|
| POST checkpoints/save / scene-save | runtime_contract_version、workspace_key、expected_checkpoint_revision、idempotency_key、focus_keys、view、drafts | scene-ack：只在事务提交后确认持久保存 |
| POST checkpoints/restore / scene-restore | 版本、workspace_key、body_budget_bytes | scene-restored：已保存现场 + 当前重建包 + 陈旧/缺失说明 |
| POST checkpoints/delete / scene-delete | 版本、工作区、预期检查点版本、幂等键 | scene-ack.deleted=true；清除 payload 与旧保存回执，保留版本墓碑 |
| POST checkpoints/list / scene-list | 运行版本 | scene-list-result：仅当前主体/旅行的元数据，便于自动发现现场 |
| POST checkpoints/status / scene-status | 运行版本 | scene-status-result：后端能力、最后确认/数据库当前版本、是否待保存及错误码 |
| POST checkpoints/retry / scene-retry | 运行版本 | scene-ack：重试待确认的现场保存，不是业务重试 |

`turn` 新增 `runtime_id`（当前授权代次）及 nullable checkpoint_ack。`WriteGrant.runtime_id` 在持久模式必须匹配当前代次；它由宿主内存注入，不是请求可伪造的字段。

| 现场字段 | 精确定义/约束 |
|---|---|
| checkpoint_format_version | 当前 1，未知格式拒绝，不猜测迁移 |
| trip_id / captured_state_revision | 捕获时权威旅行与 revision；不能拿检查点修复落后的权威状态 |
| captured_object_versions | 捕获时所有业务对象的 ID/版本清单，不含对象值 |
| tasks | 每项保存 task、对应 event、base_revision、处理状态/result_revision/errors；不保存 proposal_id/digest/Grant |
| focus_keys | 当前主问题集合；不能因切换焦点将其他问题标已结束 |
| view.entry | dialogue/map/timeline/comparison，语义入口，不是像素或动画帧 |
| view.comparison_refs | 比较对象 ID 和当时版本；恢复后仍展示“当时看哪版”，同时说明其是否已过时 |
| view.selected_id / expanded_task_keys | 选中业务对象与展开的问题，不能因此产生用户价值确认 |
| drafts | draft_id、draft_kind、base_revision、target_ids、text、source_reference、nullable proposal；proposal 按原 change-request 校验但绝不执行 |
| deferred_issue_ids | 捕获时当前 dismissed 问题引用；恢复时以当前问题状态为准 |

草稿原话/来源/基准版本必须与结构提案一致，ID 唯一；新视图/草稿对象在保存时必须可解析，已保存而后来不可解析的历史引用可以保留并标缺失。保存上限为 2MB payload、128 个任务、20 个草稿；超过上限明确失败，不截断、不假确认。它们是参考容量边界，不是实测 SLA 或无限历史承诺。

Ack 包含 workspace_key、checkpoint_revision、saved_at、expires_at、payload_digest、durable、deleted。**checkpoint_revision 与 Trip State revision 完全不同**：前者保护现场并发编辑，后者保护业务状态；不能互换。

## 5. 事务、并发、幂等和失败

SQLite 存储表仅有 checkpoints 当前头与 receipts 保存回执；持久写入使用 BEGIN IMMEDIATE，将新 payload、头版本和幂等回执在同一事务内提交。初始化也有事务，不允许并发启动观察到半建表。

- 预期检查点版本必须等于当前头，成功 +1；两会话/进程同基线同时保存，最多一个成功，另一个 CHECKPOINT_CONFLICT。没有最后写入者覆盖、自动合并或自动换版本硬写。
- 同键同 payload/预期版本且仍为当前头，返回原确认，解决“提交成功但回执丢失”；同键异内容 CHECKPOINT_IDEMPOTENCY。
- 旧保存回执已经被新头取代，返回 CHECKPOINT_SUPERSEDED，不把旧成功冒充最新现场。
- 提交前失败回滚；提交后结果不确定返回 CHECKPOINT_ACK_UNKNOWN，须用原键/原内容重试或读取当前头确认，不判断为业务失败。
- 删现场不删 Trip State；清空存储 payload、摘要和旧回执并增版本墓碑，旧请求不能复活它。删除回执丢失可同键重试。仍拥有授权的用户可显式开始新的空现场，不等于自动恢复已删除内容。

当前 SQLite 事务和 SIGKILL 已实测；真实电源故障、磁盘/介质损坏、生产网络与分布式事务未由这些测试证明。

## 6. 恢复顺序与旧授权隔离

1. 用最新 Principal 验证访问，按 owner/trip/workspace 读取当前检查点，校验摘要/格式/任务关系/来源区段。账号切换或权限撤回不能读取旧用户现场。
2. 若权威状态 revision 小于捕获版本，返回 STATE_BEHIND_CHECKPOINT；不以检查点回填业务对象。
3. 恢复任务身份、进程、关系和焦点；新建只读 turn_id，**轮换 runtime_id 授权代次**，清空该主体旧 Packet、交付集合、写缓存及可操作提案关联。即使同一进程恢复，旧 Grant 也不继续有效。
4. 按当前权威状态重新组装焦点 Context/Hydration，保留完整底座并重新检查事实时效；不恢复旧 Packet。焦点目标缺失时保留问题和缺失提示，不造相似对象替代，也不为该焦点给出可行性包。
5. 返回保存的比较/视图/草稿，以及 current/saved state_revision、stale_draft_ids、stale_comparison_ids、missing_target_ids、当前 deferred/reopened 问题和限制。
6. 旧输入只读，submit/confirm 返回 RESTORED_INPUT_READ_ONLY；已恢复的旧 event_id 不能重新注册为新输入。新明确输入、当前读取/预览、当前代次 Grant 和原守卫均满足后，才可形成新合法业务变更。

恢复不改变根采用或 Decision 状态；草稿不会自动应用；已撤回采用仍撤回；pending_confirmation 仅作历史处理状态展示，proposal_id 为 null，必须重新预览。阶段性处理结果与当前业务对象不一致时，以当前对象为权威，而不是从旧处理标签判断今天已采用哪版。

暂停/暂缓不会因恢复自动重开或完成。当前权威问题若已重开，覆盖历史暂缓标签，返回 reopened_issue_ids，并保留决定性限制。注释只决定消费资格，不实现 Policy 的提醒路由。

八项机制融合后，同一规则也适用于含歧义的旧任务：最近成功保存的 `saved_task.event`、`task.certainty=ambiguous`、未知 `target_ids` 与未提交草稿可以恢复，但只能只读呈现；用户跳过或不回答不会在恢复时自动变成确认。恢复重新调用当前 TS 投影，争议事实、过期事实、当前 Decision 的 `review_state` 和新权限仍以现状为准；旧 Packet、旧确认人身份、旧 Grant 与旧提案都不能复活。若先前多轮未提交解释已被同一 task_key 的较新事件覆盖，现行 payload 不保存其完整原话链。宿主证据读取由解释器在恢复**现有现场、并读取最新 TS 之后**按需进行，须重新验当前身份/旅行/任务、来源和时间，见[运行契约 §4](01_运行契约与任务定位.md)；不能把宿主读取或事件关联失败等同 Checkpoint 损坏。未关联、缺页、记录缺失/删除、权限拒绝或来源不可核实时，不向恢复包补造旧事件/旧授权，保留未知与当前已保存任务，按原只读恢复和 TS 重建继续。原话可追溯、当前解释可重建与当年模型候选精确重放是不同验收层，见[E11 数据契约](../03_评审与工程衔接/16_E11宿主交互证据数据契约与验收轨迹.md)。当前参考实现没有宿主交互记录接入，不能把最近保存点的精确恢复承诺解释为完整交互事件溯源。

## 7. 权限、隐私与保留生命周期

文件和其目录由受信宿主管理；SQLite 参考存储不含加密/登录系统。文件权限测试不证明生产访问控制真实性。所有 HTTP-body 额外 owner/actor 字段拒绝，允许旅行集合须由宿主鉴权后注入；共享旅行不代表可读取其他用户草稿。

retention_seconds 是宿主配置，不是模型/客户端字段。参考默认 None 表示无自动到期，直至明确删除；生产接入须明确保留政策并向用户展示，不宣称该默认已满足任何合规要求。配置到期后拒绝恢复，宿主可调用删除清除到期 payload；没有静默续期或伪造恢复。备份、日志、底层介质擦除由生产政策另行管理，secure_delete 不等于取证级擦除保证。

2026-11-05 Owner 批准的 [DC-AC8-PRIVACY-01](../03_评审与工程衔接/17_DC-AC8-PRIVACY-01_Owner裁决与执行边界.md) 限定的是 E11 **宿主完整原话记录**，不把 30/180/12 个月窗口悄悄写入此 Checkpoint 格式或参考 `retention_seconds` 默认值。Checkpoint 原有恢复合同、删除和配置责任保持；若 E11 原话已删/过期，Checkpoint 仍按本合同安全恢复当前任务现场，但不得借最近 event、旧 Packet 或备份还原已删原话，见[E11 数据契约](../03_评审与工程衔接/16_E11宿主交互证据数据契约与验收轨迹.md)。

## 8. 新错误与兼容升级

运行合同保持首版 `0.1.0`，新 `$id` 为 `/runtime/0.1/`；跨会话恢复接口与原运行接口同属这一版本。未发布的早期本地快照不作为正式包内容；检查点数据库 user_version 与 payload 格式分别校验，未知版本不降级，不覆盖其他数据库。

| 错误 | 结果 |
|---|---|
| RECOVERY_UNAVAILABLE / CHECKPOINT_STORAGE / CHECKPOINT_ACK_UNKNOWN | 503，不能宣称现场已保存；相同现场请求可技术重试，不重放业务 |
| CHECKPOINT_CONFLICT / CHECKPOINT_SUPERSEDED | 409，读当前头并对照本地未确认修改，不静默覆盖 |
| CHECKPOINT_NOT_FOUND | 404，无此主体可恢复现场 |
| CHECKPOINT_EXPIRED / CHECKPOINT_CORRUPT / CHECKPOINT_DB_VERSION | 422，明确拒绝伪恢复，不猜测旧格式/内容 |
| WORKSPACE_MISMATCH / CHECKPOINT_POLICY / CHECKPOINT_IDEMPOTENCY / CHECKPOINT_TOO_LARGE | 422，工作区/配置/键/容量不合法，修正调用 |
| STATE_BEHIND_CHECKPOINT | 409，权威状态服务需先恢复正确版本 |
| RESTORED_INPUT_READ_ONLY / RECOVERED_EVENT_REPLAY / WRITE_GRANT | 422，旧输入/授权不能成为新提交 |
| CHECKPOINT_RETRY_EMPTY | 422，本实例无可按原内容重试的现场保存；重新读取已保存点，不凭空提交 |
