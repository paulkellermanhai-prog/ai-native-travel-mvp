# Context 消费时效精度修复

独立审核任务 `01a1b027-3800-7602-aab1-7bf191a81033` 发现：JavaScript `Date` 只有毫秒，事实截止为 `.000500Z` 而实际时刻处于 `.000900Z` 时，旧代码会把时钟表示为 `.000Z`，从而可能在事实已过期后仍通过 Context 消费或分页复验。这是 E03-02 已验收实现中的后续增量风险，不改变原固定 head 的阶段验收结论。

当前修订把 `Date` 视作整个毫秒区间：若该区间的最后一个微秒已到或超过所选事实/Context 截止，则拒绝消费。对于未选中但可影响已选事实争议或注释的事实，按时间顺序逐个检查该毫秒内的观察/到期边界（计算保留最多 18 位小数）；只要任一位置改变选中证据或注释，即拒绝。不是只比较区间两端：同一毫秒内争议先出现后消失也会拒绝；无关的七位小数事实不会单独改变结果。分页仍对前后两次读取分别执行同一复验；失败不推进交付账本。

这是保守失败关闭：时间非常接近截止或争议切换时，可能提前不足一毫秒拒绝，不能宣称获得微秒精度时钟；单毫秒内超过 128 个不同边界、边界数与事实时间戳、全量/选中对象及选中对象×目标数的估算乘积超过 100,000、边界数与快照字节数乘积超过 64 MiB，或小数超过 18 位且余数非零时也失败关闭，以控制计算和精度风险。这是逐边界额外工作的保守估算，并非整体 CPU 上限；原有两次 Context 组装发生在预算检查前，仍依赖上游请求和状态规模限制。不存在毫秒内切换时不做逐边界复算。若将来提供已验证的更高精度可信时钟，应单独设计并复验。规则不改变原数据或 R6 冻结来源，不自动改变已批准的争议计算。审查指出的事件时间第七位截断、Turn/pending 一致性和可信交付账本属于各自未闭合问题，本修订不宣称解决。

新增反例先在旧实现运行，`.000500` 截止的消费和跨截止分页均未抛错；第一次修订也在“同毫秒内争议先出现后消失”和“无关七位事实”两项独立反例中失败，已改为逐边界比较。共享 TS 时间解析器也统一处理既有合同允许的小写 `z`、`±HHMM` 和 `±HH`，避免小数被忽略；这会影响命令、状态语义和持久化，必须同时运行 TS 全量回归。AJV 接受的闰秒仍无法由 `Date.parse` 解析，保持失败关闭。当前测试覆盖截止前、对齐相等、截止后、跨页失败及账本不变，并覆盖 C12 争议的瞬时出现与消失、无关事实控制、第七位未来观察和不同时间偏移；具体测试和同 head 验证结果以集成交付报告为准。
