## D/E/F 全场景实际逐步结果

每场景从其完整原始 initial_state 开始，TS 每步输入是它自己的上一笔输出。独立进程里的原 Python Store 接收相同请求、Actor、时钟和原 UUID 序列。逐步**完整**比较 response（含 digest/diff/errors）、state、revision、对象版本、assessment、OperationIntent、ChangeRecord、有效根和累计历史，再核对原机器轨迹。以下是实际 TS 运行摘要，不是读取原轨迹生成的“执行结果”。

| 原步骤 | 命令摘要 | outcome / revision | 有效根 / 评估 |
| --- | --- | --- | --- |
| D-1 | User adopt skeleton-a | applied / 1 | skeleton-a / pending（费用部分覆盖） |
| D-2 | User create 新硬上限 | applied / 2 | skeleton-a / stale |
| D-3 | User activate 新硬上限 | applied / 3 | skeleton-a / stale |
| D-4 | System recalculate | applied / 4 | skeleton-a / blocked；旧确认/根保留，决定待复核 |
| E-1 | Tool ingest 住宿确认 | applied / 1 | null |
| E-2 | User reject 已承诺城市 | rejected / 1 | null；COMMITTED_FACT_CONFLICT，无提交 |
| E-3 | Model create 冲突草案 | applied / 2 | null |
| E-4 | User adopt 冲突草案 | rejected / 2 | null；HARD_CONFLICT，无提交 |
| E-5 | Tool 同笔 supersede + 取消回执 | applied / 3 | null；双方回执/历史保留 |
| E-6 | User 再次 adopt 草案 | applied / 4 | skeleton-booking-conflict / pending |
| F-1 | User adopt skeleton-a | applied / 1 | skeleton-a / pending |
| F-2 | Tool 替代交通事实，导入 no_service | applied / 2 | skeleton-a / stale；确认不自动撤销 |
| F-3 | Model create 无服务草案 | applied / 3 | 原 skeleton-a / stale |
| F-4 | System recalculate 无服务草案 | applied / 4 | 原 skeleton-a / stale；新草案 blocked |
| F-5 | Model create 替代草案 | applied / 5 | 原 skeleton-a / stale |
| F-6 | User adopt 替代草案 | applied / 6 | skeleton-alternative / pending；旧骨架/决定正确替代 |

三份原末态及完整历史均完全一致。真实 PG 再执行全部 16 步，每步回读四表与 state/history，独立对照 Python；仅 trip_id 命名空间变化以隔离测试，未删除任何夹具对象。两个正式拒绝步骤四表逐值不变。加上保留的 A/B/C/G，七场景共 **31 步**均由 TS 实际执行，其中 2 步按原规则拒绝。

## Issue 原测试与完整处理链

原交接没有独立的 Issue 机器轨迹。本轮依据 `test_tripstate.py` 的 known_fact_issue、unrelated_evidence、H10 dismiss/remaining_unknown 等测试和正式转换表，执行其动作及以下组合链；明确是原规则测试组合，不伪造一份“权威机器轨迹”。

| 实际步骤 | outcome / revision | 核对 |
| --- | --- | --- |
| User create 已知班次核验 Issue | applied / 1 | 正式字段、来源与创建记录 |
| User resolve，提供该班次事实 | applied / 2 | 关联、可用证据及被影响事实满足条件 |
| Model 提议 dismiss 原费用 Issue | pending_confirmation / 2 | 仅提案/系统历史，权威 Issue 未关闭 |
| 可信 User confirm | applied / 3 | 原提案 Actor 与实际确认人分别保留；不改变事实或预算可行性 |
| System 正式 reopen 已解决 Issue | applied / 4 | 原历史保留，遵从原 reopen 语义 |
| System 再 resolve 关联核验 Issue | applied / 5 | 重验实际证据和业务条件 |

该六步通过真实 PG；每步完整 response/state/history 与独立 Python Store 相等。另有纯 TS 的逐类正反例和真实 PG 的权限、陈旧事实、无关证据及仍 pending 的骨架拒绝测试。Issue 的“解决”严格限于原程序对 affected_ids、关联证据和对象条件的判断，不新增对 question/required_inputs 自由文字的语义推断。
