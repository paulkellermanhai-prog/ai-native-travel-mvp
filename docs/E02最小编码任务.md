## 1. 首条场景与最小对象

首条闭环采用 `TS/SCENARIO_VALIDATION.md` 的 **A｜陌生目的地探索**，逐步对照 `examples/scenario-traces.json` 中的 `A-new-destination`，保留原七步：

1. System 通过正式 `create` 命令建立合成国家、城市 DestinationEntity。
2. User 创建 draft TripGoal。
3. User 执行 `transition(event=activate)`。
4. AI（宿主 actor role 实为 `model`）创建 `certainty=inferred, support=weak` 的局部 Preference。
5. User 用正式 `revise` 白名单明确纠正该 Preference；保留前值和证据。
6. AI 创建关联该偏好的 Candidate。
7. User 执行 `decide_candidate(value=accept)`，产生 confirmed Decision；候选 retained，根 `effective_skeleton_id` 仍为 null。

最小业务对象为 DestinationEntity、TripGoal、Preference、Candidate、Decision；每次合法业务提交的 OperationIntent / ChangeRecord 是两类系统记录。旅行根容器和数据库表不是新业务对象。Decision 由专用命令生成，不能开放 generic create Decision。首条场景不需要编造预算、日期、骨架、外部事实或真实供应商查询。

强制保留的后续保护测试来自 B、C、G：跨候选偏好不能随候选退出删除；用户纠正推断后下游待复核；用户反转决定保留旧决定与历史。B 中合法 reconsider 依赖已有 Constraint 的正式三值条件，G 的既有骨架失效亦需验证；这些既有完整夹具中的其他对象按原 Schema 读取和校验，不为了缩小代码而篡改或删掉它们。

## 2. 数据库 Schema 与持久化切片

采用 PostgreSQL 17 + Prisma，**按旅行聚合保存原 state JSONB**，不另发明五份简化对象表，不复制全局偏好或把候选当事实。正式业务字段仍全部位于原 Schema 文档中。

| Prisma 基础设施模型（拟） | 最小字段/约束 | 与正式契约的关系 |
| --- | --- | --- |
| `TripStateDocument` | `tripId` 主键、`revision` 整数、`snapshot` JSONB | snapshot 完整符合 state.schema.json；SQL 主键/revision 是同一根值的并发索引，写入时必须与 JSON 一致，不能成为第二份业务真值 |
| `TripStateHistory` | `tripId`、追加序号、`changeRecordId`、`intent` JSONB、`change` JSONB；同旅行记录 ID 唯一 | intent/change 原样符合 OperationIntent/ChangeRecord，按原 history Schema 读回；序号仅作存储顺序，不替代业务 revision |
| `TripStateProposal` | `(tripId, proposalId)` 唯一、`payload` JSONB、`digest`、`basisRevision`、`expiresAt` | 保存参考 Store 的 request/actor/cache-key 等确认依据，重启不能丢失；消费需同事务锁定，不引入新的业务状态枚举 |
| `TripStateIdempotency` | 唯一 `(tripId, actorId, operationDomain, key)`、`requestDigest`、`response` JSONB | submit 的 operationDomain 按 actor.role；confirm 按 `confirmation`；与原缓存空间一致，确认后还要原子更新原提交键的最终响应 |

字段命名最终以迁移实现和 Prisma 格式审查为准，不能据此修改原 JSON 契约。数据库不创建 DecisionContext、NAP 日志或自造订单实体。历史只追加；应用无历史更新/删除入口，迁移增加防止运行账号更新/删除历史的数据库保护，并验证其效果。

状态、revision、传播副作用、追加历史、待确认提案、幂等结果组成同一数据库事务。使用行锁或带 expected revision 的条件更新，并保留唯一约束；选择一种机制后以并发/故障测试证明，不靠最后写入者胜出。条件更新受影响行数不为 1 时返回原 `VERSION_CONFLICT`。不要把 Prisma 中的多个顺序写入当作原子事务。

## 3. 状态入口与权限边界

核心服务和测试必须可独立运行，不依赖 LLM、真实数据提供方或 UI。使用 TS/Schema 的离线 Draft 2020-12 注册表解析原 `$id`，禁止向 `trip-state.example` 网络取 Schema；新校验库及格式插件只在 E02 实际编码时按需求加入。

实现顺序：规范校验 → 旅行访问授权/宿主 Actor → 版本与幂等检查 → 复制快照 → 正式命令与权限守卫 → 引用/全局不变量校验 → 依赖传播 → 同笔持久提交。实际检查顺序及重复请求处理以原 Store 为准，特别是幂等重放先于旧 revision 拒绝，不因本表顺序简写改变原行为。

首条场景必须实现的命令是正式 `create`（上述可创建对象）、`revise`（原类型字段白名单）、`transition`（原转换表）与 `decide_candidate`；同时实现 preview/submit/confirm 及其持久化。B/C/G 保证项还需要 `reconsider` 和原有条件求值/传播，不允许直接写 status 绕过。

事实保护采用原 `ExternalFact` 结构、独立 verification/freshness/applicability/query_status 语义，以及受控 `ingest_fact` / `check_freshness` 通道的合成测试；不接真实供应商，不把用户选择提升为事实核验。对于本切片尚未实现的命令，不能伪造 applied；在公开命令子集之前由负责人审阅支持矩阵，沿用原 response Schema 和既有错误语义，不静默改变规则。

HTTP 适配范围按 TS §8：GET `/trips/{id}/state`、GET `/trips/{id}/changes`、POST `/trips/{id}/changes/preview`、POST `/trips/{id}/changes`、POST `/trips/{id}/changes/{proposalId}/confirm`。根初始化由宿主内部工厂/受控测试入口创建合法空 state，不发明一个无鉴权的任意 state 导入 API。Decision Context 接口不在 E02 实现范围。

Actor 只能由可信宿主在完成身份和旅行访问授权后注入；请求 JSON、原样透传的 header 或模型输出都不能决定权限。测试使用明确隔离的合成宿主适配器，不把测试 actor 当生产鉴权完成；若需外部公开 API，必须先落实宿主身份适配，不开放默认 user 管理权限。

确认绑定原请求、拟议 diff、根引用摘要、当前 revision 和有效期；默认上限 5 分钟且不晚于已有事实下一次到期。摘要算法逐字对照 `tripstate/engine.py:digest` 的排序键、UTF-8、无多余分隔空格和 Unicode 语义；增加跨语言固定向量，不自行选另一个不可互认的摘要规则。preview 不写 state/history/idempotency；pending 只保存拟议结果和系统记录，读取当前 state 不得混入拟议值。

响应严格沿用原 HTTP/outcome：preview/applied 200、pending_confirmation 202、conflict 409、rejected 422、权限 403、未找到 404、方法 405、内部失败 500；不把未知错误包成成功，不把 proposalId 与 ChangeRecord.id 混用。

当前执行切片：E02-04A 为用户确认与 Proposal 生命周期；E02-04B 保留跨候选 Preference、B/C/G 复杂命令与传播；E02-04C 保留 ExternalFact 核验、时效、权限及完整保护回归；E02-05 为真实宿主认证适配、HTTP 和完整端到端验收。以下八项原始任务编号及通过标准完整保留，是需求追踪编号，不因新的执行分组而删减。

| 任务 | 实际交付 | 必须通过的验收 |
| --- | --- | --- |
| E02-01 契约接入 | `src/server/trip-state/` 的原 Schema 注册表、严格输入/输出和类型边界；原文不变 | 全部现行 state/change/command/confirm/history/response `$ref` 离线闭合；未知字段、跨旅行/悬空/错类型引用拒绝；固定哈希通过 |

| E02-03 A 场景引擎 | 执行原 A 的七步，不接 DC/NAP | 每步请求、outcome、revision、对象版本、diff 和末态按原轨迹核对；accept 与根采用分离；未表达信息保持未知 |

| E02-05 偏好与淘汰保护 | 原 B/C/G 对照测试，必要的条件/传播通路 | 排除候选不删共享 Preference/证据/事实/历史；局部范围不扩大；reconsider 真实触发且条件 true 才 reintroduced，不自动接受；不允许 retain 绕过；反转决定留下 revised/supersedes，相关既有骨架 stale，无关状态不变 |

| E02-07 原子性与并发 | 独立 PostgreSQL 连接/进程的集成测试 | 同 revision 两写仅一笔成功；事务中途故障后状态/历史/提案/幂等全部回滚；重试无重复历史；非法整批提交无半应用 |
| E02-08 HTTP 与文档 | 受宿主保护的 Next 路由、响应 Schema 检查、复现说明 | 上述 HTTP 成功/失败均符合原契约；无任意 patch/status/actor 输入；restart 复验；同一 PR CI 在最新提交通过 |

测试中时钟和 ID 生成使用明确的确定性测试替身，生产实现使用实际 UTC 时刻与合法唯一 ID；不能为了通过轨迹比较忽略任何业务字段差异。测试统计按真实执行数报告，不事先宣称未来测试已通过。
