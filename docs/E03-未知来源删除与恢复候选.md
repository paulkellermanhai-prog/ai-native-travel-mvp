# E03 未知来源删除与恢复候选

本地隔离候选，仅供技术审核；不发布、合并、部署或改变已验收进度。历史 `4611878` 对无关删除的局部清理结论已被本次更保守门槛取代。冻结 R6 和 UX02 R7 未改；当前限制不能写成 R6 等价或最终产品规则。

## 真实复现与保守阻断

在真实 PostgreSQL 和真实 Session 中先复现：事件 A 的正文出现在任务 B 的 `question`，而 B 的证据只引用事件 B；原候选成功保存，删除 A 后 E11 companion 仍有 A 的文字。修复前同一反例失败，修复后通过：删除事件时按工作区保守清掉整个 companion、checkpoint 引用与旧回执、旧 Task 来源及签发键；旧事件不能被重放为新 Turn。删除前已排队的记录请求绑定旧代次，不得在删除后插入相同正文。持久 deletion epoch 和首次截止水位允许外部提交后失败关闭及重试同步；重复删除沿用原 cutoff，不破坏之后的新 Task。

完整自由文本来源账本尚不存在，不能把已登记 TaskSource 当成全部来源。当前保存/恢复候选进一步要求：候选持久场景的 Task key 由 PostgreSQL 安全随机签发、按范围绑定的请求键幂等重试并验证同范围；question 必须逐字存在于当前工作区至少一条已验证 Task 来源；同一工作区所有事件都作为潜在来源，锁定并复验删除及最早期限；捕获状态中的对象标识、目标/比较/选中/暂缓对象标识因缺可信来源证明一律关闭。草稿、错误内容和非 unprocessed Task 仍关闭。单 workspace 候选最多核验 256 个事件和签发 256 个 Task key，超过上限失败关闭，不抽样跳过；第 257 条事件仍可记录，只是后续候选保存/恢复关闭，没有自动压缩或全局配额。这是临时工程容量上限，尚非产品额度。普通 Task 注册仍可使用其他合法 key，只有候选持久场景要求签发证明。任一事件删除后该 workspace 的保存与恢复继续关闭，直到后续完整来源和安全重建机制明确；这可能影响完全无关任务，是待审核的保守工程限制，不是产品决定。

事件发生在同一工作区之外，或文本通过 TS 的 trip/对象标识、其他已存在场景、外部模型上下文流入时，上述门槛不证明所有潜在来源已闭合；已有其他工作区 legacy companion 也不会因本工作区删除自动清除。跨工作区删除范围、TS 不透明标识/来源证明及老副本治理仍需明确方案并复验；即使两个不同事件正文相同，也不能仅据文本判断是复制还是用户重新输入。同一删除代数内，Task key 提交后回执丢失可凭同一请求键重试得到原 key；跨删除代数时当前进程拒绝旧请求键，须用新请求键。签发记录和跨代键映射没有持久生命周期清理，随机候选仍可被反复挑选，生产还须限制滥用及审查侧信道，不能上线或宣称完整删除覆盖。自然到期目前只阻断访问，伴随正文自动物理清理、备份/WAL 与恢复重放删除标记仍未实现。

## 恢复候选并行工作

`integration/restored-scene-candidate.ts` 根据冻结合同在传入的同一当前状态上构造纯 `scene-restored` 候选、新 Turn 和仅供内部使用的 Packet；保留原视图/草稿、缺失引用、过期比较/草稿和原警告，恢复输入只读。它不创建认证或实际交付能力，返回体可能包含原话，不能从未受控入口调用。真实 `restoreCheckpoint` 如显式提供预算，可在同一个受权事务中试组装 Turn/Packet 并仅返回候选数量，不返回正文，不安装完整 Turn 或 Packet，不记录实际送达；保存未确认警告取自同进程受信宿主状态，不能由外部参数伪造；不同失败请求不因旧成功回执重放而自动清除。早期无法规范化的失败采用粘滞告警，尚无用户主动解决/清除接口，属于保守候选，可能比 R6 参考更严格。真实草稿仍因缺独立来源和删除屏障而不支持保存恢复；纯函数的草稿测试只是合同对照，不是用户草稿已恢复。

真实 Task/Turn 存储、私有交付账本、Grant/旧提案/跨服务缓存失效、实际网络交付、跨进程/重新登录的工作区认领、可信旅行结束与续期来源仍未完成。原规范允许概括 question、调用方合法 Task key、历史场景及真实目标/草稿；本候选的字面 question、签发 key、无 TS 对象、删除后永久禁存等均更窄，须由技术负责人裁定后才能扩大或替换。
