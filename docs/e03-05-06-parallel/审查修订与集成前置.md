## 本次修订

- 保存与读取在范围 advisory lock 和对应行锁之后，使用 PostgreSQL `clock_timestamp()` 判断旧现场的到期；新的保存时间和配置期限均从该数据库时点计算，调用方的旧 `now` 不再决定是否过期或使旧现场续期。列表可用状态也按数据库时钟计算。`now` 仍用于表达受信宿主配置的相对保存期限，不能被客户端选作生产保留政策。
- 对仍为当前头的**同键同请求重试**，保持 R6 回执优先：返回原回执、原截止时间，不创建新版本或延长保留。过期后读取仍拒绝；较新头和同键异内容分别保留原错误。数据库时间文本为 UTC 微秒精度；实际正式时钟与全路径精度仍需同源联审。
- Session 包装函数先验证身份并持有 Session/成员关系行锁，取得检查点锁后再次检查；**线性化点为取得检查点锁之后、执行存取之前的第二次授权检查**。若 Session 在等待检查点锁期间到期，操作拒绝；若在该检查点后自然到期，已授权操作可提交，下一次操作必须重新授权。成员撤销先持锁时后续操作拒绝；操作先持授权锁时撤销等待该操作结束。这不保证数据库提交之后的外部撤权与已交付内容严格原子。
- Session 仓储实例固定用户、旅行、工作区并复制绑定，拒绝外部修改对象或以另一个工作区访问；只列出绑定工作区。真实 PG 测试先创建两个均存在的工作区，再验证适配层拒绝伪造范围、列表过滤；测试受限角色不能调用原始读/写/列表函数或直接访问表。

**真实工作区归属仍未完成。** 当前 Session SQL 包装函数仍接受宿主提供的工作区字符串；测试明确保留反例：持有该函数执行权的调用者，若知道同一用户的另一个工作区，可以直接调用包装函数读取它。固定的仓储实例只是内部边界，不是数据库级的可信工作区授权。主集成人的宿主负责提供可复验的工作区归属和跨会话策略；在此之前不能向不受信角色授予包装函数，也不能开放保存/恢复入口。

## 行锁增量复审

针对 `01a1b060-a881-74fe-b1e2-217e3b79801b` 对 `1285935ad5d0067a190e0e1a8c2eafcdeb8641ed` 的增量复审，本次只增加隔离测试和锁纪律说明，不改变产品规则或 Session 线性化点：

- 真实 PostgreSQL 测试让受信维护连接故意**只持有** `heads` 行锁，而不持 advisory lock；确认保存进程确实被该连接阻塞。保存点在等待行锁期间到期后，写入在获得行锁后用数据库时间拒绝；版本保持不变，同键原回执不续期。
- 另一个真实 Session 测试在最终授权检查之后等待该独立行锁，直到 Session 自然过期，再释放行锁。按已经声明的线性化规则，本次操作完成，下一次读取重新授权并拒绝。此结果不表示提交或交付时 Session 仍有效，也不把维护连接不遵守锁纪律合理化。
- 受限 Session 测试角色额外验证对两个表无直接读取、写入、删除、截断等权限，无 schema CREATE、表所有权或原始读写/列表函数 EXECUTE；正反例仍明确区分该测试角色与尚待正式部署审核的运行角色。

**集成锁纪律：**所有保存点的业务写入、删除和将来需要修改头或回执的维护/清理流程，必须先按相同 `(owner, trip, workspace)` 键取得同一 transaction-scoped advisory lock，再按一致顺序取得行锁并做事务内权限/时间检查；不得先持有行锁再取 advisory lock，也不得由运行角色直接修改表。正式迁移与维护脚本由主集成人审核并落实，当前代码无法约束有特权的数据库管理员。工作区归属反例和 E11 屏障依然开放，不能用于对外恢复。
