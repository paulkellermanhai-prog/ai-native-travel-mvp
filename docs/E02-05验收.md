## E02-05A 身份与授权

仓库原先只有四表和宿主注入点，没有用户/会话/归属基础设施。本轮选择锁定的 Better Auth 1.7.14 + 官方 Prisma 适配器，自托管真实邮箱/密码认证，使用库的密码哈希、签名 Cookie 和数据库 Session。无需付费身份平台、供应商密钥或邮件资源；不实现认证 UI。账号由受信 CLI 创建，邮箱仅作为登录名，不冒充已验证的邮箱所有权；授权始终绑定不可变 user ID，绝不凭客户端声称的邮箱或 Header 分配旅行。

参考：[官方 Prisma 集成](https://better-auth.com/docs/adapters/prisma)、[会话管理](https://better-auth.com/docs/concepts/session-management)、[密码认证](https://better-auth.com/docs/authentication/email-password)、[安全机制](https://better-auth.com/docs/reference/security)。官方依赖按稳定版本锁定，未自造密码散列或浏览器会话协议。

- 新增 AuthUser/Session/Account/Verification/RateLimit 与 TripMembership 基础设施，不新增 Trip State 业务对象。迁移追加到原数据库，未重建。原四表的历史不可改写、事务/幂等/确认保护保持不变。
- 认证库使用独立非 owner 身份：身份/账号限必要列更新、Session/限流表必要 CRUD、归属只读；不能读写原业务四表。Trip 运行身份不能读取 Session 或修改归属，只获得固定签名授权校验函数 EXECUTE，无身份 UPDATE/DELETE/DDL。
- `sessionHost` 每次通过 Better Auth 实查签名 Cookie、Session 失效和 TripMembership，再由服务端派生 `user-<immutable UUID>` Actor。禁用 Session Cookie 缓存与 GET 刷新；没有测试令牌或默认 User 回退。
- 读取/preview 再执行授权事务；写入在取得旅行行锁后、缓存重放和变更前复验活跃 Session 与归属，并持有 SHARE 锁至提交。撤权期间排队的请求不能沿用旧授权，撤权后缓存结果也不泄露。
- 内部 Model/System/Tool 使用独立密钥、HS256、固定 issuer/audience、60 秒、绑定 trip/role/sub 的 jose 签名能力；公开路由不签发该能力；E02-05B 仅对显式 Model 服务开放签名认证，System/Tool 继续只用私有 SDK，普通 User Cookie 不能升级身份。服务端令牌不能签发 User，User Cookie 也不能伪装内部角色。
- `auth:admin` 为显式受信运维命令：输入 JSON 走 stdin，不把密码放 argv 或日志。创建账号调用成熟库的服务端注册 API；新旅行只能由现有 System createTrip 创建合法空根，再由迁移身份授予真实 user ID 访问。无公开注册/创建旅行/导入状态接口。

## E02-05B 正式 HTTP

实际 Next.js Node 路由为 `/trips/[id]/[...resource]`，对外恰好提供 §8 五条业务接口；decision-context 为 NOT_FOUND，不返回虚假 E03 结果。所有业务请求在路径存在性判断和解析正文前验证可信身份及旅行授权，之后仍经过同一宿主及事务守卫。GET state/history 用原 Schema；业务提交/确认/preview 将原始 JSON 文本交给既有受控数字解码及 Schema/引用/语义执行器，不建立另一状态写通道。

普通用户只用 Better Auth 的真实 Cookie。显式 Model 服务可提交可信签名能力，以便正式 HTTP 实际产生 202 pending；只接受固定 issuer/audience/HS256、trip/sub/role=model、60 秒内的签名。原始 `x-user-id`、`x-actor-role`、请求体 Actor 都不能授予权限。System/Tool 即便带有效内部签名也不能使用公开业务路由；Cookie+Bearer 混合一律拒绝，User 不能被 Header 切成 Model，Model 不能确认。

成功/失败沿用原 response/outcome 与状态映射：200 applied/preview，202 pending，403 权限，404 NOT_FOUND，405 METHOD_NOT_ALLOWED，409 冲突，422 合约/业务拒绝，500 INTERNAL_FAILURE。原 PROPOSAL_NOT_FOUND 按参考 dispatch 仍为 422，不擅改错误语义；路径里的 proposalId 不是 ChangeRecord.id。基础设施错误对外隐藏 SQL/连接/栈，撤权错误不泄露旅行 revision。

正文同时限制 Content-Length 和实际读取字节：业务 256 KiB、登录 4 KiB；只接收 application/json（可带 UTF-8 charset）。Cookie 写请求严格匹配固定 Origin，并拒绝 cross-site fetch，不靠可伪造的角色/代理 Header。所有响应 private/no-store、Vary Cookie、nosniff；会话缓存和 GET 刷新禁用；有效会话下 preview 的业务及认证表零写入已实测。过期会话可能由成熟认证库清理，这是认证维护，不产生旅行状态/历史/幂等写入。

认证 HTTP 仅 `/api/auth/sign-in/email`、`/api/auth/sign-out`，真实密码验证后只回 ok 与 HttpOnly/SameSite Cookie，不回原始 Session token/账号字段。公共注册/改密/账号管理端点未暴露。固定 HTTPS origin（回环 HTTP 例外）；未配置可信代理前覆盖客户端转发 IP，使用持久数据库的保守共享限流桶，防止自行填写 IP 绕过；实际部署需按可信入口安排代理限流，不能把该保守策略宣称为按真实客户端区分的防护。

首轮 B 检查：17 项正文/Origin/数字 token/缓存/正式状态映射测试通过，类型、Lint、生产构建通过；完整真实 HTTP 验收留给 C。框架支持的 GET/POST/PUT/PATCH/DELETE/OPTIONS/HEAD 均显式经过适配器，HEAD 按 HTTP 协议不带响应正文。

### 原遗漏与修复

原 Auth 启动检查和身份部署脚本只探测 `TripStateDocument` 的 SELECT/INSERT/UPDATE/DELETE；漏掉 `TripStateHistory`、`TripStateProposal`、`TripStateIdempotency`，以及列级权限和其他表级权限。Trip 的身份部署检查只探测 `AuthSession`，漏掉 `AuthUser`、`AuthAccount`、`AuthVerification`、`AuthRateLimit`、`TripMembership`；Trip 命令运行时原来仅拒绝管理员及业务表 owner，没有拒绝身份表 ACL。原 owner 检查也没有完整覆盖十张表及可 SET ROLE 的角色。

- `src/server/database/runtime-role-safety.mjs`：新增一份固定、参数化的 PostgreSQL 17 查询；Auth 禁止访问全部四张 Trip State 表，Trip 禁止访问全部六张身份/归属表。检查全部表级 SELECT/INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER/MAINTAIN，及所有列级 SELECT/INSERT/UPDATE/REFERENCES。
- 通过 PostgreSQL 原生 `has_table_privilege` / `has_any_column_privilege` 检查已有的有效授权，包含 PUBLIC 与继承，不只读取显式 ACL 或角色名；另外枚举 `pg_has_role(...,'USAGE'/'SET')` 可达角色，覆盖 NOINHERIT 但可 SET ROLE 的路径。全部十张表的 owner 及可达管理员角色均拒绝。表缺失、角色不存在或查询失败也不能继续启动/部署。
- `src/server/auth/config.ts`、`scripts/grant-identity-runtime.mjs`、`src/server/trip-state/internal/persistence.ts` 复用这份查询。部署在任何 GRANT 前先检查两类角色；实际 Auth、Trip 命令、Synthetic Harness 启动及只读存储操作均检查，避免另一入口漏过。
- 查询只判断角色，不执行撤权。原 Auth 在账号/会话/限流表的必要权限、归属只读，以及 Trip 精确授权函数 EXECUTE 均保留；没有添加新权限、修改业务 Schema/迁移或创建生产资源。`$queryRawUnsafe` 仅承载固定 SQL，角色/类别仍通过绑定参数传入，不拼接请求内容。

依据：[PostgreSQL 17 官方权限查询说明](https://www.postgresql.org/docs/17/functions-info.html#FUNCTIONS-INFO-ACCESS-TABLE)。本次不将启动检查宣称为持续数据库 ACL 监控；运行期间修改角色授权仍须受信数据库运维管理。
