# E04｜计划与输入 Packet 的纯比较

本切片基于 PR #17 已限定接受 head `bdbb805a092ead346c80bb52f390cc5ff208db9c`，其直接基线 #16 与 #14 均未合并。NAP R3 相关 15 份来源及摘要固定于 `specs/nap-r3-2026-11-06/selection.json`；CT-02 要求计划 basis 与原包对应，RT-01 要求各包关联同一旅行和状态版本、摘要。R3 限定接受的是规格、追溯与合成参考，C3 和发布基线的 Owner 审核仍未记录；本切片不扩大已批准范围。

## 实现

`validatePlanRequestConsistency` 是同步无副作用的内存比较函数。它先沿用 #16 的 NAP 消息结构及 #17 的计划内部一致性检查；对 request 中的 Packet 使用 #14 已锁 R6 DC 合同检查和现有内存安全整数边界。然后：

1. 比较计划与请求的 `decision_id`、`runtime_id`。
2. 拒绝重复 Packet ID（即使两条内容相同）；每包 `context.task_id` 必须等于其 `task.task_key`，不同包的 trip、state revision、snapshot digest 必须一致。
3. 对每条计划 basis，在请求中找到对应 Packet，逐项比较 packet ID、turn ID、task key、state revision、snapshot digest 和 expires_at；期限必须按原字符串一致。请求可包含未被计划选择的额外包，完全相同的重复 basis 仍按 #17 规则允许。

这些检查依照已选 R3 的 CT-02/RT-01 和已锁 DC 的组包规则，拒绝计划与所给数据之间可见的不一致；不引入新字段或产品阈值。不修改输入、不执行行动或读取数据库。

## 安全和集成边界

传入的 request 和 Packet 可以被伪造；匹配本身**不证明来源、主体、旅行授权、快照真实性、当前 revision 或当前时间有效性**。`runtime_id` 只在计划与请求之间比较，原 Packet 中没有可由此证明的运行代次。digest 只做等值比较，不对状态重算，也不是签名；本函数不检查真实状态、事实适用性、完整分页/交付、受保护集合、能力注册、写授权或执行资格。

本函数接受内存对象，不能检测 JSON 数字 token 已经被 JavaScript 舍入。即使形状检查和内存安全整数通过，进入真实接口前仍须对原始 token 使用经审核的精确解码，并通过可信宿主取得 Packet、在当前身份及权限下重新检查全部内容。回归测试明确展示：自洽但伪造或过期的输入仍可能通过本比较，不允许用成功结果作为安全凭证。

真实宿主需要 #15 公共认证与 TS 应用、E03 权威读取及同一集成提交的身份/撤权、同版/TTL、保护集、分页/交付、数字精度及 PostgreSQL/HTTP 验证。跨模块语义与 14 组来源差异仍需固定基线审核和实际场景回归；本次不构成 NAP decide、Policy Evals 或用户产品验收。既有 E02 HTTP 测试只作为原系统回归，不是 NAP 接口验收。
