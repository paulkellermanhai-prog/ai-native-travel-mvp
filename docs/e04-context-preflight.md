# E04 current Context comparison — narrow, read-only candidate

Source: NAP R3 `engineering/runtime.md` RT-02/03, `contracts.md` CT-01/02/03 and `engineering/ac8-ux02-integration.md` P10/P19, UX E15/E21/E23–28. Accepted E03-02 #18 head `9b92c1c0c9b5ffcfca468ddf9cc6c7baec69f911` provides a real session-bound, private in-process Context ticket with live authorization and same-revision/body/time revalidation. Its acceptance is recorded by `E03-02-PR18-TECH-ACCEPTANCE-2026-11-06-01`; it is not an accepted Packet or a full E03 stage.

`openNapContextBasisPreflight` is a server-only, read-only adapter: it internally creates the E03 service, obtains its opaque ticket and re-consumes it for the same live authenticated session/trip, and checks a structurally valid single-basis NAP plan's reported task label, revision, snapshot digest and exact expiry against the revalidated Context. It fails closed on mismatch and conservatively treats an expiry with fractional milliseconds as expired at the start of that millisecond, preventing this adapter from extending an E03 expiry. It captures a copy of the input plan before asynchronous reads. E03 checks permissions and current TS state, not the supplied plan. This is a point-in-time diagnostic; E03's final recheck and a later action are not atomic.

**Not an action authorization or Packet validation:** the Context `task_id` is an unverified label; a match does not prove task/turn ownership, Packet ID, runtime generation, original trusted Packet, actual delivery, correct plan digest, fact-level policy, Grant, step eligibility or external receipt. A forged Packet ID can still match these Context fields. No write, policy execution, tool invocation, recovery or persistent log is implemented. Multi-basis plans are rejected, not deemed invalid under the NAP contract; full multi-packet execution remains blocked until the trusted E03 Packet host exists. The adapter must never be used as a sole gate for dispatch or confirmation.

Next integration requires (1) accepted Packet/task/session ownership and actual delivery with current R6/R7 decision; (2) E03 final high-precision time fix; (3) runtime/Packet and capability binding with pre-dispatch and post-completion revalidation; (4) persistent atomic claim and authoritative idempotency/receipt lookup; (5) CT-05 observation storage under trusted workspace/E11 deletion and retention; (6) restore last acknowledged checkpoint, reauthenticate and reread current state, do not revive old Grant or replay unknown business commits. A point-in-time comparison cannot make separately managed auth, state, and provider operations atomic.

The E03 checkpoint, Packet, write bridge and E11 teams own their existing files. This candidate changes none of them, does not incorporate unpublished candidate E03 source, and cannot be integrated into an externally exposed route until all host and privacy prerequisites are accepted. No true UI, model, provider, or restoration behavior is claimed by these tests.

## Session, process and revocation regression

The Session/PG integration tests additionally log in the same user twice and assert distinct Session IDs: the original ticket must be denied to the second Session even though both identities and membership match. They verify that the original object is denied by a separately created service instance and that its serialized empty object is denied in a fresh Node process using the same real credentials and database. These tests do not claim that opaque JavaScript object identity can be transferred between processes; they demonstrate that reconstructing a ticket cannot restore its WeakMap binding.

A test-only synchronous interleaving commits a real membership revocation after the first E03 snapshot validation and before its final state read. The live permission check rejects consumption before a second validation. A separate case lets the observation complete before revocation, then confirms a new check rejects it. The earlier result cannot be retroactively turned into a durable authorization: no transaction spans the completed observation and any later dispatch/write, so a future execution host must apply its own authorization and state guard at the actual effect boundary. No production synchronization hook or side effect was added. CI must actually run these with PostgreSQL; a local skip is not a pass.
