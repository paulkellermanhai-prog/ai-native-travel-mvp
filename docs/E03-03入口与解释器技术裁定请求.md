## 裁定 1：正式 HTTP 运行形态和 delivered 时点

当前项目用 `next start` 启动 Next 16 App Router；它的 Route Handler 使用 Web `Request/Response`，不给业务代码 Node `ServerResponse`。现有账本以 Node socket `finish` 加独立事务复验作为“本机已发送”的保守证据；它仍不证明客户端收到。不能把此实现直接塞入 Next Route Handler 后宣称同一证据。

**建议 A：E03 采用自托管 Node custom server**，把 `/runtime/trips/:id/{turns,assemble,pages}` 路由交给同一受信 E03 宿主，其余请求交给 Next。Next 官方允许 custom server，但须改变启动方式；它与 standalone 输出模式不能同时使用，部署包、进程数、反向代理、健康检查和重启行为需一起验收。优点是可沿用已测试的 `ServerResponse`、`finish` 与锁顺序。即使选 A，跨进程任务/账本恢复及删除通知仍需另做，不能仅靠同机进程内 Map。

**备选 B：保留 `next start`，重写交付账本**，以 Web Response 流被框架消费的具体时点定义“已发送”，并针对取消、断连、回滚、页重试和删除交错重新取证。该时点和 Node `finish` 并不自动等价。需技术负责人确认 R6 “服务器发送过正文、页失败不记 delivered”是否允许这一实现口径。不能只在返回 `Response` 时标记成功。

两个方案都采用既有 E11 删除与读取先后规则：最后受权读取和发送启动在持锁事务内线性化；已排队的网络字节无法追回。请确认这一工程解释，以及系统时钟/进程暂停的保守截止处理是否符合验收要求；不要要求软件证明任意暂停下绝对零间隙。

依据：[Next Route Handlers 使用 Web API](https://nextjs.org/docs/app/getting-started/route-handlers)；[Next custom server、启动与 standalone 限制](https://nextjs.org/docs/app/guides/custom-server)；冻结 R6《读取组装与有效性规格》§分页（服务器记录 delivered，失败页不新增）。

## 裁定 2：真实任务解释服务与可传出的数据

冻结 R6《运行契约与任务定位》§2–4 指定 `interpret(event, authorized_state_snapshot, runtime_focus) → tasks, focus_keys`，并明确程序不能从字符匹配证明语义正确；参考实现只接收合成解释结果。当前注册器会检查原话 Unicode 区段、状态引用、任务身份、焦点与关联，但没有模型服务。直接把用户原话映射成一个“明确” Task，或凭字符串识别阿斯旺，都会把未证实语义写成已证实结果。

**建议：先在 E03-03-1 落服务器侧解释器接口，要求输出冻结 Task 字段，并经现有注册器全部复验；模型供应商和提示词作为独立可替换适配。** OpenAI 官方 Responses API 支持 JSON Schema 结构化输出，但结构正确不保证问题拆分、目标选择和证据语义正确，仍须用埃及 MVP 场景评测。是否把完整当前状态、旧原话和工作区线索发送给第三方，以及选择模型、服务地区、数据保留和预算，须由产品/隐私决策确定；本仓库当前未见可用于产品环境的模型凭据。未决定之前，解释器不可用应明确失败，不能拿测试夹具或单句启发式冒充真实解释。依据：[OpenAI Structured Outputs 官方文档](https://developers.openai.com/api/docs/guides/structured-outputs)。
