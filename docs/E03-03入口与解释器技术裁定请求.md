## 裁定 1：正式 HTTP 运行形态和 delivered 时点

当前项目用 `next start` 启动 Next 16 App Router；它的 Route Handler 使用 Web `Request/Response`，不给业务代码 Node `ServerResponse`。现有账本以 Node socket `finish` 加独立事务复验作为“本机已发送”的保守证据；它仍不证明客户端收到。不能把此实现直接塞入 Next Route Handler 后宣称同一证据。

**当前验证路线：保留 `next start`，在其前方用单实例 Node 网关同源分流。** E03 事件记录、受控解释、Turn、Packet 和私有账本在网关进程内；Next 继续由原命令启动。该路线复用已测试的 `ServerResponse`、`finish` 与锁顺序，但生产进程拓扑、反向代理配置、健康检查、重启及跨进程失效仍需最终技术验收。回环测试不等于已完成生产部署。

若最终不使用独立网关，备选是重写 Next Web Response 下的交付账本；Web 流被框架消费的时点和 Node `finish` 并不自动等价，取消、断连、回滚和重试须重新取证。自托管 Next custom server 也可技术上实现，但会改变当前整体启动方式，不是本轮验证选择。

两个方案都采用既有 E11 删除与读取先后规则：最后受权读取和发送启动在持锁事务内线性化；已排队的网络字节无法追回。请确认这一工程解释，以及系统时钟/进程暂停的保守截止处理是否符合验收要求；不要要求软件证明任意暂停下绝对零间隙。

依据：[Next Route Handlers 使用 Web API](https://nextjs.org/docs/app/getting-started/route-handlers)；[Next custom server、启动与 standalone 限制](https://nextjs.org/docs/app/guides/custom-server)；冻结 R6《读取组装与有效性规格》§分页（服务器记录 delivered，失败页不新增）。

## 裁定 2：真实任务解释服务与可传出的数据

冻结 R6《运行契约与任务定位》§2–4 指定 `interpret(event, authorized_state_snapshot, runtime_focus) → tasks, focus_keys`，并明确程序不能从字符匹配证明语义正确；参考实现只接收合成解释结果。当前注册器会检查原话 Unicode 区段、状态引用、任务身份、焦点与关联，但没有模型服务。直接把用户原话映射成一个“明确” Task，或凭字符串识别阿斯旺，都会把未证实语义写成已证实结果。

**已落服务器侧受控解释器接口**：记录原话后，在真实 Session/PG 授权下读取同版状态并签发新任务键；解释器输出冻结 Task 字段，注册器复验原话区段、目标、版本与身份。Turn 响应在持有真实 Session、来源和当前状态锁时再次核对原登记内容与保守截止，然后启动发送；`finish` 仍不等于浏览器收到。未安装解释器返回 503，不记录原话；解释器失败后持久删除标记并失败关闭，物理清理仍待 E11 维护任务。当前只允许一个新任务，不能把多问题、延续或纠错说成已支持；测试解释器是受信夹具，**没有真实模型调用**。OpenAI 官方 Responses API 支持 JSON Schema 结构化输出，但结构正确不保证问题拆分、目标选择和证据语义正确，仍须用埃及 MVP 场景评测。是否把完整当前状态、旧原话和工作区线索发送给第三方，以及选择模型、服务地区、数据保留和预算，须由产品/隐私决策确定；本仓库当前未见可用于产品环境的模型凭据。依据：[OpenAI Structured Outputs 官方文档](https://developers.openai.com/api/docs/guides/structured-outputs)。
